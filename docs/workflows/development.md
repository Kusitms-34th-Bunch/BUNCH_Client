# Workflow

1. 요청과 영향 범위를 확인하고 관련 코드·설정을 읽는다.
2. 구현·수정 요청이면 아래 "worktree를 만드는 기준"으로 작업 위치와 세션 수를 먼저 결정한다. `docs/agent/bootstrap.md`의 "요청에서 실행까지"에 따라 스킬을 선택하고 최소 규칙과 guide만 읽는다. 사용자가 worktree나 후속 스킬을 따로 호출하지 않아도 연결한다.
3. 관찰 가능한 성공 기준을 정한다. 예: 상태별 UI, API 계약, 유지될 public API를 명확히 한다.
4. 기존 구현의 재사용과 불필요한 코드 제거를 먼저 검토한 뒤 가장 작은 변경으로 구현한다. 확정되지 않은 공통화나 의존성 추가는 하지 않는다.
5. 변경 유형에 맞는 가장 구체적인 검증을 실행한다.
6. 변경 내용, 검증 결과, 남은 위험을 간결히 보고한다.

아래에 해당하면 구현 전에 접근 방식과 검증 계획을 먼저 정리한다. 요청 범위와 계약이 분명하고 되돌릴 수 있는 로컬 작업은 계획에 따라 계속 진행한다. 결과가 달라지는 필수 정보나 권한이 부족하거나 되돌리기 어려운 작업이면 해당 부분을 확인한다.

- 두 개 이상의 app·package에 걸쳐 있거나 새 아키텍처 경계·공용 모듈을 만드는 변경
- 요구사항이 모호해 구현 방향이 여러 갈래로 나뉘는 변경
- 되돌리기 어려운 구조 변경(디렉토리 재배치, 의존성 교체, 마이그레이션)

위에 해당하지 않는 통상 규모의 변경은 바로 진행한다.

문서만 바꿀 때는 링크와 경로를 확인한다. 코드·설정·구조 변경 시 관련 문서도 같은 작업에서 갱신할 필요가 있는지 판단한다.

구조, 라이브러리, 공통 규칙처럼 다음 작업에도 영향을 주는 결정은 `docs/decisions/records/`에 근거와 대안을 짧게 남긴다. 기존 규칙을 따르는 단순 구현을 작업 로그처럼 기록하지는 않는다.

## 여러 작업을 동시에 구현할 때

단일 작업은 해당 feature 브랜치와 현재 세션으로 진행한다. 기존 작업을 보존하며 다른 작업을 시작해야 하면 worktree로 격리하고, 독립적인 여러 작업을 동시에 구현할 때만 별도 메인 세션을 추가한다. worktree 생성과 세션 추가는 별개의 판단이다. 같은 폴더를 여러 구현 세션이 수정하지 않는다.

### worktree를 만드는 기준

메인 세션은 모든 구현·수정 요청에서 다음 순서로 판단하고, 요청 범위 안의 안전한 로컬 준비는 별도 호출이나 재승인을 기다리지 않고 수행한다. 질문·조사·초안에는 적용하지 않는다.

1. 요청한 작업과 연결된 이슈·feature 브랜치, `git status --short --branch`, `git worktree list`, 알고 있는 실행 중 세션과 인계문을 확인한다. 같은 이슈를 이어 하는지 다른 작업을 시작하는지 구분한다. 담당 여부를 확인할 수 없는 worktree에 새 구현 세션을 실행하지 않는다.
2. 아래 표로 현재 폴더 유지·브랜치 이동·격리·동시 구현을 선택한다. 단일 작업이면 worktree를 강제하지 않는다. 해당 브랜치의 기존 worktree가 있으면 재사용하고, 실행 중인 세션이 담당하면 중복 실행하지 않는다.
3. 필요한 브랜치 연결·설치·최신 기준 확인은 `docs/conventions/git.md`의 "작업 시작과 병렬 세션"을 따른다. 이슈 자동화가 만든 브랜치를 우선 사용한다. worktree 준비를 위해 이슈를 임의 발급하거나 새 원격 브랜치를 push하지 않는다.
4. 동시 구현을 선택한 경우에만 아래 독립성 조건을 확인하고 "작업 분리와 인계" → "별도 세션 실행과 링크"까지 진행한다. 여러 파일·컴포넌트가 있다는 이유만으로 세션을 늘리지 않는다.

동시 구현은 다음 조건을 **모두** 만족해야 한다. 사용자가 요청한 여러 작업 안에서 독립성이 확인되면 메인 세션이 선택할 수 있고, 순차 진행을 명시했으면 그 지시를 따른다.

- 동시에 구현할 작업이 둘 이상이고, 각 작업의 완료 조건과 수정 경로를 따로 적을 수 있다.
- 다른 작업의 미완료 구현을 기다리지 않고 각각 구현·검증할 수 있다. 공통 계약·토큰·의존성·생성기 변경은 먼저 확정하고 기준 커밋으로 사용할 수 있다.
- 같은 소스 파일을 동시에 고치지 않는다. lockfile·공개 export 등 통합 파일은 담당자와 반영 순서를 정했으며, 자동 생성물은 통합 후 재생성할 수 있다.
- 각 작업의 브랜치·기준 커밋·담당 세션·검증 명령을 확인했다. 기존 worktree·실행 중인 세션과 중복되지 않는다.

| 상황                                                                 | 처리                                                                                 |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 단일 작업, 현재 폴더가 해당 feature 브랜치이고 다른 작업과 충돌 없음 | 현재 폴더·현재 세션 유지                                                             |
| 단일 작업, 브랜치 이동 필요, 다른 작업·실행 중 세션과 충돌 없음      | 자동 생성된 feature 브랜치로 이동, worktree·별도 세션 생성 안 함                     |
| 독립적인 두 기능을 동시에 구현하며 위 조건을 모두 만족               | 현재 작업 폴더는 유지하고 나머지 작업을 worktree로 분리, 작업별 메인 세션 사용       |
| 한 기능의 구현 → 테스트 → 리뷰, 같은 원인에 대한 여러 파일 수정      | 현재 세션에서 순서대로 진행                                                          |
| 공용 컴포넌트를 만들고 이를 사용하는 화면 구현                       | 공용 기반을 먼저 완료한 뒤 독립 가능한 화면만 병렬화                                 |
| 조사·코드 리뷰·검증만 병렬로 수행                                    | 읽기 전용 서브에이전트, worktree 생성 안 함                                          |
| 다른 작업의 미커밋 변경 또는 실행 중 세션을 보존하며 별도 작업 시작  | 새 작업을 worktree로 격리. 단일 작업이면 현재 세션에서 처리하며 별도 세션 추가 안 함 |
| 단일 작업이지만 사용자가 격리를 명시적으로 요청                      | worktree 사용, 세션 수는 늘리지 않아도 됨                                            |
| 기준 커밋·공통 파일 담당이 불명확하거나 수정 경로가 겹침             | 현재 세션에서 선행 작업과 경계를 먼저 정하고 순차 진행                               |

판단 결과는 `작업 / 브랜치 / 작업 경로 / 현재·별도 세션 / 선택 이유`로 짧게 알린 뒤 진행한다. 병렬 구현이면 공통 파일 담당·선행 커밋·검증도 남긴다. 현재 작업의 미커밋 변경을 다른 폴더에서 이어 해야 한다면 자동 복사·stash·commit하지 않고, 현 위치에서 완료할 수 있는 범위를 먼저 진행한다.

이 자동 선택은 AGENTS → bootstrap → 이 문서를 읽은 메인 세션의 실행 절차다. GitHub Actions는 원격 브랜치를 만들고, `agent:session`은 준비된 worktree에서 Codex 또는 Claude Code 세션을 실행할 뿐 작업 분류·worktree 생성·세션 중복 판정을 하지 않는다. 문서 지침은 실행 누락을 기계적으로 차단하는 hook이 아니며, CLI 실패 시 자동 실행 완료로 보고하지 않는다.

### 작업 분리와 인계

1. 동시 구현 요청을 받으면 작업별 목표·수정 경로·선행 작업·검증 범위를 먼저 나눈다. 토큰·공개 계약·생성기·의존성처럼 공통 기반이 필요한 작업은 먼저 확정하고, 이를 사용하는 구현을 뒤에 진행한다.
2. 각 작업의 worktree를 `docs/conventions/git.md`의 "작업 시작과 병렬 세션"에 따라 준비한다. 현재 폴더의 미커밋 변경은 그대로 보존하며 자동 이동·stash·commit하지 않는다.
3. 각 세션은 자기 worktree에서 구현·검증한다. 공통 파일(`package.json`, `yarn.lock`, 토큰 원본, 생성 스크립트, 공통 문서)은 담당 세션 하나를 정한다. 생성 export는 각 작업의 생성 명령으로 갱신하고 통합 시 다시 생성한다. 다른 세션의 폴더를 직접 수정하지 않는다.
4. 현재 메인 세션이 담당하는 작업은 해당 폴더에서 계속하고, 나머지 작업만 아래 "별도 세션 실행과 링크" 절차로 시작한다. 실행할 수 없으면 경로와 아래 시작 지시문을 제공하고, 현재 세션에서 가능한 독립 작업을 계속한다. worktree 생성만으로 별도 세션 실행이나 컨텍스트 공유가 완료됐다고 쓰지 않는다.
5. 통합 담당 세션을 정해 선행 작업 순서대로 반영하고, 생성물과 영향을 받는 consumer를 다시 검증한다. 각 브랜치의 통과 결과로 통합 검증을 대신하지 않는다. commit·push·PR·merge는 각각 기존 실행 승인 기준을 따른다.

새 세션에는 아래 정보를 전달한다. 세션 딥링크는 대화 참고용이며, 결정·현재 상태·검증 근거를 대신하지 않는다. 로컬 인계 파일은 worktree 간 자동 공유되지 않으므로 필요한 내용을 직접 전달한다. 팀 공유가 필요하면 승인된 이슈·PR에 옮기며 전체 대화 로그나 별도 공유 폴더를 만들지 않는다.

```text
작업: <이슈/목표와 완료 조건>
작업 위치: <worktree 절대 경로>, <브랜치>, <기준 커밋>
담당 범위: <수정 경로>, 공통 파일 담당: <세션/작업>
선행 작업: <의존 브랜치/커밋과 반영 여부>
기준: AGENTS.md, <spec/결정 문서>, <Figma node/자료>
현재 상태: <변경·검증 결과와 미검증 항목>
다음 행동: <바로 실행할 작업>, 제외 범위: <다른 세션 담당>
```

### 별도 세션 실행과 링크

위 기준으로 동시 구현하기로 정한 작업만 실행한다. 격리용 worktree 하나를 만들었다는 이유로 별도 세션을 추가하지 않는다. 메인 세션이 worktree·설치·선행 커밋·담당 범위를 확인하고 인계문을 해당 worktree의 `.agents/notes/handoff-<작업명>.md`에 작성한다. 실행 중인 담당 세션이 있으면 중복 실행하지 않는다. 인계문에는 비밀 값과 전체 대화 로그를 넣지 않는다.

Codex 또는 Claude Code CLI가 설치·인증된 환경에서는 저장소 루트의 다음 명령으로 별도 세션을 시작한다. 인자는 실제 절대 경로로 치환한다. 메인 세션은 자신이 쓰는 CLI를 `--agent`로 명시한다. Codex 세션은 `codex`, Claude Code 세션은 `claude`를 쓴다. `--agent`를 생략하면 `codex`로 실행한다.

```sh
yarn agent:session --agent codex '<worktree 절대 경로>' '<인계문 절대 경로>'
yarn agent:session --agent claude '<worktree 절대 경로>' '<인계문 절대 경로>'
```

- 공통: 스크립트는 별도 worktree 루트와 작업 브랜치(develop·main·master·detached HEAD 제외)를 확인하고, 인계문을 shell 없이 stdin으로 전달한다. 설치·브랜치 생성·commit·push·PR·merge는 실행하지 않는다. sandbox·권한·hook 우회 옵션은 사용하지 않는다.
- 호출한 폴더의 PnP 설정이 전파되지 않도록 자식 프로세스의 `NODE_OPTIONS`·`NODE_PATH`·`PROJECT_CWD`·`INIT_CWD`·`BERRY_BIN_FOLDER`를 비운다. 각 worktree는 자신의 Yarn 설치를 사용한다. 중단 신호(SIGINT·SIGTERM)는 CLI에 전달한다.
- Codex: `codex exec --cd <경로> --sandbox workspace-write --json -`을 실행한다. `thread.started`에서 받은 실제 ID로 세션 딥링크(`codex://threads/<ID>`)와 `codex resume <ID>`를 출력하고, `turn.completed`를 받고 실패 이벤트가 없을 때만 성공으로 본다.
- Claude Code: worktree를 작업 폴더로 `claude -p --output-format stream-json --verbose --permission-mode acceptEdits --permission-prompts none --allowedTools <검증용 yarn 명령>`을 실행한다(`--permission-prompts`는 Claude Code v2.1.259 이상, [비대화형 실행 문서](https://code.claude.com/docs/en/headless) 기준). `system/init` 이벤트의 `session_id`로 `claude --resume <ID>`를 출력한다. 재개는 해당 worktree에서 한다. 공식 형식이 확인되지 않은 딥링크는 만들지 않는다.
- Claude Code 성공 판정: 종료 코드 0이고 `result` 이벤트가 `is_error: false`, `terminal_reason: completed`이며 세션 ID가 `init`과 같을 때만 성공이다. 인증 실패도 `result.subtype`이 `success`로 오므로 `subtype`만으로 판단하지 않는다. 세션 ID·`result` 누락, 중단(SIGTERM은 `result` 없이 종료 코드 143)도 실패다. 권한 거부는 건수만 알리고 성공·실패 판정은 바꾸지 않는다.
- Claude Code 권한: `acceptEdits`는 파일 편집과 함께 `mkdir`·`mv`·`cp` 같은 흔한 파일 명령도 자동 승인한다([권한 모드 문서](https://code.claude.com/docs/en/permission-modes) 기준). 그 밖의 명령은 검증용 yarn 명령만 스크립트의 `CLAUDE_ALLOWED_TOOLS`에 정확한 형태로 미리 허용하고, 나머지는 비대화형이라 자동 거부된다. 허용 목록의 정본은 이 스크립트다. `--dangerously-skip-permissions`와 `bypassPermissions`는 쓰지 않는다. 거부된 명령은 통합 담당이 처리한다.
- 실행 도구가 반환한 프로세스 ID로 진행과 종료 코드를 추적한다. 인계문에 CLI가 낸 세션 ID·재개 명령·실행 상태를 덧붙인다. 재개는 해당 worktree에서 하고, 실행 중인 세션을 동시에 재개하지 않는다.
- 자동 생성한 링크·명령은 같은 로컬 환경에서 접근하는 용도다. 팀 공유에는 이슈·PR과 짧은 인계문을 사용한다. 링크 열기 성공이나 프로세스 시작을 구현 완료로 간주하지 않으며, 결과·종료 코드·변경 diff와 검증을 통합 담당이 확인한다.
- CLI 미설치·인증·모델 미지원·sandbox·hook·네트워크 실패는 실행 실패로 보고한다. 선택한 CLI가 실패해도 다른 CLI로 자동 전환하지 않는다. 권한을 우회하거나 같은 작업을 자동으로 여러 번 시작하지 않는다. 계정에서 지원하지 않는 모델을 자동으로 바꾸거나 전역 설정을 수정하지 않는다. 이 비대화형 실행에서 추가 권한이나 질문이 필요하면 통합 담당이 처리한다.

앱에서 새 채팅을 여는 도구가 있으면 Codex는 `codex://new`에 `URLSearchParams`로 인코딩한 `path`(worktree 절대 경로)·`prompt`(짧은 인계문)를 넣을 수도 있다. 이 링크는 입력창만 채우며 자동 전송하지 않는다. 기존 세션 링크와 새 채팅 링크를 구분하고, 자동 작업 시작에는 위 CLI 경로를 사용한다. Claude Code는 공식으로 확인된 딥링크가 없어 CLI 재개 명령만 쓴다. [Codex 딥링크 문서](https://developers.openai.com/codex/app/commands), [Codex 비대화형 실행 문서](https://developers.openai.com/codex/noninteractive)를 참고한다.

실행 스크립트 변경은 `node --test .agents/scripts/start-work-session.test.mjs`와 대상 ESLint·Prettier, `yarn check:agent-docs`로 검증한다. 이 테스트는 실제 AI 세션을 실행하지 않고 두 CLI의 출력에서 판정에 쓰는 필드만 남긴 이벤트로 성공·실패 판정을 확인한다. 실제 CLI 동작은 임시 저장소의 worktree에서 파일 변경 없는 짧은 세션으로 따로 확인한다.

## Figma·스크린샷 구현

Figma 링크·node 또는 디자인 스크린샷의 구현 요청은 `implement-from-figma`를 진입점으로 삼는다. 추천 훅은 관련 지침을 안내하며 스킬·도구를 직접 실행하지 않는다. 에이전트가 아래 순서로 필요한 스킬을 읽고 적용한다. 링크에 대한 질문·조사만 요청했으면 구현을 시작하지 않는다.

1. 대상 앱·기존 화면·요청한 node·현재 route와 spec을 확인한다. 저장소에서 판단할 수 있는 범위는 진행하고, URL·권한·완료 동작처럼 구현 결과가 달라지는 필수 계약이 불명확하면 해당 부분만 확인한다. 새 기능의 범위 정리가 필요하면 `prepare-feature-scope`를 적용한다.
2. Figma 도구를 사용하기 전에 현재 제공된 Figma 플러그인의 디자인 구현 스킬(`figma-design-to-code`)을 읽고 도구별 필수 지침을 따른다. 요청 node의 구조·속성·에셋과 기준 스크린샷을 확보한다. 응답이 불완전하면 필요한 하위 node를 추가로 확인한다. 도구·권한이 없으면 접근 실패를 명시하고 제공된 스크린샷 범위에서만 진행한다. 원본을 읽지 못한 상태에서 Figma 속성을 확인했다고 쓰지 않는다.
3. `implement-from-figma`로 토큰·기존 컴포넌트·Code Connect 매핑·에셋을 대조한다. 플러그인이 반환한 코드는 저장소 구조에 맞춰 옮기며, 디자인 스크린샷 자체를 화면 이미지로 사용하거나 임시 에셋 URL을 제품 코드에 남기지 않는다.
4. 변경 소유자에 따라 아래 스킬을 추가로 적용한다. 필요하지 않은 스킬·공통화·테스트·이슈·PR은 생성하지 않는다.

| 변경 범위               | 후속 스킬                                            |
| ----------------------- | ---------------------------------------------------- |
| route·page·layout       | `create-page-feature`                                |
| 앱 내부 재사용 UI       | `create-app-component`                               |
| 앱 간 공용 UI primitive | `create-ds-component`                                |
| 폼·검증·제출            | `implement-form-flow`                                |
| API 계약·서버 상태      | `assess-api-contract` → 계약 확인 후 `integrate-api` |

5. `verify-changes`로 변경 범위의 검사와 브라우저 확인을 수행한다. UI 구현은 `bunch-ui-accessibility-reviewer`, route·layout·접근 조건 변경은 `bunch-route-reviewer`, API 계약·query·mutation 변경은 `bunch-api-contract-reviewer`를 호출한다. 리뷰 지적을 수정하고 영향을 받은 검증을 다시 실행한다. 핵심 사용자 흐름의 회귀 위험이 있으면 `plan-e2e`를 적용한다.
6. 시각 검증은 `docs/agent/agent-browser-mcp.md`에 따라 수행한다. 요청한 화면의 기준 스크린샷과 같은 viewport·상태·데이터의 실제 렌더를 비교하고, 390px 수준의 좁은 폭·긴 텍스트·키보드·focus와 해당 화면의 loading·error·empty 상태도 확인한다. 레이아웃·타이포그래피·색상·에셋 차이를 고친 뒤 다시 비교한다. 기준 화면이나 실제 렌더가 없으면 시각 검증은 미검증으로 남긴다.
7. 변경 파일, 사용한 토큰·컴포넌트, 실제 검사 결과, 디자인과 다른 점·미확정 동작·미검증 범위를 보고한다. 구현 요청만으로 commit·push·PR 게시를 수행하지 않는다. 미완료 작업을 넘길 때는 아래 인계 기준을 따른다.

## 미완료 작업 인계

미완료 작업을 중단하거나 다른 세션·담당자에게 넘길 때, 대화 없이 작업을 재개하기 어려운 경우에만 짧은 인계 메모를 남긴다. 완료된 작은 작업마다 작성하거나 전체 대화·명령 로그를 복사하지 않는다.

- 로컬 메모는 `.agents/notes/handoff-<주제>.md`에 두고, 같은 작업은 기존 메모를 갱신한다. 이 경로는 Git에서 제외되므로 다른 사람에게 인계할 때는 필요한 내용을 이슈·PR에 옮긴다.
- 브랜치·변경 파일·staged 여부를 확인하고, 실제 검증 결과와 미검증 항목을 구분한다. 커밋·push·게시 승인 대기 여부도 남기며, 메모 자체를 실행 승인으로 해석하지 않는다.
- 다음 행동은 바로 실행할 수 있는 명령이나 확인 대상까지 적는다. 토큰·환경변수 값·개인정보는 기록하지 않는다.
- 재개할 때는 메모를 읽고 현재 `git status --short --branch`·diff와 대조한다. 오래된 검증 결과를 현재 상태의 통과 근거로 사용하지 않는다. 작업이 끝나면 메모를 완료로 표시한다.

```md
# 작업 인계: <주제>

- 목표:
- 현재 상태: worktree 경로, 브랜치, 기준 커밋, 변경 파일, staged 여부
- 완료한 내용:
- 검증: 실행 명령·결과, 미검증 항목
- 다음 행동:
- 주의사항: 막힌 점, 남은 위험, 승인 대기 여부
```

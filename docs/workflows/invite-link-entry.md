# 초대 링크 진입

초대 링크(`/invite/{토큰}`)로 들어온 사람이 번치에 참여하기까지의 흐름과, 아직 연결하지 않은 것(유니버셜 링크, 초대 카드 번치 타입)을 모은다. 화면별 상세는 각 컴포넌트의 spec을 본다.

- 진입 페이지: `apps/web/src/features/invite-entry/components/InviteEntry.spec.md`
- 초대 진입 확인: `apps/web/src/features/onboarding/components/join/BunchJoinEntry.spec.md`
- 초대 확인·참여: `BunchJoinInvitation.spec.md`, `BunchJoined.spec.md`
- 기능명세: 1.2.8(로그인 후 도착지), 1.4.7(가입 완료), 1.5.1(초대 정보 보관), 2.5~2.7(초대 참여·웹 초대장)

## 지금 동작하는 흐름

```text
외부(카카오톡 등)에서 링크 클릭
  → /invite/{토큰}                          진입 페이지(앱 밖에서도 열림, 로그인 불필요)
  → 「초대장 확인하기」
      GET /invitations/{토큰}                공개 조회로 링크가 유효한지 확인(무효면 토스트 「유효하지 않은 링크입니다.」)
      초대 정보 보관(24시간, 가장 최근 하나)  로그인·가입을 거치는 동안 유지
  → /onboarding/join/enter                  접근 가드가 로그인 여부를 판별
      비로그인 → 로그인 → (가입 중이면 약관·프로필) → 가입이 끝나면 다시 /onboarding/join/enter
      로그인 → 그대로
  → POST /invitations/verify                참여 가능 여부(AVAILABLE·FULL·ALREADY_MEMBER·LIMIT_EXCEEDED)
  → /onboarding/join/invitation             초대 확인 화면(「참여하기」)
  → POST /invitations/join                  참여(멱등 키 필수) → 참여 완료 화면, 보관한 초대 삭제
```

- 로그인 판별은 새로 만들지 않고 기존 접근 가드(`AuthGate`)를 그대로 쓴다. 진입 페이지는 `(app)` 그룹 밖(`app/invite`)에 있어 비로그인도 볼 수 있다.
- 로그인·가입이 끝나면 가입 완료 사용자의 도착지는 번치 홈보다 **보관된 초대가 먼저**다(`resolvePostLoginPath`, 기능명세 1.2.8 첫 번째 규칙).
- 보관한 초대는 참여 성공, 참여 포기(나가기), 다시 해도 안 되는 실패(무효·정원 초과·소속 한도), 로그아웃에서 지운다. 일시적 오류는 유지한다.
- 보관소는 `apps/web/src/shared/lib/pendingInvitation.ts`다. 로그인이 화면을 새로 불러오는 이동을 거쳐서 WebView 저장소(`localStorage`)를 쓰고, 저장할 수 없으면 메모리로 이어 간다.

## 아직 연결하지 않은 것

### 유니버셜 링크(앱으로 먼저 넘기기)와 앱스토어 이동

지금은 앱 밖에서 링크를 누르면 웹 진입 페이지가 열린다. **앱이 설치된 사용자는 이 페이지를 거치지 않고 앱으로 바로 열려야** 하고, 그 연결이 아직 없다.

| 항목                    | 내용                                                                                                                                                                   | 담당·메모                                                                     |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Universal Link 설정     | 초대 링크 도메인의 `apple-app-site-association` 배포, 앱의 Associated Domains 설정. 앱이 있으면 앱이 열리고 없으면 같은 URL이 이 웹 진입 페이지를 연다                 | 인프라·mobile-shell. 서버가 허용하는 초대 URL의 origin·path 확정 필요(백엔드) |
| 앱이 링크를 웹뷰에 전달 | 앱이 링크로 열리면 mobile-shell이 `/invite/{토큰}`을 WebView에 열거나 토큰을 웹에 전달. 앱 안에서는 기존 접근 가드가 토큰 유무를 판별해 비로그인이면 로그인으로 보낸다 | mobile-shell, `packages/bridge` 계약 변경 시 보안 검토 대상                   |
| 「앱 설치하기」         | 앱스토어 앱 페이지로 이동. 지금은 `InviteEntry`의 `onInstallApp`이 없어 임시 안내 토스트만 보인다(`InviteEntry` 호출부 `app/invite/[token]/page.tsx`에서 연결)         | 앱스토어 주소 확정 후                                                         |
| 설치 직후 이어받기      | 앱을 설치한 뒤 첫 실행에서 초대 정보를 이어받는 기능(Deferred Deep Link). 기능명세 2.7.1 「구현 가능한 상황이면 구현」                                                 | 선택                                                                          |
| 링크 미리보기(OG)       | 「{번치 이름}에 초대받았어요」와 번치 프로필 이미지. 서버 렌더에서 공개 조회로 번치 정보를 읽어야 한다                                                                 | 후속                                                                          |

앱 밖(브라우저)에서는 소셜 로그인을 할 수 없다(`socialSignIn.ts`: 네이티브 SDK 필요). 그래서 앱 없는 사용자가 「초대장 확인하기」를 누르면 로그인 화면까지 가도 거기서 막힌다. **Universal Link가 연결되면 앱이 설치된 사용자는 이 구간을 겪지 않는다.** 앱이 없는 사용자의 흐름(앱 설치 안내)은 유니버셜 링크와 함께 정한다.

### 초대 카드의 번치 타입(`characterType`)

초대 확인 응답의 카드(`InvitationCard`)에 번치 타입(`TYPE_1`~`TYPE_4`)이 없다.

- 영향: 초대 확인 화면의 봉투·인장 색과, 번치 사진이 없을 때의 기본 이미지를 **타입 1로 고정**해 두었다(`BunchJoinInvitation.tsx`의 `CARD_CHARACTER_TYPE`). 참여 완료 화면은 참여 응답의 `bunch.characterType`을 써서, 사진이 없는 번치는 두 화면의 기본 이미지가 다를 수 있다.
- 요청(백엔드): `POST /invitations/verify`의 `card`(와 같은 모양의 `GET /invitations/{token}`)에 `characterType`을 추가. 값이 오면 고정값을 걷어 내고 그 값을 쓴다.
- 상태: 디스코드 스레드로 요청 예정. 이 문서와 이슈 #308에 TODO로 남겼다.

## 알려진 한계

- 보관한 초대는 사용자 구분 없이 이 기기에 24시간 남는다. 공용 기기에서 로그인하지 않은 채 떠나면(`logout()`을 거치지 않으면 지워지지 않음) 다음에 로그인하는 다른 사용자의 도착지가 그 초대가 된다. 토큰은 원래 링크를 가진 누구나 쓰는 값이고 참여는 사용자의 명시적 동작이 필요해 영향은 제한적이다. 로그인 사용자가 바뀔 때 지우는 것은 후속으로 검토한다.
- 카카오톡 인앱 브라우저와 앱 WebView는 저장소가 분리돼 있어, 브라우저에서 보관한 초대가 앱으로 넘어가지 않는다. 유니버셜 링크가 앱을 URL과 함께 열면 해소되는 사항이다.
- 링크 입력으로 직접 참여하다가(`/onboarding/join`) 보관된 다른 초대가 남아 있으면, 초대 확인 화면에서 새로고침했을 때 직접 입력한 링크가 아니라 보관된 초대로 다시 확인한다. 발생 가능성이 낮고 확인 카드로 구분된다.
- 진입 페이지에서 흰 글씨(소개 문구)의 사진 위 실제 대비는 측정하지 못했다(딤 40% 가정, 최악의 경우 약 2.8:1). 디자인 확인이 필요하다.

## 백엔드·팀에 확인할 것

- 초대 입력 형식: 보조 코드의 문자 범위(프론트는 영숫자 8자 또는 43자 Base64URL 토큰만 서버로 보낸다), 서버가 허용하는 초대 URL의 origin·path.
- 멱등 키: 사용자 단위로 범위가 지정되는지, 키 길이 제한, 4xx 실패 응답도 같은 키로 재생하는지(프론트는 4xx 뒤 키를 버리고 408·429는 유지한다).
- 공개 조회(`GET /invitations/{token}`)에 만료된 access 쿠키가 Bearer로 붙을 때의 처리: BFF 프록시는 쿠키가 있으면 경로와 상관없이 `Authorization`을 붙인다. 서버가 공개 경로의 무효 Bearer를 무시하는지, 401로 거부하는지 확인이 필요하다(거부하면 로그인했다가 만료된 사용자가 링크를 열 때 일시적 오류로 보인다).
- 공개 조회 응답의 `imageUrl`·`inviterNickname`: OpenAPI는 non-null, Notion 명세는 null 가능으로 어긋나 있다(프론트는 둘 다 받는다).
- 429 `REQUEST_002`(무효 입력 반복 제한)의 안내 문구: 기획 문구가 없어 일반 오류 토스트로 처리 중이다.

## 디자인에서 확인할 것

- 진입 페이지 모션: Figma 모션 데이터는 2.4초 주기 **반복 재생**이다. 장식이 계속 깜빡이지 않도록 한 번만 재생하게 했다(동작 줄이기에서는 이동 없이 투명도만). 모션은 CSS 키프레임만으로 재생해 JS·hydration과 무관하다. 반복 재생이 의도라면 알려 달라.
- 소개 문구 「함께한 순간이 모이는 곳」: Figma는 Noto Sans KR 14px(자간 -0.28)인데 프로젝트 폰트는 Pretendard라 `typography-body-3-regular`로 맞췄다.
- 「앱 설치하기」: Figma대로 활성 모양이고, 앱스토어 연결 전에는 누르면 임시 문구 토스트(「앱스토어 이동은 곧 지원돼요.」)만 보인다. 문구는 기획 원문이 없다.

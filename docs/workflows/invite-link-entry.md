# 초대 링크 진입

초대 링크(`/invite/{토큰}`)로 들어온 사람이 번치에 참여하기까지의 흐름과, 앱으로 넘기기(유니버셜 링크)·아직 연결하지 않은 것을 모은다. 화면별 상세는 각 컴포넌트의 spec을 본다.

- 진입 페이지: `apps/web/src/features/invite-entry/components/InviteEntry.spec.md`
- 초대 진입 확인: `apps/web/src/features/onboarding/components/join/BunchJoinEntry.spec.md`
- 초대 확인·참여: `BunchJoinInvitation.spec.md`, `BunchJoined.spec.md`
- 기능명세: 1.2.8(로그인 후 도착지), 1.4.7(가입 완료), 1.5.1(초대 정보 보관), 2.5~2.7(초대 참여·웹 초대장)

## 지금 동작하는 흐름

참여는 **앱 안에서만** 된다. 앱 밖(브라우저)은 소셜 로그인을 할 수 없어(`socialSignIn.ts`: 네이티브 SDK 필요) 진입 페이지가 앱이나 App Store로 넘긴다(아래 「유니버셜 링크」).

```text
앱 안 WebView에서 /invite/{토큰}             유니버셜 링크로 앱이 열려 쉘이 연 경우
  → 진입 페이지가 바로 확인(「초대장 확인하기」와 같은 동작)
      GET /invitations/{토큰}                공개 조회로 링크가 유효한지 확인(무효면 토스트 「유효하지 않은 링크입니다.」)
      초대 정보 보관(24시간, 가장 최근 하나)  로그인·가입을 거치는 동안 유지
  → /onboarding/join/enter(history 교체)    접근 가드가 로그인 여부를 판별(앱 WebView의 로그인 쿠키 기준)
      비로그인 → 로그인 → (가입 중이면 약관·프로필) → 가입이 끝나면 다시 /onboarding/join/enter
      로그인 → 그대로
  → POST /invitations/verify                참여 가능 여부(AVAILABLE·FULL·ALREADY_MEMBER·LIMIT_EXCEEDED)
  → /onboarding/join/invitation             초대 확인 화면(「참여하기」)
  → POST /invitations/join                  참여(멱등 키 필수) → 참여 완료 화면, 보관한 초대 삭제
```

- 로그인 판별은 새로 만들지 않고 기존 접근 가드(`AuthGate`)를 그대로 쓴다. 진입 페이지는 `(app)` 그룹 밖(`app/invite`)에 있어 비로그인도 볼 수 있다.
- 로그인 쿠키는 앱 WebView에만 있고 카카오톡 인앱 브라우저·Safari와 공유되지 않는다. 그래서 브라우저에서 이 흐름으로 보내면 항상 비로그인으로 판정돼 로그인 화면에서 막힌다. 앱 밖의 「초대장 확인하기」가 참여 흐름 대신 앱·App Store로 넘기는 이유다(#489).
- 로그인·가입이 끝나면 가입 완료 사용자의 도착지는 번치 홈보다 **보관된 초대가 먼저**다(`resolvePostLoginPath`, 기능명세 1.2.8 첫 번째 규칙).
- 보관한 초대는 참여 성공, 참여 포기(나가기), 다시 해도 안 되는 실패(무효·정원 초과·소속 한도), 로그아웃에서 지운다. 일시적 오류는 유지한다.
- 보관소는 `apps/web/src/shared/lib/pendingInvitation.ts`다. 로그인이 화면을 새로 불러오는 이동을 거쳐서 WebView 저장소(`localStorage`)를 쓰고, 저장할 수 없으면 메모리로 이어 간다.

## 아직 연결하지 않은 것

### 유니버셜 링크(앱으로 먼저 넘기기)와 앱스토어 이동 — 반영함(#489, 실기기 확인 전)

iOS 앱이 App Store에 출시돼(App Store만, Android 앱 없음) 링크를 누르면 앱이 있으면 앱이, 없으면 이 웹 진입 페이지가 열린다. 앱 쪽 설정(Associated Domains)은 네이티브 변경이라 **App Store 업데이트 심사를 거쳐야 기존 사용자에게 반영된다.**

```text
카카오톡·메시지 등에서 https://app.bunch.kr/invite/{토큰} 누름
  ├ 앱 있음 → iOS가 앱을 엶 → 쉘이 WebView에 /invite/{토큰}
  │             → 진입 페이지가 앱 안임을 알고 설치 버튼 없이 바로 링크 확인 → /onboarding/join/enter(history 교체)
  ├ 카카오톡 인앱 브라우저(iOS) → 열리자마자 한 번 kakaotalk://web/openExternal로 밖에서 다시 열기
  │             → 앱 있음: 앱이 열림 / 앱 없음: Safari의 진입 페이지(아래)
  │             (막혀 남으면 「초대장 확인하기」가 링크 확인 뒤 같은 요청을 다시 함)
  └ 그 밖의 브라우저 → 웹 진입 페이지
                「앱 설치하기」 → App Store
                「초대장 확인하기」 → 형식 확인 → 초대 링크 복사 → https://open.bunch.kr/invite/{토큰}
                    ├ 앱 있음: iOS가 요청 전에 앱을 엶(토큰 그대로) → 초대 확인
                    └ 앱 없음: 서버가 화면 없이 App Store로(307) → 설치·가입 뒤 「참여하기」에서 붙여넣기
                iOS가 아니면 두 버튼 모두 「지금은 iOS 앱만 지원해요.」
```

웹은 앱 설치 여부를 알 수 없어 판단을 iOS에 넘긴다. 같은 도메인 안 이동으로는 유니버셜 링크가 앱을 열지 않아, 「초대장 확인하기」는 다른 하위 도메인(`open.bunch.kr`, 사용자가 보는 화면 없음)으로 넘긴다. 앱이 있으면 iOS가 그 이동을 가로채 앱을 열고, 없으면 `apps/web/next.config.mjs`의 호스트 조건 리다이렉트가 App Store로 보낸다. 서버 리다이렉트라 그동안 진입 페이지가 그대로 보인다.

- iOS는 누른 그 순간의 이동이어야 앱을 열고 클립보드 복사도 누른 동작 안에서만 허용해, 앱 밖에서는 서버 조회를 기다리지 않고 형식만 확인한 뒤 바로 넘긴다. 링크가 유효한지는 앱이 확인한다(무효 링크로 App Store에 간 사용자는 붙여넣은 뒤 앱에서 무효 안내를 받는다).
- 설치 직후 이어받기는 클립보드로 한다. 「초대장 확인하기」를 누르면 앱이 있든 없든 `https://app.bunch.kr/invite/{토큰}`을 안내 없이 복사한다(곧바로 앱·App Store로 넘어가 토스트는 보이자마자 사라지고, 안내를 보이려고 이동을 늦추면 iOS가 누른 동작으로 인정하지 않아 앱이 열리지 않을 수 있음). 사용자 클립보드를 덮어쓰고, 앱에서 붙여넣을 때 iOS 허용 창이 뜬다. 앱 첫 실행 때 자동으로 읽지는 않는다.
- 쉘이 `open.bunch.kr`을 아는 새 앱 버전이 심사를 통과하기 전에는 앱이 있어도 App Store로 간다(App Store의 「열기」는 초대 없이 앱 첫 화면).
- 외부 이동(앱 열기, 카카오톡 외부 열기)이 막혀도 페이지에 따로 안내하지 않는다. 버튼은 잠그지 않되, 연달아 누르면 1.5초 안의 두 번째는 무시한다(복사·안내·이동이 겹치지 않게).

남은 확인(실기기, TestFlight):

- Safari 진입 페이지에서 「초대장 확인하기」를 눌렀을 때 앱이 있으면 확인 창 없이 앱이 열리고(초대 확인으로), 없으면 흰 화면 없이 App Store로 가는지. 배포 뒤 `https://open.bunch.kr/.well-known/apple-app-site-association`이 리다이렉트 없이 200·JSON인지.
- 메모·메시지 앱에서 링크를 눌러 앱이 열리는지(Safari 주소창 직접 입력·같은 도메인 안 이동으로는 열리지 않는 것이 정상).
- **카카오톡에서 누르면 앱이 열리는지.** 카카오톡이 링크를 자기 인앱 브라우저로 열면 진입 페이지가 `kakaotalk://web/openExternal`로 밖에서 다시 열기를 요청한다. 이때 iOS가 앱 있으면 앱, 없으면 Safari를 여는지, 자동 요청이 막히는지(막히면 「초대장 확인하기」로 다시 시도) 확인 전이다. 카카오 인앱 브라우저의 User-Agent에 `KAKAOTALK`이 들어 있는지도 확인한다.
- 앱 실행 중(로그인 화면·탭 화면) 링크로 돌아왔을 때 보이는 화면이 초대 확인으로 바뀌는지, 비로그인·가입 중 사용자가 로그인을 거쳐 초대로 돌아오는지.
- Smart App Banner가 전체 화면 레이아웃을 밀거나 가리지 않는지.
- 탭 WebView에서 초대 화면을 연 뒤 뒤로 가기로 탭 화면에 돌아왔을 때 탭 바가 다시 보이는지(이전 문서가 그대로 복원되면 탭 바 표시를 다시 보내지 않아 숨김으로 남을 수 있음).
- 탭 WebView에서 링크 확인이 실패하면 탭 바가 숨은 채 진입 페이지에 머물고, 나가는 길은 뒤로 가기 제스처뿐이다. 이 동선이 괜찮은지 디자인 확인이 필요하다.
- 목적지가 아닌 탭에서 참여·번치 만들기를 마치거나 나가면(목적지는 피드, 만들기 완료는 번치 홈), 쉘이 목적지 탭으로 전환하고 흐름을 연 탭 WebView는 자기 첫 화면으로 되돌린다(웹 `replaceTabPath`). 「이미 참여 중인 번치예요.」 안내는 흐름을 연 WebView가 곧 가려지므로 전환한 탭에 쉘 토스트(`showNativeToast`, 3초)로 띄운다. 전에는 `router.replace`로 그 탭 WebView 안에 피드를 열어 탭 바 선택과 어긋났다(2026-11-23 팀 QA 제보, #518). 실기기 확인 전이다.
- 첫 화면에서 탭 화면으로 넘어가는 바로 그 순간 들어온 링크는 열 WebView가 없어 무시된다(10초 뒤 버림). 다시 누르면 열린다.

앱 밖(브라우저)에서는 소셜 로그인을 할 수 없어(`socialSignIn.ts`: 네이티브 SDK 필요), 앱 밖의 「초대장 확인하기」는 참여 흐름으로 보내지 않고 위처럼 앱·App Store로 넘긴다. 브라우저에서는 초대를 보관하지 않는다(앱과 저장소가 달라 쓰이지 않음).

### 초대 카드의 번치 타입(`characterType`) — 반영함

백엔드가 초대 카드(`InvitationCard`)에 번치 타입(`TYPE_1`~`TYPE_4`, 필수)을 추가했다. `POST /invitations/verify`의 `card`와 같은 모양의 `GET /invitations/{token}` 응답에 모두 있다.

- 반영: 초대 확인 화면(`BunchJoinInvitation`)의 봉투·인장 색과, 번치 사진이 없을 때의 기본 이미지가 카드의 `characterType`을 따른다. 이전에 타입 1로 고정했던 값은 없앴다.
- 생성 타입: `packages/api-core/src/generated/openapi.ts`의 `InvitationCard`에만 `characterType`을 더했다. 전체를 다시 생성하면 이번 변경과 무관한 엔드포인트·스키마 차이가 크게 따라와서(최신 명세 기준) 별도 작업으로 남긴다.
- 진입 페이지(`InviteEntry`)는 링크가 유효한지만 알면 돼 이 값을 쓰지 않는다. 링크 미리보기(OG)는 번치 이름만 쓴다(아래).

### 링크 미리보기(OG) — 반영함(#442)

메신저에 초대 링크를 붙이면 미리보기 제목이 「{번치 이름}에 초대받았어요」로 보인다(기능명세 2.4.3·2.7.1).

- `app/invite/[token]/page.tsx`의 `generateMetadata`가 서버 렌더에서 공개 조회(`GET /invitations/{token}`, `shared/api/server/invitationPreview.ts`)로 번치 이름을 읽는다. 재시도 없이 3초 안에 못 읽거나 없는·만료된 링크면 기본 제목 「bunch 초대장」이다.
- 이미지는 번치마다 만들지 않고 고정 이미지 `public/images/og/invite.png`(Figma 「오픈그래프 이미지」 `6468:114571`, 1800×945)를 쓴다. 절대 주소는 Next 기본값을 따른다(운영 `VERCEL_PROJECT_PRODUCTION_URL`, 미리보기 배포 `VERCEL_BRANCH_URL`·`VERCEL_URL`, `docs/workflows/seo.md`).
- 토큰이 든 주소라 `og:url`을 넣지 않고, 검색 제외(`noindex`)와 `no-referrer`는 유지한다.
- 카카오톡 미리보기는 배포 뒤 실제 링크로 확인해야 한다(카카오는 미리보기를 캐시하므로 바꾼 뒤에는 카카오 개발자 도구의 캐시 초기화가 필요할 수 있다).

## 알려진 한계

- 보관한 초대는 사용자 구분 없이 이 기기에 24시간 남는다. 공용 기기에서 로그인하지 않은 채 떠나면(`logout()`을 거치지 않으면 지워지지 않음) 다음에 로그인하는 다른 사용자의 도착지가 그 초대가 된다. 토큰은 원래 링크를 가진 누구나 쓰는 값이고 참여는 사용자의 명시적 동작이 필요해 영향은 제한적이다. 로그인 사용자가 바뀔 때 지우는 것은 후속으로 검토한다.
- 카카오톡 인앱 브라우저와 앱 WebView는 저장소가 분리돼 있어, 브라우저에서 보관한 초대가 앱으로 넘어가지 않는다. 유니버셜 링크로 앱이 열리면 앱 안에서 링크를 다시 확인해 보관하므로 해소된다. 인앱 브라우저에서 유니버셜 링크가 동작하는지는 실기기 확인 전이다.
- 링크 입력으로 직접 참여하다가(`/onboarding/join`) 보관된 다른 초대가 남아 있으면, 초대 확인 화면에서 새로고침했을 때 직접 입력한 링크가 아니라 보관된 초대로 다시 확인한다. 발생 가능성이 낮고 확인 카드로 구분된다.
- 진입 페이지에서 흰 글씨(소개 문구)의 사진 위 실제 대비는 측정하지 못했다(딤 40% 가정, 최악의 경우 약 2.8:1). 디자인 확인이 필요하다.

## 백엔드·팀에 확인할 것

- 초대 입력 형식: 보조 코드의 문자 범위(프론트는 영숫자 8자 또는 43자 Base64URL 토큰만 서버로 보낸다), 서버가 허용하는 초대 URL의 path(origin은 `app.bunch.kr`로 확정).
- 멱등 키: 사용자 단위로 범위가 지정되는지, 키 길이 제한, 4xx 실패 응답도 같은 키로 재생하는지(프론트는 4xx 뒤 키를 버리고 408·429는 유지한다).
- 공개 조회(`GET /invitations/{token}`)에 만료된 access 쿠키가 Bearer로 붙을 때의 처리: BFF 프록시는 쿠키가 있으면 경로와 상관없이 `Authorization`을 붙인다. 서버가 공개 경로의 무효 Bearer를 무시하는지, 401로 거부하는지 확인이 필요하다(거부하면 로그인했다가 만료된 사용자가 링크를 열 때 일시적 오류로 보인다).
- 공개 조회 응답의 `imageUrl`·`inviterNickname`: OpenAPI는 non-null, Notion 명세는 null 가능으로 어긋나 있다(프론트는 둘 다 받는다).
- 429 `REQUEST_002`(무효 입력 반복 제한)의 안내 문구: 기획 문구가 없어 일반 오류 토스트로 처리 중이다.

## 디자인에서 확인할 것

- 진입 페이지 모션: Figma 모션 데이터는 2.4초 주기 **반복 재생**이다. 장식이 계속 깜빡이지 않도록 한 번만 재생하게 했다(동작 줄이기에서는 이동 없이 투명도만). 모션은 CSS 키프레임만으로 재생해 JS·hydration과 무관하다. 반복 재생이 의도라면 알려 달라.
- 소개 문구 「함께한 순간이 모이는 곳」: Figma는 Noto Sans KR 14px(자간 -0.28)인데 프로젝트 폰트는 Pretendard라 `typography-body-3-regular`로 맞췄다.
- 「앱 설치하기」: Figma대로 활성 모양이고, 누르면 같은 탭에서 App Store 앱 페이지로 이동한다(#479). 앱 공개 전에는 App Store가 앱을 찾지 못한다고 보일 수 있다.

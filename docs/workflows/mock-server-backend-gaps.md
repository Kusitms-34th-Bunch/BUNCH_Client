# 가짜 서버와 서버 명세의 차이

가짜 서버가 명세와 다른 부분, 백엔드에 확인할 것, 실서버를 연결할 때 정리할 것이다. 연동 상태는 [mock-server-status.md](mock-server-status.md)를 본다.

## 가짜 서버와 서버 명세의 차이, 백엔드 확인 항목

가짜 서버(`src/mocks`)는 Swagger와 Notion 명세를 기준으로 만들었지만, 명세끼리 다르거나 가짜 서버가 다르게 동작하는 부분이 있다. 실서버를 연결할 때 아래를 확인한다. 화면별 후속은 각 feature의 spec에 있다.

### 가짜 서버가 명세와 다른 부분

| 영역             | 차이                                                                                                                                                                                                                                                                                                                                                                                                                                | 비고                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 사진 날짜 변경   | `clearDate: true`(날짜 미확인 사진을 끌어 옮긴 뒤 되돌리기)는 `capturedDate`와 함께 보내면 400으로 거절하지만, 서버의 「날짜 출처가 사용자 지정이고 시각이 없는 사진에만 쓸 수 있고 하나라도 아니면 요청 전체 400」 규칙은 흉내 내지 않는다(현재 화면 경로는 항상 통과하는 흐름)                                                                                                                                                    | 서버 명세 `photo-date.md`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 사진 업로드      | 같은 파일 판별은 파일 바이트의 SHA-256이고, 합치기는 사진함 1,000장 한도를 넘어도 허용하며 합쳐진 요청도 같은 묶음 50장에 센다. 하루 100장(`PHOTO_002`)은 흉내 내지 않고, 올린 파일은 보관하지 않고 시작 데이터의 이미지로 대신 보인다                                                                                                                                                                                              | 서버는 지금 업로드된 JPEG의 SHA-256으로 판별하지만, 실기기에서 같은 원본의 가공본 해시가 기기마다 달라 합쳐지지 않았다(원본 해시는 같음). 앱은 가공 전 원본의 SHA-256(`originalFileHash`, 소문자 hex 64자)을 평면 폼 필드로 보내고 목 서버는 이 값이 있으면 같은 사진 판별에 쓴다(서버의 필드 이름·형식·기존 사진 처리는 확정 대기, 지각 해시는 도입하지 않고 외부 매체 전송본은 다른 사진), 한도 집계는 확정 전, 요청은 Swagger와 달리 `request` JSON 파트가 아니라 `uploadBatchId`·`capturedDate`·`capturedTime` 별도 필드로 받음(실서버 확인, `capturedTime`은 `HH:mm:ss` 문자열) |
| 번들 작성        | 날짜 미래 금지 검사가 없다                                                                                                                                                                                                                                                                                                                                                                                                          | 명세에는 있음                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| 번들 발행        | 다른 멱등 키로 같은 본문을 다시 발행하면 `BUNDLE_002`                                                                                                                                                                                                                                                                                                                                                                               | 명세는 최초 요청과 같으면 허용                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 번치 프로필 편집 | 버전 충돌을 409 `MOCK_PROFILE_VERSION`(가짜 코드)으로 거절한다                                                                                                                                                                                                                                                                                                                                                                      | Swagger에 오류 코드가 없음. 화면은 `BUNCH_001` 밖의 실패를 하나로 다뤄 코드와 무관하게 동작                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 번치 멤버 관리   | 버전 충돌을 409 `MOCK_MEMBERSHIP_VERSION`(가짜 코드)으로 거절한다                                                                                                                                                                                                                                                                                                                                                                   | Swagger에 오류 코드가 없음. 화면은 실패 뒤 다시 받은 버전으로 충돌을 판단                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 번들 삭제        | 생성자 또는 번치 관리자(OWNER·CO_OWNER)면 초안·발행본 모두 삭제한다                                                                                                                                                                                                                                                                                                                                                                 | 2026-11-19 확인한 계약(아래 #453)은 초안 삭제를 참여 중인 생성자 또는 OWNER·CO_OWNER로, 발행본 삭제를 OWNER로 정한다. 가짜 서버는 아직 이보다 넓게 허용한다(참여하지 않은 생성자의 초안 삭제, 생성자·CO_OWNER의 발행본 삭제). 화면은 서버의 403을 받으면 그대로 실패로 다룬다                                                                                                                                                                                                                                                                                                        |
| 금칙어           | 실서버는 공개 목록을 공백·특수문자를 뺀 뒤에도 비교하지만, 가짜 서버는 「금칙어」 낱말이 들어간 값만 걸린다(이름 확인 `status: PROHIBITED_WORD`, 저장·등록 400 `COMMON_003`·`detail.fields`). 번들 초안은 스냅샷·제목 병합 응답의 `profanity`와 발행 차단 사유(`TITLE_PROHIBITED_WORD`·`COMMENTS_PROHIBITED_WORD`)를 주고, 발행은 `COMMON_003`(`fields`·`commentMemberIds`)으로 거부한다. 가짜 서버는 실시간 이벤트를 보내지 않는다 | `src/mocks/lib/prohibitedWord.ts`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

### 백엔드에 확인할 것

| 영역      | 확인할 것                                                                                                                                                                                                                                                                        |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 사진함    | `capturedTime`은 Swagger가 `LocalTime` 객체로 보이지만 서버는 `"HH:mm:ss"` 문자열만 받는다(백엔드 확인, 목도 문자열만 받는다)                                                                                                                                                    |
| 사진함    | 사진 날짜 변경 메서드가 문서 헤더는 PATCH, Swagger는 POST이다                                                                                                                                                                                                                    |
| 사진함    | 업로드 시각을 응답에 줄 수 있는지(지금은 사진 id로 파생한 값으로 정렬 기준만 맞춘다)                                                                                                                                                                                             |
| 번들 작성 | 사진이 사라졌을 때(`PHOTO_004`)의 HTTP 상태와 detail 모양, READY가 아닌 사진의 오류 코드                                                                                                                                                                                         |
| 번들 작성 | 발행·수정 권한이 OWNER 전용으로 좁혀지는지                                                                                                                                                                                                                                       |
| 번들 작성 | 사진 이동에서 맨 앞·맨 뒤 anchor를 키 생략과 null 중 무엇으로 받는지(화면은 키를 생략해 보냄)                                                                                                                                                                                    |
| 번들 작성 | 사진 구성 변경에서 같은 원본을 한 요청에 추가·제거했을 때의 오류 코드(가짜 서버는 `COMMON_001`, 실서버는 `BUNDLE_006`일 수 있음)                                                                                                                                                 |
| 번들 작성 | 멱등 키로 실패 응답도 재생하는지, 추가 사진의 READY 상태 검증과 이미 담긴 원본 재추가 처리                                                                                                                                                                                       |
| 번치 홈   | 작성 중인 번들 목록(`GET …/bundles?status=DRAFT`)의 정렬이 명세에서 갱신 최신순(updatedAt)과 생성 최신순(createdAt)으로 달리 적혀 있다(가짜 서버는 갱신 최신순)                                                                                                                  |
| 번치 홈   | 같은 목록이 번치의 모든 초안인지 내가 참여한 초안만인지(화면은 거르지 않고 그대로 보임)                                                                                                                                                                                          |
| 번치 홈   | `members/me`의 기본 번치와 서버 `currentBunchId`가 항상 같은지(다르면 EXTERNAL 응답이 와서 오류 화면이 된다)                                                                                                                                                                     |
| 번치 전환 | `PUT /bunches/{id}/last-used` 뒤 `members/me`의 `defaultBunch`와 `members/me/bunches`의 `defaultBunchId`가 그 번치로 바뀌는지(화면은 그렇게 보고 다시 읽음)                                                                                                                      |
| 번치 전환 | `activeBunches`의 정렬 기준(화면은 `lastUsedAt` 최신순으로 다시 정렬), 접근 불가 안내 30일 만료 뒤 목록에서 빠지는지                                                                                                                                                             |
| 번치 홈   | 운영 `/home` 응답이 접근 범위 필드(`accessScope`·`followState`·`canView*`·`isCurrentBunch`)를 항상 주는지(주면 선택이 아니라 필수로 받음)                                                                                                                                        |
| 번치 홈   | 다른 번치(EXTERNAL) `/home`의 `memberCount`·`followerCount`·`followingCount`가 null로 오는지(Swagger·스키마는 필수 숫자라 null이면 계약 위반으로 화면 오류)                                                                                                                      |
| 인증      | 백엔드 `POST /auth/reissue`가 만료·폐기·재사용된 refresh 토큰에 주는 상태·code(Swagger에 오류 정의 없음, 웹은 502·503·504만 일시 장애로 봄)                                                                                                                                      |
| 다른 번치 | 같은 번치를 24시간 안에 세 번째 신고할 때의 거절 HTTP 상태와 오류 코드(기능명세 5.10.7 「이미 신고가 접수되어 검토 중이에요.」). API 명세 086 「번치 신고」는 반복 신고를 처음 신고 ID로 성공시키고 제한이 없어 화면은 미구현(#453). 번들·댓글 신고(018·019)는 `BUNCH_011`(#457) |

2026-11-19 확인(#453, 사용자 답변과 API 명세 v6):

- 번치를 만들면 새로 만든 번치가 기본 번치가 된다. 만든 직후 `/bunch`로 가는 동작은 이 기준이다.
- 번치 이름 안의 공백을 서버가 받는다.
- 초안 삭제는 참여 중인 생성자 또는 OWNER·CO_OWNER만 가능하고 아니면 403 `AUTH_002`다. 발행본 삭제는 OWNER만 가능하며, 그사이 발행된 초안을 OWNER가 지우면 거절 코드 없이 발행본이 삭제된다. 그래서 화면은 삭제 직전에 상세를 다시 받아 발행 여부를 확인한다.
- 초안 개수(`BundlePage.total`·홈 `draftCount`)는 번치 전체 기준이다.
- `BUNDLE_001`은 멤버 부족과 초안 한도에 함께 쓴다(화면은 멤버 목록을 새로 받아 구분).
- 다른 번치 홈 404는 「삭제된 번치예요.」로 처리하는 지금 방식을 유지한다(사용자 결정, 서버는 삭제와 없는 번치를 구분하지 않음).

### 실서버를 연결할 때 정리할 것

- 가짜 서버만 있는 확장은 지금 없다(편집권·캡션은 #354에서 제거). 번들 응답의 `locations`·`locationVersion`은 2026-11 타입 재생성으로 서버 계약(BundleSnapshot)에 들어와 확장이 아니다. 가짜 서버는 저장된 위치를 계약 모양(`id`·`position` 포함)으로 돌려준다. 위치를 저장하는 요청 계약(`BundleLocationInput`)도 생성 타입에 있지만, 화면 연결은 장소 검색 이슈에서 한다.
- `public/mock/photos`(약 7MB)는 `NEXT_PUBLIC_API_MOCKING`과 무관하게 운영 배포에도 정적 파일로 공개된다. 얼굴이 없는 시연 사진이라 기밀 문제는 아니고 용량 문제다. 운영 배포에서 제외할 방안을 정한다.
- 사진 목록의 `thumbnailUrl`은 URL 형식을 검증하지 않고(상세 `imageUrl`만 검증), 이미지 호스트 allowlist도 없다. 실서버를 연결할 때 함께 정한다.
- 사진 목록은 100장씩 마지막 쪽까지 순차로 받는다(상한 1,000장). 사진함 화면은 첫 쪽이 오면 먼저 보여 주고 나머지는 이어서 받으며, 번들 만들기 화면은 마지막 쪽까지 받은 뒤에만 열린다. 날짜 미확인 영역의 「N장」은 받은 쪽까지의 수라 100장을 넘으면 다 받기 전까지 적게 보일 수 있다. 목록 query는 30초가 지나면 진입·앱 복귀 때 다시 받는다.
- 번치 쪽의 쪽 번호 목록(완성된 번들, 팔로워·팔로잉, 차단, 알림)은 `page`(0부터)·`size`(50)로 이어서 받는다. 받는 사이 앞에 항목이 생기면 다음 쪽이 겹쳐 같은 ID는 처음 것만 남긴다(`lib/pages.ts`). 서버가 커서 방식으로 바꾸면 다시 맞춘다. 가짜 서버는 네 API 모두 `page`·`size`를 받고 `hasNext`를 돌려준다.
- 번치 홈 화면의 후속(쪽 크기, 다른 번치 열람, 표지 주소 대체 등)은 `BunchHomeScreen.spec.md`의 「서버 연동의 후속과 알려진 차이」에 있다.

# 사용성 테스트(UT) 세팅

UT는 웹에서 한 기기로 진행하고, 다른 멤버가 할 행동은 "미리 해 둔 상태"로 세팅한다(확정). 진행자가 다른 기기로 같은 번치를 함께 조작하지 않는다.

## 왜 미리 세팅하나

- 번들 업로드에는 참여 멤버 2명 이상과 참여 멤버 전원의 코멘트가 필요하다. 그래서 참여자 혼자서는 업로드까지 갈 수 없다.
- 가짜 데이터는 기기(브라우저)마다 따로 있다. 진행자 기기에서 남긴 코멘트는 참여자 화면에 보이지 않는다. MSW 가짜 DB도 브라우저의 IndexedDB에 저장된다(`docs/workflows/testing.md`의 "MSW 가짜 서버").
- 따라서 진행자의 행동은 시작 데이터에 넣어 둔다. 참여자가 업로드 직전까지 막히지 않게 하는 것이 목적이다.

## 역할

| 역할   | 계정 상태                                                    | 하는 일                                           |
| ------ | ------------------------------------------------------------ | ------------------------------------------------- |
| 참여자 | 번들 초안을 처음 만드는 사람(초안 생성자, 업로드 권한 있음)  | 과제를 수행한다                                   |
| 진행자 | 같은 번치의 일반 멤버. 이미 참여 멤버이고 코멘트를 남긴 상태 | 화면은 조작하지 않고 과제 안내와 관찰·기록만 한다 |

문서와 시작 데이터에는 실제 사람 이름 대신 역할만 쓴다. 계정 정보와 배포 주소는 저장소에 올리지 않는다.

## 시작 데이터

세팅 위치는 화면의 연동 상태에 따라 다르다.

- 서버 연동 전 화면: 화면이 읽는 샘플 데이터(`features/<feature>/fixtures/`)에 넣는다. 번들 공동 편집 화면은 `features/bundle/fixtures/draft.fixture.ts`를 읽는다.
- 서버 연동 후 화면: MSW 가짜 DB 시작 데이터(`src/mocks/db/seed.ts`)에 넣고, `NEXT_PUBLIC_API_MOCKING=enabled`로 빌드한다.

넣어 둘 상태는 아래와 같다.

- 참여자는 번치 멤버이고, 번들 초안의 생성자다.
- 진행자는 같은 번치의 일반 멤버이고, 그 초안의 참여 멤버다.
- 진행자는 그 초안에 코멘트를 이미 남겼다.
- 참여자가 자기 코멘트를 쓰면 업로드 조건이 채워진다.

## 상태 B 시나리오(가짜 서버)

번치 홈에서 시작해 「+」로 사진 P1~~P4를 고르고 번들을 만들면, 가짜 서버가 초안 생성 직후 상태 B를 덧입힌다(`src/mocks/scenario/`). 고른 사진이 정확히 P1~~P4일 때만 적용되고, 다른 구성은 일반 초안이다. UT가 끝나면 `mocks/scenario/` 폴더와 `handlers/bundles.ts`의 `onDraftCreated` 호출만 지우면 된다.

| 항목                | 상태 B 값                                                                                            |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| 참여 멤버·사진 순서 | 서버 규칙 그대로(큐시즘·경진·은우, 고른 순서)                                                        |
| 제목·날짜·위치      | 제목 채움, 날짜 10월 17일, 위치 속초해수욕장 1곳                                                     |
| 캡션                | 사진 1번 작성 완료, 2번은 경진이 편집 중(비어 있음), 3·4번 비어 있음                                 |
| 코멘트              | 경진·은우 작성 완료, 큐시즘(참여자)은 미작성                                                         |
| 공개 범위           | 미선택                                                                                               |
| 편집 중 표시        | 2번 사진 캡션은 경진, 위치는 은우가 편집 중이며 만료·해제되지 않는다(참여자는 편집권을 얻을 수 없음) |

- 위치 저장과 편집권(`LOCATION`)은 서버 명세에 없는 가짜 서버 확장이다. 응답에 `locations`(provider, externalId, name, address)와 `locationsVersion`을 더했고, 화면은 위치를 바꾸기 전까지 서버 값을 보인다. 위치를 바꾸는 저장은 아직 화면에서만 유지된다(장소 검색 이슈에서 계약을 정한 뒤 연결).
- 임의로 정한 값(시나리오 원문 없음): 제목「속초 첫째 날 🌊」, 1번 캡션「도착하자마자 바다부터!」, 경진·은우 코멘트 문구, 위치 주소. `src/mocks/scenario/utStateB.ts`에서 바꾼다.
- 진행자 초기화·복구 장치는 아직 없다(방향을 정한 뒤 만든다). 회차 사이에는 아래 「회차 사이 초기화」대로 사이트 데이터를 지운다.

## 시작 화면과 홈 화면 앱

- UT는 **번치 홈(`/bunch`)에서 시작**한다. 번치 홈 → 「+」 → 사진 선택(상태 A) → 번들 만들기 → 작성(상태 B) → 업로드 → 번치 홈 순서다.
- 참여자 기기에서는 주소창 없이 앱처럼 열리도록 홈 화면에 추가해 쓸 수 있다. iOS는 Safari의 공유 메뉴에서 「홈 화면에 추가」, Android는 Chrome 메뉴에서 「홈 화면에 추가」를 쓴다. 홈 화면에서 열었을 때 번치 홈이 첫 화면인지, 서비스 워커가 등록되는지, Safe Area가 맞는지는 실기기에서 확인해야 한다(#216에서 확인하고 이 문서에 결과를 적는다). 현재는 확인하지 않았다.
- 서비스 워커는 HTTPS 또는 localhost에서만 동작한다. `http://IP` 접속은 가짜 서버가 켜지지 않을 수 있다.

| ----------------------- | --------------------------------------------------------------- | -------------------------------------------------------------- |

위 자동 테스트는 각 단계를 따로 확인한다. 처음부터 끝까지 이어서 브라우저에서 돌려 본 것은 아니므로 회차 전에 한 번 직접 확인한다.

## 회차 전 준비

1. UT용 빌드를 HTTPS 주소 또는 localhost로 연다. 서비스 워커는 `http://IP` 접속에서 동작하지 않을 수 있다.
2. 브라우저의 사이트 데이터를 지운다. MSW 가짜 DB는 IndexedDB에 남아 새로고침해도 이전 회차 상태가 유지된다. 샘플 데이터 화면은 새로고침만으로 시작 상태로 돌아간다.
3. 새로고침한 뒤 첫 화면이 시작 데이터 상태인지 확인한다. 진행자가 참여 멤버로 보이고 코멘트가 있어야 한다.

## 회차 사이 초기화

회차가 끝나면 "회차 전 준비"의 2·3단계를 다시 한다. 앞 참여자가 남긴 사진·코멘트가 다음 참여자에게 보이면 안 된다.

## 연동 상태와 샘플로 남긴 부분

## 가짜 서버와 서버 명세의 차이, 백엔드 확인 항목

가짜 서버(`src/mocks`)는 Swagger와 Notion 명세를 기준으로 만들었지만, 명세끼리 다르거나 가짜 서버가 다르게 동작하는 부분이 있다. 실서버를 연결할 때 아래를 확인한다. 화면별 후속은 각 feature의 spec에 있다.

### 가짜 서버가 명세와 다른 부분

| 영역      | 차이                                                                  | 비고                                                         |
| --------- | --------------------------------------------------------------------- | ------------------------------------------------------------ |
| 번들 작성 | 날짜 미래 금지 검사가 없다                                            | 명세에는 있음                                                |
| 번들 발행 | 다른 멱등 키로 같은 본문을 다시 발행하면 `BUNDLE_002`                 | 명세는 최초 요청과 같으면 허용                               |
| 번들 작성 | 편집권이 REST 경로(`leases/acquire`·`heartbeat`·`release`, 15초 만료) | 실제는 STOMP, 교체 때 5초 heartbeat와 token 교체 처리가 필요 |
| 번치 홈   | 비소속 번치의 `/home`을 `AUTH_002`로 막는다                           | 명세는 최소 EXTERNAL 응답(`canView*` false)                  |
| 번치 홈   | 비소속 번치의 `/published-bundles`가 내 번치 발행본 전체를 돌려준다   | 명세는 EXTERNAL이면 PUBLIC 발행본만                          |

### 백엔드에 확인할 것

| 영역      | 확인할 것                                                                                                    |
| --------- | ------------------------------------------------------------------------------------------------------------ |
| 사진함    | `capturedTime`이 Swagger는 `LocalTime` 객체, 명세 문서는 `"HH:mm:ss"` 문자열이다(둘 다 받도록 했다)          |
| 사진함    | 사진 날짜 변경 메서드가 문서 헤더는 PATCH, Swagger는 POST이다                                                |
| 사진함    | 업로드 시각을 응답에 줄 수 있는지(지금은 사진 id로 파생한 값으로 정렬 기준만 맞춘다)                         |
| 번들 작성 | 사진 누락·READY 아님 오류 코드, 발행 충돌 `BUNDLE_003`의 detail 모양                                         |
| 번들 작성 | 편집권 REST 대체 여부(없으면 운영에서 제목·날짜·캡션 저장이 실패한다)                                        |
| 번들 작성 | 발행·수정 권한이 OWNER 전용으로 좁혀지는지                                                                   |
| 번치 홈   | `members/me`의 기본 번치와 서버 `currentBunchId`가 항상 같은지(다르면 EXTERNAL 응답이 와서 오류 화면이 된다) |
| 번치 홈   | 서버 PR #62(`/home`, `/published-bundles`) 병합 뒤 응답이 명세와 같은지                                      |

### 실서버를 연결할 때 정리할 것

- `public/mock/photos`(약 7MB)는 `NEXT_PUBLIC_API_MOCKING`과 무관하게 운영 배포에도 정적 파일로 공개된다. 얼굴이 없는 시연 사진이라 기밀 문제는 아니고 용량 문제다. UT 이후 배포에서 제외할 방안을 정한다.
- 사진 목록의 `thumbnailUrl`은 URL 형식을 검증하지 않고(상세 `imageUrl`만 검증), 이미지 호스트 allowlist도 없다. 실서버를 연결할 때 함께 정한다.
- 사진 목록은 마지막 쪽까지 순차로 받는다. 사진이 많아지면 무한 스크롤 구조로 바꾼다(`PhotoBoxScreen.spec.md`).
- 번치 홈 화면의 후속(쪽 크기, 다른 번치 열람, 표지 주소 대체 등)은 `BunchHomeScreen.spec.md`의 「서버 연동의 후속과 알려진 차이」에 있다.

## 확인하지 않은 것

- 진행 대본(과제 문구, 진행자가 개입하는 시점)은 정해지지 않았다(미정).
- UT 상태 B(번들 초안 직후 제목·캡션·위치·날짜·다른 멤버 코멘트가 채워진 상태), 편집 중 표시 고정, 회차 초기화·복구 장치는 아직 없다. 이것이 없으면 UT에서 업로드(참여 멤버 전원 코멘트)를 끝까지 할 수 없다.
- UT 시작 화면(번치 홈 또는 번들 만들기 선택 화면)이 확정되지 않았다.

# 007: 로그인·온보딩 API 계약 확정 후 MSW를 도입한다

- 상태: accepted
- 구현 상태(2026-10-15 확인): 미구현. MSW 설치와 초기 설정은 아래 후속 작업에 따라 진행한다.

## 배경

로그인·온보딩 UI를 개발할 때 백엔드 준비 여부와 관계없이 성공·로딩·인증 실패·서버 오류 상태를 재현할 필요가 있다. 화면마다 가짜 데이터를 넣으면 실제 API 연결 시 수정 범위가 늘어나고, API 계약이 정해지기 전에 mock을 만들면 실제 응답과 어긋날 수 있다.

## 결정

로그인·온보딩 endpoint와 요청·응답 계약이 확정되면 `apps/web`에 MSW를 작게 도입한다. 지금은 설치하거나 명세 없는 endpoint를 미리 구현하지 않는다.

- 최초 범위는 합의된 API의 성공·응답 지연·401·500 응답이다. 실제 계약에서 사용하는 오류 형식과 상태 코드를 따른다.
- 브라우저 개발 환경에서 명시적으로 켜고, 운영 환경에서는 mock을 활성화하지 않는다.
- 같은 handler와 fixture를 개발 환경 및 화면/API 통합 테스트에서 재사용한다. 기존 HTTP client의 fetch 단위 테스트는 유지한다.
- Next.js 서버 요청 mocking은 해당 기능에 필요할 때 별도로 설정한다. 브라우저용 mock이 서버 요청까지 처리한다고 가정하지 않는다.
- 초기 도입은 웹에 한정한다. 모바일 WebView에서의 동작은 별도로 확인하고, admin은 기능 개발이 재개될 때 필요성을 판단한다.

## 검토한 대안

- **즉시 모든 API를 mock**: 화면 개발을 빨리 시작할 수 있지만 미확정 계약을 추정해야 하고 실제 API와 맞추는 비용이 커진다.
- **화면에 가짜 데이터를 직접 넣기**: 단순 UI에는 충분하지만 요청·캐시·오류 처리 흐름을 함께 확인하기 어렵다.
- **실제 백엔드만 사용**: mock 유지 비용은 없지만 개발 서버 가용성에 의존하고 지연·오류 상태를 반복 재현하기 어렵다.

## 영향

API 요청 코드를 유지한 채 응답 상태를 재현할 수 있다. 대신 mock과 실제 API 계약이 달라지지 않도록 endpoint·응답 변경 시 handler와 fixture를 함께 갱신해야 한다. API 테스트를 전부 MSW로 전환하거나 공용 mock package를 미리 만들지는 않는다.

## 검증 / 후속 작업

1. 로그인·온보딩 API 계약과 화면 상태를 확정한다.
2. 웹 workspace에 개발 의존성·브라우저 초기화·Vitest 설정을 필요한 범위로 추가한다.
3. 성공·지연·401·500에서 화면 동작을 확인하고 테스트별 handler 초기화 및 운영 환경 비활성화를 검증한다.
4. 실제 API로 전환해 요청·응답 계약을 대조하고 `docs/workflows/testing.md`에 실제 사용법을 기록한다.

현재는 도입 결정만 기록했으며 설치·실행과 개발 효율 효과는 검증하지 않았다.

## 재검토 조건

- 실제 API만으로 개발과 오류 상태 재현이 충분하고 mock 유지 비용이 더 클 때는 도입 범위를 줄이거나 보류한다.
- 여러 앱에서 같은 API mock을 실제로 재사용하게 되면 공용화 경계를 검토한다.

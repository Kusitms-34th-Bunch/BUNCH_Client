# 029: 앱 쉘 핵심 흐름은 Maestro로 iOS 시뮬레이터에서 확인한다

- 상태: proposed
- 기록일: 2026-11-21
- 구현 상태(2026-11-21 확인): flow 5개와 알려진 문제 flow 1개, E2E 빌드 스크립트, CI workflow(`mobile-e2e.yml`)를 추가했다(#483). 로컬 iPhone 17 Pro 시뮬레이터(Xcode 26.6)에서 5개 모두 통과(약 2분)했다. CI 실행은 아직 확인하지 못했다. 2026-11-23(#518): 시스템 탭 바의 번치 탭 꾹 누르기(전환 시트 → 화면 전체 번치 전환)와 두 번 누르기(최근 번치 왕복) flow 2개를 더했다(`06`·`07`). 로컬에 Maestro가 없어 아직 돌려 보지 않았다.

## 배경

웹 E2E(Playwright)는 웹 화면만 본다. 최근 문제는 대부분 웹 밖의 쉘에서 생겼다.

- 탭 바가 화면과 어긋남(#481), 앱 시작 직후 입력이 무시됨(QA 2차 F-3)
- 스플래시 앞 흰 화면, 네이티브 모듈 누락으로 앱이 바로 꺼짐(`expo-video`)
- 키보드 입력, bridge 동작

이런 문제는 실기기나 사람이 시뮬레이터를 눌러 봐야 알 수 있었다.

## 결정

- Maestro로 쉘의 핵심 흐름을 확인한다. Maestro는 시스템 탭 바와 WebView 안의 요소를 같은 접근성 트리로 보고 판정한다.
- 대상 앱은 E2E 전용 iOS 시뮬레이터 Release 빌드다(`scripts/e2e-ios-build.mjs`). JS가 앱에 들어가 Metro와 개발용 런처 없이 실행된다.
- 웹은 같은 기기에 가짜 서버(MSW)를 켠 운영 빌드로 띄운다(`http://127.0.0.1:3200`, Playwright E2E와 같은 방식). 가짜 DB가 로그인·가입 완료 상태로 시작해 소셜 로그인을 자동화하지 않고, 운영 데이터를 건드리지 않는다.
- Release 빌드는 HTTPS 웹만 열기 때문에, E2E 빌드에만 `EXPO_PUBLIC_E2E=1`을 넣어 루프백 http(`localhost`·`127.0.0.1`)를 허용한다. 다른 http 주소는 E2E 빌드도 거절한다. iOS ATS는 이미 `NSAllowsLocalNetworking`으로 로컬 주소를 허용한다.
  - 루프백 판정은 URL 파싱이 아니라 주소 문자열 전체로 한다. 앱 런타임(React Native)의 URL 해석이 표준과 달라 `http://evil.com?@127.0.0.1`을 루프백으로 읽기 때문이다.
  - EAS production 빌드에 이 값이 있으면 `app.config.js`가 빌드를 멈춘다. EAS를 거치지 않는 Release 빌드(Xcode Archive 등)는 막지 않는다.
- CI는 `macos-26` 러너에서 돈다. 저장소가 공개라 기본 macOS 러너는 무료지만 실행이 무거워, PR마다가 아니라 develop push와 수동 실행에서만 돌린다. push는 쉘·bridge와 쉘을 부르는 웹 코드 일부(웹 bridge 모듈 `shared/bridge`, 탭 바, 탭 동기화, 가짜 서버 데이터)가 바뀔 때만 돈다. 그 밖의 화면 변경은 필요할 때 수동 실행으로 확인한다.
- Maestro CLI는 버전과 SHA-256을 고정한 GitHub 릴리스 zip으로 받는다(설치 스크립트를 실행하지 않음).
- flow는 iOS가 번역하는 시스템 문구(예: 탭 바의 접근성 이름) 대신 웹이 정한 문구(탭 이름 등)로 판정한다. 시뮬레이터 언어에 따라 결과가 바뀌지 않게 하기 위해서다.
- 아직 고치지 않은 문제를 재현하는 flow는 `known-issue` 태그로 기본 실행에서 뺀다. 고치면 태그를 지워 회귀 테스트로 쓴다. 해당 flow가 있는 동안은 CI가 job을 막지 않는 별도 단계로 돌려 결과를 요약에 남긴다. 지금은 해당 flow가 없어 그 단계도 지웠다(2026-11-23 #520, `docs/workflows/mobile-e2e.md`).

## 비교한 대안

- 개발 빌드 + Metro: http 개발 주소를 바로 쓸 수 있지만, 개발용 런처·메뉴가 끼어 flow가 흔들리고 Metro를 함께 띄워야 한다.
- 배포된 HTTPS 웹을 여는 Release 빌드: 쉘 규칙을 바꾸지 않아도 되지만, 운영이면 데이터를 건드리고 가짜 서버 배포는 따로 관리해야 한다.
- Maestro Cloud·EAS Workflows: 관리가 쉽지만 비용이 들고, 빌드·실행 기록이 저장소 밖에 남는다.
- Android 에뮬레이터(Linux 러너): 싸지만 시스템 탭 바·스플래시 등 iOS 전용 동작을 확인할 수 없다.

## 결과

- 쉘에서만 생기는 문제를 빌드를 올리기 전에 자동으로 잡을 수 있다. 처음 돌린 날 시작 직후 입력 무시(F-3)를 재현했다.
- 시뮬레이터는 실기기와 입력·렌더 속도가 다르다(QA 2차에서 시뮬레이터 스와이프 0/7, 실기기 정상). flow는 접근성 트리로 판정하고, 실기기 확인을 대신하지 않는다.
- 시작 직후 입력 무시 때문에 각 flow의 첫 입력만 「다음 화면이 보일 때까지 다시 누르기」(`subflows/tap-until-visible.yaml`)를 쓴다. 그 뒤 입력은 한 번만 눌러 회귀를 숨기지 않는다. 이 문제를 고치면 재시도를 지운다. 2026-11-23 #520에서 원인(사라지는 스플래시 덮개가 입력을 먹음)을 고쳐 flow 90을 기본 실행에 넣었다. CI에서 90이 통과하는 것을 확인한 뒤 재시도를 지운다.
- CI 빌드에는 소셜 로그인 키가 없다. 가짜 DB가 로그인 상태로 시작해 flow에는 영향이 없지만, 로그인 화면·SDK 동작은 이 E2E로 확인하지 않는다.
- E2E 빌드 플래그가 스토어 빌드에 들어가면 http 루프백을 여는 셈이라, 스토어 빌드 설정에 넣지 않는다.

- CI 첫 실행(2026-11-21, `macos-26`)에서 flow 하나가 로컬보다 약 5~8배 오래 걸렸다(실행 6초→58초, 탭 전환 24초→1분 51초). 앱 실행 대기(60초)와 탭 첫 로딩 대기(10초)를 넘겨 2개가 실패해, 대기 상한을 CI 기준(앱 실행 120초, 탭 첫 로딩 30초)으로 늘렸다. 상한은 기다리는 최대 시간이라 빠른 환경의 통과 시간은 그대로다.
- 2026-11-22 실행에서는 시뮬레이터 첫 부팅의 데이터 이전이 1분 43초 걸린 뒤 Maestro iOS 드라이버 시작이 기본 상한을 넘겨 flow가 하나도 돌지 않았다. 시뮬레이터 부팅을 잡 맨 앞에서 시작해 iOS 빌드(약 20분)와 겹치게 했고, 드라이버 시작 상한(`MAESTRO_DRIVER_STARTUP_TIMEOUT`)은 느린 러너를 위한 안전 상한으로 5분을 둔다. 본 flow가 실패한 실행에서는 알려진 문제 flow의 실패 화면·로그도 결과에 함께 올린다. flow를 러너 여러 대로 나누는 방식은 러너마다 빌드와 부팅을 다시 해야 해서 쓰지 않는다.
- 2026-11-23 실행은 드라이버 문제 없이 flow가 통과하다가 잡 상한 60분에 걸려 취소됐다(웹 빌드 약 4분 + 네이티브 생성 약 1.5분 + iOS 빌드 약 20분 + flow마다 1.5~2.5분). 네이티브 지문(`@expo/fingerprint`)과 Node 버전(`ios/.xcode.env.local`에 node 절대 경로가 들어가서)을 키로 `ios/`(Pods 포함)를 캐시해 같으면 생성 단계를 건너뛰고, 빌드 중간 결과(`build/e2e`)도 지문 단위로 캐시해 지문이 달라도 최근 것으로 증분 빌드한다(실행마다 새로 저장하지 않음). 캐시가 없는 첫 실행이 끝나도록 상한을 120분으로 올렸다. 캐시 효과는 다음 실행 두 번(캐시 만들기·쓰기)으로 확인한다.
- 2026-11-26: 한 러너 안에서 시뮬레이터 두 대에 flow를 나눠 돌린다(`--shard-split 2`). flow 9개의 합이 약 16분이었고, 대부분 flow마다 `clearState`로 앱을 새로 켜는 시간이다. 두 번째 기기는 첫 기기와 같은 기종으로 새로 만들어 화면 크기를 맞추고, iOS 빌드와 자원을 나누지 않게 빌드가 끝난 뒤 부팅한다. 러너 자원(3코어 수준)에서 실제로 빨라지는지는 다음 실행으로 확인하고, 느려지거나 불안정하면 `--shard-split`을 빼 한 대로 되돌린다.
- 2026-11-26 실행에서 두 번째 기기가 빌드 뒤 첫 부팅을 끝내지 못했다(`bootstatus` 5분 25초 뒤 실패, 「Waiting on System App」). 이어 Maestro 드라이버가 상한 5분 안에 뜨지 않아 flow 9개가 모두 실패했다. 러너 자원으로는 두 대가 안정적으로 뜨지 않아 한 대로 되돌렸다. 잡 상한(120분) 안에서 flow 합 약 16분은 감당된다.

## 다시 검토할 조건

- CI 실행 시간이 길거나 자주 흔들리면 캐시(Pods·DerivedData)와 flow 수를 줄이거나 수동 실행만 남긴다.
- PR 단계에서 쉘 회귀를 막아야 하면 쉘 변경 PR에만 돌리는 trigger를 검토한다.
- Android 쉘을 출시하면 같은 flow를 Android 에뮬레이터에서도 돌린다.

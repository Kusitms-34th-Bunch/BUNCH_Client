# 023: 운영 서버의 로그인 뒤 화면 Lighthouse 측정 방식

- 상태: accepted(2026-11-23, 4번을 3번과 함께 씀)
- 기록일: 2026-11-15
- 구현 상태(2026-11-23 확인): 4번 구현(#524). 운영 Lighthouse는 그대로 로그인 없이 열리는 페이지만 측정한다(`.github/workflows/lighthouse-production.yml`). 로그인 뒤 화면은 PR에서 가짜 서버 빌드로 측정하고(`.github/workflows/lighthouse.yml`), 운영 실사용 지표는 아래 「결정」대로 모은다.

## 배경

사용자가 실제로 머무는 화면은 피드·번치 홈·MY 같은 로그인 뒤 화면이다. PR에서는 가짜 서버(MSW)를 켠 빌드로 이 화면을 측정하지만, 가짜 서버 코드와 준비 대기가 들어가 성능 절대값은 운영과 다르다. 운영 서버의 로그인 뒤 화면을 재려면 측정 도구가 사람 없이 로그인 상태를 만들어야 한다. 지금은 그 방법이 없다.

- 웹은 브라우저에서 로그인할 수 없다. 소셜 로그인은 앱 쉘의 네이티브 SDK로만 하고, 웹은 받은 토큰을 BFF(`/api/auth/login`)로 넘긴다(`docs/workflows/web-deployment.md`).
- 닉네임만으로 토큰을 받는 개발용 로그인(`/api/dev/token`)은 운영 빌드에서 꺼진다(`apps/web/src/shared/api/server/devTokenFlag.ts`). 이것을 열면 닉네임만으로 아무 계정에 들어갈 수 있으므로 운영 측정을 위해 열지 않는다.

## 대안

1. 측정 전용 계정의 토큰을 secret으로 둔다. 백엔드가 측정 전용 계정을 만들고, 사람 없이 쓸 수 있는 refresh 토큰(또는 그에 준하는 발급 방식)을 준다. workflow가 `/api/auth/reissue`로 쿠키를 받아 Lighthouse 요청에 붙인다.
   - 장점: 실제 운영 화면과 백엔드 응답을 그대로 잰다.
   - 조건: 계정은 실제 사용자 데이터와 분리하고(혼자 쓰는 번치), 제품 분석(PostHog)과 오류 수집에서 뺀다. 토큰을 가진 job은 외부 도구(`yarn dlx`로 받는 Lighthouse)를 실행하므로, 유출돼도 피해가 이 계정에 한정돼야 한다. 토큰 수명과 교체 방법을 백엔드와 정한다.
   - 쿠키를 Lighthouse 요청 헤더(`extraHeaders`)로 넘기면 결과 JSON(`configSettings`)에 원문이 남아 artifact로 저장된다. 헤더가 결과에 남지 않는 방식으로 넣거나 올리기 전에 지우고, artifact 보존 기간과 열람 범위를 다시 정한다. 측정 계정 화면의 스크린샷과 요청 주소도 함께 남는다.
   - 토큰을 가진 job은 캐시를 저장하지 않고, 배포 묶음 artifact와 같은 실행에서 돌지 않는다(운영 측정을 배포 workflow와 나눈 것과 같은 이유).
   - refresh 토큰이 회전하는 방식이면 `/api/auth/reissue`를 한 번 부를 때마다 secret이 무효가 되는지 백엔드와 확인한다.
2. 스테이징 서버에서만 로그인 화면을 잰다. 개발용 로그인을 쓸 수 있는 스테이징 배포를 따로 둔다.
   - 장점: 운영 계정·토큰을 CI에 두지 않는다.
   - 단점: 스테이징 배포가 없다. 운영 CDN·데이터 규모와 달라 「실제 사용자 화면」이라는 목적과 멀어진다.
3. 운영 로그인 화면은 재지 않는다. 회귀는 PR의 가짜 서버 측정으로, 운영 품질은 공개 페이지 측정과 실기기 확인으로 본다.
   - 장점: 추가 secret·계정이 없다.
   - 단점: 실제 백엔드 응답 시간과 데이터 규모가 반영된 로그인 화면 점수가 없다.

4. 운영 사용자의 실제 성능 지표(필드 데이터)를 모은다. 앱 안 WebView에서 로딩(LCP)·반응(INP)·화면 밀림(CLS) 같은 Web Vitals를 제품 분석에 동의한 회원만, 일부 표본만 보낸다(2026-11-23 추가).
   - 장점: 측정 계정·토큰이 필요 없다. 실제 iOS WKWebView, 실제 데이터 규모와 백엔드 응답이 그대로 반영된다. 로그인이 앱 안에서만 되는 지금 구조에 맞는다.
   - 단점: 실험실 점수가 아니라 사용자 분포(예: 75번째 백분위)라 PR 사이 비교가 어렵고, 표본이 쌓여야 의미가 있다. 동의하지 않은 회원·로그인 전 화면은 빠진다(ADR 018). 수집 도구(PostHog·Sentry)의 사용량이 늘어난다.
   - PostHog 자동 수집(`capture_performance: false`)과 Sentry 성능 추적은 끈 채로 두고, 2026-11-23부터 Next가 잰 값을 직접 보낸다(「결정」). 1~3번과 함께 쓸 수 있다.

## 결정

4번을 고르고 3번과 함께 쓴다(2026-11-23, #524). 회귀는 PR의 가짜 서버 측정으로, 운영 품질은 공개 페이지 측정과 실사용 지표로 본다. 1번은 백엔드와 측정 전용 계정이 합의되면 다시 본다.

- 수집: `apps/web/src/shared/components/layout/WebVitalsReporter.tsx`가 Next `useReportWebVitals`로 LCP·INP·CLS·FCP·TTFB를 받아 PostHog `web_vitals` 이벤트로 보낸다(`captureWebVital`). PostHog의 성능 자동 수집(`capture_performance`)은 PostHog에서 확장 스크립트를 받아 와서 끈 채로 두고, Sentry 성능 추적도 쓰지 않는다(ADR 006).
- 동의: 제품 분석에 동의한 회원만 보낸다(ADR 018). 첫 화면 지표는 로그인 확인보다 먼저 나오므로 동의가 정해질 때까지 최대 20건을 모아 두었다가, 동의하면 보내고 아니면 버린다. 미동의로 정해진 뒤에 나온 지표는 같은 방문에서 나중에 동의해도 보내지 않는다.
- 속성: 지표 이름·값(ms, CLS는 점수)·평가(`rating`)·이동 종류·경로·`surface`(앱 WebView면 `app`, 아니면 `web`). 경로는 보내기 직전 정제로 숫자 ID와 초대 토큰을 감춘다. 사용자 글자는 보내지 않는다.
- 표본: 방문(문서)마다 한 번 정한다. 사용자가 적은 지금은 전부(`SAMPLE_RATE = 1`)이고, 이벤트 한도(ADR 018, 월 100만 건)에 다가가면 줄인다.
- 기준값: 화면(경로)별 75번째 백분위를 본다. 화면 이동 뒤 표본(`navigation_type`이 `soft-navigation`)은 첫 로드와 나눠 본다. PostHog 대시보드 구성은 저장소 밖이라 아직 하지 않았다(2026-11-23).
- 한계: 경로는 측정한 화면 주소(`navigationURL`)를 쓰되, 이를 주지 않는 브라우저에서는 보고 시점의 경로라 INP·CLS가 옮긴 화면으로 기록될 수 있다. 동의하지 않은 회원과 로그인 전 화면은 빠진다.

## 결정 전 상태(2026-11-15~23)

백엔드와 1번의 가능 여부(측정 전용 계정, 사람 없이 쓰는 토큰 발급, 수명·교체 방식)를 정하기 전까지 3번으로 운영한다. 정해지면 이 기록을 `accepted`로 바꾸고 고른 방식과 이유, 보안 리뷰 결과를 적는다. 1번을 고르면 토큰을 가진 job이 저장소 코드를 설치·실행하지 않는 `web-deploy.yml`의 원칙을 지킨다.

## 영향

- 운영 서버의 로그인 뒤 화면 점수가 없다. 로그인 화면의 회귀는 PR의 가짜 서버 측정(성능 절대값은 운영과 다름)으로만 본다.
- 운영 측정은 로그인 전 방문이라 제품 분석에 들어가지 않는다(약관에 동의한 회원만 수집, ADR 018).

## 후속 작업

- 백엔드에 확인할 것: 측정 전용 계정을 둘 수 있는지, 사람 없이 쓰는 토큰 발급 방식과 수명·교체·회전 여부, 운영 데이터·통계에서 이 계정을 빼는 방법.
- 합의되면 이 기록을 고친 뒤 구현 이슈를 따로 만들고, 구현 전후에 보안 리뷰를 한다.

## 재검토 조건

- 스테이징 배포가 생기면 2번을 다시 본다.
- 운영 사용자에게서 로그인 뒤 화면의 속도 문제가 보고되는데 PR 측정과 실기기 확인으로 원인을 찾지 못하면, 1번 합의를 서두른다.

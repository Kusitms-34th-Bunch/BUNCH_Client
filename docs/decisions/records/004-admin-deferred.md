# 004: apps/admin은 scaffold로 유지하고 기능 개발은 보류한다

- 상태: accepted

## 배경

이 저장소는 일반적인 웹 서비스 구성, 곧 사용자용 웹(`apps/web`)과 관리자용 웹(`apps/admin`)을 따로 두는 구조로 시작했다. 이후 기획상 모바일 앱이 필요해져 `apps/mobile-shell`을 추가했고(`docs/architecture/mobile-shell.md`), 개발 우선순위가 사용자 웹과 모바일 앱으로 옮겨갔다. 그 결과 `apps/admin`은 당장 기능을 개발하지 않는 상태다.

## 결정

`apps/admin`은 삭제하지 않고 scaffold 상태로 유지한다. 기능 개발은 의도적으로 보류한다.

- admin이 실제로 필요한지 아직 확정되지 않았다. 지금 지우면 필요해질 때 구조·CI·e2e 연결을 다시 만들어야 한다.
- 보류 중에는 admin에 기능 코드를 추가하지 않고, 기존 scaffold가 build·lint·typecheck를 통과하는 상태만 유지한다.
- README와 이 문서에 보류 사실과 이유를 남겨, 방치가 아니라 우선순위 판단임을 확인할 수 있게 한다.

## 검토한 대안

- **admin 삭제**: 안 쓰는 코드가 사라진다. 다만 README, CI, e2e, generator, docs의 admin 참조를 함께 정리해야 하고, 나중에 필요해지면 되살리는 비용이 든다. 필요 여부가 확정되지 않아 지금은 택하지 않는다.
- **기능을 일부라도 구현**: 모바일 앱·사용자 웹 일정을 해치고, 요구가 불분명한 상태에서 만든 코드는 다시 방치될 가능성이 크다.

## 영향

- admin은 build·lint·typecheck 대상에 계속 포함되어 유지 비용이 조금 든다.
- 새 기능은 web과 mobile-shell을 기준으로 개발한다. admin 전용 요구가 생기기 전까지 admin을 고려해 구조를 복잡하게 만들지 않는다.

## 검증 / 후속 작업

- `yarn typecheck`와 `yarn lint`에서 admin이 계속 통과하는지 확인한다.

## 재검토 조건

- 운영·검수·콘텐츠 관리처럼 admin 전용 요구가 생겨 기능 개발이 필요해질 때 → 보류를 해제한다.
- 프로젝트 마감까지 admin을 쓰지 않을 것이 확실해지고 유지 비용(CI 시간, 의존성 업데이트)이 부담될 때 → 삭제를 검토한다. 삭제 전에 백업 또는 git 이력을 확보한다.

# 017: 하단 탭 전환은 웹과 iOS 앱 모두 80ms 크로스페이드로 한다

- 상태: accepted
- 기록일: 2026-11-01
- 구현 상태(2026-11-01 확인): 구현됨(#162). 웹은 `AppTransitions.tsx`의 탭 크로스페이드와 `MainTabPage`(탭 page 전환 대상), iOS 앱은 `apps/mobile-shell/modules/tab-crossfade`. 웹은 개발 서버 Chromium에서 사진함↔번치 양방향을 측정했다. iOS 시뮬레이터와 안드로이드 에뮬레이터에서 동작을 확인했고 실기기는 확인하지 않았다.

## 배경

- 하단 탭(피드·사진함·번치·MY)을 오갈 때 화면이 툭 바뀌어 자연스럽지 않다는 의견이 나왔다.
- 사진함과 번치 탭의 헤더는 왼쪽 번치 전환(대표 이미지·이름·화살표)이 같고, 오른쪽 버튼과 뒤 배경만 다르다. 같은 부분은 그대로 보이고 다른 부분만 바뀌는 느낌을 원했다.
- 같은 방식의 WebView 앱에서 탭 사이에 80ms 정도의 동시 크로스페이드를 써서 이런 느낌을 낸 사례를 확인했다. 탭 막대는 전환 밖에 두어 고정하고, 헤더는 탭마다 화면 안에 그대로 둔 구조였다.
- iOS 쉘은 시스템 탭 바와 탭마다 WebView를 쓴다([012](./012-ios-system-tab-bar.md)). 웹에서 넣는 페이지 전환은 iOS 앱의 탭 전환에 적용되지 않아, 쉘에서 따로 넣어야 한다.

## 결정

- 웹 탭 막대를 쓰는 환경(브라우저·안드로이드)에서 네 탭 사이 이동에 크로스페이드를 넣는다.
  - 들어오는 화면은 아래에 처음부터 불투명하게 두고, 위에 올린 나가는 화면만 불투명도 1→0으로 바꾼다. 위치 이동은 넣지 않는다.
  - 두 화면을 함께 페이드하면 같은 자리의 같은 요소(예: 사진함·번치 헤더 왼쪽의 번치 전환)가 중간에 원래 색의 약 75%로 흐려져 깜빡여 보인다. 위 화면만 바꾸면 매 순간 「나가는 화면 × (1 − t) + 들어오는 화면 × t」라 같은 부분은 그대로 보인다.
  - 시간은 80ms, 곡선은 등속이다(디자이너 확정, 2026-11-01).
  - 탭 막대는 `(main)` layout에 있어 전환 대상 밖이라 그대로 남는다.
  - 상단 상태 바·하단 Safe Area 배경은 `AppFrame`이 칠한다(번치 탭은 연보라). 나가는 탭에 `data-page-leaving`을 붙여 `AppFrame`이 그 탭의 배경 표식을 무시하게 하고, 웹 탭 막대가 있는 화면에서는 배경색을 같은 80ms 등속으로 바꾼다. 다른 등록 전환(예: 번치 추가 디졸브)도 같은 표식으로 150ms ease-out에 바뀐다(#165에서 확장). 참여 모션 → 초대 확인은 앞 화면 장식이 Safe Area를 덮고 있어 `data-app-background-instant`로 바로 바뀐다. 이렇게 하지 않으면 나가는 탭이 사라진 뒤 상태 바 영역만 툭 바뀐다. iOS 앱은 탭마다 WebView가 상태 바 영역까지 그려 화면과 함께 페이드된다.
  - 헤더는 탭마다 화면 안에 둔다. 공통 헤더로 올리지 않는다.
  - 동작 줄이기 설정에서는 전환 없이 바뀐다.
- iOS 앱도 같은 방식(아래 화면은 불투명, 위 화면만 80ms 등속 1→0)으로 전환한다. 웹과 앱의 탭 전환 느낌을 맞추기 위해서다.
  - expo-router 네이티브 탭과 react-native-screens 4.26.2는 전환 애니메이션 설정을 열어 주지 않는다. 그래서 로컬 Expo 모듈이 탭 컨트롤러(`RNSTabBarController`)에 UIKit의 전환 애니메이션 delegate 메서드를 런타임으로 추가한다.
  - 탭에서 떨어졌다 다시 붙은 WebView는 잠깐 빈 화면이다. 그대로 페이드하면 흰 화면을 거쳐 새 탭이 나타나므로, 들어오는 탭 페이지가 프레임을 그린 뒤(최대 150ms) 페이드를 시작한다.
  - 동작 줄이기 설정에서는 시스템 기본(즉시 전환)이다.
  - 탭을 누를 때마다(지금 탭을 다시 눌러도) 선택 햅틱을 준다(2026-11-01 요청). iOS는 쉘 모듈, 안드로이드는 웹 탭 막대가 bridge `tabSelectionHaptic`으로 요청한다. 코드로 탭이 바뀔 때는 울리지 않는다.

## 검토한 대안

- **즉시 전환 유지**: 가장 단순하고 iOS 기본과 같지만, 웹에서 탭을 오갈 때 화면이 끊겨 보인다는 의견에 답하지 못한다.
- **탭 공통 헤더(헤더를 `(main)` layout으로 올리고 오른쪽 버튼·배경만 전환)**: 공통 부분이 정확히 이어지지만, 사진함 「선택」처럼 화면 상태에 따라 바뀌는 버튼을 layout으로 넘기는 연결이 필요하다. iOS 앱에서는 탭마다 WebView가 따로라 효과가 없다.
- **두 화면을 함께 페이드(동시 크로스페이드)**: 구현은 가장 단순하지만 같은 요소가 중간에 흐려진다.
- **SSGOI 기본 `fade`(순차)**: 나가는 화면이 사라진 뒤 들어오는 화면이 나타나 그 사이 빈 순간이 생긴다. 탭처럼 자주 오가는 이동에는 동시 크로스페이드가 낫다.
- **iOS 앱도 같은 전환을 위해 WebView 하나와 웹 탭 막대로 되돌리기**: 웹 전환이 앱에도 그대로 적용되지만 [012](./012-ios-system-tab-bar.md)의 시스템 탭 바(Liquid Glass·끌기·접근성)를 잃는다.
- **iOS 앱은 시스템 기본(즉시 전환) 유지**: 네이티브 코드가 없지만 웹과 앱의 탭 전환 느낌이 달라진다.
- **react-native-screens에 patch로 delegate 메서드 추가**: 같은 효과지만 pnpm patch를 의존성 버전마다 다시 맞춰야 한다. 런타임 추가는 라이브러리가 같은 메서드를 직접 구현하면 그쪽을 따르고 손대지 않는다.

## 영향

- 탭 page는 `MainTabPage`(불투명 배경 + `data-ssgoi-transition`)로 감싸고, `AppTransitions.tsx`가 네 탭 사이 모든 이동에 `defineTransition`으로 만든 크로스페이드를 등록한다. SSGOI가 나가는 화면을 `position: absolute`로 겹치므로 나가는 화면은 z-index 2, 들어오는 화면은 z-index 1로 둔다.
- SSGOI 7.4.1의 `LinearIntegrator`는 이름과 달리 남은 거리에 비례해 움직여(지수 감속) 80ms를 주면 300ms 넘게 끌린다. 그래서 등속 integrator를 직접 둔다. 라이브러리를 올릴 때 다시 확인한다.
- 탭은 하루에도 여러 번 오가는 요소라 [motion.md](../../architecture/motion.md)의 빈도 기준상 모션을 최소화한다. 80ms 투명도 전환만 쓰는 것은 그 기준 안에서 고른 값이다.
- iOS 쉘은 라이브러리 내부 클래스 이름(`RNSTabBarController`)과 그 클래스가 자기 자신을 delegate로 두는 구조에 기댄다. 바뀌면 추가가 조용히 빠져 즉시 전환으로 돌아가므로, react-native-screens를 올릴 때 다시 확인한다.
- 쉘 모듈을 바꾸면 `pod install`과 개발 앱·EAS 빌드를 다시 만들어야 한다.

## 검증 / 후속 작업

- 확인함(개발 서버 Chromium, 사진함→번치·번치→사진함): 나가는 화면 불투명도 0.79 → 0.58 → 0.37 → 0.16 → 0으로 약 80ms 등속, 들어오는 화면은 내내 1, 탭 막대 유지.
- 확인함(안드로이드 에뮬레이터 Pixel_8): 빌드·설치, `adb` 탭으로 이동·재선택 때 시스템 햅틱 호출 2회(`performHapticFeedback`, TICK). 화면 녹화는 프레임이 성겨 상태 바 영역 동기화는 Chromium 측정으로 판정했다.
- 확인함(Chromium): 나가는 탭은 페이드가 시작될 때 `inert`가 된다. 80ms 안에 사진함→번치→사진함으로 연속 탭해도 남은 투명도·`data-page-leaving`이 없다.
- 확인하지 않음: 실기기 크로스페이드·진동, 탭별 스크롤 위치 유지, 동작 줄이기 설정의 실제 렌더.
- iOS 쉘(시뮬레이터 iPhone 17 Pro, iOS 26.5, 사진함↔번치를 lldb로 `selectedIndex` 변경, 화면 녹화의 본문 밝기로 판정):
  - 애니메이터 없는 기본 전환도 다시 붙은 WebView 때문에 약 60ms 흰 화면이 생긴다.
  - 그린 뒤 페이드로 바꾼 뒤 다시 들어가는 전환 5회는 흰 구간 없이 약 80ms에 바뀌었다.
  - 앱 실행 후 그 탭에 처음 들어갈 때 1회는 약 0.35초 흰 화면이 남았다. 아직 한 번도 그리지 않은 WebView라 기다림 신호가 먼저 오는 것으로 보인다(미해결).
  - 확인하지 않음: 실제 손가락 탭(코드 변경으로 대신함), 햅틱(시뮬레이터는 진동 없음, 실기기 필요), 실기기, 동작 줄이기 설정.

## 재검토 조건

- 디자이너가 탭 전환 값이나 방식을 따로 정하면 그 값으로 바꾼다.
- expo-router 네이티브 탭이 전환 애니메이션 설정을 공식으로 열어 주면 쉘 모듈을 지우고 그 설정으로 옮긴다.
- 탭 page가 무거워져 전환 중 끊김이 생기면 전환을 끄거나 시간을 줄인다.

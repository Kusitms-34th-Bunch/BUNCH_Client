# 015: 사진 상세의 스와이프·확대는 Swiper(Zoom·Keyboard·A11y 모듈)로 처리한다

- 상태: accepted
- 구현 상태(2026-10-31 확인): 구현됨(`features/photo-box/components/PhotoDetailScreen.tsx`). headless Chrome에서 마우스 드래그·더블클릭 확대를 확인했고 iOS·안드로이드 쉘 실기기는 미확인.

## 배경

사진 상세(`/photos/[photoId]`)는 사진함 순서대로 좌우로 이전·다음 사진을 넘기고(처음·끝에서 멈춤), 확대하면 헤더와 올린 멤버 배지를 숨기며, 숨긴 상태를 넘겨도 유지해야 한다(기능 spec 3.5, Figma 화면 설계서 상세 2번·2-1). 핵심 난점은 **확대한 상태의 스와이프와 이동이 서로 충돌하는 것**이다. 확대 중에는 슬라이드가 넘어가지 않고 사진 가장자리 안에서만 움직여야 한다. 저장소에는 제스처 라이브러리가 없었다(`lottie-react`만 있음).

## 결정

`swiper`(14.3.0)를 `apps/web`의 `dependencies`에 추가하고 `Zoom`(핀치·더블탭·이동·경계), `Keyboard`(좌우 방향키), `A11y`(슬라이드 안내) 모듈만 쓴다. 페이지 순서와 렌더 범위(현재 사진 앞뒤 한 장)는 우리가 정하고, 라이브러리는 제스처와 확대 상태 전이만 맡는다.

- 스와이프, 핀치, 더블탭 확대, 확대 중 슬라이드 잠금과 경계 안 이동이 한 라이브러리의 한 동작으로 이어진다. 접합부 버그를 우리가 책임지지 않는다.
- 처음·끝에서 멈추도록 `resistance={false}`를 준다.
- 스와이프만으로는 단일 포인터·키보드 사용자가 사진을 넘길 수 없어서(WCAG 2.5.1), 포커스가 있을 때만 보이는 「이전 사진」·「다음 사진」 버튼과 방향키를 함께 둔다.
- 헤더·배지를 숨기는 상태(탭 숨김, 확대 숨김)는 Swiper 바깥(React state)에서 관리해 사진을 넘겨도 유지한다.

## 검토한 대안

- **`embla-carousel-react`(8.6.0) + `react-zoom-pan-pinch`(4.2.0)**: embla는 작고 좋은 캐러셀이지만 확대·이동·더블탭은 별도 라이브러리다. 확대 중 `watchDrag`를 끄는 연결을 직접 만들어야 하고 라이브러리 두 개를 접합부까지 책임진다.
- **`embla` + `@use-gesture/react`(10.3.1)**: 가장 작지만 핀치만 제공하고 이동·경계·더블탭·충돌 처리는 직접 구현한다. 분량과 위험이 크다.
- **직접 구현(pointer 이벤트)**: 의존성이 없고 `web-interface-guidelines.md`의 「Drag와 제스처」와 가장 맞지만, 핀치·관성·경계·슬라이드 전환을 모두 만들어야 한다.

## 영향

- 번들: `swiper`는 `swiper/react`와 필요한 모듈만 가져오며 사진 상세 route 번들에만 들어간다. 정확한 증가량은 측정하지 않았다.
- 스타일: `swiper/css`, `swiper/css/zoom` 두 파일을 상세 화면 컴포넌트가 가져온다(Next가 해당 route에만 포함).
- 제약: Swiper는 터치 이벤트 기반이라 가이드의 「pointer 이벤트 통일」과 다르다. 라이브러리 내부 사항이고 WebView 사용 사례가 많아 허용했다.
- 제약: 사진 한 장당 Swiper 슬라이드를 만들되 현재 사진 앞뒤 한 장만 이미지를 그린다. 수백 장에서의 성능은 실기기 확인 전이다.

## 검증 / 후속 작업

1. 구현에서 확인함: headless Chrome에서 마우스 드래그로 다음·이전 이동, 처음에서 멈춤, 더블클릭 3배 확대와 헤더·배지 숨김, 숨긴 채 넘기기.
2. iOS WebView에서 핀치 확대, 가장자리 스와이프(iOS 뒤로가기 제스처와 충돌 여부), 확대 중 이동을 실기기로 확인한다.
3. 실기기에서 프레임이 떨어지면 슬라이드 렌더 범위를 줄이거나 라이브러리를 교체한다(상세 화면 컴포넌트 한 곳에 모아 두었다).
4. 앱의 실제 번들 증가량을 측정한다.

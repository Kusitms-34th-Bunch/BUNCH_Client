# 024: 실시간(STOMP) 인증은 BFF가 발급받은 연결용 토큰을 브라우저에 한 번 전달한다

- 상태: accepted
- 날짜: 2026-11-15
- 구현 상태: 구현됨(#358). 개발 서버에서 `ws-token` 응답 모양과 만료(약 60초)는 확인했고, `/ws` CONNECT와 Origin 검사도 Node 클라이언트로 확인했고, 웹 도메인 Origin 등록과 브라우저 연결은 아직 확인하지 못함

## 배경

번들 공동 편집은 백엔드 `/ws`에 네이티브 WebSocket과 STOMP로 연결한다(v5 명세). 서버는 연결 직후 **STOMP CONNECT frame의 `Authorization: Bearer <토큰>` 헤더**로만 인증하고, 주소에 query string이 있으면 연결을 거절한다(HTTP handshake 헤더로 대신할 수 없음).

이 앱은 access·refresh 토큰을 httpOnly 쿠키에만 두고 브라우저 JS는 읽지 않는다(`docs/architecture/api-boundary.md`). 그래서 브라우저가 CONNECT 헤더를 직접 만들 수 없다. 웹은 Vercel 서버리스에 올라가 WebSocket을 중계할 수도 없다(연결을 오래 유지하는 서버가 없음).

백엔드가 `POST /api/v1/auth/ws-token`을 제공한다. 응답은 `{ token, expiresAt }`이고, 일회용이 아니라 만료 시각 안에 연결하면 세션이 유지된다.

## 결정

- BFF에 전용 Route Handler `POST /api/auth/ws-token`을 둔다. access 쿠키로 백엔드 `ws-token`을 불러 `{ token, expiresAt }`를 성공 응답에 `Cache-Control: no-store`를 붙여 돌려준다.
- 브라우저는 **연결(재연결)할 때마다 직전에** 이 토큰을 받아 CONNECT 헤더에만 싣는다. 저장소(localStorage·쿠키·query cache)에 두지 않는다. 연결하는 동안 STOMP Client 설정에 메모리로만 남는다. 연결된 동안에는 갱신하지 않는다.
- 브라우저가 백엔드 `wss`에 직접 연결한다(`NEXT_PUBLIC_WS_URL`). `wss:`만 허용하고 `ws:`는 localhost·127.0.0.1에만 허용하며 query·hash가 있으면 쓰지 않는다. 백엔드는 접속 Origin을 허용 목록으로 검사하므로 웹 도메인과 로컬 주소가 등록돼 있어야 한다. `NEXT_PUBLIC_*`는 빌드에 박히므로 값이 바뀌면 다시 배포한다.
- 토큰 발급이 401·403이면 세션이 끝난 것이므로 재연결을 멈추고 「재시도」로만 다시 시도한다. 연결이 붙자마자 끊기는 경우를 위해 10초 이상 이어져야 재연결 대기를 처음으로 되돌리고, CONNECTED가 10초 안에 오지 않으면 실패로 본다.
- heart-beat는 쓰지 않고(`0,0`), 자동 재연결 대신 연결마다 토큰을 새로 받아 새 연결을 맺는다. 끊긴 사이의 이벤트는 재생되지 않으므로 다시 연결되면 최신 상세를 다시 받는다.
- 연결을 닫을 때는 서버의 RECEIPT를 기다리지 않고 바로 닫는다(`deactivate({ force: true })`, 연결 시간 초과도 `discardWebsocketOnCommFailure`). 개발 서버가 RECEIPT를 보내지 않아 기다리면 소켓이 남을 수 있다. 화면을 나갈 때 보내는 LEAVE는 닫기 전에 나간다.
- 재연결 대기(1·2·4·8·15초)는 ±20% 흔들어 서버 재시작 뒤 한꺼번에 몰리지 않게 한다. 화면이 숨겨진 동안 끊기면 다시 붙지 않고 보일 때 한 번 연결한다. 네트워크가 돌아오거나(`online`) 화면이 다시 보이면 대기를 기다리지 않는다. heart-beat가 없어 죽은 연결을 모르므로 30초 넘게 숨겨졌다 돌아오면 「연결됨」을 유지한 채 새 연결로 갈아 끼우고 상세를 편집을 막지 않고 다시 받는다(#542). 갈아 끼우는 동안은 presence를 보내지 못해 다른 멤버 화면의 복귀 표시가 다음 VIEW 주기(최대 5초)까지 늦을 수 있다.
- 가짜 서버(MSW) 모드에서는 연결하지 않는다.

## 대안

- **access 토큰을 브라우저에 내려 CONNECT에 쓰기**: 가장 단순하지만 장기 토큰이 JS에 노출돼 httpOnly 원칙을 깬다. 쓰지 않는다.
- **STOMP 프레임을 읽어 헤더를 넣어 주는 상시 WebSocket 프록시**: 서버리스에서는 불가능하고 별도 서버 운영이 필요하다.
- **백엔드 일회용 티켓**: 가장 안전하지만 백엔드 협의가 더 필요했다. 백엔드가 제공한 `ws-token`이 짧은 만료의 연결용 토큰이라 이 방식으로 갈음한다.

## 결과와 위험

- JS가 연결용 토큰을 잠깐 볼 수 있다. 토큰은 만료가 짧고 연결에만 쓰이며 로그·저장으로 남기지 않는 것으로 위험을 줄인다. XSS가 있으면 이 토큰도 탈취될 수 있다. 현재 앱에는 CSP가 없어 이 위험을 막아 주는 장치가 없으므로 후속 보안 과제로 남긴다. stompjs `debug` 로그는 CONNECT frame을 남기므로 켜지 않는다.
- 개발 서버 확인(2026-11-15): 응답은 `{ token, expiresAt }`이고 만료는 발급 후 약 60초다. 그래서 연결 직전에 받아 바로 쓴다. `ws-token`으로 `/ws`에 CONNECT하면 `CONNECTED`(STOMP 1.2, heart-beat 0,0)가 온다. 연결은 만료(60초)가 지난 75초 뒤에도 열려 있었다(서버가 RECEIPT를 보내지 않아 그 뒤 구독이 유효한지는 확인하지 못함). 재연결 때 새 토큰이 필요한지는 확인하지 못했다.
- Origin 검사(개발 서버): `http://localhost:3000`은 허용, 허용되지 않은 Origin(`https://evil.example.com`)과 `https://app.bunch.kr`은 소켓이 거절(1006), Origin 헤더가 없으면 허용. 배포 웹 도메인을 서버 허용 목록에 등록해야 한다.
- 브라우저가 백엔드에 직접 연결하므로 Origin 허용 목록 설정이 필요하다. Origin 검사는 브라우저가 아닌 클라이언트를 막지 못하므로 인증은 토큰이 담당한다.
- 서버가 destination 구독 권한(참여 멤버만)을 검사하는지는 확인하지 못했다.

## 다시 검토할 조건

- 백엔드가 일회용 티켓이나 쿠키 기반 WebSocket 인증을 제공하면 바꾼다.
- 웹을 상시 실행 서버로 옮기면 서버 쪽 프록시를 다시 검토한다.

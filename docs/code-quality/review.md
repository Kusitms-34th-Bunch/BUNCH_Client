# Review

## 변경 전 판단

- 현재 코드, 타입, 테스트, 관련 문서를 확인한 뒤 구현한다. 근거 없는 추측을 기존 계약처럼 다루지 않는다.
- 요청을 확인 가능한 성공 기준으로 바꾼다. 예: 특정 상태에서 보일 UI, 호출될 API, 유지될 public API를 정한다.
- 모호함이 설계나 사용자 동작을 크게 바꾸면, 가능한 해석과 각각의 영향을 먼저 드러내고 확인한다. 그렇지 않으면 가장 작은 합리적 가정으로 진행하고 변경 범위를 넓히지 않는다.

## 변경 범위와 단순성

- 요청을 해결하는 데 필요한 파일과 줄만 수정한다. 관련 없는 refactor와 metadata churn은 섞지 않는다.
- 이번 변경으로 생긴 미사용 import, 변수, 코드만 정리한다. 기존의 관련 없는 dead code는 별도 작업으로 남긴다.
- 추상화는 호출부를 더 단순하게 만들 때만 추가한다. 미래 사용처만을 위한 레이어, 설정, 확장 지점은 만들지 않는다.
- 리팩터링은 어색해 보인다는 이유만으로 진행하지 않고, 안전성·가독성·변경 비용 중 구체적인 이득을 확인한 뒤 진행한다.

## 사용자와 계약 확인

- UI는 loading, empty, error, disabled, invalid 같은 관찰 가능한 상태를 의도적으로 다룬다.
- 조작 요소의 의미, 키보드 접근, focus 흐름, 오류 안내가 깨지지 않는지 확인한다.
- API 입력·출력, route, package public API, workspace boundary에 영향을 주면 호환성과 관련 문서를 함께 갱신한다.
- design-system public API와 app-local product wrapper 책임이 섞이지 않는지, 긴 텍스트·overflow·click target이 실제 상태에서 유지되는지 확인한다.

## Finding 기준

- Critical: 데이터 손실·보안 노출, 서비스 불가, 접근성 차단, 확실한 광범위 회귀, 빌드가 깨지는 문제
- Major: 일반 사용 흐름이 실패하는 실제 버그, 잘못된 cache·권한·계약, 회귀 가능성이 높은 경계·상태 처리 문제, 문서화된 소유 경계·import 방향·public API 규칙 위반
- Minor: 제한된 edge case, 유지보수 비용이 커질 수 있는 구조 문제, 주석 규칙·네이밍처럼 고치는 편이 낫지만 동작에 영향이 없는 규칙 위반
- Suggestion: 현재 작업을 막지는 않는 개선 제안

모든 리뷰(`review-changes`, `review-code-quality`, 전용 reviewer role)는 이 기준을 심각도의 정본으로 쓴다.

발견 사항에는 파일 근거와 사용자·코드 계약에 미치는 영향을 남긴다. 실행한 검증은 결과와 함께 보고하고, 실행하지 못한 검증은 이유와 남은 위험을 구분해서 보고한다.

문제가 없을 때도 검토하지 못한 runtime state, 외부 API, browser 조건이 있다면 residual risk로 남긴다. lint·typecheck·build 결과는 이 문서의 구조 리뷰를 대체하지 않는다.

## 커밋·PR 준비에서 결과 전달

메인 세션은 커밋 계획이나 PR 초안에 앞서 리뷰 결과를 사용자에게 보여 준다. finding 개수만 보고하지 않고 아래 항목을 포함한다.

- 검토 범위와 reviewer 역할, 새 리뷰인지 이전 결과 재사용인지
- Critical·Major·Minor 개수와 각 지적의 위치·문제·영향·최소 수정 방향
- 이전 지적의 수정 여부와 남겨 둔 이유
- 코드 검토로 확인한 근거와 실행 검증으로 확인한 근거, 미검증 공백

리뷰어는 실행하지 않은 테스트를 통과로 쓰지 않는다. 메인 세션은 실행 검증마다 명령·결과·실행 시점의 코드 상태를 적는다. 이전 결과는 현재 변경에도 유효한 경우에만 재사용하고 그 범위를 밝힌다. 검증 실행과 독립 확인은 `docs/workflows/verification.md`와 `verify-changes`를 따른다. 리뷰 지적이 없다는 사실은 기능 검증 통과를 뜻하지 않는다.

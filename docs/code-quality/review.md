# Review

## 변경 전 판단

- 현재 코드, 타입, 테스트, 관련 문서를 확인한 뒤 구현한다. 근거 없는 추측을 기존 계약처럼 다루지 않는다.
- 요청을 확인 가능한 성공 기준으로 바꾼다. 예: 특정 상태에서 보일 UI, 호출될 API, 유지될 public API를 정한다.
- 모호함이 설계나 사용자 동작을 크게 바꾸면, 가능한 해석과 각각의 영향을 먼저 드러내고 확인한다. 그렇지 않으면 가장 작은 합리적 가정으로 진행하고 변경 범위를 넓히지 않는다.

## 변경 범위와 단순성

- 요청을 해결하는 데 필요한 파일과 줄만 수정한다. 관련 없는 refactor와 metadata churn은 섞지 않는다.
- 이번 변경으로 생긴 미사용 import, 변수, 코드만 정리한다. 기존의 관련 없는 dead code는 별도 작업으로 남긴다.
- 추상화는 호출부를 더 단순하게 만들 때만 추가한다. 미래 사용처만을 위한 레이어, 설정, 확장 지점은 만들지 않는다.
- 리팩터링은 어색해 보인다는 이유만으로 진행하지 않고, 안전성·가독성·변경 비용 중 구체적인 이득을 확인한 뒤 진행한다.

## 사용자와 계약 확인

- UI는 loading, empty, error, disabled, invalid 같은 관찰 가능한 상태를 의도적으로 다룬다.
- 조작 요소의 의미, 키보드 접근, focus 흐름, 오류 안내가 깨지지 않는지 확인한다.
- API 입력·출력, route, package public API, workspace boundary에 영향을 주면 호환성과 관련 문서를 함께 갱신한다.
- design-system public API와 app-local product wrapper 책임이 섞이지 않는지, 긴 텍스트·overflow·click target이 실제 상태에서 유지되는지 확인한다.

## 반복해서 나온 결함 패턴

리뷰(`review-changes`, `review-pr`, 전용 reviewer role)는 아래 패턴을 변경 유형에 맞게 확인한다. 실제 PR 리뷰에서 반복해서 지적된 항목이다. 구현하는 쪽도 리뷰를 맡기기 전에 같은 목록으로 먼저 확인한다.

### 렌더링과 상태

- 서버 렌더와 첫 hydration이 같은 글자를 그리는지 본다. 지금 시각(`Date.now`), 시간대·`toLocale*`, 난수, 브라우저 저장소를 렌더에서 읽으면 서버와 브라우저 결과가 달라진다. 브라우저에서만 계산하거나(서버 snapshot이 `null`인 `useSyncExternalStore`) 고정 값을 쓴다.
- 렌더 중에 모듈 변수·저장소를 바꾸지 않는다. `useState` 초기화 함수에서 플래그를 읽고 지우면 버려지는 렌더에서 값이 사라진다. 읽기는 렌더에서, 지우기는 effect에서 한다.
- 모듈 변수에 둔 상태는 수명과 테스트 격리를 본다. 다른 경로로 화면을 떠나도 값이 남는지, 테스트마다 초기화되는지 확인한다.
- 비동기 값은 「아직 모름」·「없음」·「실패」를 구분한다. 응답 전 자리 표시가 실패 뒤에도 계속 남지 않는지 본다.
- 응답이 와서 요소가 새로 생길 때 이미 보이는 버튼이 밀리지 않는지 본다. 누르려던 자리에 다른 링크가 들어오면 잘못 이동한다.
- 목록·내용이 바뀔 때 이전 상태(펼침, 현재 순번 등)가 다음 항목으로 새지 않는지 본다. A→B→A처럼 돌아오는 경우도 본다.
- 글꼴 로딩·크기 변화로 측정값(넘침, 높이)이 바뀌면 다시 재는지 본다.

### 비동기 처리와 서버 상태

- 서버 처리가 끝난 시점과 바뀐 화면이 그려지는 시점은 다르다. mutation 결과가 query 갱신보다 먼저 올 수 있다. 사라진 요소 대신 초점을 옮길 때는 바뀐 렌더 뒤(effect)에서 옮기고, 결과 토스트는 초점 이동 뒤에 띄운다.
- 확정하면 창을 닫는 시트·대화상자는 창이 다 닫힌 뒤 처리를 시작한다. 실패하면 시트를 유지하는 흐름(사진함 여러 장 처리 등)은 제외한다. 닫힘 중에 화면이 바뀌거나 안내가 뜨면 초점 복원과 낭독이 꼬인다.
- 진행 중 표시(ref·플래그)는 요청마다 구분하고, 성공·실패·변화 없음 모든 경로에서 끈다. 남은 플래그는 나중의 관계없는 변화에 반응한다.
- 처리 중 다시 누르기는 ref로 막는다. `isPending`은 다음 렌더부터 반영된다. 처리 중임을 화면과 상태 영역으로도 알린다.
- 본 요청과 부작용의 순서를 본다. 부작용(예: 차단 뒤 팔로우 해제)은 본 요청이 성공한 뒤에 하고, 본 요청이 실패하면 부작용이 남지 않게 한다.
- 명세에 없는 상태 코드를 특정 의미로 해석하지 않는다. 해석해야 하면 `ponytail:` 주석과 `docs/workflows/mock-server-status.md`에 가정을 남기고, 다른 이유일 수 있으니 다시 시도 경로를 둔다.

### 모션

- 화면 밖에서 재생이 끝나지 않는지 본다. 목록 아래에 있는 모션은 처음 보일 때 시작한다.
- Figma 프로토타입의 반복 재생은 미리보기일 수 있다. 제품에서 반복할지 한 번만 재생할지는 spec에 적는다.
- 동작 줄이기(`prefers-reduced-motion`)에서는 모션 없이 최종 상태가 보이는지 본다. 첫 프레임이 비어 있는 등장 모션은 마지막 장면을 보여야 한다.
- 상태가 나중에 바뀌어 요소가 다시 그려질 때(낙관적 업데이트의 롤백 등) 모션이 다시 재생되지 않는지 본다.

### 컴포넌트 계약

- `...props`를 어느 요소에 펼치는지 본다. 분기마다 공통 속성이 버려지거나, 다른 요소 전용 속성이 퍼지지 않는지 확인한다.
- 고정 속성과 `...props`의 순서를 본다. 덮어쓸 수 있으면 안 되는 속성(`role`, `aria-pressed` 등)이 호출자 값에 지워지지 않는지, 반대로 의도한 덮어쓰기가 순서에 기대는지 확인한다.
- 판별 유니온 props에서 한쪽 상태에만 쓰는 값이 다른 상태의 DOM으로 새지 않는지 본다.
- 아직 없는 화면(route)으로 이동하는 링크·버튼이 있는지 본다. 있으면 PR 설명과 spec에 머지 순서나 후속 이슈가 적혀 있어야 한다.
- 훅·상태를 쓰는 디자인 시스템 컴포넌트에 `'use client'`가 있는지 본다.

### 접근성

- live region은 처음부터 DOM에 두고 내용만 바꾼다. 내용과 함께 새로 끼워 넣은 `role="status"`는 일부 스크린 리더가 읽지 않는다.
- 초점을 가진 요소가 사라지는 동작(숨기기, 삭제, 화면 전환)에서 초점이 어디로 가는지 본다.
- 크기·간격·색 대비는 토큰 이름이 아니라 `tokens.css`의 실제 값으로 계산한다. 기준에 못 미치면 Figma 값과 같아도 접근성 지적으로 보고한다. 코드에서 색을 임의로 바꾸지 않고 디자인 협의 대상으로 표시하며, 출시 전 해결 여부를 확인한다.
- 같은 글자의 버튼이 목록에 반복되면(「콕하기」 등) 무엇에 대한 버튼인지 구분할 방법이 있는지 본다.

### 테스트와 문서

- 테스트가 동작을 증명하는지 본다. 검증 대상 코드를 지워도 통과하는 단언(빈 배열에서 버튼만 없는지 확인 등)은 보강한다.
- 사용자가 바꿀 수 있는 값(커스텀 글자, 다른 형태의 prop)이 실제로 반영되는지 확인하는 테스트가 있는지 본다.
- spec의 체크(`- [x]`)가 구현과 테스트로 확인된 항목만인지 본다. 코드가 지원해도 테스트하지 않은 분기는 체크하지 않는다.
- 「임시」·「예정」 같은 주석과 문서 문장이 이번 변경 뒤에도 맞는지 본다.

## Finding 기준

- Critical: 데이터 손실·보안 노출, 서비스 불가, 접근성 차단, 확실한 광범위 회귀, 빌드가 깨지는 문제
- Major: 일반 사용 흐름이 실패하는 실제 버그, 잘못된 cache·권한·계약, 회귀 가능성이 높은 경계·상태 처리 문제, 문서화된 소유 경계·import 방향·public API 규칙 위반
- Minor: 제한된 edge case, 유지보수 비용이 커질 수 있는 구조 문제, 주석 규칙·네이밍처럼 고치는 편이 낫지만 동작에 영향이 없는 규칙 위반
- Suggestion: 현재 작업을 막지는 않는 개선 제안

모든 리뷰(`review-changes`, `review-code-quality`, 전용 reviewer role)는 이 기준을 심각도의 정본으로 쓴다.

발견 사항에는 파일 근거와 사용자·코드 계약에 미치는 영향을 남긴다. 실행한 검증은 결과와 함께 보고하고, 실행하지 못한 검증은 이유와 남은 위험을 구분해서 보고한다.

문제가 없을 때도 검토하지 못한 runtime state, 외부 API, browser 조건이 있다면 residual risk로 남긴다. lint·typecheck·build 결과는 이 문서의 구조 리뷰를 대체하지 않는다.

## 커밋·PR 준비에서 결과 전달

메인 세션은 커밋 계획이나 PR 초안에 앞서 리뷰 결과를 사용자에게 보여 준다. finding 개수만 보고하지 않고 아래 항목을 포함한다.

- 검토 범위와 reviewer 역할, 새 리뷰인지 이전 결과 재사용인지
- Critical·Major·Minor 개수와 각 지적의 위치·문제·영향·최소 수정 방향
- 이전 지적의 수정 여부와 남겨 둔 이유
- 코드 검토로 확인한 근거와 실행 검증으로 확인한 근거, 미검증 공백

리뷰어는 실행하지 않은 테스트를 통과로 쓰지 않는다. 메인 세션은 실행 검증마다 명령·결과·실행 시점의 코드 상태를 적는다. 이전 결과는 현재 변경에도 유효한 경우에만 재사용하고 그 범위를 밝힌다. 검증 실행과 독립 확인은 `docs/workflows/verification.md`와 `verify-changes`를 따른다. 리뷰 지적이 없다는 사실은 기능 검증 통과를 뜻하지 않는다.

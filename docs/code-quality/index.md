# Code Quality

코드 품질 문서는 구현을 읽고, 바꾸고, 검토하기 쉽게 만드는 기준이다. 특정 아키텍처나 라이브러리를 강제하기보다, 현재 코드와 변경 목적에 맞는 가장 단순한 선택을 돕는다.

- [Readability](./readability.md): 코드 흐름과 상태를 이해하기 쉽게 표현하는 기준
- [Contracts](./contracts.md): 함수·hook·component의 입력, 반환, 오류와 부수효과를 예측 가능하게 유지하는 기준
- [Maintainability](./maintainability.md): 책임, 재사용, 의존성, 공개 API를 유지하는 기준
- [Component Logic](./component-logic.md): 컴포넌트, 순수 함수, 단일 책임 hook, 화면 조합 hook의 경계를 정하는 기준
- [Review](./review.md): 변경 범위와 품질 검토를 판단하는 기준

이 문서는 lint, typecheck, test, build 같은 자동 검증을 대체하지 않는다. 검증 명령 선택은 `docs/workflows/verification.md`를 따른다.

## 네 가지 기준과 문서의 관계

코드 품질은 가독성, 예측 가능성, 응집도, 결합도 네 가지 기준으로 판단한다. 각 문서는 이 중 하나를 중심으로 다룬다.

- 가독성: [readability.md](./readability.md)
- 예측 가능성: [contracts.md](./contracts.md)
- 응집도(함께 바뀌는 코드를 가까이 두기): [maintainability.md](./maintainability.md)의 "책임과 배치"
- 결합도(변경 영향 범위 줄이기): [maintainability.md](./maintainability.md)의 "재사용과 의존성", [component-logic.md](./component-logic.md)의 "공용 Hook 승격"

네 기준은 동시에 완벽히 satisfy되지 않는다. 응집도를 높이려는 추상화가 가독성을 해칠 수 있고, 결합도를 낮추려는 중복 허용이 응집도를 낮출 수 있다. 기준이 서로 충돌하면 "지금 이 코드를 가장 변경하기 쉽게 만드는 선택이 무엇인가"를 기준으로 우선순위를 정한다.

## 적용 방식

1. 변경 전에 관련 코드, 타입, 테스트, 문서를 확인해 현재 계약과 경계를 파악한다.
2. 요청을 확인 가능한 결과로 바꾼다. 예: “목록을 고친다”보다 “loading, empty, error 상태에서 의도한 화면을 보인다”가 좋다.
3. 모호함이 구현 방향을 크게 바꾸면 확인한다. 그렇지 않으면 합리적인 가정을 변경 범위 안에 남기고 가장 작은 구현을 선택한다.
4. 기존 코드의 스타일, 이름, 배치를 우선 존중한다. 이번 변경 때문에 생긴 미사용 코드만 함께 정리한다.

## 판단 원칙

- 실제 요구사항, 기존 구현, 디자인·API 계약을 근거로 판단한다. 아직 도입하지 않은 패턴을 문서만으로 강제하지 않는다.
- 코드가 문제보다 커졌다면 한 단계 단순한 구현이 가능한지 다시 확인한다.
- 공통화, 전역 상태, 새 설정은 현재의 중복이나 복잡도를 실제로 줄일 때만 도입한다.
- 함수·hook·component의 이름과 반환 계약이 실제 부수효과·오류 처리와 어긋나지 않는지 확인한다.
- 비밀값, 토큰, 개인 정보와 같은 민감한 값은 코드·문서·로그에 남기지 않는다.

# 화면 안 모션 기록

사진함 업로드 상태 줄, 당겨서 새로고침, 헤더 숨김, Lottie처럼 화면 안 요소의 모션 결정과 확인 기록이다. 일반 규칙은 [motion.md](motion.md)를 따른다.

## 사진함 업로드 상태 줄

Figma `Upload Status 애니메이션 스펙`(`7724:48227`)이 정한 값이다(2026-11, 이슈 #511). 디자이너 값이라 "UI 애니메이션은 300ms를 넘지 않는다"보다 우선한다. 단계는 겹치지 않고 이어 재생한다.

- 진행 바: 앞으로만 간다. 사진마다 쉘에서 받을 때와 결과가 나올 때 반 칸씩, 900ms `0.4, 0, 0.2, 1`로 채운다. 너비 대신 막대를 `transform`으로 밀어 덜 찬 것으로 보인다. 스펙의 채움 전 대기 450ms는 프로토타입이 50%에서 시작하는 시연용이라 넣지 않는다.
- 문구 교체: 마지막 사진이 끝난 뒤 채움(900ms)과 250ms를 기다려, 기존 문구와 진행 바가 위로 10px 올라가며 흐려지고(320ms `0.4, 0, 1, 1`) 결과 문구가 아래 10px에서 올라오며 나타난다(420ms `0.2, 0, 0, 1`). 썸네일은 움직이지 않고 글자는 잘라내지 않는다.
- 접힘: 결과가 처음 화면에 보인 때부터 5초 유지 뒤(다른 탭에 있는 동안 끝나면 사진함 탭이 다시 보일 때부터 셈) 높이를 grid 행 1fr→0fr로, 투명도를 1→0으로 함께 줄인다(380ms `0.4, 0, 0.2, 1`). 아래 목록을 끌어올려야 해서 위 「성능」의 높이 예외를 쓴다. 나타날 때는 스펙에 모션이 없어 바로 자리를 잡는다.
- 구현: `PhotoUploadStatus`가 `lib/uploadStatus.ts`의 시간·곡선을 CSS 변수로 받아 transition delay로 단계를 잇는다. 접힘 시작은 결과가 처음 보인 시각 기준 타이머라 화면에 늦게 돌아와도 남은 시간만 기다린다(그때는 완료 상태부터 보이고 교체 모션은 다시 재생하지 않는다). 동작 줄이기에서는 이동·높이·진행 바 전환과 교체 대기를 빼고 투명도만 남기며, 접힐 때는 높이를 둔 채 흐려진 뒤 자리를 비운다. 완료 문구 중 새로 올리면 줄을 새로 그려 진행 바가 거꾸로 줄어들지 않는다.

## 당겨서 새로고침

Figma `6673:45282`(피드 · Refresh Motion)와 표시기 `6672:47286`이 정한 값이다(2026-11, 이슈 #340). 피드·번치 홈·사진함이 쓴다. 공통 모션처럼 디자이너 값이라 "UI 애니메이션은 300ms를 넘지 않는다"보다 우선한다.

- 동작: 맨 위(`scrollTop` 0)에서 아래로 당겼다 놓는다. 손가락 이동의 0.6배만큼 내용이 내려오고(최대 72px), 64px 이상 내려온 채 놓으면 새로고침을 시작해 64px에 머문다(Figma는 80px이나 로고 아래 간격이 넓어 보여 사용자 요청으로 줄임). 끝나면 0으로 닫힌다. 끝나도 최소 0.6초는 열려 있어 깜빡이지 않는다. 가로로 더 움직이거나 위로 밀거나 이미 스크롤된 상태는 당김으로 보지 않는다. 당긴 채로 손가락을 시작 자리보다 위로 올리면 내용이 로딩 영역 위로 올라와 헤더 밑으로 들어갈 수 있고(기본 스크롤은 막혀 있어 hook이 손가락만큼 직접 스크롤), 놓으면 최상단으로 돌아온다. 그 당김에서 기준 거리(64px)에 한 번이라도 닿았다면 헤더 밑으로 올렸다 놓아도 새로고침한다. 새로고침 중에는 목록을 평소처럼 스크롤할 수 있고, 스크롤로 내용이 표시기 자리를 덮는 만큼 표시기는 흐려져 카드 사이 틈으로 비치지 않는다. 끝나면 스크롤 위치와 무관하게 간격을 닫으면서 내용을 항상 최상단(스크롤 0, 간격 0)으로 올린다(동작 줄이기에서는 즉시).
- 모양: 내용(`main`의 직계 자식)이 `translate`로 내려오고, 36px Spark(4px 모듈 13개, gray-300)가 본문 위 20px(Figma는 30px)에서 20px 위에서 내려오며(0→1 투명도) 나타난다. 당기기 시작하면(새로고침 중에도 이어서) Spark가 2초 주기로 90°씩 세 번 끊어 돈다(사용자 요청, Figma는 표시기가 나타난 뒤 계속 도는 것으로 정의)(곡선 `0.45, 0, 0.2, 1`). Spark는 90° 회전 대칭이라 마지막 멈춤에서 처음으로 돌아가도 이음매가 보이지 않는다.
- 시간·곡선: 열릴 때 `0.33, 0, 0.15, 1`, 닫힐 때 `0.45, 0, 0.2, 1`, 각 600ms(3.5초 타임라인의 17.1%·91.4% 구간).
- 구현: `PageShell`의 `onRefresh`(Promise를 돌려주면 끝날 때까지 기다림)와 `refreshDisabled`. `usePullToRefresh`가 터치를 읽어 컨테이너의 CSS 변수 `--pull-y`·`--pull-p`를 직접 쓰므로 당기는 동안 React가 다시 그리지 않는다. 두 변수는 `globals.css`의 `@property`로 등록해 transition이 보간한다. 내용에는 당기는 동안에만 `translate`를 걸어 평소에는 fixed 자손의 기준 상자가 바뀌지 않는다. `transform`이 아니라 `translate`를 써서 화면을 떠날 때 스크롤을 옮겨 두는 `useHoldScrollOnLeave`의 `transform`과 겹치지 않는다. 표시기는 `RefreshSpark`(`shared/components/refresh/`).
- 제약: 당기는 동안과 새로고침 중(최소 0.6초 + 요청 + 닫힘 0.6초)에는 `main` 직계 자식에 `translate`가 걸려 그 자손의 `fixed`는 화면이 아니라 그 자식을 기준으로 놓인다. 이 세 화면의 `main` 안에는 `fixed`를 두지 않는다. 시스템 제스처 등으로 터치가 취소(`touchcancel`)되면 새로고침하지 않고 닫는다. Spark 회전은 새로고침이 끝날 때까지 반복한다(Figma는 한 주기 2초만 정의).
- 서버 상태(실패하면 `onRefresh`가 거부해 위 실패 안내가 나간다. 시각적인 실패 표시는 없고 화면 낭독 안내만 있다, 2026-11-16 확인): 피드·번치 홈은 `useRefreshActiveQueries`(지금 화면이 쓰는 query 전부 다시 받기)를, 사진함은 `usePhotoBox().refresh`(프로필·멤버·사진 목록)를 넘긴다. 실패해도 표시를 닫고, query 자체의 오류 표시는 각 query를 쓰는 화면이 맡는다.
- 접근성: 동작 줄이기에서는 열리고 닫히는 전환, 표시기의 이동·회전을 뺀다. 손가락을 따라 내용이 내려오는 것은 사용자가 직접 하는 조작이라 남기며(빼면 표시기가 내용과 겹친다), 표시기는 투명도로만 나타난다. 표시기는 장식이라 `aria-hidden`이고, 「새로고침하고 있어요」·「새로고침을 마쳤어요」는 `role="status"`로 알리고 3초 뒤 비운다. 요청이 하나라도 실패하면(`onRefresh`가 거부) 「새로고침하지 못했어요」를 알린다. 마우스·키보드에는 반응하지 않는다. 키보드·스크린 리더 사용자는 화면 진입·앱 복귀 때 다시 받을 수 있지만 query의 신선 시간 안에서는 다시 받지 않는다. 접근 가능한 새로고침 수단(예: 헤더 메뉴)은 후속 과제다(디자이너·기획 확인 필요).
- 확인한 범위: Chromium(Pixel 7 에뮬레이션, 터치 이벤트 주입)에서 세 화면의 당김·머묾·닫힘과 짧게 당겨 취소되는 것을 확인했고(거리를 80px로 둔 때의 측정이며, 64px로 줄인 뒤와 표시기를 내용 뒤로 옮긴 뒤는 단위 테스트만 돌리고 화면은 확인하지 못했다), 단위 테스트가 임계값·중복 방지·가로 제스처·비활성을 확인한다. 실기기(iOS WKWebView의 바운스, Android 뒤로 가기 제스처와의 충돌)와 동작 줄이기, 사진함의 사진 길게 눌러 선택과의 충돌은 확인하지 않았다.
- 범위 밖: 피드 맨 아래 「모든 피드를 확인했어요」의 체크 표시와 조각 모음은 같은 Figma 노드에 있지만 새로고침 표시기가 아니라 피드 끝 안내의 모션이라, 새로고침 표시기와 따로 `features/feed/components/FeedCaughtUp.tsx`가 로티로 재생한다(2026-11-16 확인).

## 스크롤로 헤더 숨김

피드 헤더(2026-11-15, #400): 아래로 스크롤하면 헤더가 위로 빠져 숨고, 위로 올리면 다시 나온다. Facebook 앱과 같은 방식(A안, 사용자 결정)이다.

- 동작: 헤더가 스크롤한 거리만큼 1:1로 따라 올라간다(손가락을 따라감). 다 숨은 헤더는 위로 60px 올린 뒤부터 올린 만큼 내려온다(Instagram처럼 조금 올렸다고 바로 나오지 않음, 사용자 요청). 그 사이 다시 내리면 처음부터 센다. 헤더 높이 안에서만 움직인다. 손가락을 놓고 스크롤이 멈추면(관성 포함, 120ms 동안 스크롤 이벤트가 없으면) 절반 넘게 숨은 헤더는 끝까지 넣고 덜 숨은 헤더는 꺼낸다. 손가락을 댄 채 멈춰 있는 동안은 정리하지 않는다. 다 숨길 때는 자기 높이보다 2px 더 올리고, 1px 이내로 남은 상태는 다 숨은 것으로 본다(iOS 스크롤 값이 소수라 헤더 아래 끝이 실처럼 남던 것을 막음). 맨 위에서는 스크롤한 거리보다 더 숨지 않아 위로 갈수록 헤더가 따라 나오고, 멈추면 다 보인다. 사용자가 손가락·휠·키보드·스크롤바로 스크롤을 시작하기 전의 이동(돌아올 때 스크롤 복원)에는 숨기지 않는다. 헤더 안에 초점이 있으면 숨기지 않는다.
- 모양: 헤더는 본문 위에 겹쳐 있고(불투명 흰 배경) 따라가는 동안에는 전환 없이 위치만 바꾸고, 멈춘 뒤 끝까지 넣거나 꺼낼 때만 200ms ease-out(진입·이탈)이다. 위치는 hook이 `style.transform`을 직접 바꿔 스크롤 중 React가 다시 그리지 않는다. 헤더의 흰 배경은 상태 표시줄 자리까지 덮고 헤더와 한 덩어리로 오르내린다. 그래서 헤더가 숨으면 본문이 상태 표시줄 뒤까지 올라가고, 내려오면 상태 표시줄 배경도 함께 내려온다(Facebook 앱과 같은 모습, 사용자 요청). 헤더가 숨은 동안 상태 표시줄 자리는 처음(2026-11-15)에는 아무것도 덮지 않았고, 지금은 아래 「상태 표시줄 흐림」대로 점진적으로 흐린다(#502). 상태 표시줄 글자가 검은색 고정이라 어두운 사진 위에서는 잘 안 보일 수 있다. 페이지 전환 틀(`AppTransitions`)은 평소 넘친 부분을 모두 자르지만, 접는 헤더 화면이 있으면 `clip-path: inset(-상태 표시줄 높이 0 0 0)`으로 위만 상태 표시줄 높이만큼 더 보이게 자른다. 처음에는 `overflow-x: clip` + `overflow-y: visible`로 좌우만 잘랐는데, WebKit이 이를 세로 ±2^24px의 클립 층으로 만들어 iOS에서 큰 좌표의 소수 정밀도 때문에 내용이 약 1pt 아래로 밀렸고, 화면 맨 위에 흰 선(뒤의 흰 바탕)이 남았다(2026-11-15, 시뮬레이터 뷰 계층과 화면 픽셀로 확인). 이 조합은 쓰지 않는다. 당겨서 새로고침 표시기는 헤더 높이만큼 내려 둔다.
- 화면 전환 중 상태 표시줄(#516, 2026-11-22 사용자 제보): 피드 → 알림 목록 drill에서 나가는 피드의 흰 헤더가 상태 표시줄 자리를 덮은 채 20%만 밀려, 전환 내내 흰색이 남았다가 끝나야 회색으로 바뀌었다(들어오는 화면은 상태 표시줄 아래부터 그림). 나가는 동안(`data-page-leaving`)에는 접는 헤더 화면의 상태 표시줄 자리를 `clip-path`로 잘라, 다른 화면처럼 `AppFrame`의 틀 색이 전환 시작과 함께 바뀐다. WebKit(Playwright, 상단 Safe Area 47px 흉내, 가짜 서버 개발 서버)에서 녹화 프레임으로 상태 표시줄 색이 헤더 자리와 같은 프레임에 바뀌기 시작하는 것을 확인했다(고치기 전에는 약 240ms 늦음). 실기기는 확인 전이다.
- 구현: `PageShell`의 `collapsibleHeader`와 `useHideOnScroll`(`shared/hooks/`). 헤더 높이는 화면을 그리기 전(`useLayoutEffect`)과 크기가 바뀔 때(`ResizeObserver`) 재서 `--page-header-height`로 넘긴다. 본문 위 여백·`scroll-padding-top`·표시기 위치는 상태 표시줄을 포함한 헤더 높이(`--page-top-inset`)를 쓰고, 재기 전(서버 렌더)에는 상태 표시줄 + 디자인 시스템 `Header` 높이 3rem을 써서 첫 화면이 밀리지 않는다.
- 접근성: 다 숨은 동안 헤더는 `inert`라 Tab 순서와 스크린 리더에서 빠진다(위로 스크롤하면 다시 보인다). 동작 줄이기에서는 멈춘 뒤의 정리 이동을 전환 없이 한다(손가락을 따라가는 것은 사용자가 직접 하는 조작이라 남김, 당겨서 새로고침과 같은 기준). 실기기 VoiceOver(세 손가락 스크롤 포함)는 확인하지 못했다.
- 헤더 자체를 흐린 유리로 할지(B안)는 디자이너 확인 뒤 정한다. 구조는 같고 헤더 배경만 바꾸면 된다.
- 상태 표시줄 흐림(#502, 2026-11-22 기획 결정): Instagram처럼 헤더가 숨은 동안 상태 표시줄 뒤로 지나가는 본문을 흐린다. 다이내믹 아일랜드 위쪽만이 아니라 상태 표시줄 전체에 위가 가장 진하고 아래로 갈수록 자연스럽고 부드럽게 사라지게 한다. 흐림 한 장을 투명도로만 옅게 하면 경계가 보이므로 세기가 다른 층(1·2·4·8px)을 겹치고, 층마다 아래로 사라지는 지점을 다르게 한 마스크를 씌운 점진적 흐림으로 한다. 흰색은 얹지 않는다(흰 띠처럼 보임). `PageShell`이 접는 헤더 화면에만 상태 표시줄 높이로 둔다. 헤더가 보일 때는 헤더의 흰 배경 위라 보이지 않는다. 실기기 확인 전이다.

## Lottie

디자이너가 Lottie 애니메이션을 전달할 예정이다(2026-10-14). 온보딩에 쓸 예정이고, 로그인 화면에 쓸지는 미정이다. 재생 라이브러리는 `lottie-react`(3.1.2, 2026-10-19 사용자 확인 후 `apps/web`에 추가)다. 아래는 도입 기준과 첫 도입(초대 링크 확인 화면의 초대장 로티)의 결과다. 초대장 연출은 2026-11 Figma 변경(`Seal & Flip`)으로 코드 모션으로 바뀌었고(아래 「온보딩 초대장·컨페티」), 로티는 로딩·편집 중·피드 끝 표시에 쓴다.

- 온보딩은 로그인 뒤에 나오므로, 첫 화면 로딩을 늦추지 않고 동적 import로 자산을 받을 수 있다. 온보딩 한 단계가 보이는 동안 다음 단계의 자산을 미리 받아 두면 전환할 때 끊기지 않는다(FE 판단). 로그인 화면에 쓰기로 정해지면 그 화면은 첫 렌더가 늦어질 수 있으니 다시 판단한다.
- 자산 형식(`.json` 또는 압축된 `.lottie`)과 재생 라이브러리는 디자이너의 자산을 받은 뒤 정한다. 다른 프로젝트에서는 `lottie-react`를 썼다. production dependency 추가는 사용자 확인을 받는다.
- 웹 앱의 로티 JSON은 `apps/web/src/shared/assets/lotties/`에서 관리한다. 재생 컴포넌트와 기능 로직은 사용하는 feature에 둔다. 앱 전용 자산을 디자인 시스템으로 옮기지 않는다.
- 재생 컴포넌트는 브라우저 API를 쓰므로 클라이언트 컴포넌트(`'use client'`)로 둔다. 서버 컴포넌트에서 직접 import하지 않는다.
- 자산이 50KB 이상이면 동적 import로 쓰는 시점에 받는다(제안). 정적 import하면 그 화면 번들에 JSON 전체가 들어간다. PR에는 자산 용량을 적는다.
- `prefers-reduced-motion: reduce`이면 자동 재생과 반복을 끄고 정지 프레임을 보여준다. 애니메이션을 유일한 정보 전달 수단으로 쓰지 않고, 같은 정보를 텍스트로도 준다.
- 장식용이면 `aria-hidden`을 주고, 의미가 있으면 텍스트 대체를 함께 준다.
- 컨테이너 크기를 고정해서, 자산을 받기 전후에 layout이 밀리지 않게 한다.
- 위 "애니메이션을 넣을지 판단" 표를 따른다. 자주 보는 요소에는 쓰지 않고 온보딩, 축하, 로딩 같은 드문 장면에 쓴다. "UI 애니메이션은 300ms를 넘지 않는다"는 전환에 대한 규칙이라 Lottie 연출 길이에는 적용하지 않지만, 재생 중에도 사용자의 interaction을 막지 않는다.
- 복잡한 애니메이션은 WebView에서 프레임이 떨어질 수 있다. 렌더러 선택과 프레임은 실기기에서 확인한다(FE 판단, 미검증).
- 테스트에서는 재생 라이브러리를 mock한다. 애니메이션의 모양은 테스트하지 않는다.
- 도입 결과 (2026-10-19): `lottie-react` 3.x는 엔진 세 빌드(full·svg·light)를 함께 내보내서 모듈 전체를 동적 `import()`하면 셋이 모두 내려받아진다(합계 약 180KB gzip). 표현식이 없는 로티는 light 빌드만 쓰도록 `export { LottieLight } from 'lottie-react'` 래퍼(`shared/lib/lottieLight.ts`)를 동적 import해서 엔진 하나(약 164KB)와 래퍼(약 47KB)만 내려받는다. 새 로티를 넣을 때 표현식이 있으면 `LottieSvg`로 바꾼다.
- 자산 위치 (확정): 로티 JSON은 `apps/web/src/shared/assets/lotties/`에 두고 재생 컴포넌트에서 동적 import한다. 초대장 로티(`inviteAnimation.json`)는 코드 모션으로 대체해 삭제했다(#292).
- 로딩 상태 (2026-11-09, 앞으로의 기준): 「편집 중」(Editing)이 아닌 로딩 표시는 모두 디자이너가 전달한 `loading.json`(90×90, 물결처럼 번지는 점 패턴, 표현식 없음)으로 처리한다. 덮개를 쓸 때는 사진별·요소별이 아니라 페이지 전체에 하며, 화면 전체를 `overlay-dim-subtle`로 덮고 가운데에 재생한다. 2026-11-20(디자이너 확인)부터 덮개는 필요할 때만 쓴다. 보여 줄 내용이 아직 없을 때(첫 진입)와 기다리는 동안 다른 것을 누르면 안 되는 길거나 되돌릴 수 없는 작업(사진 업로드·여러 장 저장·삭제, 번치 만들기, 번들 발행, 발행한 번들 수정 저장 등)에는 덮는다. 짧은 저장·확인 뒤 다음 화면으로 넘어가는 동작(약관·프로필 시작하기, 초대 코드·링크 확인, 알림 열기, 번들 초안 만들기)은 덮지 않고 누른 버튼을 바로 비활성으로 바꾼 뒤 끝나면 넘어간다. 첫 진입도 화면 모양을 알면 스켈레톤을 우선한다(#466). 버튼만 비활성으로 바꾼 짧은 동작이 1초를 넘기면 그때 덮는다(`PageLoading`의 `delayMs`, `LATE_OVERLAY_MS` 1000ms, 2026-11-20 #477 제안값). 흐름 안의 단계(번들 만들기·편집, 초대 확인 진입)의 첫 진입 로딩도 1초를 넘길 때만 덮는다. 로그인 확인 가드(`AuthGate`)의 덮개도 첫 확인은 1초를 넘길 때만 덮는다(#505). 한 번 화면이 정해진 뒤 다시 로딩되면 바로 덮는다. 앱은 탭마다 WebView가 따로 열려 각 탭이 로그인 상태를 새로 확인하는데, 바로 덮으면 탭을 열 때마다 덮개가 번쩍인 뒤 스켈레톤으로 바뀌었다(로그인된 브라우저에서 탭 주소를 새로 열어 약 2초 덮개 확인, 개발 서버). 앱 스플래시를 닫는 판정은 덮개가 보이는지가 아니라 `PageLoading`이 붙었는지로 하므로 그대로다. 스켈레톤은 디자인 시스템 `Skeleton`(회색 상자, `motion-safe:animate-pulse`로 은은하게 깜빡이고 동작 줄이기면 멈춤)과 앱 공용 조합(`shared/components/skeleton/`)으로 만들고, 실제 화면과 구조·크기·색을 맞추며 고정 부분(헤더 버튼·고정 문구)은 실제로 그린다(#473). 깜빡임은 프런트엔드 제안이라 결과를 보고 유지 여부를 정한다. 같은 이름의 이전 로티(점 3개, 2026-10-31)를 2026-11-09에 물결 점 패턴으로 교체했다. 자산은 `apps/web/src/shared/assets/lotties/loading.json`, 공통 컴포넌트는 `shared/components/loading/PageLoading.tsx`(dim + 로티)와 `LoadingRipple.tsx`다. 재생은 `shared/components/loading/LazyLottie.tsx`, 엔진(`shared/lib/lottieLight.ts`)과 JSON의 동적 import·캐시는 `shared/lib/lottieLoader.ts`가 맡고 `EditingLottie`도 같이 쓴다. 엔진·JSON은 모듈에서 한 번만 받아 공유하고, 동작 줄이기에서는 첫 프레임에 정지하며, 받지 못하면 빈 자리만 남긴다. 상태 안내는 사용하는 화면이 live region으로 맡고, 덮개가 필요한 로딩은 `PageLoading`으로 쓴다. 화면 전체 로딩(`PageLoading`)의 덮개는 하이드레이션 뒤 `document.body`에 그린다. 화면 틀(전환 영역)이 `fixed`의 기준이 되고 넘친 곳을 잘라 상태 바·홈 표시 영역이 흰색으로 남았기 때문이다(#500, 2026-11-21 팀 QA).
- 편집 중 표시 (Editing, 2026-11-01, 디자이너 확정): 입력창·코멘트 카드의 「다른 멤버가 편집 중」 표시는 모두 디자이너가 전달한 `editing.json`(30×25)으로 처리하고 DS의 점 애니메이션 컴포넌트는 두지 않는다. 자산은 `apps/web/src/shared/assets/lotties/editing.json`, 공통 컴포넌트는 `shared/components/loading/EditingLottie.tsx`다. DS `TextField`·`BundleCommentCard`는 `editing`과 `editingContent`(앱이 넘기는 애니메이션 자리)만 받아 로티 의존을 갖지 않는다. 엔진·JSON 공유, 동작 줄이기(첫 프레임 정지), 받지 못했을 때 빈 자리는 `LoadingRipple`과 같다.
- 재생 실패 (확정): 로티가 화면 전환을 이끄는 경우(로딩 화면) 라이브러리·자산을 못 받거나 재생 오류가 나면 멈추지 않고 다음 화면으로 넘긴다. 앱 첫 실행 인트로(`IntroMotion`)가 이 경우다(이전 초대장 로딩 화면은 코드 모션으로 대체되어 삭제).
- 동작 줄이기 (확정): 정지 프레임이 의미가 없는 장면은 로티를 불러오지 않고 짧게 안내만 둔 뒤 넘어간다. 로티를 쓰는 화면이 새로 생길 때의 기준이다.
- 앱 첫 실행 인트로 (2026-11-10): 장면마다 사용자가 누를 때까지 머무는데, 머무는 동안에도 타일·사진 줄이 계속 흘러야 한다. 디자이너 로티(`인트로_01~04`)는 줄이 정해진 거리만 움직이고 멈추는 키프레임이라, 로티나 영상을 반복 재생하면 처음 위치로 튄다. 그래서 줄 레이어만 로티에서 빼고 화면이 직접 그린다. 한 주기를 세 벌 이어 붙인 뒤 한 주기만큼 등속으로 옮기는 것을 반복해 이음매가 없다(`features/auth/components/intro/IntroRows.tsx`). 나머지(다이아몬드, 문구, 브랜드 화면)는 로티(`shared/assets/lotties/intro.json`, 130KB·gzip 16KB)로 재생하고, 장면마다 멈춤 프레임까지 `playSegments`로 이어서 재생한다. 줄의 나타남·사라짐 시간과 곡선은 원본 로티의 키프레임 값을 옮겼다. 원본 로티는 위에서 떨어져 쌓이는 타일 7개만 115px 격자에서 1에서 4px 벗어나 있어 x·y 키프레임을 격자(Figma 정적 화면의 x)에 맞췄다. 로티에서 뺀 것은 줄, 브랜드 배경(로티는 812pt 안만 칠하고, 안쪽과 Safe Area를 따로 칠하면 경계가 늦게 따라와 보여 `AppFrame` 배경 하나가 552f에서 585f까지의 타이밍(누른 뒤 200ms에 550ms)으로 화면 전체를 칠하고, 가이드로 넘어갈 때 350ms로 돌아옴), 오른쪽 아래 터치 안내 원(1.4초 주기로 번짐, `IntroTouchHint`), 가짜 상태 바, 흰 배경이다. 터치 안내도 장면에 머무는 동안 계속 반복돼야 해서 CSS 무한 애니메이션으로 옮겼다. 첫 장면의 다이아몬드 타일은 쌓이는 동작까지 로티로 두고, 다 쌓이는 97f(멈춤 141f보다 먼저)부터 로티 그룹에 붙인 class(`intro-module`, 로티의 `cl`)를 찾아 대각선 순서로 떠오르게 하고 하나씩 장면 2 색으로 잠깐 물들인다(`useTileStackIdle`, 사용자 제안). 넘길 때는 200ms 동안 제자리·원래 색으로 돌린 뒤 로티가 이어 재생한다. 브랜드 화면은 모션(540~809f)이 끝나면 누르지 않아도 가이드로 넘어간다(2026-11-10 사용자 결정). 동작 줄이기에서는 자동으로 넘기지 않고 다른 장면처럼 눌러서 넘긴다. 화면을 천천히 읽거나 스크린 리더를 쓰는 사용자가 문구를 다 읽기 전에 넘어가지 않게 하려는 것이다(WCAG 2.2.1). 이때 Figma에 정해진 전환이 없어 가이드 장 전환(`6105:42792`)과 같은 방식을 쓴다: 브랜드 화면이 350ms(`0.45, 0, 0.55, 1`) 흐려지고 50ms 뒤 가이드 첫 장의 그림과 문구가 함께 32px 아래에서 700ms(`0.25, 0.1, 0.15, 1`) 떠오르며 하단 바는 투명도만 바뀐다. 첫 장 그림은 브랜드 화면 동안 미리 받아 둔다. 가이드 장 전환에서 문구는 명세(제자리에서 흐려짐, 12px 올라옴) 대신 그림과 같은 거리(위로 24px 사라짐, 32px 아래에서 나타남)로 움직인다. 같은 시간에 거리가 달라 그림과 따로 노는 것처럼 보였기 때문이다(2026-11-10 사용자 확인, 디자이너 확인 필요). 줄은 5초 넘게 자동으로 흘러 WCAG 2.2.2(멈추는 수단)에 걸리지만, 장식이고 느리며(초당 약 40px) 동작 줄이기에서는 멈춰서 의도한 예외로 둔다(2026-11-10 사용자 결정, 화면 안 정지 수단은 디자이너 확인 필요).

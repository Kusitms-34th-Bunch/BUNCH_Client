# Motion

web 페이지 전환은 `@ssgoi/react` 7.4.1을 사용한다. 컴포넌트와 admin 모션에는 CSS transition·Web Animations API를 사용하며, 아래 기준을 함께 따른다.

## 애니메이션을 넣을지 판단

| 사용 빈도                                       | 판단              |
| ----------------------------------------------- | ----------------- |
| 하루 100번+ (키보드 단축키, 커맨드 팔레트 토글) | 애니메이션 없음   |
| 하루 수십 번 (hover, 목록 탐색)                 | 제거하거나 최소화 |
| 가끔 (모달, drawer, toast)                      | 기본 애니메이션   |
| 드묾 (온보딩, 축하, 최초 피드백)                | 장식적 요소 허용  |

모션의 유효한 목적은 공간적 일관성, 상태 전달, 설명, 피드백, 급격한 변화 완충이다. "예뻐 보여서"는 자주 보이는 요소에 넣는 이유로는 부족하다.

## Easing과 duration

- 진입·이탈은 `ease-out`, 화면 안에서의 이동·모핑은 `ease-in-out`, hover·색상 전환은 `ease`, 등속(마퀴, 진행바)은 `linear`를 쓴다.
- 기본 진입에는 `ease-in`을 피한다. 온보딩의 페이지 Slide In은 끝에서 감속하도록 Ease Out 300ms를 적용한다.
- duration 기준: 버튼 피드백 100–160ms, 툴팁·작은 팝오버 125–200ms, 드롭다운·셀렉트 150–250ms, 모달·drawer 200–500ms. UI 애니메이션은 300ms를 넘지 않는다.

## 물리감

- `scale(0)`에서 시작하지 않는다. `scale(0.9~0.97)` + `opacity: 0`에서 시작한다.
- 팝오버·드롭다운은 트리거 쪽에서 자라나도록 `transform-origin`을 트리거 위치에 맞춘다. 모달은 예외로, 화면 중앙에 뜨므로 `transform-origin: center`를 유지한다.
- 버튼 눌림 피드백은 디자이너 공통 지침 `Dissolve / Ease Out / 75ms`를 따른다(2026-10-22, 이전 100ms). 크기를 바꾸지 않고 눌림 오버레이의 투명도만 75ms ease-out으로 바꾼다. 적용: `Button`, `TextButton`, `LoginButton`, `Label`, `TermsLabel`, `CameraButton`(디자인 시스템). 동작 줄이기에서는 전환을 끈다. 곡선은 `Button`·`TextButton`이 CSS Ease Out(`cubic-bezier(0,0,0.58,1)`), 나머지는 Tailwind `ease-out`(`cubic-bezier(0,0,0.2,1)`)이라 아직 다르다.

## 성능

- `transform`과 `opacity`만 애니메이션한다. `width`, `height`, `top`, `left`, `padding`, `margin`을 애니메이션하면 매 프레임 layout을 다시 계산해 jank가 생긴다.
  - 예외: 내용 높이를 모르는 칸을 펼치고 접을 때는 `grid-template-rows` 0fr↔1fr로 자리를 벌린다(아코디언, 번치 프로필 편집 공개 안내, 신고 상세 사유). `transform`으로는 아래 내용과 시트 높이를 밀어낼 수 없다. 사용자가 누를 때 한 번만 일어나고 반복 재생되지 않아 layout 비용을 받아들인다.
- 모션 라이브러리를 도입하면, 짧은 shorthand API(예: `x`/`y`/`scale`을 직접 넘기는 형태)가 실제로 하드웨어 가속되는 transform 문자열로 적용되는지 확인한다. 라이브러리에 따라 shorthand가 메인 스레드에서 계산되어 부하 상황에 프레임을 떨어뜨릴 수 있다.
- toast 추가, toggle처럼 빠르게 반복 트리거되는 대상은 `@keyframes`보다 CSS `transition`을 쓴다. transition은 진행 중에 재시작되면 현재 값에서 이어지지만, keyframes는 처음부터 다시 시작한다.

## 접근성

- `prefers-reduced-motion: reduce`를 존중한다. 모든 모션을 없애는 게 아니라 이동·위치 변화 중심의 모션은 줄이거나 제거하고, 상태 전달에 필요한 opacity·색상 전환은 남긴다.
- hover 애니메이션은 `@media (hover: hover) and (pointer: fine)`로 감싼다. 터치 기기는 탭에서도 hover 이벤트가 발생해 의도치 않게 재생된다.

## Stagger

그룹 진입 애니메이션은 항목 간 30–80ms 간격으로 순차 적용한다. 그 이상 벌어지면 느리게 느껴진다. stagger는 장식이므로, 재생 중에도 사용자의 interaction을 막지 않는다.

## 당겨서 새로고침

Figma `6673:45282`(피드 · Refresh Motion)와 표시기 `6672:47286`이 정한 값이다(2026-11, 이슈 #340). 피드·번치 홈·사진함이 쓴다. 공통 모션처럼 디자이너 값이라 "UI 애니메이션은 300ms를 넘지 않는다"보다 우선한다.

- 동작: 맨 위(`scrollTop` 0)에서 아래로 당겼다 놓는다. 손가락 이동의 0.6배만큼 내용이 내려오고(최대 72px), 64px 이상 내려온 채 놓으면 새로고침을 시작해 64px에 머문다(Figma는 80px이나 로고 아래 간격이 넓어 보여 사용자 요청으로 줄임). 끝나면 0으로 닫힌다. 끝나도 최소 0.6초는 열려 있어 깜빡이지 않는다. 가로로 더 움직이거나 위로 밀거나 이미 스크롤된 상태는 당김으로 보지 않는다. 당긴 채로 손가락을 시작 자리보다 위로 올리면 내용이 로딩 영역 위로 올라와 헤더 밑으로 들어갈 수 있고(기본 스크롤은 막혀 있어 hook이 손가락만큼 직접 스크롤), 놓으면 최상단으로 돌아온다. 그 당김에서 기준 거리(64px)에 한 번이라도 닿았다면 헤더 밑으로 올렸다 놓아도 새로고침한다. 새로고침 중에는 목록을 평소처럼 스크롤할 수 있고, 스크롤로 내용이 표시기 자리를 덮는 만큼 표시기는 흐려져 카드 사이 틈으로 비치지 않는다. 끝나면 스크롤 위치와 무관하게 간격을 닫으면서 내용을 항상 최상단(스크롤 0, 간격 0)으로 올린다(동작 줄이기에서는 즉시).
- 모양: 내용(`main`의 직계 자식)이 `translate`로 내려오고, 36px Spark(4px 모듈 13개, gray-300)가 본문 위 20px(Figma는 30px)에서 20px 위에서 내려오며(0→1 투명도) 나타난다. 당기기 시작하면(새로고침 중에도 이어서) Spark가 2초 주기로 90°씩 세 번 끊어 돈다(사용자 요청, Figma는 표시기가 나타난 뒤 계속 도는 것으로 정의)(곡선 `0.45, 0, 0.2, 1`). Spark는 90° 회전 대칭이라 마지막 멈춤에서 처음으로 돌아가도 이음매가 보이지 않는다.
- 시간·곡선: 열릴 때 `0.33, 0, 0.15, 1`, 닫힐 때 `0.45, 0, 0.2, 1`, 각 600ms(3.5초 타임라인의 17.1%·91.4% 구간).
- 구현: `PageShell`의 `onRefresh`(Promise를 돌려주면 끝날 때까지 기다림)와 `refreshDisabled`. `usePullToRefresh`가 터치를 읽어 컨테이너의 CSS 변수 `--pull-y`·`--pull-p`를 직접 쓰므로 당기는 동안 React가 다시 그리지 않는다. 두 변수는 `globals.css`의 `@property`로 등록해 transition이 보간한다. 내용에는 당기는 동안에만 `translate`를 걸어 평소에는 fixed 자손의 기준 상자가 바뀌지 않는다. `transform`이 아니라 `translate`를 써서 화면을 떠날 때 스크롤을 옮겨 두는 `useHoldScrollOnLeave`의 `transform`과 겹치지 않는다. 표시기는 `RefreshSpark`(`shared/components/refresh/`).
- 제약: 당기는 동안과 새로고침 중(최소 0.6초 + 요청 + 닫힘 0.6초)에는 `main` 직계 자식에 `translate`가 걸려 그 자손의 `fixed`는 화면이 아니라 그 자식을 기준으로 놓인다. 이 세 화면의 `main` 안에는 `fixed`를 두지 않는다. 시스템 제스처 등으로 터치가 취소(`touchcancel`)되면 새로고침하지 않고 닫는다. Spark 회전은 새로고침이 끝날 때까지 반복한다(Figma는 한 주기 2초만 정의).
- 서버 상태(실패하면 `onRefresh`가 거부해 위 실패 안내가 나간다. 시각적인 실패 표시는 아직 없다): 피드·번치 홈은 `useRefreshActiveQueries`(지금 화면이 쓰는 query 전부 다시 받기)를, 사진함은 `usePhotoBox().refresh`(프로필·멤버·사진 목록)를 넘긴다. 실패해도 표시를 닫고, query 자체의 오류 표시는 각 query를 쓰는 화면이 맡는다.
- 접근성: 동작 줄이기에서는 열리고 닫히는 전환, 표시기의 이동·회전을 뺀다. 손가락을 따라 내용이 내려오는 것은 사용자가 직접 하는 조작이라 남기며(빼면 표시기가 내용과 겹친다), 표시기는 투명도로만 나타난다. 표시기는 장식이라 `aria-hidden`이고, 「새로고침하고 있어요」·「새로고침을 마쳤어요」는 `role="status"`로 알리고 3초 뒤 비운다. 요청이 하나라도 실패하면(`onRefresh`가 거부) 「새로고침하지 못했어요」를 알린다. 마우스·키보드에는 반응하지 않는다. 키보드·스크린 리더 사용자는 화면 진입·앱 복귀 때 다시 받을 수 있지만 query의 신선 시간 안에서는 다시 받지 않는다. 접근 가능한 새로고침 수단(예: 헤더 메뉴)은 후속 과제다(디자이너·기획 확인 필요).
- 확인한 범위: Chromium(Pixel 7 에뮬레이션, 터치 이벤트 주입)에서 세 화면의 당김·머묾·닫힘과 짧게 당겨 취소되는 것을 확인했고(거리를 80px로 둔 때의 측정이며, 64px로 줄인 뒤와 표시기를 내용 뒤로 옮긴 뒤는 단위 테스트만 돌리고 화면은 확인하지 못했다), 단위 테스트가 임계값·중복 방지·가로 제스처·비활성을 확인한다. 실기기(iOS WKWebView의 바운스, Android 뒤로 가기 제스처와의 충돌)와 동작 줄이기, 사진함의 사진 길게 눌러 선택과의 충돌은 확인하지 않았다.
- 범위 밖: 피드 맨 아래 「모든 피드를 확인했어요」의 체크 표시와 새 소식 구분선의 조각 모음은 같은 Figma 노드에 있지만 새로고침 표시기가 아니라 피드 끝 안내의 모션이라 이번에 만들지 않았다(디자이너 확인 필요).

## Lottie

디자이너가 Lottie 애니메이션을 전달할 예정이다(2026-10-14). 온보딩에 쓸 예정이고, 로그인 화면에 쓸지는 미정이다. 재생 라이브러리는 `lottie-react`(3.1.2, 2026-10-19 사용자 확인 후 `apps/web`에 추가)다. 아래는 도입 기준과 첫 도입(초대 링크 확인 화면의 초대장 로티)의 결과다. 초대장 연출은 2026-11 Figma 변경(`Seal & Flip`)으로 코드 모션으로 바뀌었고(아래 「온보딩 초대장·컨페티」), 로티는 로딩·편집 중·피드 끝 표시에 쓴다.

- 온보딩은 로그인 뒤에 나오므로, 첫 화면 로딩을 늦추지 않고 동적 import로 자산을 받을 수 있다. 온보딩 한 단계가 보이는 동안 다음 단계의 자산을 미리 받아 두면 전환할 때 끊기지 않는다(FE 판단). 로그인 화면에 쓰기로 정해지면 그 화면은 첫 렌더가 늦어질 수 있으니 다시 판단한다.
- 자산 형식(`.json` 또는 압축된 `.lottie`)과 재생 라이브러리는 디자이너의 자산을 받은 뒤 정한다. 다른 프로젝트에서는 `lottie-react`를 썼다. production dependency 추가는 사용자 확인을 받는다.
- 웹 앱의 로티 JSON은 `apps/web/src/shared/assets/lotties/`에서 관리한다. 재생 컴포넌트와 기능 로직은 사용하는 feature에 둔다. 앱 전용 자산을 디자인 시스템으로 옮기지 않는다.
- 재생 컴포넌트는 브라우저 API를 쓰므로 클라이언트 컴포넌트(`'use client'`)로 둔다. 서버 컴포넌트에서 직접 import하지 않는다.
- 자산이 50KB 이상이면 동적 import로 쓰는 시점에 받는다(제안). 정적 import하면 그 화면 번들에 JSON 전체가 들어간다. PR에는 자산 용량을 적는다.
- `prefers-reduced-motion: reduce`이면 자동 재생과 반복을 끄고 정지 프레임을 보여준다. 애니메이션을 유일한 정보 전달 수단으로 쓰지 않고, 같은 정보를 텍스트로도 준다.
- 장식용이면 `aria-hidden`을 주고, 의미가 있으면 텍스트 대체를 함께 준다.
- 컨테이너 크기를 고정해서, 자산을 받기 전후에 layout이 밀리지 않게 한다.
- 위 "애니메이션을 넣을지 판단" 표를 따른다. 자주 보는 요소에는 쓰지 않고 온보딩, 축하, 로딩 같은 드문 장면에 쓴다. "UI 애니메이션은 300ms를 넘지 않는다"는 전환에 대한 규칙이라 Lottie 연출 길이에는 적용하지 않지만, 재생 중에도 사용자의 interaction을 막지 않는다.
- 복잡한 애니메이션은 WebView에서 프레임이 떨어질 수 있다. 렌더러 선택과 프레임은 실기기에서 확인한다(FE 판단, 미검증).
- 테스트에서는 재생 라이브러리를 mock한다. 애니메이션의 모양은 테스트하지 않는다.
- 도입 결과 (2026-10-19): `lottie-react` 3.x는 엔진 세 빌드(full·svg·light)를 함께 내보내서 모듈 전체를 동적 `import()`하면 셋이 모두 내려받아진다(합계 약 180KB gzip). 표현식이 없는 로티는 light 빌드만 쓰도록 `export { LottieLight } from 'lottie-react'` 래퍼(`shared/lib/lottieLight.ts`)를 동적 import해서 엔진 하나(약 164KB)와 래퍼(약 47KB)만 내려받는다. 새 로티를 넣을 때 표현식이 있으면 `LottieSvg`로 바꾼다.
- 자산 위치 (확정): 로티 JSON은 `apps/web/src/shared/assets/lotties/`에 두고 재생 컴포넌트에서 동적 import한다. 초대장 로티(`inviteAnimation.json`)는 코드 모션으로 대체해 삭제했다(#292).
- 로딩 상태 (2026-11-09, 앞으로의 기준): 「편집 중」(Editing)이 아닌 로딩 표시는 모두 디자이너가 전달한 `loading.json`(90×90, 물결처럼 번지는 점 패턴, 표현식 없음)으로 처리한다. 사진별·요소별이 아니라 페이지 전체에 하며, 화면 전체를 `overlay-dim-subtle`로 덮고 가운데에 재생한다. 같은 이름의 이전 로티(점 3개, 2026-10-31)를 2026-11-09에 물결 점 패턴으로 교체했다. 자산은 `apps/web/src/shared/assets/lotties/loading.json`, 공통 컴포넌트는 `shared/components/loading/PageLoading.tsx`(dim + 로티)와 `LoadingRipple.tsx`다. 재생은 `shared/components/loading/LazyLottie.tsx`, 엔진(`shared/lib/lottieLight.ts`)과 JSON의 동적 import·캐시는 `shared/lib/lottieLoader.ts`가 맡고 `EditingLottie`도 같이 쓴다. 엔진·JSON은 모듈에서 한 번만 받아 공유하고, 동작 줄이기에서는 첫 프레임에 정지하며, 받지 못하면 빈 자리만 남긴다. 상태 안내는 사용하는 화면이 live region으로 맡고, 로딩은 항상 `PageLoading`으로 쓴다.
- 편집 중 표시 (Editing, 2026-11-01, 디자이너 확정): 입력창·코멘트 카드·캡션 줄의 「다른 멤버가 편집 중」 표시는 모두 디자이너가 전달한 `editing.json`(30×25)으로 처리하고 DS의 점 애니메이션 컴포넌트는 두지 않는다. 자산은 `apps/web/src/shared/assets/lotties/editing.json`, 공통 컴포넌트는 `shared/components/loading/EditingLottie.tsx`다. DS `TextField`·`BundleCommentCard`는 `editing`과 `editingContent`(앱이 넘기는 애니메이션 자리)만 받아 로티 의존을 갖지 않는다. 엔진·JSON 공유, 동작 줄이기(첫 프레임 정지), 받지 못했을 때 빈 자리는 `LoadingRipple`과 같다.
- 재생 실패 (확정): 로티가 화면 전환을 이끄는 경우(로딩 화면) 라이브러리·자산을 못 받거나 재생 오류가 나면 멈추지 않고 다음 화면으로 넘긴다. 앱 첫 실행 인트로(`IntroMotion`)가 이 경우다(이전 초대장 로딩 화면은 코드 모션으로 대체되어 삭제).
- 동작 줄이기 (확정): 정지 프레임이 의미가 없는 장면은 로티를 불러오지 않고 짧게 안내만 둔 뒤 넘어간다. 로티를 쓰는 화면이 새로 생길 때의 기준이다.
- 앱 첫 실행 인트로 (2026-11-10): 장면마다 사용자가 누를 때까지 머무는데, 머무는 동안에도 타일·사진 줄이 계속 흘러야 한다. 디자이너 로티(`인트로_01~04`)는 줄이 정해진 거리만 움직이고 멈추는 키프레임이라, 로티나 영상을 반복 재생하면 처음 위치로 튄다. 그래서 줄 레이어만 로티에서 빼고 화면이 직접 그린다. 한 주기를 세 벌 이어 붙인 뒤 한 주기만큼 등속으로 옮기는 것을 반복해 이음매가 없다(`features/auth/components/intro/IntroRows.tsx`). 나머지(다이아몬드, 문구, 브랜드 화면)는 로티(`shared/assets/lotties/intro.json`, 130KB·gzip 16KB)로 재생하고, 장면마다 멈춤 프레임까지 `playSegments`로 이어서 재생한다. 줄의 나타남·사라짐 시간과 곡선은 원본 로티의 키프레임 값을 옮겼다. 원본 로티는 위에서 떨어져 쌓이는 타일 7개만 115px 격자에서 1에서 4px 벗어나 있어 x·y 키프레임을 격자(Figma 정적 화면의 x)에 맞췄다. 로티에서 뺀 것은 줄, 브랜드 배경(로티는 812pt 안만 칠하고, 안쪽과 Safe Area를 따로 칠하면 경계가 늦게 따라와 보여 `AppFrame` 배경 하나가 552f에서 585f까지의 타이밍(누른 뒤 200ms에 550ms)으로 화면 전체를 칠하고, 가이드로 넘어갈 때 350ms로 돌아옴), 오른쪽 아래 터치 안내 원(1.4초 주기로 번짐, `IntroTouchHint`), 가짜 상태 바, 흰 배경이다. 터치 안내도 장면에 머무는 동안 계속 반복돼야 해서 CSS 무한 애니메이션으로 옮겼다. 첫 장면의 다이아몬드 타일은 쌓이는 동작까지 로티로 두고, 다 쌓이는 97f(멈춤 141f보다 먼저)부터 로티 그룹에 붙인 class(`intro-module`, 로티의 `cl`)를 찾아 대각선 순서로 떠오르게 하고 하나씩 장면 2 색으로 잠깐 물들인다(`useTileStackIdle`, 사용자 제안). 넘길 때는 200ms 동안 제자리·원래 색으로 돌린 뒤 로티가 이어 재생한다. 브랜드 화면은 모션(540~809f)이 끝나면 누르지 않아도 가이드로 넘어간다(2026-11-10 사용자 결정). 동작 줄이기에서는 자동으로 넘기지 않고 다른 장면처럼 눌러서 넘긴다. 화면을 천천히 읽거나 스크린 리더를 쓰는 사용자가 문구를 다 읽기 전에 넘어가지 않게 하려는 것이다(WCAG 2.2.1). 이때 Figma에 정해진 전환이 없어 가이드 장 전환(`6105:42792`)과 같은 방식을 쓴다: 브랜드 화면이 350ms(`0.45, 0, 0.55, 1`) 흐려지고 50ms 뒤 가이드 첫 장의 그림과 문구가 함께 32px 아래에서 700ms(`0.25, 0.1, 0.15, 1`) 떠오르며 하단 바는 투명도만 바뀐다. 첫 장 그림은 브랜드 화면 동안 미리 받아 둔다. 가이드 장 전환에서 문구는 명세(제자리에서 흐려짐, 12px 올라옴) 대신 그림과 같은 거리(위로 24px 사라짐, 32px 아래에서 나타남)로 움직인다. 같은 시간에 거리가 달라 그림과 따로 노는 것처럼 보였기 때문이다(2026-11-10 사용자 확인, 디자이너 확인 필요). 줄은 5초 넘게 자동으로 흘러 WCAG 2.2.2(멈추는 수단)에 걸리지만, 장식이고 느리며(초당 약 40px) 동작 줄이기에서는 멈춰서 의도한 예외로 둔다(2026-11-10 사용자 결정, 화면 안 정지 수단은 디자이너 확인 필요).

## 페이지 전환

web은 [SSGOI의 DOM 경계](https://ssgoi.dev/docs/how-it-works)를 사용한다. React 실험 기능 `ViewTransition`과 별도의 전역 전환 CSS는 사용하지 않는다.

전환을 고르는 순서는 아래와 같다(2026-11-02 결정). 라이브러리를 들인 이유가 검증된 전환을 그대로 쓰는 것이라, 직접 만든 전환은 예외로만 둔다.

1. SSGOI 프리셋(`drill`·`slide`·`sheet`·`fade`·`zoom`·`hero` 등)에서 화면 관계에 맞는 것을 고른다. 목록 → 상세처럼 한 단계 들어가는 이동은 `drill`, 순서가 있는 단계는 `slide`, 모달 같은 화면은 `sheet`다.
2. 화면설계서의 시간·곡선은 프리셋의 `override`로만 맞춘다(예: `slide`에 `easeOutIntegrator`). 프리셋 기본값이 화면 관계에 맞으면 그대로 둔다.
3. 프리셋으로 표현할 수 없을 때만 직접 만들고, 이 문서에 이유를 적는다. 지금은 하단 탭 크로스페이드(결정 기록 017, 프리셋 `fade`가 순차 방식이라 같은 헤더가 흐려짐)가 해당한다.
4. 어느 전환이든 나가는 화면 처리(`inert`, `data-page-leaving`)는 `override`로 더한다.

- 설정: `apps/web/src/app/(app)/AppTransitions.tsx`의 경로 쌍과 `ONBOARDING_TRANSITION_DURATION_MS`를 수정한다. 전역 provider만 공유하며, 등록하지 않은 이동과 첫 진입에는 전환을 적용하지 않는다.
- 효과: 온보딩 시작 → 만들기·참여, 만들기 완료 → 초대는 `slide`를 사용한다. 새 화면은 오른쪽에서 들어오고 기존 화면은 왼쪽으로 화면 폭만큼 밀린다. 반대 이동은 방향을 뒤집는다. 페이드는 섞지 않고 경계 밖을 잘라낸다. 참여 화면의 시각 전환은 미검증이다.
- 시간·곡선: Slide In / Left / 이동 시간 300ms를 적용한다. 곡선은 사용자 합의에 따라 설계서의 Ease In 대신 Ease Out으로 조정한다. SSGOI의 `override`에 `easeOutIntegrator`를 넣어 CSS `cubic-bezier(0, 0, .58, 1)`의 진행도를 계산한다. 라이브러리의 `easeOut({ duration })`은 관성 기반 곡선이므로 CSS 곡선과 동일하다고 취급하지 않는다. 이동 시간과 라이브러리의 종료 판정 시간은 구분한다. 이전 200ms 설정에서 SSGOI 7.4.1의 WAAPI timeline 약 233ms를 확인했으며, 현재 300ms 설정의 실제 종료 시간은 브라우저 재검증 전이다.

- 번들 만들기 진입 (2026-11-06, 이슈 #230, 사용자 결정): 번치 홈 플로팅 「번들 만들기」 → 사진 선택 `/bunch/bundles/new`와 닫기는 SSGOI `sheet` 기본 프리셋이다(SSGOI 데모 YouTube의 Home → Create와 같은 `sheet()`). 모달처럼 아래에서 올라오고 닫으면 내려가며, 시간·곡선은 프리셋 기본(spring)이다. `sheet`는 움직이는 화면만 애니메이션 대상이라 뒤 화면을 같은 전환 영역에서 찾아 다른 전환처럼 `data-page-leaving`·`inert`를 붙인다(`guardSheet`). 그래서 상태 바 영역 색이 시트가 다 올라온 뒤가 아니라 전환 시작과 함께 바뀐다. 시트가 움직이는 동안은 화면에 `data-sheet-moving`을 붙여 `AppFrame`의 색 전환을 150ms 대신 300ms ease-in-out으로 늘려, 시트가 위에 닿는 시점에 색이 다 바뀐다(Chromium에서 시트가 47px 남았을 때 흰색 도달, 약 0.31초). 하단 탭 막대는 전환 대상 밖이라 이동과 함께 바로 사라진다. Chromium(앱 폭 430px)에서 열 때 화면 위치가 547→0px로 약 300ms에 대부분 올라오고 약 0.7초에 멈추며, 닫을 때 반대로 내려가는 것을 확인했다. 실기기와 동작 줄이기는 확인하지 않았다.
- 번들 만들기 추천 상세 (2026-11-01, 이슈 #161): 사진 선택 `/bunch/bundles/new`와 추천 번들 상세 사이는 `slide`·200ms(`BUNDLE_DETAIL_SLIDE_DURATION_MS`)이고 양방향 규칙 하나다. 상세는 동적 route라 약관 원문처럼 고정 id(`BUNDLE_SELECT_PATHS.transitionIds.recommendation`)를 규칙과 각 화면 DOM의 `data-ssgoi-transition`에 함께 쓴다. 곡선은 온보딩과 같은 합의에 따라 설계서의 Ease In 대신 Ease Out이다. 상세 ↔ 뷰어 전환은 시안이 없어 등록하지 않았다. Chromium(headless 375px)에서 프레임을 재서 새 화면 324→0·이전 화면 0→-375, 약 185ms로 끝나는 것을 확인했고, 실기기와 동작 줄이기는 아직 확인하지 않았다.
- 접근성: `prefers-reduced-motion` 변경을 구독해 전환 규칙을 비운다. SSGOI가 함수형 규칙을 캐시하므로 함수 안에서 설정을 읽는 것으로 대체하지 않는다. 전환 중 이전 화면은 `inert`로 포커스·접근성 탐색에서 제외하고 종료 시 복원한다.
- 검증: 진행도 단위 테스트와 온보딩 회귀 테스트, Chromium의 순방향·뒤로 가기·입력 유지·헤더 유지·동작 줄이기 변경·좁은 화면/넓은 화면 중간 프레임을 확인한다. iOS WKWebView와 실제 화면 읽기 도구는 별도 확인이 필요하다. 네이티브 스와이프와 전환 중 빠른 연속 이동도 실기기에서 확인한다.

### 온보딩 단계 진행바

- Header Animation(Figma `1998:35008`, Smart animation·Slow·600ms): 진행바는 현재 단계의 막대만 채우고(2026-11 Figma 수정, 이전에는 누적) 새 막대가 왼쪽에서 오른쪽으로 늘어난다(Fill Right). 제목은 5px 아래에서 올라오며 나타난다(Slide Up). 곡선은 둘 다 Slow 근사 `cubic-bezier(0.24, 0.3, 0.14, 1)`이다. Figma가 지정한 곡선이라 공통 규칙의 「진행바는 `linear`」의 예외다. 이전 기준(화면설계서 `791:8480` 「진행바만 인터랙션 O」, 색만 300ms)을 대체한다.
- `CreateBunchFrame`이 같은 `Stepper` 요소를 유지하고 `current`만 바꾼다. 첫 표시는 `@starting-style`로 채운다. 제목은 단계 화면마다 새로 마운트되므로 `PageHeader`에 `animate-step-title-in`(`globals.css`의 keyframe·`@utility`)을 건다. `@starting-style`을 지원하지 않는 브라우저(Safari 17.5·Chrome 117 미만)에서는 첫 표시 채움 없이 채운 상태로 바로 보인다. 모션 감소 설정에서는 둘 다 끈다. 전체 페이지의 300ms 슬라이드와 별도이다.

### 온보딩 초대장·컨페티

- 초대장 열람(Figma `6174:15909` Seal & Flip, 2026-11, 이슈 #292): 초대 확인 화면에 들어오면 봉투 뒷면이 아래에서 올라오고, 인장이 살짝 커졌다 사라지며 가운데 조각 13개가 사방으로 흩어지고, 봉투가 가로로 접히며(`scaleX`) 카드가 펼쳐진 뒤 제목이 10px 아래에서 올라온다.

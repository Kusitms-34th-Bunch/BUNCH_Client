# Motion

web 페이지 전환은 `@ssgoi/react` 7.4.1을 사용한다. 컴포넌트와 admin 모션에는 CSS transition·Web Animations API를 사용하며, 아래 기준을 함께 따른다.

화면별 전환·모션 기록은 각 기능 스펙의 「모션」 절에 둔다(`docs/specs/`의 기능 스펙, 기능 스펙이 없는 화면·컴포넌트는 co-located spec). 이 문서에는 여러 화면에 걸친 규칙만 둔다.

## 애니메이션을 넣을지 판단

| 사용 빈도                                       | 판단              |
| ----------------------------------------------- | ----------------- |
| 하루 100번+ (키보드 단축키, 커맨드 팔레트 토글) | 애니메이션 없음   |
| 하루 수십 번 (hover, 목록 탐색)                 | 제거하거나 최소화 |
| 가끔 (모달, drawer, toast)                      | 기본 애니메이션   |
| 드묾 (온보딩, 축하, 최초 피드백)                | 장식적 요소 허용  |

모션의 유효한 목적은 공간적 일관성, 상태 전달, 설명, 피드백, 급격한 변화 완충이다. "예뻐 보여서"는 자주 보이는 요소에 넣는 이유로는 부족하다.

## Easing과 duration

- 진입·이탈은 `ease-out`, 화면 안에서의 이동·모핑은 `ease-in-out`, hover·색상 전환은 `ease`, 등속(마퀴, 진행바)은 `linear`를 쓴다.
- 기본 진입에는 `ease-in`을 피한다.
- duration 기준: 버튼 피드백 100–160ms, 툴팁·작은 팝오버 125–200ms, 드롭다운·셀렉트 150–250ms, 모달·drawer 200–500ms. UI 애니메이션은 300ms를 넘지 않는다. 화면 이동은 아래 「화면 이동 시간」의 예외다.

### 화면 이동 시간

- 한 단계 들어가는 이동(`drill`)과 단계·하위 화면으로 미는 이동(`slide`)은 모두 350ms, `cubic-bezier(0.4, 0, 0.2, 1)`(천천히 시작해 길게 감속)이다(#560, FE 판단). 값은 `AppTransitions.tsx`의 `PUSH_DURATION_MS`·`PUSH_EASING` 하나로 둔다.
- 위 진입 기본(ease-out)과 다른 이유: 실기기는 새 화면을 처음 그리기까지 약 90ms가 걸려 그동안 이동이 지나간다. ease-out 250ms는 첫 보이는 프레임에 이미 약 48%였고(120fps 녹화, 브라우저는 6~11%), 같은 90ms 동안 ease-out 300ms는 45%, 200ms는 63%를 지난다(계산값). 새 곡선 350ms는 약 25%이고 마지막 25% 시간의 이동도 9%에서 4%로 줄어 끝이 부드럽다.
- 이동하는 동안 두 화면은 각자 배경색의 상태 바 높이 띠를 달고 함께 밀린다(`_transitions/pageGuards.ts`의 `guardPush`). 상태 바 영역을 `AppFrame`이 따로 페이드하면 화면이 도착하기 전에 색이 먼저 바뀌었다.
- 맨 위로(탭 다시 누르기·피드 로고)는 직접 스크롤한다(`shared/lib/navigation/scrollPageToTop.ts`). 브라우저 기본 smooth는 거리마다 속도가 달라 WebKit에서 시작·끝이 끊겨 보였다. 순간 이동 없이 전체 거리를 감속 곡선 `cubic-bezier(0.2,0,0,1)`(빠르게 출발해 맨 위에서 천천히 멈춤)로 움직이고, 시간은 한 화면 이내 350ms에서 한 화면마다 50ms씩 늘려 650ms까지다. 손가락·휠이 닿으면 멈춘다. 예전에는 두 화면보다 멀면 한 화면 위치로 바로 옮겨 튀어 보였다(#583).
- 실기기 확인은 전이다.

## 물리감

- `scale(0)`에서 시작하지 않는다. `scale(0.9~0.97)` + `opacity: 0`에서 시작한다.
- 팝오버·드롭다운은 트리거 쪽에서 자라나도록 `transform-origin`을 트리거 위치에 맞춘다. 모달은 예외로, 화면 중앙에 뜨므로 `transform-origin: center`를 유지한다.
- 버튼 눌림 피드백은 디자이너 공통 지침 `Dissolve / Ease Out / 75ms`를 따른다(2026-10-22, 이전 100ms). 눌림 오버레이의 투명도는 75ms ease-out으로 바꾸고(2026-11-27부터 아래 「시간·곡선」의 150ms, Figma `7982:51780`), 2026-11-25(#562)부터 크기도 함께 살짝 줄인다(아래 「눌림 효과」). 적용: `Button`, `TextButton`, `LoginButton`, `Label`, `TermsLabel`, `CameraButton`(디자인 시스템). 동작 줄이기에서는 전환을 끈다. 글자·배경색 전환 곡선은 `Button`·`TextButton`이 CSS Ease Out(`cubic-bezier(0,0,0.58,1)`), 나머지는 Tailwind `ease-out`(`cubic-bezier(0,0,0.2,1)`)이라 아직 다르다.

### 눌림 효과

- 누르는 동안 살짝 줄었다가 떼면 돌아온다(Figma 「Press Interaction · 눌림 효과」 `7982:51780`, 2026-11-25 #562). 색은 각 컴포넌트의 Pressed 색을 그대로 쓰고, 크기는 `scale`로만 바꿔 레이아웃은 그대로다. 다만 누르는 동안 브라우저는 줄어든 박스로 터치 위치를 판정해, 가장자리를 누른 손가락이 박스 밖이 되면 눌림이 풀리고 `click`이 나지 않을 수 있다(한 변에 약 1~2.5%, 실기기 확인 전).
- 줄어드는 정도(2026-11-27 Figma 수정): 단계 고정값 대신 크기로 계산해 어떤 크기든 약 2px만 줄인다. `scale = (기준 − 2) ÷ 기준`, `기준 = max(높이, 너비 ÷ 4, 24)`(예: 아이콘 24px 0.917, 아이콘 버튼 40px 0.950, 꽉 찬 CTA 342×48 0.977, 목록 줄 375×42 0.979, 큰 카드 348×308 0.994). CSS는 자기 크기로 나눌 수 없어 웹 `PressScrollGuard`가 누르는 순간(`pointerdown`) 줄어들 요소의 레이아웃 크기(`offsetWidth`·`offsetHeight`, 이미 줄어든 중에도 같음)로 `--press-scale`을 넣는다. 아래 단계값은 측정 전(Storybook, 키보드로 누름) 기본값이다.
- 디자인 시스템 유틸리티(`packages/design-system/src/styles/utilities.css`)를 루트 요소에 쓴다.
  - `press-scale-small`(기본 0.95): 칩, 아이콘 버튼, 캘린더 날짜, 글자 버튼, 번치 이름 전환(`AccountSwitcher`)
  - `press-scale-medium`(기본 0.97): `Button`(SolidButton), 팔로우 버튼
  - `press-scale-large`(기본 0.98): 번치 분위기 카드(Card), 라디오 카드(`RadioCard`·`DescriptionRadioCard`), 업로드 선택 카드, 목록 줄(`MenuLabel`·`MenuItem`·`BunchListItem`·`BunchRadioItem`(Profile - Label)·`NotificationCard`(Alert_Label)·`NudgeBanner`·`Label`). 목록 줄은 회색 배경과 내용이 함께 줄어든다. 추천 번들 카드는 카드 버튼을 누를 때만 줄어든다(위에 겹친 「상세 보기」를 누를 때는 그대로). 그래서 유틸리티 대신 표의 값(0.994, 348×308 기준)과 같은 시간·곡선을 직접 쓰므로 수치를 바꾸면 함께 바꾼다.
  - 입력 필드는 쓰지 않는다(배경색만).
  - 디자인 명세에 없어 크기 축소(`press-scale`)를 적용하지 않은 요소(덮개 눌림은 별도): `ProfileRadioCard`, `TermsLabel`(행 전체 축소, 보기 화살표는 목록 줄 장식이라 아이콘 눌림도 없음), `ProfileListItem`, `BundleCard`, `EntryCard`, `InviteMemberCard`, `LocationCard`, `LoginButton`, `FloatingButton`, `CameraButton`, `MenuTabs`, `TextButtonUnderline`, `BunchLabel`. 디자이너 확인 뒤 추가한다.
- 시간·곡선(2026-11-27 Figma 수정, 이전 누를 때 100ms·뗄 때 180ms `0.2, 0, 0, 1`): 누를 때·뗄 때 150ms, `cubic-bezier(0, 0, 0.15, 1)`, 기준점 가운데, 튕김 없음. 뗄 때는 지금 크기에서 바로 1.0으로 돌아온다. 헤더 안의 번치 이름 전환은 왼쪽 가운데 기준이라 제목이 옆으로 움직이지 않고, 웹은 `will-change: transform`을 준다(Figma 5번 헤더 규칙).
- 아이콘만 있는 버튼(Figma `8311:57033` 「헤더 아이콘 눌림 효과」, `8332:57930` 「아이콘 버튼 눌림 효과 · 적용 범위」, 2026-11-27): 「아이콘 혼자서 하나의 동작을 하는가」로 정한다. 버튼 영역(24×24, 누르는 범위 포함)은 그대로 두고 안쪽 아이콘 그림만 가운데 기준 0.917(24px 기준 2px)로 줄이며, 시간·곡선·해제는 위와 같다(150ms). 단독 아이콘은 `IconButton`의 `plain` 변형으로 모았다(`IconButton.spec.md`). 동작 줄이기면 줄지 않고 흐려짐·배경만 바로 바뀐다.
  - A·배경 없는 아이콘(`press="fade"`): 누르는 동안 아이콘 불투명도 60%. 헤더 뒤로 가기(`HeaderBackButton`), 사진 위 아이콘(광고 사진 카드 ⋯).
  - B·기본 아이콘 버튼(`press="overlay"`, 기본값): 누르는 동안 아이콘 뒤에 `overlay-hover` 배경 36×36·모서리 8(`::after`, 레이아웃 영향 없음). 헤더 ⋯·알림·닫기(`HeaderIconButton`, 번치 홈·피드 헤더의 알림·더보기는 화면 이동 링크라 `press-icon-overlay` 클래스), 다른 번치 더보기, 댓글·멤버 줄(`ProfileListItem`)·콕 장소(`LocationCard`) 더보기, 번들 멤버 빼기, 선택 칸 지우기, 번들 카드 삭제(회색 원 배경 유지), 초대 링크 복사, 추천 번들 상세 화살표, 답글 취소.
  - 적용하지 않음: 더 큰 눌림 영역 안의 장식 아이콘(버튼·칩·목록 줄·아코디언·약관 줄의 화살표 등)은 부모 눌림을 따르고, 표시용 아이콘(지도 핀·자물쇠·체크·역할 배지)과 좋아요·댓글 아이콘은 효과가 없다. 입력 필드(검색)는 배경만 바뀐다. 하단 탭·플로팅 버튼과 배경 있는 `IconButton`(subtle·outline·primary, Pressed variant 반영 예정)은 별도 규칙이다.
- 유틸리티가 루트의 색 전환(`color`·`background-color`·`border-color`·`opacity`, 기본 75ms)도 함께 정해 `transition`이 서로 덮어쓰지 않는다. 색 전환 시간·곡선이 다르면 `--press-color-duration`·`--press-color-ease`로 바꾼다(칩 300ms, 버튼 CSS Ease Out). 루트에 `transition-colors`를 따로 두지 않고, 쓰는 쪽도 이 컴포넌트에 `className`으로 `transition-*`를 넘기지 않는다(뒤에 오는 클래스가 평상시 전환을 덮어 뗄 때 축소가 바로 튀어 돌아옴).
- 비활성(`disabled`, `aria-disabled`, 안의 입력이 비활성)에서는 줄어들지 않는다. 마우스 호버 표시는 칩만 뺐다(디자인이 Hover를 Pressed로 바꿈). 라디오 카드의 선택 전 호버는 이전 시안 그대로 두었다. 동작 줄이기에서는 줄지 않고 색도 전환 없이 바로 바뀐다.
- 스크롤과 해제(2026-11-26 #583): iOS WebView는 누른 채 스크롤해도 `:active`가 남아(실기기 녹화) Figma 규칙 「스크롤 제스처엔 효과 없음」을 어겼다. 웹 `PressScrollGuard`가 손가락이 8px 넘게 움직이거나 스크롤이 일어나면 문서에 `data-touch-scrolling`을 달고, `press-overlay`·`press-scale`은 손을 떼기 전에도 눌림(덮개·줄어듦·`active:` 배경 그라데이션)을 끈다. 눌림 덮개도 위 시간·곡선(150ms)을 따르게 바꿔 「바로 바뀌는 느낌」을 줄였고, 컴포넌트마다 따로 그리던 75ms 덮개(`Button`·`TextButton`·아코디언·카드·목록 줄 등)를 `press-overlay` 하나로 모았다. 위 버튼 공통 지침 75ms와 다르다. 컴포넌트 명세(`*.spec.md`)의 눌림 75ms·단계 scale 표기는 이 문서가 기준이다. 누를 때 늦게 켜는 지연(iOS 목록 방식)은 넣지 않는다. 빠른 탭(약 100ms)에서 눌림이 거의 보이지 않고, 스크롤 중 해제는 위 표시가 맡는다. 2026-11-27부터는 유틸리티 밖에서 직접 그린 눌림도 같은 표시로 푼다. `utilities.css`가 Tailwind `active` 변형을 `&:active:not(:where(:root[data-touch-scrolling] *))`(우선순위는 그대로)로 다시 정의해 `active:`·`group-active`·`peer-active`·`has-active`가 모두 따른다. 대괄호로 직접 쓴 `:active`(체크박스·라디오·라벨·카드의 `has-[…:active]` 등)에는 같은 `:not(:root[data-touch-scrolling] *)`를 붙인다. 새 눌림 스타일도 같은 방식으로 쓴다. 배경 그라데이션으로 겹치던 눌림(`NotificationCard`·`NudgeBanner`·`InviteMemberCard`·`ProfileRadioCard`·`Checkbox`)은 그라데이션이 전환되지 않아 툭 바뀌어 같은 날 `press-overlay`로 옮겼다(색은 그대로). `ChipButton`(300ms Dissolve)과 라디오(테두리·점 색)는 이 범위에서 뺐다.
- 누른 채 영역 밖으로 나가 떼면 `click`이 나지 않는다. iOS·Android 실기기 느낌은 확인 전이다.

## 성능

- `transform`과 `opacity`만 애니메이션한다(예외: 아래 표의 메뉴 탭 선택 밑줄 `left`·`width` 250ms). `width`, `height`, `top`, `left`, `padding`, `margin`을 애니메이션하면 매 프레임 layout을 다시 계산해 jank가 생긴다.
  - 예외: 내용 높이를 모르는 칸을 펼치고 접을 때는 `grid-template-rows` 0fr↔1fr로 자리를 벌린다(아코디언, 번치 프로필 편집 공개 안내, 신고 상세 사유). `transform`으로는 아래 내용과 시트 높이를 밀어낼 수 없다. 사용자가 누를 때 한 번만 일어나고 반복 재생되지 않아 layout 비용을 받아들인다.
- 모션 라이브러리를 도입하면, 짧은 shorthand API(예: `x`/`y`/`scale`을 직접 넘기는 형태)가 실제로 하드웨어 가속되는 transform 문자열로 적용되는지 확인한다. 라이브러리에 따라 shorthand가 메인 스레드에서 계산되어 부하 상황에 프레임을 떨어뜨릴 수 있다.
- 화면과 박자를 맞춰야 하는 작업은 `requestAnimationFrame`(rAF)으로 한다.
  - 끌기·스크롤·당기기처럼 포인터·스크롤 이벤트가 프레임보다 자주 오는 동안 화면을 바꾸면, 이벤트마다 그리지 않고 프레임마다 한 번만 그린다. 값은 이벤트에서 기억하고 rAF 안에서 DOM style·CSS 변수에 쓴다(`useCropDrag`). 이때 React state로 다시 그리지 않는다([feed.md](../specs/feed.md)의 「모션」 「당겨서 새로고침」「스크롤로 헤더 숨김」).
  - 계속 움직이는 효과(가장자리 자동 스크롤 등)는 `setInterval` 대신 rAF 반복으로 돌리고, 멈추거나 화면을 떠날 때 `cancelAnimationFrame`으로 끊는다(`useEdgeAutoScroll`).
  - 크기·위치를 읽는 일(`getBoundingClientRect`, `offsetHeight`, `scrollTop`)과 쓰는 일을 한 프레임 안에서 번갈아 하지 않는다. 읽기를 먼저 모으고 쓰기는 그 뒤(다음 rAF)에 한다. 번갈아 하면 브라우저가 매번 layout을 다시 계산한다.
  - 「화면이 그려진 다음」이 필요한 작업(새 화면의 초점 이동, 붙여넣기 뒤 커서 위치, 전환이 시작된 뒤의 스크롤)은 `setTimeout(0)`이 아니라 rAF로 미룬다(`RouteFocus`, 번들 상세 댓글로 이동 `useCommentsEntry`). `setTimeout`은 그리기와 박자가 맞지 않아 한 프레임 늦거나 먼저 실행될 수 있다.
  - 예약한 rAF는 effect 정리(cleanup)에서 취소한다. 화면이 사라진 뒤 실행되면 없는 요소를 건드린다.
- toast 추가, toggle처럼 빠르게 반복 트리거되는 대상은 `@keyframes`보다 CSS `transition`을 쓴다. transition은 진행 중에 재시작되면 현재 값에서 이어지지만, keyframes는 처음부터 다시 시작한다.

## 접근성

- `prefers-reduced-motion: reduce`를 존중한다. 모든 모션을 없애는 게 아니라 이동·위치 변화 중심의 모션은 줄이거나 제거하고, 상태 전달에 필요한 opacity·색상 전환은 남긴다.
- hover 애니메이션은 `@media (hover: hover) and (pointer: fine)`로 감싼다. 터치 기기는 탭에서도 hover 이벤트가 발생해 의도치 않게 재생된다.

## Stagger

그룹 진입 애니메이션은 항목 간 30–80ms 간격으로 순차 적용한다. 그 이상 벌어지면 느리게 느껴진다. stagger는 장식이므로, 재생 중에도 사용자의 interaction을 막지 않는다.

## 어드민 모션

어드민 Figma에 모션이 없어 web 값과 이 문서의 기본 규칙을 따른다(2026-11-27 사용자 결정). 위 「공통 모션」처럼 디자이너가 지정한 값이 아니므로 기본 규칙보다 우선하지 않는다. 기록은 각 컴포넌트 spec의 「모션」이다.

- `Dropdown`·`DatePickerField` 펼침: 「물리감」·duration 기준대로 트리거 쪽에서 scale 0.9→1·투명도, 열기 150ms ease-out. 닫기는 100ms ease-in으로 팝오버 메뉴 닫기와 같은 예외다(진입·이탈 ease-out 기본과 다름). Base UI transition, 기준점 `--transform-origin`. 팝오버 메뉴의 0.35→1·280ms는 모바일 값이라 데스크톱에서 튀어 보여 쓰지 않는다.
- `TabList` 선택 선: 메뉴 탭 밑줄과 같은 250ms ease-out 이동(`left`·`width` 예외 포함).
- `SideMenu`: 배경·글자 색만 150ms `ease`. 선택 배경이 항목 사이를 미끄러지는 방식은 시선이 쏠려 쓰지 않는다.
- `PlaceSearch`: 패널 자리는 나타날 때(150ms ease-out)·없어질 때(100ms ease-in, 같은 예외)만 투명도로 움직이고, 떠 있는 동안은 안쪽 내용만 바뀐다.
- 동작 줄이기: 이동·크기 변화(선택 선 이동, 팝업 크기)만 빼고 투명도·색 전환은 남긴다.
- 버튼·행 눌림 축소는 데스크톱이라 넣지 않는다.

## Lottie

디자이너가 Lottie 애니메이션을 전달할 예정이다(2026-10-14). 온보딩에 쓸 예정이고, 로그인 화면에 쓸지는 미정이다. 재생 라이브러리는 `lottie-react`(3.1.2, 2026-10-19 사용자 확인 후 `apps/web`에 추가)다. 아래는 도입 기준과 첫 도입(초대 링크 확인 화면의 초대장 로티)의 결과다. 초대장 연출은 2026-11 Figma 변경(`Seal & Flip`)으로 코드 모션으로 바뀌었고(`apps/web/src/features/onboarding/components/join/BunchJoinInvitation.spec.md`의 「모션」), 로티는 로딩·편집 중·피드 끝 표시에 쓴다.

- 온보딩은 로그인 뒤에 나오므로, 첫 화면 로딩을 늦추지 않고 동적 import로 자산을 받을 수 있다. 온보딩 한 단계가 보이는 동안 다음 단계의 자산을 미리 받아 두면 전환할 때 끊기지 않는다(FE 판단). 로그인 화면에 쓰기로 정해지면 그 화면은 첫 렌더가 늦어질 수 있으니 다시 판단한다.
- 자산 형식(`.json` 또는 압축된 `.lottie`)과 재생 라이브러리는 디자이너의 자산을 받은 뒤 정한다. 다른 프로젝트에서는 `lottie-react`를 썼다. production dependency 추가는 사용자 확인을 받는다.
- 웹 앱의 로티 JSON은 `apps/web/src/shared/assets/lotties/`에서 관리한다. 재생 컴포넌트와 기능 로직은 사용하는 feature에 둔다. 앱 전용 자산을 디자인 시스템으로 옮기지 않는다.
- 재생 컴포넌트는 브라우저 API를 쓰므로 클라이언트 컴포넌트(`'use client'`)로 둔다. 서버 컴포넌트에서 직접 import하지 않는다.
- 자산이 50KB 이상이면 동적 import로 쓰는 시점에 받는다(제안). 정적 import하면 그 화면 번들에 JSON 전체가 들어간다. PR에는 자산 용량을 적는다.
- `prefers-reduced-motion: reduce`이면 자동 재생과 반복을 끄고 정지 프레임을 보여준다. 애니메이션을 유일한 정보 전달 수단으로 쓰지 않고, 같은 정보를 텍스트로도 준다.
- 장식용이면 `aria-hidden`을 주고, 의미가 있으면 텍스트 대체를 함께 준다.
- 컨테이너 크기를 고정해서, 자산을 받기 전후에 layout이 밀리지 않게 한다.
- 위 "애니메이션을 넣을지 판단" 표를 따른다. 자주 보는 요소에는 쓰지 않고 온보딩, 축하, 로딩 같은 드문 장면에 쓴다. "UI 애니메이션은 300ms를 넘지 않는다"는 전환에 대한 규칙이라 Lottie 연출 길이에는 적용하지 않지만, 재생 중에도 사용자의 interaction을 막지 않는다.
- 복잡한 애니메이션은 WebView에서 프레임이 떨어질 수 있다. 렌더러 선택과 프레임은 실기기에서 확인한다(FE 판단, 미검증).
- 테스트에서는 재생 라이브러리를 mock한다. 애니메이션의 모양은 테스트하지 않는다.
- 도입 결과 (2026-10-19): `lottie-react` 3.x는 엔진 세 빌드(full·svg·light)를 함께 내보내서 모듈 전체를 동적 `import()`하면 셋이 모두 내려받아진다(합계 약 180KB gzip). 표현식이 없는 로티는 light 빌드만 쓰도록 `export { LottieLight } from 'lottie-react'` 래퍼(`shared/lib/lottieLight.ts`)를 동적 import해서 엔진 하나(약 164KB)와 래퍼(약 47KB)만 내려받는다. 새 로티를 넣을 때 표현식이 있으면 `LottieSvg`로 바꾼다.
- 자산 위치 (확정): 로티 JSON은 `apps/web/src/shared/assets/lotties/`에 두고 재생 컴포넌트에서 동적 import한다. 초대장 로티(`inviteAnimation.json`)는 코드 모션으로 대체해 삭제했다(#292).
- 로딩 상태 (2026-11-09, 앞으로의 기준): 「편집 중」(Editing)이 아닌 로딩 표시는 모두 디자이너가 전달한 `loading.json`(90×90, 물결처럼 번지는 점 패턴, 표현식 없음)으로 처리한다. 덮개를 쓸 때는 사진별·요소별이 아니라 페이지 전체에 하며, 화면 전체를 `overlay-dim-subtle`로 덮고 가운데에 재생한다. 2026-11-20(디자이너 확인)부터 덮개는 필요할 때만 쓴다. 보여 줄 내용이 아직 없을 때(첫 진입)와 기다리는 동안 다른 것을 누르면 안 되는 길거나 되돌릴 수 없는 작업(사진 업로드·여러 장 저장·삭제, 번치 만들기, 번들 발행, 발행한 번들 수정 저장 등)에는 덮는다. 짧은 저장·확인 뒤 다음 화면으로 넘어가는 동작(약관·프로필 시작하기, 초대 코드·링크 확인, 알림 열기, 번들 초안 만들기)은 덮지 않고 누른 버튼을 바로 비활성으로 바꾼 뒤 끝나면 넘어간다. 첫 진입도 화면 모양을 알면 스켈레톤을 우선한다(#466). 버튼만 비활성으로 바꾼 짧은 동작이 1초를 넘기면 그때 덮는다(`PageLoading`의 `delayMs`, `LATE_OVERLAY_MS` 1000ms, 2026-11-20 #477 제안값). 흐름 안의 단계(번들 만들기·편집, 초대 확인 진입)의 첫 진입 로딩도 1초를 넘길 때만 덮는다. 로그인 확인 가드(`AuthGate`)의 덮개도 첫 확인은 1초를 넘길 때만 덮는다(#505). 한 번 화면이 정해진 뒤 다시 로딩되면 바로 덮는다. 앱은 탭마다 WebView가 따로 열려 각 탭이 로그인 상태를 새로 확인하는데, 바로 덮으면 탭을 열 때마다 덮개가 번쩍인 뒤 스켈레톤으로 바뀌었다(로그인된 브라우저에서 탭 주소를 새로 열어 약 2초 덮개 확인, 개발 서버). 앱 스플래시를 닫는 판정은 덮개가 보이는지가 아니라 `PageLoading`이 붙었는지로 하므로 그대로다. 스켈레톤을 만드는 기준(층·배치, 회색으로 그리는 범위, 안내)은 `skeleton.md`를 따른다. 같은 이름의 이전 로티(점 3개, 2026-10-31)를 2026-11-09에 물결 점 패턴으로 교체했다. 자산은 `apps/web/src/shared/assets/lotties/loading.json`, 공통 컴포넌트는 `shared/components/loading/PageLoading.tsx`(dim + 로티)와 `LoadingRipple.tsx`다. 재생은 `shared/components/loading/LazyLottie.tsx`, 엔진(`shared/lib/lottieLight.ts`)과 JSON의 동적 import·캐시는 `shared/lib/lottieLoader.ts`가 맡는다. 엔진·JSON은 모듈에서 한 번만 받아 공유하고, 동작 줄이기에서는 첫 프레임에 정지하며, 받지 못하면 빈 자리만 남긴다. 상태 안내는 사용하는 화면이 live region으로 맡고, 덮개가 필요한 로딩은 `PageLoading`으로 쓴다. 화면 전체 로딩(`PageLoading`)의 덮개는 하이드레이션 뒤 `document.body`에 그린다. 화면 틀(전환 영역)이 `fixed`의 기준이 되고 넘친 곳을 잘라 상태 바·홈 표시 영역이 흰색으로 남았기 때문이다(#500, 2026-11-21 팀 QA).
- 편집 중 표시 (Editing): 번들 작성 화면의 「다른 멤버가 편집 중」은 초록 점과 「○○님이 편집 중」 문구로 보인다(2026-11-15 presence 개편부터). 그 전에 쓰던 디자이너 전달 로티 `editing.json`(점 3개, 2026-11-01)과 `EditingLottie`는 쓰는 곳이 없어 2026-11-24에 지웠다(#546). DS `TextField`·`BundleCommentCard`의 `editingContent`는 앱이 넘기는 표시 자리로 남아 있다.
- 재생 실패 (확정): 로티가 화면 전환을 이끄는 경우(로딩 화면) 라이브러리·자산을 못 받거나 재생 오류가 나면 멈추지 않고 다음 화면으로 넘긴다. 앱 첫 실행 인트로(`IntroMotion`)가 이 경우다(이전 초대장 로딩 화면은 코드 모션으로 대체되어 삭제).
- 동작 줄이기 (확정): 정지 프레임이 의미가 없는 장면은 로티를 불러오지 않고 짧게 안내만 둔 뒤 넘어간다. 로티를 쓰는 화면이 새로 생길 때의 기준이다.
- 앱 첫 실행 인트로(2026-11-10)의 로티·줄 모션 기록은 [login-signup.md](../specs/login-signup.md)의 「모션」으로 옮겼다(2026-11-23).

## 페이지 전환

web은 [SSGOI의 DOM 경계](https://ssgoi.dev/docs/how-it-works)를 사용한다. React 실험 기능 `ViewTransition`과 별도의 전역 전환 CSS는 사용하지 않는다.

전환을 고르는 순서는 아래와 같다(2026-11-02 결정). 라이브러리를 들인 이유가 검증된 전환을 그대로 쓰는 것이라, 직접 만든 전환은 예외로만 둔다.

1. SSGOI 프리셋(`drill`·`slide`·`sheet`·`fade`·`zoom`·`hero` 등)에서 화면 관계에 맞는 것을 고른다. 목록 → 상세처럼 한 단계 들어가는 이동은 `drill`, 순서가 있는 단계는 `slide`, 모달 같은 화면은 `sheet`다.
2. 화면설계서의 시간·곡선은 프리셋의 `override`로만 맞춘다(예: `slide`에 `easeOutIntegrator`). 프리셋 기본값이 화면 관계에 맞으면 그대로 둔다.
3. 프리셋으로 표현할 수 없을 때만 직접 만들고, 해당 기능 스펙의 「모션」 절에 이유를 적는다. 지금은 하단 탭 크로스페이드(결정 기록 017, 프리셋 `fade`가 순차 방식이라 같은 헤더가 흐려짐)가 해당한다.
4. 어느 전환이든 나가는 화면 처리(`inert`, `data-page-leaving`)는 `override`로 더한다.

- 설정: `apps/web/src/app/(app)/AppTransitions.tsx`의 경로 쌍과 화면 이동 공통 시간(`PUSH_DURATION_MS`·`PUSH_EASING`)을 수정한다. 전역 provider만 공유하며, 등록하지 않은 이동과 첫 진입에는 전환을 적용하지 않는다. 나가는 화면 표식·상태 바 처리는 같은 폴더의 `_transitions/pageGuards.ts`, 하단 탭 크로스페이드는 `_transitions/tabCrossfade.ts`에 둔다.
- 접근성: `prefers-reduced-motion` 변경을 구독해 전환 규칙을 비운다. SSGOI가 함수형 규칙을 캐시하므로 함수 안에서 설정을 읽는 것으로 대체하지 않는다. 전환 중 이전 화면은 `inert`로 포커스·접근성 탐색에서 제외하고 종료 시 복원한다.
- iOS 스와이프 뒤로 가기(2026-11-27 #587): 손가락을 따라 앞 화면이 밀리는 것은 WebView 기본 스와이프(앞 화면 스냅샷)가 맡고, 웹 전환은 건너뛴다. 전에는 웹이 스와이프인지 몰라 놓은 뒤 지난 화면을 다시 꺼내 한 번 더 전환했고(hero), 전환을 건너뛰어도 WebKit이 스냅샷을 걷는 순간 아직 그리지 않은 흰 화면이 보였다(시뮬레이터 녹화). SSGOI 자체 감지(가장자리 터치 뒤 600ms)와 `popstate`의 `hasUAVisualTransition`만으로는 앱 WebView에서 놓친다. 그래서 쉘(`modules/swipe-back`)이 같은 가장자리 제스처를 함께 받아 시작·취소를 `ssgoi:swipe-back` 이벤트로 알리고, `@ssgoi/core` 패치(`docs/conventions/libraries.md`)가 이 이벤트를 자체 감지와 따로 기억해(도착 화면에 들어서거나 취소 신호가 올 때 해제) 전환을 건너뛴다. 이동하면 쉘이 iOS가 남은 거리를 다 민 뒤(레이어 애니메이션이 끝날 때, 최대 0.6초) 그 화면을 덮개로 덮고, 웹이 돌아간 화면을 그린 뒤(`useSwipeBackSettled`, 두 프레임 뒤 화면 안 사진의 디코딩까지 최대 150ms 기다려 bridge `swipeBackSettled`) 걷는다(신호가 없으면 1초 뒤). 덮기 전에 신호가 오면 덮지 않는다. 두 프레임만 기다리면 틀만 그리고 사진 칸이 빈 화면이 한 프레임 보였다(시뮬레이터 녹화). 1.2.0 쉘은 주소가 바뀌는 순간(실기기는 손을 떼자마자) 바로 덮어, 반쯤 밀린 화면이 웹 신호(당시 최대 400ms)까지 멈춰 보였다(#598, 실기기 녹화). 1.2.0 앱에서도 멈춤이 짧도록 웹 대기 상한을 150ms로 줄였다. 덮는 시점 변경(쉘)은 시뮬레이터 빌드만 확인했고 실기기는 미검증이다. 뒤로 갈 때 SSGOI는 앞으로 갈 때 쓴 규칙을 기억해 다시 쓰므로 앱 설정·`middleware`로는 막을 수 없다. 뒤로 가기 버튼은 지금처럼 웹 전환을 재생한다.
- 검증: 진행도 단위 테스트와 온보딩 회귀 테스트, Chromium의 순방향·뒤로 가기·입력 유지·헤더 유지·동작 줄이기 변경·좁은 화면/넓은 화면 중간 프레임을 확인한다. iOS WKWebView와 실제 화면 읽기 도구는 별도 확인이 필요하다. 네이티브 스와이프와 전환 중 빠른 연속 이동도 실기기에서 확인한다.
- 공유 사진(`hero`·`zoom`으로 이어지는 사진)은 SSGOI 데모처럼 같은 주소의 이미 받은 사진을 `decoding` 속성 없이 쓴다(#573).
  - 문제: SSGOI hero는 출발·도착 사진을 `cloneNode`로 복사해 날린다. 사진 주소가 다르거나 `decoding="async"`이면, 복사본과 돌아온 화면의 사진이 받거나 decode할 때까지 비어 깜빡였다(1.1.1 녹화, 시뮬레이터 녹화).
  - 원인: 서버가 사진 주소를 요청마다 새로 서명해, 같은 사진도 응답마다 주소가 바뀌었다(개발 백엔드에서 사진 하나가 3시간 동안 27개 주소로 받아짐).
  - 처리: BFF 응답을 받는 `requestData`가 같은 파일(출처+경로+서명 밖 쿼리)이면, 유효 시간이 절반 넘게 남은 이전 서명 주소를 그대로 쓴다(`shared/api/client/stableSignedUrls.ts`). 남은 시간은 받은 순간부터 잰다(기기 시계와 무관). 유효 시간이 7일을 넘는 값은 서명 주소로 보지 않는다.
  - 한계: 기억은 메모리에만 있다. 그래서 앱을 새로 열면 저장된 캐시의 옛 주소와 첫 응답의 새 주소가 달라 사진이 한 번 바뀐다. 근본 해결은 백엔드가 같은 파일에 같은 주소를 주는 것이다(공개 CDN이나 서명 시각을 묶는 방식).
  - 만료(2026-11-27 #587): 개발 백엔드 주소는 30분(`X-Amz-Expires=1800`) 뒤 만료된다. 켜 둔 앱이 캐시의 지난 주소로 새 사진 칸을 그리면 이미지가 비고, 앱을 다시 켜야 보였다(팀 QA). 서명 주소 이미지가 실패하면 `shared/query/SignedImageRecovery`가 그 주소를 재사용 목록에서 빼고, 그 주소를 가진 query를 무효로 해 보이는 화면만 다시 받는다. 같은 파일은 15분에 한 번만 다시 받는다(없는 사진이면 반복하지 않게, 자세한 규칙은 `docs/architecture/data-layer.md` 「서명 사진 주소 만료」). 사진 상세 원본 주소의 신선도는 무한에서 10분으로 줄였다(받은 주소는 15분 넘게 남음).
  - 적용 범위: `decoding` 속성은 `BundlePhoto`의 키가 있는 첫 사진과 번치 격자의 한 번 보인 칸에서만 뺀다. 나머지 사진은 스크롤 중 메인 스레드를 막지 않게 `async`로 둔다.

- `hero`·`zoom`은 도착 화면이 그려진 뒤 재생한다(#573, `_transitions/pageGuards.ts`의 `playAfterPaint`).
  - 동작: 첫 재생에서 시작 모습을 적용하고 바로 멈춘 뒤, 두 프레임 뒤에 이어 간다. 기다리는 동안은 출발 화면이 그대로 보이고, 누른 뒤 반응이 약 두 프레임 늦어진다.
  - 이유: 데모와 달리 피드는 돌아올 때 화면을 새로 그린다. iOS는 그리기 전에 재생을 시작해 돌아가기 첫 프레임이 하얗게 비었다.
  - 근거(시뮬레이터 녹화): 이 처리를 넣으면 깜빡임이 사라지고, 빼면 다시 생겼다.
  - 적용 범위: 사진함 hero도 같은 가드(`guardHero`)라 함께 적용된다.
- 사진함 → 사진 상세(2026-11-27 #598, 결정 기록 032): 앱 안에서 연 상세는 사진함 위에 겹쳐 띄우고(사진함 유지) hero를 직접 움직인다(`app/(app)/@overlay/(.)photos/[photoId]/_components/overlayHero.ts`). 열기는 SSGOI 사진 hero와 같은 450ms `0.3, 0, 0.15, 1`(`_transitions/photoHeroMotion.ts`)로 칸에서 상세 자리로 날고 상세 화면은 같은 시간에 나타난다. 상세 사진이 그려진 뒤(디코딩 포함 최대 200ms) 시작한다. 그때까지 상세 사진을 받지 못했거나 칸이 화면 밖이면(상세에서 사진을 넘긴 경우 등) hero 없이 페이드만 한다(받기 전 사진은 캔버스에 그려지지 않음). 닫기는 상세를 복제해 400ms 같은 곡선으로 흐리게 하고 사진을 칸으로 날린다. 날아가는 복사본은 `canvas`다(WebKit은 캐시에 있는 사진도 새 `img`가 2~3프레임 비어 보임). 칸은 복사본이 그려진 다음 프레임에 숨기고(먼저 숨기면 누른 칸이 흰 구멍으로 보임), 날아가는 동안 뒤 사진함에 `data-page-leaving`을 달아 상세의 원본 교체를 미루고 누른 칸 뒤 사진을 보인다. 닫을 때는 칸을 숨기지 않는다. 동작 줄이기·iOS 스와이프 뒤로 가기는 움직임 없이 열고 닫는다. 주소로 바로 연 상세에서 돌아갈 때는 기존 SSGOI 사진 hero다.

# 공유 요소·시트 전환

한 요소가 다음 화면으로 이어지거나(hero·zoom) 화면이 아래에서 올라오는(sheet) 전환의 화면별 결정과 확인 기록이다. 일반 규칙은 [motion.md](motion.md), 다른 화면 전환은 [motion-page-transitions.md](motion-page-transitions.md)를 따른다.

- 피드 → 번들 상세 (2026-11-09 이슈 #266 `drill`, 2026-11-15 #400에서 변경): 카드 사진을 누르면 SSGOI `hero`(`type: 'fade'`)로 카드가 상세의 첫 사진 자리로 옮겨 가며 상세 화면이 겹쳐 나타난다(디자이너 요청, Figma `6892:46500` 「게시글 확대 모션」). #266에서는 카드와 상세 사진 크기가 같아 움직임이 작다고 hero를 쓰지 않았는데, 디자이너가 이 움직임(아래로 미끄러짐)을 정해 바꿨다.
  - 짝: 디자인 시스템 `BundlePhoto`의 `heroKey`가 피드 카드 전체(사진과 위 글자·딤)에 `data-hero-enter-key`, 상세 첫 사진에 `data-hero-exit-key`를 붙인다. 키는 `bundleHeroKey(bundleId)`. 이 조합이면 SSGOI가 두 장을 페이지 위 별도 층에 그린다. 같은 `data-hero-key`를 쓰면 상세 사진을 페이지 안에서 움직이는데, 상세 사진은 가로 스크롤 줄(`overflow-x: auto`) 안이라 줄 밖으로 나간 부분이 잘렸다. 그 위로 카드 복사본만 보여 딤이 아래로 벗겨지듯 보였다(2026-11-15 느린 재생 캡처로 확인).
  - 시간: 550ms·`cubic-bezier(0.3, 0, 0.15, 1)`(Figma 사진 이동). 카드의 딤·글자는 사진과 함께 움직이며 같은 시간에 고르게 사라진다. Figma는 글자 덮개를 300ms에 먼저 지우지만, SSGOI는 복사본의 위치와 투명도를 한 진행값으로 움직여 복사본만 빠르게 하면 두 장이 어긋나(가로 띠·겹친 상) 같은 시간으로 둔다. SSGOI의 기본 spring 대신 `cubicBezierIntegrator`로 CSS 곡선을 정해진 시간에 재생한다.
  - 미리 받기: hero는 전환 순간 상세에 짝이 있어야 하는데, 상세는 데이터를 받는 동안 받는 중 화면이라 처음 여는 번들에서는 짝이 없어 전환 없이 바뀌었다. 그래서 사진에 손가락이 닿을 때(`pointerdown`) 상세와 번치 홈을 미리 받고(`ensureQueryData`, 캐시가 있으면 바로), 사진·말풍선을 누르면 받기가 끝나거나 400ms가 지난 뒤 이동했다. 실기기에서는 처음 여는 번들의 응답이 400ms를 넘겨 hero 없이 들어갔고, 누른 뒤 400ms 동안 반응이 없어 끊겨 보였다(2026-11-20, 사용자 제보). 지금은 기다리지 않고 바로 이동한다. 상세는 받는 동안 피드 카드 데이터로 번치 정보·제목·첫 사진을 본문과 같은 자리에 먼저 그려(누를 수 없게 `inert`) 짝을 만든다. 다 받으면 본문으로 바뀐다.
  - 뒤로 가기: 같은 hero 규칙을 양방향으로 쓴다(Figma는 들어갈 때만 정의, 시간·곡선은 같은 값). 돌아갈 때는 SSGOI가 피드 카드를 제자리에서 상세 사진 자리 → 카드 자리로 움직이고 상세 화면은 흐려진다. 처음에는 양방향 hero가 짝을 잇지 못해 `drill`로 따로 뒀지만, enter·exit 키로 바꾼 뒤 다시 확인하니 이어졌다(2026-11-15 #400). 움직이는 카드가 아래 카드에 가리지 않게 SSGOI 복사본(`data-ssgoi-crossfade`)이 들어 있는 동안만 목록 항목을 위로 올린다. 전환 중 나가는 화면은 다른 전환과 같이 `inert`·나가는 화면 표식을 단다.
  - 스크롤: 스크롤은 페이지 안 `main`이 맡아 SSGOI 자동 복원 대상이 아니다. 나가는 화면이 DOM에 다시 붙으면 0이 되어 맨 위로 튀므로, 화면이 사라질 때 스크롤을 `transform`으로 옮겨 둔다(`useHoldScrollOnLeave`, `shared/hooks`). 피드는 스크롤할 때 값을 그 history 항목에 저장해 뒤로 오면 복원한다(`useScrollInHistory`).
  - 확인(2026-11-20 바로 이동으로 바꾸기 전 기준, 바꾼 뒤 브라우저·실기기 측정은 아직): Chromium에서 처음 여는 번들과 다시 여는 번들 모두 hero(프레임 측정), 8배 느린 재생 캡처에서 카드가 한 덩어리로 내려가며 딤이 고르게 사라짐, 두 번 눌러도 이동 1번. 뒤로 가기는 첫 카드와 둘째 카드에서 카드가 상세 사진 자리에서 카드 자리로 약 550ms에 돌아오고 그동안 목록 항목이 위로 올라오는 것을 프레임으로 확인했다. 실기기, 동작 줄이기는 확인하지 않았다.
  - 전환 중 스크롤(2026-11-15, #398 확인): 새 화면이 옆에서 들어오는 동안 `scrollIntoView`를 부르면 밀려 있는 화면을 보이려고 바깥 틀까지 가로로 스크롤해 화면이 튄다. 진입하자마자 위치를 옮겨야 하면 세로 스크롤 영역(`main`)의 `scrollTop`만 바꾼다(상세의 「댓글로 이동」, `BundleDetail.tsx`). 다른 `scrollIntoView` 사용처(피드 로고의 맨 위 이동, 번들 선택의 추천 적용, `useScrollFocusedIntoView`, 등록한 댓글 보이기)는 사용자가 화면을 보는 중에만 불려 전환과 겹치지 않는 것을 코드 경로로 확인했다. 진입 직후에 부르는 곳이 새로 생기면 같은 방식으로 바꾼다.
  - 말풍선 진입(2026-11-22, #505, 사용자 결정): 말풍선(`?focus=comments`)은 hero가 아니라 SSGOI `zoom`(`type: 'static'`)이다. 눌린 카드가 상세 화면 전체로 벌어지고(뒤 피드는 그대로), 상세는 처음 그려질 때 이미 댓글 위치로 내려 두어 열리는 동안 댓글이 보인다. 뒤로 가면 화면 전체가 카드 자리로 접힌다. 키보드는 열림이 끝난 뒤(`data-page-leaving`이 사라진 뒤) 준다. 말풍선에 손가락이 닿을 때 상세를 미리 받기 시작하고, 누르면 그 요청을 최대 400ms 기다렸다가 이동한다. 받기 전에 열면 카드가 받는 중 화면(맨 위)으로 열린 뒤 도착하는 순간 댓글로 넘어가 보여서다(실서버에서 사용자 확인). 400ms를 넘기면 그대로 열고 도착하면 댓글로 내린다.
    - 이유: hero는 상세 첫 사진을 카드 사진과 잇는데, 말풍선 진입은 상세가 댓글까지 내려가 있어 들어갈 때는 「사진이 날아옴 → 툭 내려감」, 뒤로 갈 때는 화면 위 밖의 사진에서 출발해 「위에서 쓸려 내려옴」으로 보였다. SSGOI 문서도 카드 하나가 화면 전체로 열리면 zoom, 같은 사진이 이어지면 hero를 권하고, 데모(Instagram·Pinterest·YouTube·Airbnb·Voyage)도 카드 → 상세는 zoom이다. 사진 탭은 Figma 「게시글 확대 모션」대로 hero를 유지한다.
    - 구현: 같은 상세 주소라 SSGOI 규칙이 구분하지 못해, 말풍선 진입만 상세 틀의 전환 이름을 `FEED_PATHS.transitionIds.bundleComments`로 나눈다. 상세에서 번치·멤버·공개 범위·수정으로 가는 규칙은 두 이름에 함께 건다. 다만 번치 이름으로 가는 push는 두 진입 모두 이동 직전에 `bundleToBunch`로 바뀌어 그 drill 규칙을 탄다(아래 「번치 탭 번들 진입」). 짝 표식은 hero와 이름이 반대다: 나가는 피드 카드에 `data-zoom-exit-key`(여러 개 가능), 들어가는 상세 안에 같은 값의 `data-zoom-enter-key`가 정확히 하나. SSGOI는 화면 틀 안쪽에서 찾으므로(`querySelectorAll`, 틀 자신은 찾지 않음) 표식은 틀 안 요소에 둔다(`@ssgoi/core` 7.4.1 코드 확인). 나가는 화면 표식은 다른 전환처럼 `guardPair`(경계 id로 피드·상세를 찾음). zoom은 열리는 동안 나가는 카드를 복제해 화면 크기로 키우는데, 카드는 맨 위 사진부터라 그 뒤로 댓글 화면이 드러나면 점프처럼 보였다. 그래서 말풍선 진입에서는 복제본을 숨기고(`visibility: hidden`) 댓글 위치의 상세 자체가 카드 자리에서 펼쳐지게 했다. 복제본은 계산된 스타일을 inline으로 받고 zoom 표식이 지워져서, 상세 틀 안에서 enter 표식이 없는 형제를 `!important`로 숨긴다. 뒤로 갈 때도 숨긴 채라 상세가 거의 제 크기로 흐려지다가 카드 자리로 들어간다(사용자 확인). 복제본을 살리거나 앱 틀에서 넘친 곳을 자르면 화면 전체가 줄어드는 느낌이 나서 쓰지 않았다(녹화로 비교). zoom이 상세 틀을 transform으로 옮기는 동안 문서 높이가 잠깐 늘어 데스크톱에서 스크롤바가 깜빡였는데, 문서는 스크롤하지 않는 구조라 `html`의 스크롤바만 숨겼다(`scrollbar-width: none`, `globals.css`).
    - 개발 모드 점프: 로컬 개발 서버에서는 열리는 동안 맨 위였다가 끝나고 댓글로 넘어갔다. Strict Mode가 효과를 한 번 정리했다 다시 실행할 때 `useHoldScrollOnLeave`가 떠나는 화면으로 보고 스크롤을 0으로 돌리고 되돌리지 않았기 때문이다. 다시 실행될 때 붙잡아 둔 위치로 되돌리게 고쳤다(실서버 개발 화면에서 열리는 첫 프레임부터 댓글 위치 확인).
    - 확인: Chromium 운영 빌드(가짜 서버)에서 들어갈 때 약 220ms에 다 열리고 579ms에 입력란 초점, 뒤로 갈 때 약 160ms에 카드로 접히는 것을 프레임으로 확인했다. iOS WKWebView, 동작 줄이기, VoiceOver는 확인 전이다.
- 번치 탭 번들 진입 (2026-11-22, 이슈 #514, 사용자 결정): 화면설계서(`1892:37781`)에 번들 영역을 눌렀을 때의 전환 정의가 없다. 완성된 번들 격자(번치 탭·다른 번치 프로필) → 번들 상세는 SSGOI `zoom`(`type: 'static'`)이다. 칸이 상세 화면 전체로 열리고 뒤 번치 화면은 그대로이며, 뒤로 가면 상세 화면 전체가 칸 자리로 접힌다(SSGOI showcase Instagram 「Grid → Post」와 같은 설정). 칸에는 `data-zoom-exit-key`, 상세 틀 안에는 같은 값의 `data-zoom-enter-key`가 있다. 처음에는 피드 사진 탭과 같은 `hero`로 만들었다. 상세가 사진 한 장이 아니라 제목·작성자·여러 사진·댓글이 있는 게시물이라 인스타처럼 화면 전체가 열리는 쪽이 맞고, hero는 착지 자리가 상세 사진 자리와 정확히 같아야 해서 위치·날짜 줄이나 늦은 데이터에 쉽게 어긋나 zoom으로 정했다(사용자가 두 방식을 비교). hero로 되돌리려면 `AppTransitions` 격자 규칙의 `transition`만 `feedBundleHero`로 바꾸면 된다(칸의 hero 키와 아래 hero용 정리는 남겨 둠). 아래는 hero로 다듬을 때 확인한 내용이다. 칸 링크에 `data-hero-enter-key`, 상세 첫 사진에 같은 키의 exit 표식이다(키는 피드·번치 홈이 함께 써서 `shared/lib/heroKeys.ts`). 상세의 번치 이름 → 번치 탭·다른 번치 프로필은 새 화면으로 들어가는 이동이라 예전처럼 `drill`이다. 그대로 두면 이 zoom 규칙의 돌아가는 방향으로 잡히는데 짝이 없어 전환 없이 바뀌었다. 그래서 이동 직전에 상세 틀의 `data-ssgoi-transition`을 `FEED_PATHS.transitionIds.bundleToBunch`로 바꾸고, 그 id에서 번치 화면으로 가는 drill 규칙을 둔다(SSGOI는 이 속성이 바뀌면 바로 다시 등록한다). 이동이 일어나지 않고 이 화면에 남으면 다음 입력에서 원래 id로 되돌린다. 번치 화면에서 뒤로 가기로 돌아오면 drill 반대 방향이다. SSGOI는 push 때 쓴 규칙을 기록 항목별로 기억해 뒤로 가기에 반대로 재생하는데, 돌아온 상세가 원래 id로 그려지면 기억한 규칙과 맞지 않아 격자 칸에서 zoom이 열렸다. 그래서 떠날 때 기록 항목(`history.state`)에 표시하고, 돌아온 상세는 같은 drill id로 그린 뒤 전환이 끝나면 원래 id로 되돌린다(`features/feed/lib/bunchDrillId.ts`). 다음 뒤로 가기는 다시 격자 칸으로 접히는 zoom이다. Chromium 개발 서버(앱 폭 390px)에서 격자 → 상세 zoom, 번치 이름 → 번치 drill(약 0.3초), 뒤로 가기 drill 반대(약 0.3초), 다시 뒤로 가기 zoom 접힘(약 0.5초)을 프레임으로 확인했다. 실기기와 네이티브 스와이프 뒤로 가기는 확인하지 않았다. 남은 제약: 번치 화면을 받는 동안 상세를 다시 누르면 id가 되돌아가 전환 없이 바뀌고, 캐시가 없어 상세가 받는 중 화면으로 먼저 그려지면 돌아올 때 id가 늦게 바뀌어 zoom이 열릴 수 있다(확인 안 함). 작성 중인 번들 → 번들 작성 화면은 번들 만들기를 이어서 하는 흐름이라 번치 탭 + → 번들 만들기와 같은 `sheet`다. 가짜 서버 개발 서버(Chromium 390px)에서 격자 칸(128x172) ↔ 상세 첫 사진 자리 hero와 작성 화면이 아래(799px)에서 올라오고 내려가는 것을 프레임으로 확인했다. zoom으로 바꾼 뒤 실서버 개발 화면(다른 번치 프로필 격자) 녹화로 칸이 상세 전체로 열리고 돌아갈 때 칸 자리로 접히는 것을 확인했다. 비어 있던 정의라 디자이너에게 공유한다. 처음에는 격자 칸 링크가 넘친 곳을 자르지 않아, SSGOI hero가 칸이 아니라 `object-cover`로 넘친 사진 전체를 날리고 모서리 반경도 읽지 못했다(SSGOI는 스스로 `overflow`를 자르는 요소만 틀·반경으로 봄). 칸 링크에 `overflow: hidden`을 둬 칸 틀(반경 0) → 상세 첫 사진 틀(반경 24px)로 자르며 이어진다. 사진은 링크 안에서 한 번 감싼다. 바로 아래 자식이 사진이면 SSGOI가 사진으로 보고 날아가는 사본을 그 칸 옆에 넣어, 칸(`li`)·링크에 잘려 돌아갈 때 날아가는 모습이 보이지 않았다(사용자 녹화·Playwright 녹화로 확인). 그래서 칸(`li`)은 자르지 않고 사진 자르기는 링크가 맡는다. 또 SSGOI hero(`fade`)는 들어오는 화면을 통째로가 아니라 공유 요소로 가는 길에 있지 않은 요소마다 따로 흐리게 하는데, 투명도는 쌓임 맥락을 만들어 배경 영역 안의 프로필 이미지(`z-index` 10)가 전환 동안 흰 시트 아래로 깔렸다가 끝나면 올라왔다(사용자 제보, 녹화로 확인). 프로필 이미지를 배경 영역 밖 형제로 옮겨 전환 중에도 시트 위에 있다(번치 홈·다른 번치 프로필)(로그인된 개발 화면에서 착지 때 보이는 자리 358x445·top 212와 상세 사진 212·358x448 일치, 반경 0 → 24px 확인). 상세를 받는 동안 칸 데이터로 먼저 그리는 화면은 위치·날짜 두 줄 자리를 잡는다. 칸 데이터에 위치·날짜가 없어 한 줄만 잡으면, 위치가 있는 번들은 다 받은 뒤 사진이 한 줄(27px) 밀려 hero 착지 자리와 어긋났다. 위치·날짜가 없는 번들은 반대로 어긋나(사용자 녹화에서 착지 뒤 사진이 위로 튐), 실제 원인은 번치 탭이 격자 칸을 누를 때 번들 상세만 미리 받고 상세 화면이 함께 쓰는 번치 정보는 받지 않아 늘 미리 그린 화면을 거친 것이었다. 번치 정보도 함께 받아 400ms 안에 다 받은 화면으로 열린다(한때 기다림을 1초로 늘렸지만 누른 뒤 반응이 늦어 되돌림). 그래도 늦으면 미리 그린 화면을 거치므로 격자 응답에 위치·날짜를 넣어 달라고 백엔드에 요청한다. 상세에서 돌아와 격자를 다시 그릴 때 칸 사진이 회색으로 비었다가 나타나 착지 자리가 비어 보였다(녹화에서 약 300ms). 한 번 받은 표지는 다시 그릴 때 페이드 없이 바로 보인다.
- 사진함 → 사진 상세 (2026-11-15, 이슈 #400, 사용자 요청): 썸네일을 누르면 SSGOI `hero`(`type: 'fade'`)로 썸네일이 상세의 원본 비율 사진 자리로 커지고, 뒤로 가면 지금 보는 사진의 썸네일 자리로 돌아간다. Figma에 정의가 없다. 처음에는 두 방향 모두 `variant: 'smooth'`(spring, 약 0.3초에 90%)였는데, 들어갈 때 확대가 아니라 바뀌는 느낌이라는 의견으로 들어갈 때만 피드와 같은 550ms·`(0.3, 0, 0.15, 1)`로 바꿨다. 돌아갈 때는 `smooth` 그대로다. 썸네일은 정사각형이라 원본이 늦게 오면 도착 순간 틀이 툭 늘어났다(2026-11-20, 사용자 제보). 누르기 시작할 때 원본을 미리 받아 비율을 기억하고, 그래도 늦으면 틀 높이를 300ms·`(0.2, 0.9, 0.3, 1)`로 늘려 위아래가 서서히 드러나게 했다. 실기기 녹화(2026-11-22, #514)에서 착지 약 0.7초 뒤 원본 주소가 오는 순간 같은 img의 주소를 바꿔 약 50ms(2프레임) 흰 화면이 보였다. 원본은 보이지 않는 img로 따로 받고, 다 받으면 그 img를 그대로 썸네일 위로 200ms 페이드인하며 그때 틀 높이도 바꾼다(새 img를 만들면 다시 디코딩해 빈 칸이 생길 수 있어 주소 key 목록으로 DOM을 옮김). 들어오는 hero가 날아가는 동안에는 바꾸지 않고 전환이 끝난 뒤 바꾼다. SSGOI hero는 시작 때 짝과 형제만 숨겨, 비행 중 새로 보이는 층이 날아가는 사본과 겹치기 때문이다(리뷰에서 발견). 페이드 중 hero 짝은 불투명한 아래 썸네일에 두고, 썸네일은 페이드인이 끝나면 치운다(동작 줄이기면 페이드 없이 바로). 원본만 받지 못하면 보이던 썸네일을 그대로 둔다. 원본 크기를 API가 주면 처음부터 원본 비율로 착지할 수 있어 백엔드에 요청한다. 가짜 서버는 썸네일과 원본이 같은 파일이라 브라우저로는 재현하지 못했고 단위 테스트와 실기기 확인이 남았다.
  - 시작 멈춤: 전환이 시작된 직후 상세 화면을 처음 그리느라 화면이 잠깐 멈추고, SSGOI는 미리 계산한 곡선을 실제 경과 시간으로 재생해 멈춘 만큼 건너뛴다. iOS 시뮬레이터에서 개발 서버는 약 100ms 멈춰 첫 프레임에 31%, 배포 빌드는 약 50ms 멈춰 11% 커진 채 나타났다(550ms 곡선 기준). spring은 처음이 더 급해 건너뛰는 폭이 더 크다. 실기기 수치는 확인하지 않았다. 상세는 동적 route라 고정 id(`PHOTO_BOX_PATHS.transitionIds.detail`)를 규칙과 page DOM에 함께 쓴다.
  - 짝: 썸네일(`PhotoThumbnail`의 틀, `object-cover` 사진 하나)에 `data-hero-enter-key`, 상세에서 지금 보는 사진의 `img`에만 `data-hero-exit-key`를 붙인다(`photoHeroKey(photoId)`). 옆 슬라이드까지 키를 달면 그 사진도 썸네일 자리에서 함께 날아가 지금 보는 사진에만 단다. 선택 모드에서는 상세로 가지 않아 키를 달지 않는다. 사진은 SSGOI가 정사각형으로 잘린 썸네일과 원본 비율 사진 사이를 잘림 창까지 함께 바꿔 그린다.
  - 뒤로 가기: 썸네일을 제자리에서 움직여 뒤 칸이 위에 그려지므로, SSGOI 복사본이 붙어 있는 동안만 그 칸을 위로 올린다. 사진함은 피드처럼 떠날 때 스크롤을 붙잡고 돌아오면 history에 저장한 위치로 복원한다(`useHoldScrollOnLeave`·`useScrollInHistory`, 피드에서 `shared/hooks`로 옮김). 복원하지 않으면 맨 위에서 다시 그려져, 아래로 내려 연 사진의 hero가 화면 밖 칸으로 날아갔다. 상세에서 다른 사진으로 넘긴 뒤 돌아가면 그 사진의 썸네일로 날아가며, 그 칸이 보던 위치에서 화면 밖이면 화면 밖으로 날아간다(확인 안 함). 짝이 없는 경우(처리 중·불러오지 못한 사진)는 상세만 흐려진다. 멤버 필터는 화면 상태라 돌아오면 「전체」로 바뀌는데 스크롤은 필터를 건 목록 기준이라, 필터를 건 채 연 사진은 다른 위치로 복원될 수 있다(확인 안 함, 고치려면 필터도 history에 저장).
  - 상세 높이: 쉘에서는 사진함을 떠난 뒤 시스템 탭 바가 숨으며 아래 여백이 바뀌어, 그대로면 세로 가운데의 사진이 hero가 끝난 뒤 약 24pt 내려갔다(iOS 시뮬레이터 측정). 상세는 아래 여백 없이 화면 끝까지 그린다(`data-bottom-bleed`, `docs/architecture/mobile-shell.md`).
  - 미리 받기: 상세는 사진함 목록 캐시를 그대로 쓰고 원본은 썸네일을 먼저 보여 준 뒤 바꿔 그려, 피드처럼 기다리지 않는다. 다만 사진 링크가 `prefetch={false}`라 개발 서버에서는 누른 뒤 route를 받는 동안(약 0.8초) 전환이 늦게 시작했다. 배포 빌드에서의 지연은 확인하지 않았다.
  - 확인: Chromium(앱 폭 430px)에서 썸네일(143×143)이 상세 사진(430×573) 자리로 약 0.45초, 뒤로 가기는 반대로 약 0.5초에 움직이는 것과 돌아오는 사진이 다른 칸 위로 그려지는 것을 프레임·화면으로 확인했다. 493px 내려 연 사진에서 돌아오면 스크롤이 493px로 복원되고 사진이 원래 칸 자리로 돌아오는 것도 확인했다. iOS 시뮬레이터(iPhone 17 Pro)에서 hero 뒤 사진 위치가 바뀌지 않는 것(top 224 유지)을 측정과 녹화로 확인했다. 실기기, 동작 줄이기, 다른 사진으로 넘긴 뒤의 뒤로 가기는 확인하지 않았다.
- 번들 만들기 진입 (2026-11-06, 이슈 #230, 사용자 결정): 번치 홈 플로팅 「번들 만들기」 → 사진 선택 `/bunch/bundles/new`와 닫기는 SSGOI `sheet` 기본 프리셋이다(SSGOI 데모 YouTube의 Home → Create와 같은 `sheet()`). 모달처럼 아래에서 올라오고 닫으면 내려가며, 시간·곡선은 프리셋 기본(spring)이다. `sheet`는 움직이는 화면만 애니메이션 대상이라 뒤 화면을 같은 전환 영역에서 찾아 다른 전환처럼 `data-page-leaving`·`inert`를 붙인다(`guardSheet`). 그래서 상태 바 영역 색이 시트가 다 올라온 뒤가 아니라 전환 시작과 함께 바뀐다. 시트가 움직이는 동안은 화면에 `data-sheet-moving`을 붙여 `AppFrame`의 색 전환을 150ms 대신 300ms ease-in-out으로 늘려, 시트가 위에 닿는 시점에 색이 다 바뀐다(Chromium에서 시트가 47px 남았을 때 흰색 도달, 약 0.31초). 하단 탭 막대는 전환 대상 밖이라 열 때는 이동과 함께 바로 사라진다. 닫을 때는 막대가 내려가는 시트 위로 바로 튀어나와 어색해(2026-11-22, #514, 사용자 제보), 시트가 움직이는 동안(`data-sheet-moving`) 웹 막대를 시트 아래 층(`z-index` 0, 시트는 2)으로 내려 시트가 막대를 덮었다가 내려가며 드러낸다. iOS 시스템 탭 바는 웹 위에 그려져 덮을 수 없어, 다시 보일 때는 탭 바 자리(화면 아래 15%)를 덮던 것이 비켜난 뒤에 표시를 보낸다(`NativeTabBarVisibility`, 최대 1초). 덮는 것으로 보는 요소는 움직이는 화면 sheet(`data-sheet-moving`), 전환 중 나가는 화면(`data-page-leaving`, 상세에서 뒤로 가기 등), 닫히는 중인 바텀시트·대화상자(`data-ending-style`)이고, 그 자리의 20% 넘게 덮으면 기다린다. 처음에는 시트는 완전히 멈출 때까지 기다려 늦게 떴고, 바텀시트·뒤로 가기는 바로 떠서 아직 내려가거나 나가는 화면 위로 탭 바가 튀어나왔다(2026-11-23 사용자 제보). 위치로 판단해 스프링 끝을 기다리지 않는다. 테스트(happy-dom)는 위치를 흉내 내 확인했고 실기기는 확인 전. 로그인된 개발 화면(Chromium 390px)에서 수정 전에는 막대가 첫 프레임부터 시트 위에 있고, 수정 뒤에는 시트가 지나간 자리에서 드러나는 것을 녹화로 확인했다. 실기기는 확인 전. Chromium(앱 폭 430px)에서 열 때 화면 위치가 547→0px로 약 300ms에 대부분 올라오고 약 0.7초에 멈추며, 닫을 때 반대로 내려가는 것을 확인했다. 실기기와 동작 줄이기는 확인하지 않았다. 2026-11-21(#492, 사용자 요청): 시트가 오기 전에 상태 바가 먼저 흰색이 돼 어색해, 올라오는 동안은 뒤 화면 배경 표식을 시트에 잠시 옮겨 상태 바를 번치 색으로 두고, 시트 위에 상태 바 높이의 흰 띠(`box-shadow`)를 붙여 시트가 상태 바를 덮으며 흰색이 되게 했다. 도착 뒤 배경을 흰색으로 바꾸고 띠는 200ms 더 둔다. 닫을 때는 띠가 내려가며 번치 색을 드러낸다. 다음 전환이 이어지면 이전 전환의 띠 걷기 타이머는 취소한다. 상태 바 아이콘은 쉘이 어두운 색으로 고정해(`StatusBar style="dark"`) 흰 띠 위 대비가 유지된다(번치 색 위 대비는 수치 미검증).

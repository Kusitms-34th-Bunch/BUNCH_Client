# 기능: 로그인·가입 (기능명세서 1장)

> Status: Draft
> Date: 2026-10-17

기능명세서(시트 「로그인온보딩」)의 **1장 로그인**(1.1 앱 실행, 1.2 Entry, 1.3 약관 동의, 1.4 프로필 설정, 1.5 초대 맥락 유지)을 구현 범위로 정리한 문서다. 2장 온보딩(번치 시작 선택·번치 만들기·초대 참여)은 다음 범위이고, 이 문서는 그쪽으로 넘기는 경계만 정한다. 기능 ID(AUTH·USER)와 명세서 절 번호(1.2.5 등)로 원본과 대조한다. 플랫폼·로그인 방식의 전제는 `docs/specs/bunch-prd.md` 8장이 정본이다.

이 spec은 web·mobile-shell·bridge에 걸치고 구현 위치가 아직 확정되지 않아 `docs/specs/`에 둔다. 도메인이 확정되어 `apps/web/src/features/<feature>/` 위치가 정해지면 해당 위치로 옮기거나 링크를 남긴다.

## 목적

앱을 처음 연 사람이 소셜 계정 하나로 가입하고(약관 → 프로필), 기존 회원은 같은 화면에서 로그인해 서비스에 들어가게 한다. 회원가입과 로그인을 사용자에게 나눠 보여주지 않는다.

## 문제 정의

- 지금은 로그인·가입 화면, 소셜 로그인 연동, 가입 상태에 따른 진입 분기가 없다. `apps/web`에는 쿠키를 읽는 `createAuthorizedRoute`와 `api/session`(토큰 존재 확인)만 있고, 로그인으로 쿠키를 만드는 경로가 없다.
- 소셜 로그인은 네이티브 SDK로만 할 수 있다(웹 리다이렉트를 쓰지 않기로 확정, PRD 8장). 현재 `packages/bridge`에는 `share` 하나뿐이라 ID 토큰을 웹으로 가져올 수단이 없다.
- 번치 생성·초대 참여는 가입을 마친 사용자만 쓸 수 있어서, 이 범위가 서비스의 첫 진입 조건이다.

## 범위 외 항목

- 2장 온보딩(번치 시작 선택 2.1, 새 번치 만들기 2.2–2.4, 초대 링크 입력·확인·참여 2.5–2.6, 웹 초대장과 앱의 초대 링크 열기 2.7). 이 문서는 도착지 규칙(1.2.8)의 계약만 정하고 그 화면은 만들지 않는다.
- 번치 홈, 번치 전환, 마지막 사용 번치 복원의 구현(BUNCH 범위). 도착지가 그 화면일 때는 임시 도착지로 둔다.
- 회원 탈퇴, Apple 연결 해제, 로그아웃 화면(명세에서 별도 정의).
- 이메일·비밀번호 로그인, 마케팅 수신 동의, 위치 권한 요청, 소셜 계정 병합·연결(모두 하지 않기로 확정).
- Android·모바일 웹 브라우저에서의 사용.

## 대상 사용자와 접근 권한

계정 상태 세 가지가 접근 조건이다. 상태는 서버 응답이 정하며, 앱의 저장 값만으로 판단하지 않는다.

| 상태      | 의미                           | 이용 가능                        |
| --------- | ------------------------------ | -------------------------------- |
| 비로그인  | 세션이 없거나 유지할 수 없음   | Entry                            |
| 가입 중   | 계정은 있으나 약관·프로필 미완 | 약관·프로필 등 가입 절차만       |
| 가입 완료 | 약관 동의와 프로필 저장을 마침 | 전체 서비스(번치 생성·참여 포함) |

## 사용자 흐름과 route

모든 화면은 `apps/web`의 route이고 WebView에 표시된다(`docs/architecture/mobile-shell.md`). 아래 path는 **제안**이며 구현 전에 확정한다.

| 화면(명세 절)          | path(제안)               | 접근 조건                                 | 진입·이탈                                                             |
| ---------------------- | ------------------------ | ----------------------------------------- | --------------------------------------------------------------------- |
| 앱 실행·스플래시 (1.1) | 쉘 + `/` 진입 판단       | 모두                                      | 도착지가 정해질 때까지 스플래시 유지, 결과로 아래 화면 중 하나로 이동 |
| Entry (1.2)            | `/login`                 | 비로그인만. 로그인 상태면 상태별 화면으로 | 소셜 로그인 성공 → 결과 분기(1.2.7)                                   |
| 약관 동의 (1.3)        | `/signup/terms`          | 가입 중                                   | 동의 완료 → 권한 요청 → 프로필. 뒤로가기 → Entry(로그인 해제)         |
| 약관 원문 (1.3.2)      | `/signup/terms/[termId]` | 가입 중                                   | 앱 안에서 연다. 닫으면 체크 상태 유지                                 |
| 프로필 설정 (1.4)      | `/signup/profile`        | 가입 중이며 약관 동의 완료                | 가입 완료 → 도착지(1.2.8)                                             |

- 접근 제어는 서버(layout·route 경계)에서 세션을 확인해 redirect한다. 브라우저 저장 값만으로 통과시키지 않는다(`docs/architecture/routing-and-access.md`).
- 결과 분기(1.2.7): 처음 온 사람 → 약관, 약관 미동의 가입 중 → 약관, 약관 동의한 가입 중 → 프로필, 가입 완료 → 도착지.
- 도착지(1.2.8)는 위에서부터 처음 맞는 하나다: 보관한 초대 정보 → 마지막 사용 번치 홈 → 가장 최근 번치 홈 → 번치 시작 선택(2.1.1). 이 범위에서는 이 판단의 **입력과 출력 계약**만 정하고, 도착 화면은 BUNCH·온보딩 범위에서 만든다.
- 앱 실행 시 세션 확인은 서버 한 번 호출로 가입 상태, 약관 동의 여부, 마지막 번치 유효 여부, 소속 번치 여부를 받아 진입 화면을 정한다(1.1.1).

## 요구사항

### 필수 (Must Have)

앱 실행·세션 (1.1.1, AUTH-03)

- [ ] 앱 실행 시 세션을 확인하고, 도착지가 정해질 때까지 스플래시를 유지해 빈 화면이 보이지 않는다.
- [ ] 세션이 없거나 유지할 수 없으면 Entry로 간다. 탈퇴·이용 정지 계정의 세션은 해제하고 Entry로 간다.
- [ ] 한 계정으로 여러 기기에서 동시에 로그인할 수 있다.
- [ ] 세션 확인이 실패하거나 10초 넘게 응답이 없으면 「일시적인 오류가 발생했어요. 다시 시도해 주세요」를 보여준다.

Entry와 소셜 로그인 (1.2.1~1.2.6, AUTH-01·02·06)

- [ ] 버튼 3개를 카카오 → Google → Apple 순서로 두고, 이메일 입력란과 회원가입 버튼은 두지 않는다. 버튼은 Figma 「Login Button - Brand」·「Login Button - Status」(Default·Pressed·Disabled)를 따른다.
- [ ] 버튼 하나를 누르면 그 버튼은 로딩, 나머지 둘은 Disabled가 되어 동시에 두 로그인이 진행되지 않는다. 연타는 첫 탭만 처리한다.
- [ ] 카카오·Google·Apple 공식 SDK로 로그인하고 ID 토큰을 받아 서버에 보낸다. 웹 브라우저로 나갔다 오는 방식은 쓰지 않는다.
- [ ] 카카오는 카카오톡 앱 로그인을 우선하고 불가하면 카카오 계정 로그인을 쓴다. 회원 식별자만 요청하고 닉네임·프로필 사진·이메일은 요청하지 않는다.
- [ ] Apple은 이메일·이름을 식별값이나 필수 정보로 쓰지 않는다. 계정은 (제공자, 제공자 고유 ID)로만 구분한다.
- [ ] 서버가 ID 토큰을 검증해 계정을 조회하거나 만든다. 신규 계정은 '가입 중'이고 소셜 닉네임·사진은 가져오지 않는다. 연속 요청으로 계정이 중복되지 않는다.
- [ ] 취소·실패하면 Entry로 돌아오고 「로그인에 실패했어요. 다시 시도해 주세요」를 보여준다. 버튼은 Default로 돌아오고 보관한 초대 정보는 유지한다. 소셜 인증 전에 실패하면 계정을 만들지 않는다.
- [ ] 소셜 종류가 다르면 별도 계정으로 처리하고 자동 병합하지 않는다. 탈퇴한 사용자가 같은 소셜로 다시 로그인하면 새 계정으로 가입한다.

약관 동의 (1.3, AUTH-04·NOTI-03·PHOTO-09)

- [ ] 필수 약관 3개(서비스 이용 약관, 개인정보 수집·이용 동의, 만 14세 이상 확인)와 전체 동의 버튼을 둔다. 전체 동의는 모두 체크하고, 이미 모두 체크된 상태에서 누르면 모두 해제한다. 개별 체크와 전체 동의는 서로 동기화된다.
- [ ] 3개를 모두 체크해야 하단 버튼이 활성화된다. 마케팅 수신 동의는 받지 않는다.
- [ ] 약관 원문은 앱 안 화면에서 연다(외부 브라우저 금지). 원문을 열지 않아도 체크할 수 있고, 닫아도 체크 상태가 유지된다. 항상 최신 적용 버전을 보여준다.
- [ ] 앱 접근 권한 안내(사진·카메라·알림은 선택, 위치는 요청하지 않음)를 누를 수 없는 정보 영역으로 보여준다.
- [ ] 동의를 완료하면 항목별 약관 버전과 동의 일시를 저장한다. 저장에 성공하면 사진 → 카메라 → 알림 순서로 권한을 요청하고, 허용 여부와 관계없이 프로필로 간다. 이미 허용·거부한 권한은 다시 요청하지 않는다.
- [ ] 저장에 실패하면 「일시적인 오류가 발생했어요. 다시 시도해 주세요」, 체크 상태 유지, 연타는 첫 탭만 처리한다.
- [ ] 권한 팝업 중 앱이 종료되면 다음 실행에서 프로필부터 시작한다.
- [ ] 이미 약관에 동의한 가입 중 사용자는 이 화면을 건너뛴다.

프로필 설정과 가입 완료 (1.4, USER-01·02)

- [ ] 닉네임(필수)과 프로필 사진·출생연도·성별(선택)을 입력한다. 입력값은 가입 완료 전까지 임시로 유지하고 완료 시 저장한다. 앱이 종료되면 입력값은 남기지 않는다.
- [ ] 닉네임은 1~12자이고 앞뒤 공백은 저장 시 지운다. 특수문자·이모지·줄바꿈은 쓸 수 없고 붙여넣을 때 허용되지 않는 문자만 제외한다. 글자 수 「n/12」를 갱신하고, 한글 조합 중에는 글자 수로 입력을 끊지 않는다. 저장 전에 NFC로 정규화한다.
- [ ] 입력을 멈추고 0.5초 뒤 서버에 중복을 확인한다. 영문 대소문자는 다른 글자로 보고 공백도 비교에 포함한다. 사용 중이거나 확인 중이면 가입 완료 버튼을 비활성화한다. 확인 실패 시 토스트를 보이고 버튼을 비활성화한다.
- [ ] 가입 완료 시 닉네임의 길이·문자·중복을 서버가 다시 확인한다. 그 사이 같은 닉네임이 생겼다면 가입을 완료하지 않고 「이미 사용 중인 닉네임이에요.」를 보여준다.
- [ ] 프로필 사진은 선택이다. 「앨범에서 사진 선택 / 기본 이미지 적용 / 취소」 선택지, 1:1 편집(원형 가이드, 확대·이동), 허용 형식 JPEG·PNG·HEIC·WebP. 저장 시 선택 영역을 1:1로 저장하고 위치 등 메타데이터를 제외한다. 사진 저장에 실패해도 기본 이미지로 가입을 완료한다.
- [ ] 사진 접근 권한이 거부된 상태에서 앨범을 열면 「권한 설정이 필요해요」 모달을 보이고 「취소」/「설정 열기」를 준다. 지원하지 않는 형식·손상된 사진은 「이 사진은 사용할 수 없어요」 토스트를 보이고 기본 이미지를 유지한다.
- [ ] 출생연도는 숫자 키보드로 4자리를 직접 입력한다(선택). 입력 가능한 범위는 1930년부터 (현재 연도 − 14)년까지이고, 연도가 바뀌면 최대값이 따라 바뀐다(2026년 2012, 2027년 2013). 성별은 「여성」·「남성」 중 하나이고 다시 누르면 해제된다. 출생연도·성별이 다른 사용자에게 공개되지 않는다는 문구를 성별 아래에 둔다.
- [ ] 「BUNCH 시작하기」는 닉네임이 규칙에 맞고 중복이 아닐 때만 활성화된다. 가입 완료 시 가입 완료 시각을 기록하고 상태를 '가입 완료'로 바꾼다.
- [ ] 프로필 저장에 실패하면 토스트를 보이고 입력값을 유지하며 버튼을 원래 상태로 복구한다.
- [ ] 가입을 마치면 보관한 초대 정보가 있으면 초대 참여(2.7.2), 없으면 번치 시작 선택(2.1.1)으로 간다(그 화면은 범위 외).

초대 맥락 (1.5.1, AUTH-05)

- [ ] 초대 정보는 최대 24시간 보관하고, 가장 최근 것만 유지한다. 로그인 취소·실패에도 유지한다. 로그아웃하면 삭제한다.
- [ ] 로그인 때 ID 토큰과 함께 서버에 보낸다. 참여 처리 자체는 하지 않는다(범위 외 2.6.3).

### 있으면 좋은 것 (Nice to Have)

- [ ] 로그인 시도가 비정상적으로 많으면 제한한다(기준은 별도 협의).
- [ ] 앱 설치 직후 초대 정보를 이어받는 Deferred Deep Link(2.7.1, 구현 가능할 때).

## 상태

- 로딩: 스플래시(세션 확인 중), 선택한 소셜 버튼 로딩과 나머지 Disabled, 닉네임 중복 확인 중(가입 버튼 비활성), 가입 완료 요청 중(버튼 로딩), 약관 원문 로딩.
- 빈 상태: 프로필 사진 없음 → 기본 이미지. 출생연도·성별 없음 → 빈 값으로 저장.
- 오류: 세션 확인 실패·지연, 로그인 취소·실패, 약관 저장 실패, 중복 확인 실패, 닉네임 중복·초과·허용 문자, 사진 형식·권한 오류, 프로필 저장 실패. 문구는 명세 원문을 그대로 쓴다.
- 성공: 로그인 성공 후 결과 분기, 약관 저장 후 권한 요청과 프로필 이동, 가입 완료 후 도착지 이동.
- 접근성: 소셜 버튼·체크 행·닉네임 오류 문구를 스크린 리더로 읽을 수 있어야 하고, 터치 대상은 `docs/architecture/web-interface-guidelines.md` 기준을 따른다. 키보드 표시 중 하단 버튼 위치는 실기기로 확인한다.

## API 계약

백엔드 명세가 아직 없다. 아래는 화면이 필요로 하는 동작 목록이며 method·path·필드는 **확인할 항목**이다. 확정되면 `.agents/templates/api-contract-map.md`로 정리하고 `assess-api-contract`로 넘긴다.

| 동작                   | 입력                                           | 출력                                                             | 사용 화면    |
| ---------------------- | ---------------------------------------------- | ---------------------------------------------------------------- | ------------ |
| 세션 확인              | 쿠키                                           | 가입 상태, 약관 동의 여부, 마지막 번치 유효 여부, 소속 번치 여부 | 1.1, 1.2.8   |
| 소셜 로그인            | 소셜 종류, ID 토큰, nonce, 초대 정보(선택)     | 로그인 결과(세션 설정), 가입 상태, 약관 동의 여부                | 1.2.2~1.2.5  |
| 약관 목록·원문·버전    | -                                              | 약관별 식별자·버전·원문(또는 원문 경로)                          | 1.3.1, 1.3.2 |
| 약관 동의 저장         | 항목별 약관 버전                               | 저장 결과                                                        | 1.3.4        |
| 닉네임 중복 확인       | 닉네임                                         | 사용 가능 여부                                                   | 1.4.4        |
| 프로필 저장(가입 완료) | 닉네임, 사진(선택), 출생연도(선택), 성별(선택) | 가입 완료 결과                                                   | 1.4.7        |
| 로그아웃               | 쿠키                                           | 세션 해제                                                        | 1.3.5        |

- 인증과 인가: 현재 `apps/web`은 httpOnly `accessToken` 쿠키를 BFF(`createAuthorizedRoute`)가 읽는다. 로그인 요청은 토큰이 없는 상태에서 호출되므로 이 wrapper를 그대로 쓸 수 없다. 로그인·세션 생성용 public route의 형태가 필요하다(확인할 항목).
- 가입 중 사용자의 접근 제한(번치 생성·참여 등)은 서버가 요청마다 확인한다(1.2.7).
- 실패 시 오류 코드와 정확한 문구: 서버가 주는 코드를 확인한 뒤 채운다. 화면 문구는 위 "상태"에 적은 명세 원문을 쓴다.
- Query key 후보: `auth.session`, `terms.list`·`terms.detail(termId)`, `nickname.check(nickname)`. 닉네임 중복은 입력에 따라 응답이 달라지므로 nickname을 key에 포함한다. 로그인·약관 저장·프로필 저장은 mutation이고, 성공 뒤 `auth.session`을 invalidate한 뒤 이동한다(이동 목적지의 guard가 session을 읽으므로 `await`한다).

## Bridge 계약(제안)

`packages/bridge`에 추가가 필요한 메서드다. 시그니처와 zod schema는 구현 단위에서 확정한다. 네이티브 구현은 `apps/mobile-shell`이 맡고, 웹은 호출만 한다.

| 메서드(제안)          | 입력                                 | 출력                                | 쓰는 곳 |
| --------------------- | ------------------------------------ | ----------------------------------- | ------- |
| `socialLogin`         | 소셜 종류(kakao·google·apple)        | ID 토큰, nonce(또는 오류·취소 구분) | 1.2.2~4 |
| `requestPermission`   | 권한 종류(photo·camera·notification) | 허용·거부·이미 결정됨               | 1.3.4   |
| `getPermissionStatus` | 권한 종류                            | 현재 상태                           | 1.4.2   |
| `openAppSettings`     | -                                    | -                                   | 1.4.2   |

- 초대 정보 보관 위치(앱 저장소 / WebView 저장소)와 이를 읽는 bridge는 확인할 항목이다(1.5.1). 명세는 "앱이 보관"이라고 하지만 WKWebView 저장소가 지워질 수 있는지 확인이 필요하다.
- 앨범 선택과 1:1 편집을 웹(`<input type="file">` + 편집 UI)으로 할지 네이티브 picker로 할지는 확인할 항목이다. HEIC 처리와 EXIF 제거 위치가 걸린다.

## 영향받는 컴포넌트

이 범위에 필요한 UI다. 이미 있는 것만 재사용하고, 없는 것은 해당 단위 전에 만든다(미확정 공용화는 선반영하지 않는다).

### 화면(페이지) 작업 분할

위 표의 Entry·약관·프로필 세 단위를 화면 UI부터 구현하는 이슈 후보다. 인증 BFF·bridge·쉘 네이티브가 없어도 시작할 수 있도록, 서버·네이티브 동작은 호출 지점(prop·hook 경계)만 두고 목 데이터로 화면을 완성한다. 접근 제어(redirect)·실제 로그인·약관 저장·중복 확인·사진 선택은 선행 단위가 끝난 뒤 연결한다. 권한 요청 팝업(Figma `Alert`)은 iOS 시스템 UI라 웹에서 만들지 않는다.

## 완료 기준

- [ ] 비로그인 사용자가 소셜 로그인으로 약관 → 프로필 → 도착지까지 이어진다.
- [ ] 가입 중에 앱을 닫았다 열면 멈춘 단계(약관 또는 프로필)에서 이어진다.
- [ ] 가입을 마친 기존 회원이 로그인하면 도착지 규칙(1.2.8)으로 간다. 도착 화면은 임시여도 이동 조건이 맞다.
- [ ] 로그인 취소·실패, 중복 닉네임, 저장 실패, 권한 거부에서 명세의 문구와 상태 복귀가 맞다.
- [ ] 가입 중 사용자가 가입 완료 후에만 쓸 수 있는 화면에 직접 URL로 들어가도 서버가 막고 미완료 단계로 보낸다.
- [ ] 세션이 없을 때 보호된 route에 직접 진입하면 Entry로 간다. 새로고침·브라우저 뒤로가기에서도 상태가 일관된다.
- [ ] 관련 단위 테스트·컴포넌트 테스트와 E2E가 통과하고, iOS 실기기에서 SDK 로그인·권한 팝업·키보드·Safe Area를 확인한다.
- [ ] 구현이 이 spec과 일치하는지 `verify-spec-sync`로 확인한다.

## 확인할 항목

기획·디자인·백엔드·기술로 나눈다. 구현으로 채우지 않는다. 명세서 안에서 서로 충돌하는 곳은 앞쪽에 둔다.

### 기획 (명세서 안의 충돌·빈칸)

1. 프로필 화면 뒤로가기와 약관 건너뛰기가 충돌한다. 1.4.1은 뒤로가기를 누르면 약관 화면으로 가라고 하는데, 1.3.1은 이미 약관에 동의한 가입 중 사용자는 약관 화면을 건너뛰고 프로필로 간다. 뒤로가기를 눌러도 다시 프로필로 돌아와 루프가 된다.
2. 닉네임이 12자를 넘을 때가 두 가지로 적혀 있다. 1.4.3의 3번은 12자에서 더 입력되지 않는다고 하고, 4번은 붙여넣기로 넘으면 「입력 가능한 글자수를 초과했어요」를 보이고 버튼을 비활성화한다고 한다. 번치 이름(2.2.2)은 앞 12자만 넣는다.
3. 닉네임에 공백을 쓸 수 있는지 불명확하다. 1.4.3 상세 동작의 허용 문자에는 공백이 없는데, 같은 절 로직과 1.4.4 예시(「번치 클럽」)는 공백을 허용한다.
4. 소셜 로그인 창을 닫은 경우에도 실패 토스트를 보이는지 확인이 필요하다. 1.2.6의 1번은 취소도 실패 안내 토스트를 띄운다고 하고, 1.2.1은 창을 닫으면 버튼만 Default로 되돌린다고 한다.
5. 세션 확인이 10초 넘게 걸리거나 실패한 뒤의 화면(1.1.1)이 정해지지 않았다. 토스트만 있고, 스플래시에 머무는지·재시도 UI가 있는지·Entry로 가는지 없다.
6. 약관 화면의 하단 버튼 이름이 다르다. 1.3.1은 「동의 완료」, 1.3.4는 「시작하기」다.
7. 문구 확정이 필요하다. 1.4.7의 프로필 저장 실패 문구는 따옴표가 닫혀 있지 않다(「…다시 시도해 주세요 를). 1.3.3의 알림 설명에 띄어쓰기가 없다(「새로운활동·주요소식」).
8. 가입 중 상태로 30일 넘게 방치된 계정의 처리 정책(1.2.5).
9. (Figma 화면 설계서 `796:9226`과 이 문서의 충돌, 화면 구현 전에 정한다)
   - 출생연도 (확정, 사용자 결정): 범위는 1930년 ~ (현재 연도 − 14)년, 입력은 숫자 키보드 직접 입력. 설계서의 "선택 안함이 항상 상단"은 목록 방식 문구라 직접 입력에는 해당하지 않는다(미입력이 곧 선택 안 함).
   - 닉네임 오류 문구 (확정, 사용자 결정): Figma 설계서 문구를 쓴다. 「이미 사용 중인 닉네임이에요.」·「특수문자를 제외한 영문, 한글만 사용할 수 있어요.」 다만 설계서는 허용 문자에 숫자를 넣으면서 오류 문구에는 숫자가 없어, 이 문구가 숫자를 막는다는 뜻은 아니다. 문구 보완 여부는 디자인 확인 대상이다.
   - 성별 다시 누르기 (확정, 사용자 결정): 선택한 항목을 다시 누르면 해제된다. 설계서에는 이 규칙이 없다.
   - 프로필 작성 뒤 도착지 (확정, 사용자 결정): 보관한 초대 정보가 있으면 초대 참여, 없으면 번치 시작 선택(2.1.1, 현재 `/onboarding`)이다. 설계서의 「새번치 만들기」 경로 표기는 따르지 않는다.
10. (다음 범위) 번치 이름 2.2.2는 숫자를 쓸 수 있다고 하면서 오류 문구는 「특수문자와 숫자를 제외한 영문, 한글만…」이라고 한다. 온보딩 범위에서 정한다.

### 디자인

1. Entry 화면의 로고·소개 문구·일러스트 구성(1.2.1).
2. 닉네임·출생연도 placeholder, 프로필 사진 바텀시트와 편집 화면의 문구(1.4.1~1.4.5).
3. 약관 원문 화면이 별도 디자인인지(1.3.2).
4. 스플래시와 첫 화면 사이의 전환, 소셜 버튼 로딩 모양.

### 백엔드

1. 6개 동작의 method·path·필드·오류 코드(위 "API 계약"). 명세 문서가 없다.
2. ID 토큰 검증의 nonce를 서버가 발급하는지 앱이 만드는지, Apple의 인증 코드를 함께 받는지.
3. 로그인 성공 후 쿠키를 BFF가 설정하는지 백엔드가 설정하는지, access·refresh 만료와 갱신 정책. 로그인 route는 토큰이 없는 상태에서 호출된다.
4. 약관 원문을 API로 주는지 앱 안 정적 문서인지, 약관 버전 변경 시 재동의 정책.
5. 프로필 사진 업로드 방식과 EXIF 제거를 앱이 할지 서버가 할지(1.4.2는 저장 시 제외한다고만 적었다).
6. 닉네임 중복 확인의 호출 제한.

### 기술·환경

1. 앱 식별자(bundle identifier)와 카카오·Google·Apple 앱 등록 정보가 없다. 쉘 네이티브 구현의 선행 조건이다.
2. 앱을 껐다 켜도 WKWebView의 쿠키·저장소가 유지되는지(PRD 10장 3번, 쉘 연결 전 쿠키 유지 설계).
3. 권한 팝업을 사진 → 카메라 → 알림 순서로 띄울 때 WebView 화면과의 전환, 거부 후 재요청 불가에 대한 처리(`docs/architecture/mobile-shell.md`).
4. 웹에서 HEIC를 어떻게 다룰지, 1:1 편집 UI를 웹으로 만들지 네이티브 picker로 할지.
5. 초대 정보 보관 위치(앱 저장소 / WebView 저장소)와 24시간 만료 처리.

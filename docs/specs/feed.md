# 기능: 피드·번들 상세 (기능명세서 6장)

> Status: Draft
> Date: 2026-11-04(기능명세서 1107 수정본 반영 2026-11-07, 1110판 반영 2026-11-10)

기능명세서의 **6장 피드**를 구현 범위로 정리한 문서다. 6장은 세 부분으로 나뉜다.

- 6.1 피드 탭: 화면 구성, 헤더, 번들 카드, 구간·끝 안내, 광고 카드, 광고 숨기기, 소속 번치 없음
- 6.2 번들 상세: 화면 구성, 번치 정보·참여 멤버, 제목·위치·날짜, 사진·픽, 멤버별 코멘트, 좋아요·댓글 수, 댓글, 더보기, 수정·삭제·신고, 공개 범위 수정
- 6.3 번들 상세 시트: 장소 콕하기, 참여 멤버, 멤버 프로필

기능 ID(FEED·BUNDLE·NOTI·DRAFT)와 명세서 절 번호(6.2.8 등)로 원본과 대조한다. 번들 만들기·공동 편집은 `docs/specs/bundle-create.md`, 번치 메인·다른 번치 프로필·팔로우·알림은 `docs/specs/bunch-home.md`가 맡는다.

번들 상세는 피드 말고도 번치 메인 「번들」 탭, 다른 번치 프로필, 알림에서 들어오므로 이 spec은 `docs/specs/`에 둔다. 구현을 시작하면 화면 spec은 각 feature 폴더에 둔다. 피드 탭은 `apps/web/src/features/feed`(fixture)에 있고, 나머지 화면은 아직 구현하지 않았다.

## 목적

- 다른 번치들이 발행한 번들을 둘러본다. 팔로우한 번치를 먼저, 다 보면 공개 번치를 이어서 보여 준다.
- 발행된 번들 하나를 자세히 본다. 사진, 멤버별 코멘트, 좋아요·댓글을 한곳에서 본다.
- 번치 단위로 반응한다(좋아요, 댓글, 신고, 장소 콕하기). 모두 현재 번치 명의다.
- 메인 관리자가 발행된 번들을 고치거나 지우고, 공개 범위를 바꾼다.

## 문제 정의

- 지금은 번들을 만들어도 다른 번치가 볼 곳이 없다. 번치 사이의 관계(팔로우)도 볼거리가 없으면 쓸 이유가 없다.
- 좋아요·댓글·신고·콕하기가 사람이 아니라 현재 번치 명의라서, 번치를 전환하면 피드 구성과 버튼 상태가 함께 바뀌어야 한다(6.1.1 로직 1~2).
- 노출 판단(차단, 공개 범위, 팔로우 승인)이 복잡하다. 화면이 거르지 않고 서버 판단을 그대로 따라야 어긋나지 않는다(6.1.1 로직 5).
- 1110판은 피드에 넣지 않는 번들에서 「현재 번치가 신고한 번들」을 뺐다(6.1.1 로직 4). 신고한 번들도 피드에 남는다. 1122판은 「운영자가 숨긴 번들」을 「운영자가 신고 검토 후 삭제한 번들」로 바꿨다(5.10.7 로직 2).
- 2026-11-21 변경: 피드에서 빼는 것은 현재 번치가 올린 번들뿐이고, 내가 속한 다른 번치의 공개 번들은 보인다(6.1.1 로직 6). 메뉴·좋아요·댓글은 현재 번치 명의 권한을 따르고 웹은 서버 목록·권한을 그대로 쓴다.

## 범위 외 항목

- 번들 만들기와 공동 편집(4장). 번들 수정(6.2.12)은 공동 편집 화면을 다시 쓰는 입구와 차이만 둔다.
- 다른 번치 프로필, 팔로우·팔로우 요청, 알림 목록(5장, `bunch-home.md`). 이 문서는 그 화면으로 가는 입구만 둔다.
- 콕한 장소 목록과 관리(콕 명세). 이 문서는 담는 동작만 둔다.
- 광고 내용 관리(서버에서 관리, 6.1.5 로직 1).
- 실시간 반영. 새 번들, 좋아요·댓글 수는 진입·앱 복귀·새로고침 때만 반영한다(6.1.1 로직 3, 6.2.1 로직 3).

## 대상 사용자와 접근 권한

가입을 마친 사람이면 소속 번치가 없어도 피드를 볼 수 있다. 가입 중인 사람은 서버가 거부한다(6.1.7 로직 1).

| 동작                                   | 소속 번치 없음    | 일반 멤버 | 공동 관리자 | 메인 관리자     |
| -------------------------------------- | ----------------- | --------- | ----------- | --------------- |
| 피드·번들 상세 보기                    | 가능(공개 구간만) | 가능      | 가능        | 가능            |
| 좋아요, 댓글·답글, 장소 콕하기·콕 취소 | 불가(안내 토스트) | 가능      | 가능        | 가능            |
| 댓글·번들 신고(다른 번치 번들)         | 불가(안내 토스트) | 가능      | 가능        | 가능            |
| 우리 번치 번들 신고                    | -                 | 가능      | 가능        | 불가(메뉴 없음) |
| 우리 번치 번들 수정·삭제·공개 범위     | -                 | 불가      | 불가        | 가능            |
| 내 댓글 삭제                           | -                 | 가능      | 가능        | 가능            |
| 남의 댓글 삭제                         | -                 | 불가      | 불가        | 불가            |
| 광고 숨기기(사용자 개인 단위)          | 가능              | 가능      | 가능        | 가능            |

- 소속 번치가 없을 때 번치 명의 행동을 누르면 실행하지 않고 「번치에 참여하면 할 수 있어요.」(6.1.7).
- 수정·삭제·신고 메뉴는 화면을 열 때의 역할로 정하고, 누를 때 서버가 다시 확인한다. 그사이 역할이 바뀌었으면 「권한이 변경되어 해당 기능을 이용할 수 없어요.」 후 화면을 새로 고친다(6.2.11).
- 차단 관계인 번치의 번들은 피드에 나오지 않고, 들어가면 차단된 번치 화면(5.10.6)이다. 좋아요도 누를 수 없다(6.2.6). 차단 관계인 번치의 댓글·답글과 좋아요는 목록과 수에서 뺀다(6.1.3 로직 5, 6.2.7 로직 6).
- 콕 취소는 현재 번치 멤버 누구나 할 수 있고, 다른 멤버가 콕한 장소도 취소할 수 있다(6.3.1 로직 1).

## 사용자 흐름과 route

path는 제안이다. 번들 상세는 여러 탭에서 들어오므로 탭 아래가 아니라 독립 경로로 두고, 하단 탭 막대 없이 연다(`(main)` 밖).

| 화면(명세 절)                | path(제안)                                                            | 진입·이탈                                                                                        |
| ---------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 피드 탭 (6.1)                | `/feed`(있음)                                                         | 하단 탭. 뒤로가기 없음. 다른 탭에 갔다 오면 스크롤 위치 유지                                     |
| 번들 상세 (6.2)              | `/bunches/[bunchId]/bundles/[bundleId]`                               | 피드 카드, 알림. 번치 메인 「번들」 탭·다른 번치 프로필은 후속. 뒤로가기는 들어온 화면으로       |
| 번들 상세 댓글로 바로 가기   | `/bunches/[bunchId]/bundles/[bundleId]?focus=comments`                | 카드·상세의 말풍선. 댓글 영역으로 스크롤하고 입력란 활성화                                       |
| 번들 상세 댓글 보기          | `/bunches/[bunchId]/bundles/[bundleId]?section=comments[&comment=ID]` | 댓글 알림. 댓글 영역(댓글 ID가 있으면 그 댓글)으로 스크롤만 하고 입력란 초점(키보드)은 주지 않음 |
| 번들 수정 (6.2.12)           | `/bunches/[bunchId]/bundles/[bundleId]/edit`(있음, API 연동 7번 #423) | 상세 더보기 「수정하기」(메인 관리자). 저장하면 상세로                                           |
| 번들 공개 범위 수정 (6.2.15) | `/bunches/[bunchId]/bundles/[bundleId]/visibility`(있음)              | 상세 더보기 「공개 범위 설정」(메인 관리자). 「수정하기」면 상세로                               |
| 장소 콕하기 시트 (6.3.1)     | 카드·상세 위 바텀시트                                                 | 위치 글자                                                                                        |
| 참여 멤버 시트 (6.3.2)       | 카드·상세 위 바텀시트                                                 | 참여 멤버 프로필 영역. 멤버 → 멤버 프로필                                                        |
| 멤버 프로필 (6.3.3)          | `/members/[memberId]`                                                 | 참여 멤버 시트. 번치 줄 → 그 번치 프로필(우리 번치면 번치 메인)                                  |
| 광고 외부 링크 (6.1.5)       | 앱 밖 브라우저                                                        | 광고 사진. 링크가 없으면 동작 없음                                                               |

- 번치를 전환하면 피드를 새 번치 기준으로 다시 불러오고 맨 위로 이동한다(6.1.1 로직 2).
- 피드 헤더 로고는 맨 위로 스크롤, 알림은 알림 목록(5.12.1), 현재 번치 이미지는 번치 메인(5.1.1)이다(6.1.2).

## 요구사항

### 필수 (Must Have)

피드 탭 (6.1, FEED-01)

- [x] 헤더(로고·알림·현재 번치 이미지)와 하단 탭 막대는 고정, 그 사이 목록만 스크롤. 맨 위에서 당기면 새로고침(#340, 공통 `PageShell`의 `onRefresh`, 모양은 `docs/architecture/motion.md`의 「당겨서 새로고침」).
- [ ] 알림 아이콘의 빨간 점은 현재 번치의 안 읽은 알림 기준이고 번치 메인 헤더와 같다. 화면 진입·앱 복귀 때 갱신. 남음: 점 모양이 Figma에 정해지면 번치 메인 헤더와 함께 붙인다(`FeedHeader.tsx`).
- [x] 번들 카드(6.1.3): 번치 이미지·이름, 발행 경과 시간, 대표 사진 한 장(좌우로 넘기지 않음, 첫 사진을 대표로 씀) 위에 어두운 배경과 제목·위치·날짜, 하트·좋아요 수, 말풍선·댓글 수, 참여 멤버 이미지 3개와 넘는 인원 「외 N명」(Figma 기준, 1110판 6.1.3도 같음).
- [x] 나간·탈퇴한 참여 멤버도 빼지 않고 기본 이미지로 보이며 「외 N명」에도 센다(6.1.3 로직 4). 「외 N명」을 눌러도 참여 멤버 시트.
- [x] 좋아요 수·댓글 수는 차단 관계인 번치의 것을 뺀다. 댓글 수는 원댓글·답글과 삭제된 것을 모두 센다(상세 댓글 수와 같은 기준, 6.1.3 로직 5~6). 서버가 보장하고 웹은 받은 값을 그대로 쓴다.
- [x] 경과 시간: 1분 미만 「방금 전」, 1시간 미만 「N분 전」, 24시간 미만 「N시간 전」, 1~7일 「N일 전」, 8일부터 「YYYY년 M월 D일」.
- [x] 위치가 2개 이상이면 「{첫 위치} 외 N곳」에 밑줄, 하나면 밑줄 없이 누를 수만 있다(`BundleInfo` `locationUnderline`). Figma `Bundle Info`(`3415:60928`)에는 「외 N곳」 예시만 있다. 위치나 날짜가 없으면 그 줄을 숨긴다.
- [x] 카드에서 누르는 곳별 이동: 번치 → 번치 프로필, 사진 → 번들 상세, 위치 → 콕하기 시트, 하트 → 좋아요, 말풍선 → 상세 댓글 영역, 참여 멤버 → 참여 멤버 시트.
- [x] 구간(6.1.4): 팔로우한 번치 구간(최근 14일, 업로드 최신순) → 「팔로우한 번치의 소식을 모두 확인했어요」와 축하 애니메이션 → 공개 구간(발행 최신순, 앞 구간에 나온 번들 제외) → 맨 아래 「모든 피드를 확인했어요」와 체크 애니메이션. 구간 안내는 화면에 다시 들어올 때마다 다시 재생.
- [x] 팔로우한 번치 번들이 없으면 공개 구간부터. 두 구간이 모두 비면 체크 애니메이션과 「모든 피드를 확인했어요」만.
- [x] 아래로 스크롤하면 이어서 불러온다. 커서는 지금 구간과 마지막 번들의 발행 시각·ID다(6.1.4 로직 3).
- [x] 소속 번치가 없으면 헤더에 로고만, 공개 구간만, 번치 명의 행동은 안내 토스트(6.1.7).

광고 (6.1.5~6.1.6, FEED-09)

- [x] 번들 카드 6개마다 광고 카드 1개, 같은 광고를 연달아 넣지 않는다. 광고가 여러 개면 랜덤으로 고른다. 두 구간 모두에 넣는다. 서버가 보장하고 웹은 받은 값을 그대로 쓴다.
- [x] BUNCH 로고 이미지와 「BUNCH SPOT」 배지(Figma 기준), 홍보 문구, 장소 사진(장소명·소개|위치·태그 칩), 「콕하기」, 더보기(⋯).
- [x] 「콕하기」(연한 회색)는 시트 없이 「콕 했어요」(검은 버튼)로 바꾼다. 토스트 없음. 「콕 했어요」를 누르면 장소 콕하기 시트와 같은 콕 취소 모달(6.3.1 상세 5)을 띄우고, 「삭제하기」면 「콕하기」로 돌린다. 연타는 첫 탭만.
- [x] 더보기 → 확인 시트(기획 원문의 「숨기기」/「취소」 메뉴는 Figma `5991:164178` 기준과 사용자 요청으로 뺌, 일러스트(Figma 기준), 「이 장소를 숨길까요?」, 설명, 「취소」/「숨기기」) → 카드 자리에 체크 애니메이션과 「장소를 숨김 처리 했어요」를 4초 보인 뒤 카드가 접히며 사라진다(기획 원문은 새로고침·탭 이동 뒤 제거, 요청으로 변경). 탭 이동 뒤에도 없다. 되돌리기 없음.
- [x] 광고 콕을 현재 번치 「콕한 장소」에 저장, 이미 담긴 장소(다른 멤버가 콕한 것 포함)는 처음부터 「콕 했어요」, 숨김을 사용자 개인 단위로 저장해 새로고침 뒤에도 유지(구현 단위 10).
- [ ] 광고 사진을 눌러 앱 밖 브라우저로 이동(bridge 결정 후).

번들 상세 (6.2, BUNDLE-03)

- [x] 헤더(뒤로가기)와 맨 아래 댓글 입력란은 고정, 그 사이만 스크롤.
- [x] 헤더 더보기(구현 단위 5·6). 「수정하기」는 번들 수정 화면(#423)으로 이동한다.
- [x] 번치 정보 줄의 참여 멤버도 이미지 3개와 「외 N명」이다. 3명 이하면 「외 N명」을 숨긴다(6.2.2, 1110판).
- [x] 「멤버 공개」 번들만 제목 오른쪽에 멤버 아이콘을 붙인다. 「전체 공개」·「일부 공개」에는 없다(6.2.3).

댓글 (6.2.7~6.2.10, FEED-05·FEED-07)

댓글 목록·등록·삭제는 서버에 반영한다(명세 014~017, API 연동 4번 #371). 댓글·번들 신고도 서버에 보낸다(명세 018·019, API 연동 5번).

- [x] 댓글 한 줄: 프로필 이미지, 닉네임, 번치 이름 배지(번치 분위기 4종에 따른 색), 작성 날짜(「YYYY.MM.DD」), 내용(줄바꿈 유지), 「답글 N」 또는 「답글 달기」, 더보기(내 댓글 「삭제」, 남의 댓글 「신고」).
- [x] 정렬: 원댓글 최신순, 답글은 원댓글 아래 오래된 순. 답글은 한 단계까지(답글에는 「답글 N」·「답글 달기」 없음). 삭제된 댓글에는 답글을 달 수 없다.
- [x] 삭제된 댓글·답글은 답글이 없어도 목록에 남기고 회색 기본 이미지, 「작성자」, 「삭제된 댓글입니다」. 배지·날짜·「답글 N」은 숨긴다. 원댓글이 지워져도 답글은 그대로. 「답글 N」의 N은 삭제된 답글 포함.
- [ ] 1110판 6.2.7 상세 3은 삭제된 댓글에서 「답글 달기」만 숨긴다. 「답글 N」을 남기는지는 아래 확인 항목.
- [x] 탈퇴한 사용자의 댓글·답글은 삭제된 댓글과 같게 보인다. 회색 기본 이미지, 「작성자」, 내용 대신 「삭제된 댓글입니다」(6.2.7 로직 5, 1110판). 서버가 삭제 자리로 준다(명세 014).
- [x] 차단 관계인 번치의 댓글·답글은 숨긴다. 그 번치가 쓴 원댓글이면 아래 답글도 누가 썼든 함께 숨긴다. 숨긴 것은 상세 댓글 수와 「답글 N」에서도 빼서 화면에 보이는 수와 같게 한다(6.2.6 로직 6, 6.2.7 로직 6). 서버가 목록·`totalCount`·`replyCount`에서 뺀다.

- [x] 입력란: 「{현재 번치 이름}으로 댓글 달기」(받침에 따라 「으로」/「로」), 공백만이면 보내기 비활성, 최대 200자, 앞뒤 공백 제거·줄바꿈 유지, 보내면 맨 위에 추가하고 입력란 비움·키보드 내림. 연타는 한 번만 등록(보내는 동안 막고 같은 `Idempotency-Key`).
- [x] 금칙어(1.4.3 로직 4, 6.2.8): 서버가 거부하면 등록하지 않고 쓴 내용·답글 작성 상태를 둔 채 「사용할 수 없는 단어가 포함되어 있어요.」 토스트(#431).
- [x] 답글 작성 상태: 입력란 위 「{닉네임}님에게 답글 남기는 중」 + 닫기(X), 안내 문구 「{현재 번치 이름}으로 답글 달기」. 보내면 그 댓글 아래 등록하고 일반 상태로.

- [x] 댓글 신고: 「이 댓글을 신고할까요?」 신고 시트(번치 신고 5.10.7과 같은 구성), 접수하면 「신고가 접수됐어요.」만 띄우고 댓글은 그대로 둔다(2026-11-21 변경: 신고만으로는 숨기지 않고 운영 검토 뒤 위반이면 삭제, 「삭제된 댓글입니다」). 내 댓글에는 메뉴 없음. 같은 번치는 같은 댓글을 24시간에 최대 2번까지 신고할 수 있다(3번째 처리는 5.10.7과 같음). 접수는 서버(019)다. 24시간 2회 제한은 서버가 판단하고, 3번째는 `409 BUNCH_011`이라 시트가 닫힌 뒤 「이미 신고가 접수되어 검토 중이에요.」를 띄우고 댓글은 그대로 둔다(API 명세 019, #457). 가짜 서버도 접수 시각을 저장해 첫 접수부터 고정 24시간 구간으로 센다(거절은 구간을 늘리지 않음).

- [x] 공개 범위 수정(6.2.15): 「번들의 공개 범위를 설정해 주세요」, 공개 번치는 「전체 공개」/「멤버 공개」, 비공개 번치는 「일부 공개」/「멤버 공개」. 처음엔 지금 값이 선택되고, 다른 값을 골랐을 때만 「수정하기」 활성. 누르면 확인 없이 저장하고 상세로. 뒤로가기는 버린다.

- [x] 공개 범위 반영(6.2.15 로직 3~5): 「멤버 공개」면 피드와 다른 번치의 번치 프로필에서 빠지고 우리 멤버에게는 보인다. 다른 번치의 좋아요·댓글은 남긴다. 발행 시각은 그대로, 알림 없음. 이 규칙은 서버가 보장하고, 웹은 「멤버 공개」로 저장하면 받아 둔 피드에서 그 카드를 뺀다. 실패·권한 상실·그사이 삭제는 각 토스트다(웹, 구현 단위 10).

시트·멤버 프로필 (6.3, FEED-02·10·11)

- [x] 장소 콕하기 시트: 「어느 장소를 콕할까요?」, 장소마다 위치 아이콘·이름·주소·버튼. 담기지 않은 장소는 「콕하기」(연한 회색 + 손가락 아이콘), 이미 담긴 장소는 「콕 했어요」(검은 버튼 + 손가락 아이콘). 위치가 하나여도 같은 시트.
- [x] 「콕하기」를 누르면 담고 「콕 했어요」로 바꾼다. 시트는 닫지 않고 토스트 없음.
- [x] 「콕 했어요」를 누르면 시트를 닫고 콕 취소 모달: 「이 장소의 콕을 삭제할까요?」 / 「'{장소 이름}'이 번치의 콕한 장소에서 삭제돼요.」(받침에 따라 「이」/「가」) / 「아니요」·「삭제하기」. 「삭제하기」면 빼고(토스트·되돌리기 없음), 「아니요」면 그대로 둔다. 어느 쪽이든 모달이 닫힌 뒤 콕하기 시트를 다시 올린다(화면설계서 피드 2번을 따름). 명세와 다름(확인 필요): 1110판 6.3.1 상세 5는 「아니요」면 시트를 다시 열지 않는다. 취소한 장소는 다시 콕할 수 있다.
- [x] 콕·취소를 서버에 반영하고 담긴 상태를 받아 온다(명세 009·010·021). 다른 멤버·다른 번들·광고에서 콕한 장소도 처음부터 「콕 했어요」다. 콕하기 실패는 「콕하기」로, 콕 취소 실패는 장소를 그대로 둔다.
- [x] 같은 장소는 위치의 외부 ID 기준으로 한 번만 담긴다(8.1.3 로직 4). 콕·취소해도 번들을 만든 번치에 알림을 보내지 않는다. 서버가 보장하고 웹은 받은 값을 그대로 쓴다.
- [x] 참여 멤버 시트: 「참여 멤버」, 테두리 있는 한 줄 카드에 프로필 이미지 + 닉네임, 누르면 멤버 프로필. 역할 배지는 메인 관리자 노란 왕관, 공동 관리자 회색 왕관(Figma 기준, 1110판 6.3.2도 같음). 나간·탈퇴한 멤버는 기본 이미지와 「작성자」이고 배지 없이 누를 수 없다.
- [x] 멤버 프로필: 큰 프로필 이미지·닉네임, 「참여중인 번치」 목록(이미지, 이름, 비공개면 자물쇠, 팔로우 버튼). 팔로우 버튼은 팔로워·팔로잉 목록(5.11.1)과 같은 컴포넌트이고 현재 번치 기준, 현재 번치 자신의 줄에는 버튼 없음. 정렬은 한글 → 영문(대소문자 무시) → 숫자. 번치 줄을 누르면 그 번치 프로필, 우리 번치면 번치 메인. 서버(명세 020)에서 받는다.
- [x] 멤버 프로필의 서버 반영: 팔로우 저장, 현재 번치 기준 상태 받기, 차단 관계인 번치 제외(구현 단위 10).

- 오류: 오류 토스트 기본 문구는 「일시적인 오류가 발생했어요. 다시 시도해 주세요」다.
  - 목록·상세·댓글·멤버 프로필 로딩 실패, 좋아요·콕하기·콕 취소·댓글 등록·삭제·신고·광고 숨기기·수정 저장·삭제 실패. 콕하기 실패는 버튼을 「콕하기」로, 콕 취소 실패는 장소를 그대로 둔다.
  - 다른 멤버가 그사이 이미 뺀 장소의 콕 취소, 이미 지워진 댓글 삭제 → 바뀐 상태로 맞추고 따로 안내하지 않는다.

  - 사진 로딩 실패는 회색 자리표시, 프로필 이미지 실패는 기본 이미지.

## 모션

화면별 전환·모션의 결정과 확인 기록이다. 공용 규칙은 [motion.md](../architecture/motion.md)를 따른다.

- 다른 번치 프로필 (2026-11-02, 이슈 #189): 피드 → 다른 번치 프로필 → 그 번치 멤버 목록도 한 단계 들어가는 이동이라 같은 `drill`(350ms, 번치 더보기 메뉴와 같은 곡선)이다. 화면설계서에 이 이동의 전환 정의는 없다. 동적 route라 고정 id(`BUNCH_HOME_PATHS.transitionIds`)를 규칙과 각 화면 DOM의 `data-ssgoi-transition`에 함께 쓴다.
- 피드 → 번들 상세 (2026-11-09 이슈 #266 `drill`, 2026-11-15 #400에서 변경): 카드 사진을 누르면 SSGOI `hero`(`type: 'fade'`)로 카드가 상세의 첫 사진 자리로 옮겨 가며 상세 화면이 겹쳐 나타난다(디자이너 요청, Figma `6892:46500` 「게시글 확대 모션」). #266에서는 카드와 상세 사진 크기가 같아 움직임이 작다고 hero를 쓰지 않았는데, 디자이너가 이 움직임(아래로 미끄러짐)을 정해 바꿨다.
  - 짝: 디자인 시스템 `BundlePhoto`의 `heroKey`가 피드 카드 전체(사진과 위 글자·딤)에 `data-hero-enter-key`, 상세 첫 사진에 `data-hero-exit-key`를 붙인다. 키는 `bundleHeroKey(bundleId)`. 이 조합이면 SSGOI가 두 장을 페이지 위 별도 층에 그린다. 같은 `data-hero-key`를 쓰면 상세 사진을 페이지 안에서 움직이는데, 상세 사진은 가로 스크롤 줄(`overflow-x: auto`) 안이라 줄 밖으로 나간 부분이 잘렸다. 그 위로 카드 복사본만 보여 딤이 아래로 벗겨지듯 보였다(2026-11-15 느린 재생 캡처로 확인).
  - 시간: 550ms·`cubic-bezier(0.3, 0, 0.15, 1)`(Figma 사진 이동). 카드의 딤·글자는 사진과 함께 움직이며 같은 시간에 고르게 사라진다. Figma는 글자 덮개를 300ms에 먼저 지우지만, SSGOI는 복사본의 위치와 투명도를 한 진행값으로 움직여 복사본만 빠르게 하면 두 장이 어긋나(가로 띠·겹친 상) 같은 시간으로 둔다. SSGOI의 기본 spring 대신 `cubicBezierIntegrator`로 CSS 곡선을 정해진 시간에 재생한다.
  - 미리 받기: hero는 전환 순간 상세에 짝이 있어야 하는데, 상세는 데이터를 받는 동안 받는 중 화면이라 처음 여는 번들에서는 짝이 없어 전환 없이 바뀌었다. 그래서 사진에 손가락이 닿을 때(`pointerdown`) 상세와 번치 홈을 미리 받고(`ensureQueryData`, 캐시가 있으면 바로), 사진·말풍선을 누르면 받기가 끝나거나 400ms가 지난 뒤 이동했다. 실기기에서는 처음 여는 번들의 응답이 400ms를 넘겨 hero 없이 들어갔고, 누른 뒤 400ms 동안 반응이 없어 끊겨 보였다(2026-11-20, 사용자 제보). 지금은 기다리지 않고 바로 이동한다. 상세는 받는 동안 피드 카드 데이터로 번치 정보·제목·첫 사진을 본문과 같은 자리에 먼저 그려(누를 수 없게 `inert`) 짝을 만든다. 다 받으면 본문으로 바뀐다.
  - 뒤로 가기: 같은 hero 규칙을 양방향으로 쓴다(Figma는 들어갈 때만 정의, 시간·곡선은 같은 값). 돌아갈 때는 SSGOI가 피드 카드를 제자리에서 상세 사진 자리 → 카드 자리로 움직이고 상세 화면은 흐려진다. 처음에는 양방향 hero가 짝을 잇지 못해 `drill`로 따로 뒀지만, enter·exit 키로 바꾼 뒤 다시 확인하니 이어졌다(2026-11-15 #400). 움직이는 카드가 아래 카드에 가리지 않게 SSGOI 복사본(`data-ssgoi-crossfade`)이 들어 있는 동안만 목록 항목을 위로 올린다. 전환 중 나가는 화면은 다른 전환과 같이 `inert`·나가는 화면 표식을 단다.
  - 서버 왕복(#532): 상세 화면은 처음 방문할 때 한 번 그려 캐시하는 정적 route다(빈 `generateStaticParams`, 빌드 표 `●`). 주소 query(`focus`·`section`·`comment`·`via`)는 서버가 아니라 클라이언트에서 읽는다(`BundleDetailFrame`, `useSearchParams`). 전에는 page가 `searchParams`를 읽어 요청마다 그리는 route였다. Next는 이런 route를 미리 받지 않고 받은 결과도 캐시하지 않아, 운영에서는 누른 뒤 서버 응답이 와야 hero가 시작됐다(TestFlight 실기기 「뚝 끊긴 뒤 hero」). 손가락이 닿을 때 상세 주소를 미리 받는다(`router.prefetch`). Next 16은 이 route의 경로 정보만 미리 받고 누를 때 캐시된 정적 결과를 받아, 카드가 그려질 때마다 미리 받지는 않는다(처음 보는 번들마다 서버 렌더가 생김). 가짜 서버 운영 빌드(Chromium)에서 캐시된 상세는 누른 뒤 51ms에 새 화면이 붙었고, 말풍선은 120ms에 zoom이 시작됐다. 실기기 확인 전이다.
  - 스크롤: 스크롤은 페이지 안 `main`이 맡아 SSGOI 자동 복원 대상이 아니다. 나가는 화면이 DOM에 다시 붙으면 0이 되어 맨 위로 튀므로, 화면이 사라질 때 스크롤을 `transform`으로 옮겨 둔다(`useHoldScrollOnLeave`, `shared/hooks`). 피드는 스크롤할 때 값을 그 history 항목에 저장해 뒤로 오면 복원한다(`useScrollInHistory`).
  - 확인(2026-11-20 바로 이동으로 바꾸기 전 기준, 바꾼 뒤 브라우저·실기기 측정은 아직): Chromium에서 처음 여는 번들과 다시 여는 번들 모두 hero(프레임 측정), 8배 느린 재생 캡처에서 카드가 한 덩어리로 내려가며 딤이 고르게 사라짐, 두 번 눌러도 이동 1번. 뒤로 가기는 첫 카드와 둘째 카드에서 카드가 상세 사진 자리에서 카드 자리로 약 550ms에 돌아오고 그동안 목록 항목이 위로 올라오는 것을 프레임으로 확인했다. 실기기, 동작 줄이기는 확인하지 않았다.
  - 전환 중 스크롤(2026-11-15, #398 확인): 새 화면이 옆에서 들어오는 동안 `scrollIntoView`를 부르면 밀려 있는 화면을 보이려고 바깥 틀까지 가로로 스크롤해 화면이 튄다. 진입하자마자 위치를 옮겨야 하면 세로 스크롤 영역(`main`)의 `scrollTop`만 바꾼다(상세의 「댓글로 이동」, `BundleDetail.tsx`). 다른 `scrollIntoView` 사용처(피드 로고의 맨 위 이동, 번들 선택의 추천 적용, `useScrollFocusedIntoView`, 등록한 댓글 보이기)는 사용자가 화면을 보는 중에만 불려 전환과 겹치지 않는 것을 코드 경로로 확인했다. 진입 직후에 부르는 곳이 새로 생기면 같은 방식으로 바꾼다.
  - 말풍선 진입(2026-11-22, #505, 사용자 결정): 말풍선(`?focus=comments`)은 hero가 아니라 SSGOI `zoom`(`type: 'static'`)이다. 눌린 카드가 상세 화면 전체로 벌어지고(뒤 피드는 그대로), 상세는 처음 그려질 때 이미 댓글 위치로 내려 두어 열리는 동안 댓글이 보인다. 뒤로 가면 화면 전체가 카드 자리로 접힌다. 키보드는 열림이 끝난 뒤(`data-page-leaving`이 사라진 뒤) 준다. 말풍선에 손가락이 닿을 때 상세와 댓글 목록, 말풍선 주소(`?focus=comments`)를 미리 받기 시작하고, 누르면 기다리지 않고 바로 이동한다. 처음에는 상세를 최대 400ms 기다렸는데, TestFlight 실기기에서 응답이 400ms를 넘겨 받는 중 화면으로 열렸다가 댓글로 넘어가 zoom이 없는 것처럼 보였다(#532). 받기 전에 열리면 도착할 때 댓글로 내린다. zoom은 유지한다(#532 사용자 결정, 실기기에서 다시 보고 부족하면 hero 검토).
    - 이유: hero는 상세 첫 사진을 카드 사진과 잇는데, 말풍선 진입은 상세가 댓글까지 내려가 있어 들어갈 때는 「사진이 날아옴 → 툭 내려감」, 뒤로 갈 때는 화면 위 밖의 사진에서 출발해 「위에서 쓸려 내려옴」으로 보였다. SSGOI 문서도 카드 하나가 화면 전체로 열리면 zoom, 같은 사진이 이어지면 hero를 권하고, 데모(Instagram·Pinterest·YouTube·Airbnb·Voyage)도 카드 → 상세는 zoom이다. 사진 탭은 Figma 「게시글 확대 모션」대로 hero를 유지한다.
    - 구현: 같은 상세 주소라 SSGOI 규칙이 구분하지 못해, 말풍선 진입만 상세 틀의 전환 이름을 `FEED_PATHS.transitionIds.bundleComments`로 나눈다. 상세에서 번치·멤버·공개 범위·수정으로 가는 규칙은 두 이름에 함께 건다. 다만 번치 이름으로 가는 push는 두 진입 모두 이동 직전에 `bundleToBunch`로 바뀌어 그 drill 규칙을 탄다([bunch-home.md](./bunch-home.md)의 「모션」 「번치 탭 번들 진입」). 짝 표식은 hero와 이름이 반대다: 나가는 피드 카드에 `data-zoom-exit-key`(여러 개 가능), 들어가는 상세 안에 같은 값의 `data-zoom-enter-key`가 정확히 하나. SSGOI는 화면 틀 안쪽에서 찾으므로(`querySelectorAll`, 틀 자신은 찾지 않음) 표식은 틀 안 요소에 둔다(`@ssgoi/core` 7.4.1 코드 확인). 나가는 화면 표식은 다른 전환처럼 `guardPair`(경계 id로 피드·상세를 찾음). zoom은 열리는 동안 나가는 카드를 복제해 화면 크기로 키우는데, 카드는 맨 위 사진부터라 그 뒤로 댓글 화면이 드러나면 점프처럼 보였다. 그래서 말풍선 진입에서는 복제본을 숨기고(`visibility: hidden`) 댓글 위치의 상세 자체가 카드 자리에서 펼쳐지게 했다. 복제본은 계산된 스타일을 inline으로 받고 zoom 표식이 지워져서, 상세 틀 안에서 enter 표식이 없는 형제를 `!important`로 숨긴다. 뒤로 갈 때도 숨긴 채라 상세가 거의 제 크기로 흐려지다가 카드 자리로 들어간다(사용자 확인). 복제본을 살리거나 앱 틀에서 넘친 곳을 자르면 화면 전체가 줄어드는 느낌이 나서 쓰지 않았다(녹화로 비교). zoom이 상세 틀을 transform으로 옮기는 동안 문서 높이가 잠깐 늘어 데스크톱에서 스크롤바가 깜빡였는데, 문서는 스크롤하지 않는 구조라 `html`의 스크롤바만 숨겼다(`scrollbar-width: none`, `globals.css`).
    - 개발 모드 점프: 로컬 개발 서버에서는 열리는 동안 맨 위였다가 끝나고 댓글로 넘어갔다. Strict Mode가 효과를 한 번 정리했다 다시 실행할 때 `useHoldScrollOnLeave`가 떠나는 화면으로 보고 스크롤을 0으로 돌리고 되돌리지 않았기 때문이다. 다시 실행될 때 붙잡아 둔 위치로 되돌리게 고쳤다(실서버 개발 화면에서 열리는 첫 프레임부터 댓글 위치 확인).
    - 확인: Chromium 운영 빌드(가짜 서버)에서 들어갈 때 약 220ms에 다 열리고 579ms에 입력란 초점, 뒤로 갈 때 약 160ms에 카드로 접히는 것을 프레임으로 확인했다. iOS WKWebView, 동작 줄이기, VoiceOver는 확인 전이다.
- 번치 탭·다른 번치 프로필 격자 → 번들 상세(zoom)는 [bunch-home.md](./bunch-home.md)의 「모션」에 있다.
- 참여 완료 → 피드(`axis` z)는 [login-signup.md](./login-signup.md)의 「모션」에 있다.

### 당겨서 새로고침

Figma `6673:45282`(피드 · Refresh Motion)와 표시기 `6672:47286`이 정한 값이다(2026-11, 이슈 #340). 피드·번치 홈·사진함이 쓴다. 공통 모션처럼 디자이너 값이라 "UI 애니메이션은 300ms를 넘지 않는다"보다 우선한다.

- 동작: 맨 위(`scrollTop` 0)에서 아래로 당겼다 놓는다. 손가락 이동의 0.6배만큼 내용이 내려오고(최대 72px), 64px 이상 내려온 채 놓으면 새로고침을 시작해 64px에 머문다(Figma는 80px이나 로고 아래 간격이 넓어 보여 사용자 요청으로 줄임). 끝나면 0으로 닫힌다. 끝나도 최소 0.6초는 열려 있어 깜빡이지 않는다. 가로로 더 움직이거나 위로 밀거나 이미 스크롤된 상태는 당김으로 보지 않는다. 당긴 채로 손가락을 시작 자리보다 위로 올리면 내용이 로딩 영역 위로 올라와 헤더 밑으로 들어갈 수 있고(기본 스크롤은 막혀 있어 hook이 손가락만큼 직접 스크롤), 놓으면 최상단으로 돌아온다. 그 당김에서 기준 거리(64px)에 한 번이라도 닿았다면 헤더 밑으로 올렸다 놓아도 새로고침한다. 새로고침 중에는 목록을 평소처럼 스크롤할 수 있고, 스크롤로 내용이 표시기 자리를 덮는 만큼 표시기는 흐려져 카드 사이 틈으로 비치지 않는다. 끝나면 스크롤 위치와 무관하게 간격을 닫으면서 내용을 항상 최상단(스크롤 0, 간격 0)으로 올린다(동작 줄이기에서는 즉시).
- 모양: 내용(`main`의 직계 자식)이 `translate`로 내려오고, 36px Spark(4px 모듈 13개, gray-300)가 본문 위 20px(Figma는 30px)에서 20px 위에서 내려오며(0→1 투명도) 나타난다. 당기기 시작하면(새로고침 중에도 이어서) Spark가 2초 주기로 90°씩 세 번 끊어 돈다(사용자 요청, Figma는 표시기가 나타난 뒤 계속 도는 것으로 정의)(곡선 `0.45, 0, 0.2, 1`). Spark는 90° 회전 대칭이라 마지막 멈춤에서 처음으로 돌아가도 이음매가 보이지 않는다.
- 시간·곡선: 열릴 때 `0.33, 0, 0.15, 1`, 닫힐 때 `0.45, 0, 0.2, 1`, 각 600ms(3.5초 타임라인의 17.1%·91.4% 구간).
- 구현: `PageShell`의 `onRefresh`(Promise를 돌려주면 끝날 때까지 기다림)와 `refreshDisabled`. `usePullToRefresh`가 터치를 읽어 컨테이너의 CSS 변수 `--pull-y`·`--pull-p`를 직접 쓰므로 당기는 동안 React가 다시 그리지 않는다. 두 변수는 `shared/components/refresh/pullRefresh.module.css`의 `@property`로 등록해 transition이 보간한다(새로고침 스타일 전체가 이 모듈에 있음). 내용에는 당기는 동안에만 `translate`를 걸어 평소에는 fixed 자손의 기준 상자가 바뀌지 않는다. `transform`이 아니라 `translate`를 써서 화면을 떠날 때 스크롤을 옮겨 두는 `useHoldScrollOnLeave`의 `transform`과 겹치지 않는다. 표시기는 `RefreshSpark`(`shared/components/refresh/`).
- 제약: 당기는 동안과 새로고침 중(최소 0.6초 + 요청 + 닫힘 0.6초)에는 `main` 직계 자식에 `translate`가 걸려 그 자손의 `fixed`는 화면이 아니라 그 자식을 기준으로 놓인다. 이 세 화면의 `main` 안에는 `fixed`를 두지 않는다. 시스템 제스처 등으로 터치가 취소(`touchcancel`)되면 새로고침하지 않고 닫는다. Spark 회전은 새로고침이 끝날 때까지 반복한다(Figma는 한 주기 2초만 정의).
- 서버 상태(실패하면 `onRefresh`가 거부해 위 실패 안내가 나간다. 시각적인 실패 표시는 없고 화면 낭독 안내만 있다, 2026-11-16 확인): 피드·번치 홈은 `useRefreshActiveQueries`(지금 화면이 쓰는 query 전부 다시 받기)를, 사진함은 `usePhotoBox().refresh`(프로필·멤버·사진 목록)를 넘긴다. 실패해도 표시를 닫고, query 자체의 오류 표시는 각 query를 쓰는 화면이 맡는다.
- 접근성: 동작 줄이기에서는 열리고 닫히는 전환, 표시기의 이동·회전을 뺀다. 손가락을 따라 내용이 내려오는 것은 사용자가 직접 하는 조작이라 남기며(빼면 표시기가 내용과 겹친다), 표시기는 투명도로만 나타난다. 표시기는 장식이라 `aria-hidden`이고, 「새로고침하고 있어요」·「새로고침을 마쳤어요」는 `role="status"`로 알리고 3초 뒤 비운다. 요청이 하나라도 실패하면(`onRefresh`가 거부) 「새로고침하지 못했어요」를 알린다. 마우스·키보드에는 반응하지 않는다. 키보드·스크린 리더 사용자는 화면 진입·앱 복귀 때 다시 받을 수 있지만 query의 신선 시간 안에서는 다시 받지 않는다. 접근 가능한 새로고침 수단(예: 헤더 메뉴)은 후속 과제다(디자이너·기획 확인 필요).
- 확인한 범위: Chromium(Pixel 7 에뮬레이션, 터치 이벤트 주입)에서 세 화면의 당김·머묾·닫힘과 짧게 당겨 취소되는 것을 확인했고(거리를 80px로 둔 때의 측정이며, 64px로 줄인 뒤와 표시기를 내용 뒤로 옮긴 뒤는 단위 테스트만 돌리고 화면은 확인하지 못했다), 단위 테스트가 임계값·중복 방지·가로 제스처·비활성을 확인한다. 실기기(iOS WKWebView의 바운스, Android 뒤로 가기 제스처와의 충돌)와 동작 줄이기, 사진함의 사진 길게 눌러 선택과의 충돌은 확인하지 않았다.
- 범위 밖: 피드 맨 아래 「모든 피드를 확인했어요」의 체크 표시와 조각 모음은 같은 Figma 노드에 있지만 새로고침 표시기가 아니라 피드 끝 안내의 모션이라, 새로고침 표시기와 따로 `features/feed/components/FeedCaughtUp.tsx`가 로티로 재생한다(2026-11-16 확인).

### 스크롤로 헤더 숨김

피드 헤더(2026-11-15, #400): 아래로 스크롤하면 헤더가 위로 빠져 숨고, 위로 올리면 다시 나온다. Facebook 앱과 같은 방식(A안, 사용자 결정)이다.

- 동작: 헤더가 스크롤한 거리만큼 1:1로 따라 올라간다(손가락을 따라감). 다 숨은 헤더는 위로 60px 올린 뒤부터 올린 만큼 내려온다(Instagram처럼 조금 올렸다고 바로 나오지 않음, 사용자 요청). 그 사이 다시 내리면 처음부터 센다. 헤더 높이 안에서만 움직인다. 손가락을 놓고 스크롤이 멈추면(관성 포함, 120ms 동안 스크롤 이벤트가 없으면) 절반 넘게 숨은 헤더는 끝까지 넣고 덜 숨은 헤더는 꺼낸다. 손가락을 댄 채 멈춰 있는 동안은 정리하지 않는다. 다 숨길 때는 자기 높이보다 2px 더 올리고, 1px 이내로 남은 상태는 다 숨은 것으로 본다(iOS 스크롤 값이 소수라 헤더 아래 끝이 실처럼 남던 것을 막음). 맨 위에서는 스크롤한 거리보다 더 숨지 않아 위로 갈수록 헤더가 따라 나오고, 멈추면 다 보인다. 사용자가 손가락·휠·키보드·스크롤바로 스크롤을 시작하기 전의 이동(돌아올 때 스크롤 복원)에는 숨기지 않는다. 헤더 안에 초점이 있으면 숨기지 않는다.
- 모양: 헤더는 본문 위에 겹쳐 있고(불투명 흰 배경) 따라가는 동안에는 전환 없이 위치만 바꾸고, 멈춘 뒤 끝까지 넣거나 꺼낼 때만 200ms ease-out(진입·이탈)이다. 위치는 hook이 `style.transform`을 직접 바꿔 스크롤 중 React가 다시 그리지 않는다. 헤더의 흰 배경은 상태 표시줄 자리까지 덮고 헤더와 한 덩어리로 오르내린다. 그래서 헤더가 숨으면 본문이 상태 표시줄 뒤까지 올라가고, 내려오면 상태 표시줄 배경도 함께 내려온다(Facebook 앱과 같은 모습, 사용자 요청). 헤더가 숨은 동안 상태 표시줄 자리는 처음(2026-11-15)에는 아무것도 덮지 않았고, 지금은 아래 「상태 표시줄 흐림」대로 점진적으로 흐린다(#502). 상태 표시줄 글자가 검은색 고정이라 어두운 사진 위에서는 잘 안 보일 수 있다. 페이지 전환 틀(`AppTransitions`)은 평소 넘친 부분을 모두 자르지만, 접는 헤더 화면이 있으면 `clip-path: inset(-상태 표시줄 높이 0 0 0)`으로 위만 상태 표시줄 높이만큼 더 보이게 자른다. 처음에는 `overflow-x: clip` + `overflow-y: visible`로 좌우만 잘랐는데, WebKit이 이를 세로 ±2^24px의 클립 층으로 만들어 iOS에서 큰 좌표의 소수 정밀도 때문에 내용이 약 1pt 아래로 밀렸고, 화면 맨 위에 흰 선(뒤의 흰 바탕)이 남았다(2026-11-15, 시뮬레이터 뷰 계층과 화면 픽셀로 확인). 이 조합은 쓰지 않는다. 당겨서 새로고침 표시기는 헤더 높이만큼 내려 둔다.
- 화면 전환 중 상태 표시줄(#516, 2026-11-22 사용자 제보): 피드 → 알림 목록 drill에서 나가는 피드의 흰 헤더가 상태 표시줄 자리를 덮은 채 20%만 밀려, 전환 내내 흰색이 남았다가 끝나야 회색으로 바뀌었다(들어오는 화면은 상태 표시줄 아래부터 그림). 나가는 동안(`data-page-leaving`)에는 접는 헤더 화면의 상태 표시줄 자리를 `clip-path`로 잘라, 다른 화면처럼 `AppFrame`의 틀 색이 전환 시작과 함께 바뀐다. WebKit(Playwright, 상단 Safe Area 47px 흉내, 가짜 서버 개발 서버)에서 녹화 프레임으로 상태 표시줄 색이 헤더 자리와 같은 프레임에 바뀌기 시작하는 것을 확인했다(고치기 전에는 약 240ms 늦음). 실기기는 확인 전이다.
- 구현: `PageShell`의 `collapsibleHeader`와 `useHideOnScroll`(`shared/hooks/`). 헤더 높이는 화면을 그리기 전(`useLayoutEffect`)과 크기가 바뀔 때(`ResizeObserver`) 재서 `--page-header-height`로 넘긴다. 본문 위 여백·`scroll-padding-top`·표시기 위치는 상태 표시줄을 포함한 헤더 높이(`--page-top-inset`)를 쓰고, 재기 전(서버 렌더)에는 상태 표시줄 + 디자인 시스템 `Header` 높이 3rem을 써서 첫 화면이 밀리지 않는다.
- 접근성: 다 숨은 동안 헤더는 `inert`라 Tab 순서와 스크린 리더에서 빠진다(위로 스크롤하면 다시 보인다). 동작 줄이기에서는 멈춘 뒤의 정리 이동을 전환 없이 한다(손가락을 따라가는 것은 사용자가 직접 하는 조작이라 남김, 당겨서 새로고침과 같은 기준). 실기기 VoiceOver(세 손가락 스크롤 포함)는 확인하지 못했다.
- 헤더 자체를 흐린 유리로 할지(B안)는 디자이너 확인 뒤 정한다. 구조는 같고 헤더 배경만 바꾸면 된다.
- 상태 표시줄 흐림(#502, 2026-11-22 기획 결정): Instagram처럼 헤더가 숨은 동안 상태 표시줄 뒤로 지나가는 본문을 흐린다. 다이내믹 아일랜드 위쪽만이 아니라 상태 표시줄 전체에 위가 가장 진하고 아래로 갈수록 자연스럽고 부드럽게 사라지게 한다. 흐림 한 장을 투명도로만 옅게 하면 경계가 보이므로 세기가 다른 층(1·2·4·8px)을 겹치고, 층마다 아래로 사라지는 지점을 다르게 한 마스크를 씌운 점진적 흐림으로 한다. 흰색은 얹지 않는다(흰 띠처럼 보임). `PageShell`이 접는 헤더 화면에만 상태 표시줄 높이로 둔다. 헤더가 보일 때는 헤더의 흰 배경 위라 보이지 않는다. 실기기 확인 전이다.

- 번들 삭제 확인창 제목이 「게시글을 삭제할까요?」, 번들 신고가 「이 게시글을 신고할까요?」다. 다른 곳은 「번들」이라 부른다. 의도한 용어인지.
- 피드 스크롤 위치 유지(6.1.1 상세 6)가 번치 전환 뒤 맨 위로 이동(로직 2)과 충돌하지 않는지: 전환할 때만 맨 위로 간다고 이해했다.
- 멤버 프로필(6.3.3)에 비공개 번치 이름·이미지도 보인다. 승인 전 번치에도 「이 사람이 비공개 번치 소속」임을 보여도 되는지, 프로필을 모으면 명단을 일부 복원할 수 있는데 확정인지. API 연결 전에 정한다.
- 6.3.1 로직 6 「추천카드 장소는 해당되지 않는다」: 추천카드가 광고 카드(BUNCH SPOT)를 말하는지.
- 답글 단계: 1110판 6.2.7은 「답글은 한 단계까지만」과 「답글에는 「답글 N」·「답글 달기」가 없다」를 지웠다. 답글에 다시 답글을 허용하는지. 구현은 한 단계다.
- 삭제된 댓글의 「답글 N」: 1110판 6.2.7 상세 3은 「답글 달기」만 숨긴다. 답글이 달린 삭제된 댓글에 「답글 N」을 보일지. 구현은 숨긴다.
- 1110판 6.2.13에서 「삭제 뒤 발행 번들 수로 뭉치 단계를 다시 계산」 문장이 빠졌다. 단계를 유지하는지, 다른 장으로 옮겼는지.
- 콕 취소 모달 버튼 순서: 6.3.1은 「아니요」/「삭제하기」다. 다른 확인 모달은 「취소」/「삭제」라 문구가 다르다. 의도한 것인지.

# 기능: 번치 메인·상세 (기능명세서 5장)

> Status: Draft
> Date: 2026-11-10(기능명세서 1110판, 2026-11-10 기준, 2026-11-15 최신본의 5.10 차이 반영)

기능명세서의 **5장 번치(메인/상세)**를 구현 범위로 정리한 문서다. 5장은 5.1~5.12로 나뉜다.

- 5.1 번치 메인 탭, 5.2 번치 전환 시트, 5.3 작성 중인 번들, 5.4 더보기 메뉴
- 5.5 프로필 편집, 5.6 멤버 관리, 5.7 차단 목록, 5.8 나가기, 5.9 삭제
- 5.10 다른 번치 프로필, 5.11 팔로워·팔로잉, 5.12 알림

기능 ID(BUNCH·MEMBER·FEED·NOTI·DRAFT·PROFILE)와 명세서 절 번호(5.2.3 등)로 원본과 대조한다. 번들 만들기·공동 편집은 `docs/specs/bundle-create.md`, 사진함은 `docs/specs/photo-box.md`가 맡는다.

이 spec은 web·백엔드·알림(푸시)에 걸쳐 `docs/specs/`에 둔다. 번치 메인은 `apps/web/src/features/bunch-home/`(#162)에 있고, 화면 spec은 그 폴더의 `components/home/BunchHomeScreen.spec.md`다.

## 목적

- 지금 보고 있는 번치의 대표 화면을 둔다. 번치 프로필 이미지, 소개, 함께 만든 번들을 한곳에 보여준다(5.1.1).
- 한 계정으로 여러 번치에 속한 사람이 번치를 바로 전환한다.
- 번치 관리(프로필, 멤버, 차단, 나가기, 삭제)와 다른 번치와의 관계(팔로우, 차단, 신고), 번치 단위 알림을 제공한다.

## 문제 정의

- 번치 전환이 앱 전체의 기준(사진함, 번들, 알림, 팔로우 명의)을 모두 새 번치로 바꾼다. 전환을 한곳에서 일관되게 다뤄야 한다(5.2.2 로직 2).
- 다른 관리자가 번치를 삭제하거나 내가 내보내져도 목록에서 바로 사라지면 무슨 일이 있었는지 알 수 없다. 접근 불가 상태와 안내가 필요하다(5.2.3).
- 역할(메인 관리자, 공동 관리자, 일반 멤버)에 따라 보이는 메뉴와 할 수 있는 일이 다르다. 서버가 요청 시점의 역할로 다시 판단해야 한다.

## 범위 외 항목

- 번들 만들기, 추천 번들, 공동 편집, 작성 중인 번들 삭제 처리(4장, `bundle-create.md`). 이 문서는 번치 메인에서 들어가는 입구만 둔다.
- 번치 만들기·초대 참여(2장). 번치 추가는 번치 시작 선택 화면(2.1.1)으로 보내기만 한다.
- 뭉치(번치 캐릭터)와 단계. 1110판에서 서비스에서 빠졌고, 그 자리는 번치 프로필 이미지다(5.1.3).
- 실시간 반영. 번치 탭 진입, 앱 복귀, 당겨서 새로고침 때만 다시 불러온다(5.1.1 로직 2).
- 알림 설정 화면(MY 범위). 푸시 발송은 서버가 한다.

## 대상 사용자와 접근 권한

번치 멤버만 그 번치의 메인을 본다. 역할별 권한은 아래와 같고, 서버가 요청 시점의 역할로 다시 판단한다.

| 동작                                         | 일반 멤버 | 공동 관리자 | 메인 관리자 |
| -------------------------------------------- | --------- | ----------- | ----------- |
| 메인 보기, 전환, 멤버 초대, 나가기           | 가능      | 가능        | 가능        |
| 번치 정보 바꾸기, 번치 삭제, 관리자 넘기기   | 불가      | 불가        | 가능        |
| 공동 관리자 지정·해제                        | 불가      | 불가        | 가능        |
| 멤버 내보내기(메인 관리자는 내보낼 수 없음)  | 불가      | 가능        | 가능        |
| 다른 멤버 사진 삭제·날짜 변경                | 불가      | 가능        | 가능        |
| 다른 번치 차단(기능명세 5.10.4·5.10.5)       | 가능      | 가능        | 가능        |
| 다른 번치 차단 해제(5.6.2, 서버가 다시 검증) | 불가      | 가능        | 가능        |
| 신고, 팔로우, 팔로우 요청 승인·거절          | 가능      | 가능        | 가능        |

번들 권한은 번들 최초생성자가 따로 있다(Figma 「역할별 권한보기」 `2500:54066`). 「일부」는 그 번들에 참여한 경우만이다.

| 번들 동작                                       | 메인 관리자 | 공동 관리자 | 번들 최초생성자 |
| ----------------------------------------------- | ----------- | ----------- | --------------- |
| 작성 중인 번들 업로드·삭제                      | 일부        | 일부        | 가능            |
| 번들 멤버 내보내기(최초생성자는 내보낼 수 없음) | 일부        | 일부        | 가능            |
| 발행된 번들 수정·삭제                           | 가능        | 불가        | 불가            |

- 메인 관리자는 번치마다 1명이고 아무도 내보낼 수 없다. 메인 관리자가 나가려면 새 메인 관리자를 지정한다(5.8.2).
- 작성 중인 번들 삭제 권한은 4장 기준(초안 생성자, 참여 중인 관리자)을 따른다(5.3.2).

## 사용자 흐름과 route

모든 화면은 `apps/web`의 route이고 WebView에 표시된다. `/bunch` 외의 path는 **제안**이며 구현 전에 확정한다.

| 화면(명세 절)                | path(제안)                                                                            | 진입·이탈                                                           |
| ---------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 번치 메인 (5.1)              | `/bunch`                                                                              | 하단 탭. 뒤로가기 없음. 소속 번치가 없으면 번치 없음(5.1.7)         |
| 번치 전환 시트 (5.2)         | `/bunch` 위 바텀시트                                                                  | 헤더 번치 이름. 전환은 확인 없이 즉시                               |
| 작성 중인 번들 탭 (5.3.1)    | `/bunch` 안의 탭                                                                      | 메인 번들 탭 영역. 카드 → 공동 편집(`/bunch/drafts/[draftId]`)      |
| 더보기 메뉴 (5.4)            | `/bunch/menu`(확정)                                                                   | 헤더 「⋯」. 역할별 메뉴                                             |
| 프로필 편집 (5.5)            | `/bunch/menu/profile`(확정)                                                           | 메인 관리자만                                                       |
| 멤버 관리·역할 안내 (5.6)    | `/bunch/members`, `.../roles`(확정)                                                   | 더보기 「멤버 관리」, 프로필 「멤버」                               |
| 차단 목록 (5.7)              | `/bunch/menu/blocked`(확정)                                                           | 더보기 「차단 목록」                                                |
| 나가기·관리자 지정 (5.8)     | `/bunch/menu/leave`(확정)                                                             | 더보기 「번치 나가기」. 메인 관리자는 지정 화면                     |
| 번치 삭제 안내·확인 (5.9)    | `/bunch/menu/delete`·`/bunch/menu/delete/confirm`(확정)                               | 메인 관리자만. 안내 → 문구 입력 확인                                |
| 다른 번치 프로필·멤버 (5.10) | `/bunches/[bunchId]`·`.../members`(확정)                                              | 피드 번치 이름, 팔로워·팔로잉 목록                                  |
| 팔로워·팔로잉·요청 (5.11)    | 내 번치 `/bunch/follows`·`.../requests`, 다른 번치 `/bunches/[bunchId]/follows`(확정) | 프로필 「팔로워」·「팔로잉」(`?tab=following`). 누른 쪽 탭으로 열림 |
| 알림 목록 (5.12)             | `/bunch/notifications`(확정)                                                          | 번치 메인·피드 헤더 알림. 행 → 종류별 화면                          |

- 현재 번치는 앱 공통 상태다. 전환하면 사진함, 번들 만들기, 알림, 팔로우·신고 명의가 모두 새 번치 기준이 된다(5.2.2 로직 2).
- 전환한 번치를 마지막 사용 번치로 저장하고 앱을 다시 열면 그 번치로 들어온다(5.2.2 로직 1).
- 진행 중인 사진 업로드는 시작한 번치에 저장한다(5.2.2 로직 3).

## 요구사항

### 필수 (Must Have)

번치 메인 (5.1)

- [x] 헤더: 번치 이름·화살표(누르면 전환 시트), 알림, 더보기. 헤더에는 프로필 이미지를 두지 않는다. 이름이 길면 말줄임(5.1.2). (#162)
- [ ] 알림 아이콘: 지금 번치에 안 읽은 알림이 있으면 빨간 점(5.1.2).
- [x] 번치 프로필 이미지: 헤더 아래 배경 띠 오른쪽에 원형으로 크게 둔다(5.1.3). 사진이 없으면 서버는 빈 값을 주고 앱이 분위기(2.2.9)의 기본 이미지를 고른다. 발행 번들 수에 따라 바뀌지 않는다. #300에서 구현했다.
- [ ] 같은 이미지를 전환 목록(5.2.1), 피드·번들 상세의 번치 정보(6.1.3, 6.2.2), 다른 번치 프로필(5.10.1)에 쓴다(5.1.3 로직 2).
- [x] 프로필: 이름, 비공개면 자물쇠, 한 줄 소개, 팔로워·팔로잉·멤버 수, 같은 줄 오른쪽 「콕한 장소」 버튼(5.1.4). (#162)
- [x] 「콕한 장소」 → 우리 번치의 콕 화면(5.1.4 상세 6, 콕 8.1, `docs/specs/pinned-places.md`). (#257)
- [x] 소개의 줄바꿈 유지(5.1.4). (#162)
- [x] 팔로워·팔로잉·멤버를 누르면 각 목록으로 이동(5.1.4). 팔로워·팔로잉은 연결(#192). 멤버는 1110판의 「멤버 리스트 화면」을 멤버 관리(5.6.1, `/bunch/members`)로 연결했다(#446, 같은 화면인지 확인 필요).
- [x] 번들 탭 영역: 아이콘 탭 두 개(사진 「번들」, 연필 「작성 중인 번들」), 들어오면 「번들」 탭, 발행 번들 3열 그리드, 「멤버 공개」 칸의 멤버 아이콘(5.1.5). 1110판이 Figma와 같은 구조로 바뀌었다. (#162)
- [x] 「번들」 탭 빈 상태 「추억은 많은데, 번들은 아직!」 + 「첫 번들 만들기」 → 참여 멤버 고르기(4.1.1)(5.1.5). (#162)
- [x] 발행된 번들을 누르면 번들 상세(6.2.1), 아래로 스크롤하면 이어서 불러오기(5.1.5). 삭제된 번들이면 「삭제된 번들이에요.」 토스트 후 새로고침. 삭제는 상세 404로 판단(400ms 안에 답이 없으면 그대로 이동해 상세가 안내). (#446)
- [x] 오른쪽 아래 「+」(번들 만들기 → 참여 멤버 고르기 4.1.1) 고정(5.1.6). 멤버가 1명이면 「함께할 멤버가 없어요」 모달. (#162)
- [x] 번치 없음(5.1.7): 「참여 중인 번치가 없어요」, 「새 번치 만들기」·「초대 링크로 참여하기」(1110판 문구, 구현은 아직 「초대 링크 참여하기」). 헤더·「+」 없음. 나간 번치 기준(fixture), 서버 목록 기준은 API 연결 때. (#180)

번치 전환 (5.2)

- [x] 시트: 「번치 전환하기」, 닫기, 지금 번치는 맨 위에 흐리게(누를 수 없음), 「알림 N개」, 「접근 불가」(5.2.1). (#162)
- [x] 다른 번치를 누르면 확인 없이 전환, 「{번치 이름} 번치로 전환했어요.」(5.2.2). (#162)
- [x] 접근 불가 번치를 누르면 삭제·내보내짐 안내, 「번치 목록에서 삭제」로 목록에서 제거(5.2.3). (#162)
- [x] 보고 있던 번치가 삭제·내보내짐: 같은 안내 후 최근 번치 또는 번치 없음으로 이동(5.2.3 상세 동작 4). 홈 조회의 `409 BUNCH_008` 기준(#414).
- [x] 「새로운 번치 추가하기」 → 번치 시작 선택(5.2.4). 소속 번치 10개면 「참여할 수 있는 번치는 최대 10개예요.」. (#162, 10개 토스트는 #313)
- [x] 전환 목록·마지막 사용 번치 저장·접근 불가 안내 삭제를 서버에 연결(`members/me/bunches`, `last-used`, `bunch-access-notices`). (#313)
- [x] 하단 「번치」 탭 두 번 누르기로 최근 번치 전환(기능명세 밖, 웹 막대·iOS 시스템 탭 바 공통). (#518)
- [x] 하단 「번치」 탭 꾹 누르기(500ms)로 전환 시트(기능명세 밖, 웹 막대). (#518)
- [ ] iOS 시스템 탭 바의 번치 탭 꾹 누르기(네이티브 제스처·bridge 신호, 새 iOS 빌드). (#518)

작성 중인 번들 (5.3)

- [x] 탭과 삭제 확인(5.3.1, 5.3.2). 번치 메인 안의 「작성 중인 번들」 탭과 가운데 확인 모달로 구현했다. 1110판도 별도 화면 없이 탭·모달이다. 빈 상태 「아직 작성 중인 번들이 없어요」 / 「함께한 순간을 하나의 기록으로 남겨보세요.」. (#162)
- [x] 삭제 확인 내용 「삭제한 번들은 다시 복구할 수 없지만, 사용된 사진은 사진함에 그대로 남아요.」(5.3.2). 구현 문구와 같다. 삭제 실패는 공통 실패 토스트 후 모달 유지. 충돌은 「이미 삭제된 번들이에요.」(404)·「이미 발행된 번들이에요.」(409 `BUNDLE_002`)·권한 없음 안내(403) 뒤 모달을 닫고 목록을 다시 받는다(#453).
- [x] 휴지통은 삭제 권한이 있는 사람에게만(목록 응답의 `permissions.canDelete`), 삭제 후 「작성 중인 번들을 삭제했어요.」(5.3.2). 제목이 빈 초안은 흐린 「제목 미정」, 이미 삭제·발행된 초안을 누르면 「삭제된 번들이에요.」·「발행된 번들이에요.」 뒤 목록 갱신(5.3.1, #453).

번치 관리 (5.4~5.9)

## 상태

- 번치 메인: 로딩, 오류(토스트 「일시적인 오류가 발생했어요. 다시 시도해 주세요」), 번치 없음, 번들 없음, 목록.
- 전환 시트: 목록 로딩 실패 시 토스트 후 시트를 닫는다. 전환 실패 시 지금 번치에 그대로 있는다.
- 접근 불가: 「번치 목록에서 삭제」 실패 시 토스트, 행은 그대로 둔다.
- 버튼 연타는 첫 탭만 처리한다(전환, 저장, 팔로우).

## 모션

화면별 전환·모션의 결정과 확인 기록이다. 공용 규칙은 [motion.md](../architecture/motion.md)를 따른다.

- 번치 전환 (2026-11-21, #492, 사용자 결정): 화면설계서 7의 Dissolve 150ms 대신 인스타 계정 전환처럼 바꿨다(사용자가 녹화한 영상을 프레임으로 잘라 실측). 고르는 즉시 시트를 닫고 지금 화면을 복제해 고정하며(새 번치를 받는 동안 유지), 새 번치가 그려지면 복제본은 왼쪽으로 밀려 나가고 새 화면은 92% 크기의 둥근 카드로 오른쪽에서 들어온 뒤(앞 36%) 원래 크기로 커진다(470ms, `useBunchSwitchMotion`). 2026-11-23 사용자가 다시 녹화한 영상을 30fps로 잘라 맞췄다(처음 실측 330ms는 너무 빨라 보였음). 인스타는 상태 바 글자와 탭 바까지 화면 전체가 카드로 움직여서, iOS 쉘은 쉘이 네이티브로 움직인다: 웹이 `beginScreenSwitch`를 부르면 쉘이 화면 전체(상태 바 포함)를 사진으로 덮고 진짜 상태 바를 숨기며, 새 번치를 그린 뒤 `finishScreenSwitch`를 부르면 덮은 사진은 왼쪽으로 밀려 나가고(170ms) 앱 화면 전체가 검정 바탕 위 92% 둥근 카드로 들어와 원래 크기로 커진다(300ms, `modules/screen-switch`). 끝나면 상태 바를 다시 보인다. 덮은 뒤 3초 안에 끝 신호가 없으면 치운다. 브라우저·이전 앱은 웹 안의 모션이다. 기다리는 동안 아래 화면이 눌리지 않는다. 복제 화면은 `inert`라 링크·버튼이 동작하지 않고, `inert`는 터치를 아래로 통과시키므로 바깥 틀(`aria-hidden`, 위에 그려지게 `z-index`)이 터치를 받아 막는다. 원래 화면 안의 `z-index` 요소(「+」)는 바깥 틀보다 위라 원래 화면은 기다리는 동안 `pointer-events: none`이다(초점은 유지, 최대 3초). 바깥 틀의 `z-index`를 올리면 웹 탭 막대를 덮어 올리지 않았다. 토스트는 전환과 함께 뜬다. 맞는 SSGOI 프리셋이 없고(drill은 더보기 진입과 같아 보이고 film은 세로) SSGOI 7.4.1은 화면 안 요소 전환이 없어 Web Animations로 직접 정의한 예외다. 동작 줄이기에서는 기존 150ms 디졸브. Chromium에서 재생 속도를 늦춰 카드 진입·확대·이전 화면 밀림을 확인했고 실기기는 확인 전. 화면설계서와 달라 디자이너에게 공유한다.
- 번치 추가 (2026-11-01): 화면설계서(`1892:37781` 7·8번)대로 번치 홈 전환 시트의 「새로운 번치 추가하기」는 시트가 다 내려간 뒤(`onOpenChangeComplete`) 번치 시작 선택(`/onboarding`)으로 이동하고, `/bunch` → `/onboarding`에 Dissolve / Ease out / 150ms(`fade`, 단계마다 75ms)를 등록했다(아래 2026-11-20에 axis y로 대체). 하단 탭 막대는 `(main)` layout에 있어 전환 대상 밖이라 이동과 함께 바로 사라진다. Chromium에서 시트 닫힘 → 번치 홈 페이드 아웃 → 시작 선택 페이드 인 순서를 확인했다. 2026-11-20(#468, 사용자 결정): 폰에서 150ms 디졸브가 바로 바뀐 것처럼 보여 SSGOI `axis`(`type: 'y'`, 방향형) Ease out / 300ms(`BUNCH_ADD_AXIS_DURATION_MS`)로 바꿨다. 열 때 시작 선택이 아래에서 올라오고, 닫기(뒤로 가기)는 위에서 내려간다(`bidirectional`). 화면설계서 값과 달라 디자이너에게 공유한다. 브라우저·실기기 프레임은 확인하지 않았다.
- 번치 더보기 메뉴 (2026-11-01 #169, 2026-11-02 #186에서 변경): 번치 홈 「더보기」 → 메뉴와 뒤로 가기는 SSGOI `drill`(기본 `parallax`) 프리셋에 Ease out / 250ms만 `override`로 적용한다(`BUNCH_DRILL_DURATION_MS`). 화면설계서(`1892:37780`)는 150ms지만 빨라 보여 사용자 결정으로 200ms로 했고, 2026-11-06에 다시 250ms로 늘렸다. 들어오는 화면은 오른쪽에서, 뒤 화면은 왼쪽으로 20% 함께 밀린다. 처음에는 150ms의 덮는 Move in(아래 화면 제자리)을 직접 만들었지만, [motion.md](../architecture/motion.md) 「페이지 전환」의 프리셋 우선 기준에 따라 같은 계열인 `drill`로 바꿨다. 그래서 뒤 화면도 움직이는 것이 화면설계서와 다르고, 이 차이는 디자이너에게 공유한다. 양방향 규칙 하나(`bidirectional`)다. 200ms 설정일 때 Chromium(앱 폭 430px)에서 열기·닫기 이동이 프레임 단위로 약 200ms에 끝나고(250ms는 프레임 측정 안 함) 프레임마다 이동 거리가 54→5px로 줄어(ease-out), 열자마자 뒤로 가도(0.08~0.3초) 두 화면에 남는 스타일이 없는 것을 확인했다. 실기기와 동작 줄이기는 확인하지 않았다.
- 번치 더보기 메뉴의 하위 화면 (2026-11-01, 이슈 #172): 메뉴 → 프로필 편집은 화면설계서에 정의가 없어, 한 단계 들어가는 이동으로 보고 미는 `slide`·300ms ease-out(`BUNCH_MENU_SUB_SLIDE_DURATION_MS`)으로 정했다(디자이너 요청). 번치 홈 → 메뉴의 `drill`과 구분된다. 다른 하위 화면도 같은 규칙에 경로를 더한다. 멤버 관리(메뉴 ↔ 멤버 관리, 멤버 관리 ↔ 역할별 권한, 메뉴·멤버 관리 ↔ 멤버 초대)도 같은 slide다(#175). 메뉴 ↔ 차단 목록(#178), 메뉴 ↔ 새 관리자 지정(#180)도 같다. 새 관리자를 지정하고 나가면 지정 화면에서 번치 탭으로 두 칸 되돌아가므로, 이 이동에도 메뉴와 같은 `drill`(되돌아가기)을 둔다. 번치 삭제도 메뉴 ↔ 안내 ↔ 확인 문구 입력이 같은 slide이고, 삭제하면 확인 화면에서 번치 탭으로 세 칸 되돌아가 같은 `drill`을 둔다(#184).
- 번치 알림 목록 (2026-11-02, 이슈 #186): 번치 탭 헤더 알림 → 알림 목록과 뒤로 가기는 더보기 메뉴와 같은 `drill`이다(SSGOI 데모의 Home → Notifications와 같은 프리셋). 화면설계서(`2236:41816` 3번)는 Move in / ← / Ease out / 150ms로 방향은 같다. 위에서 내려오는 `sheet` 계열도 검토했지만, 헤더의 뒤로 가기와 방향이 맞는 `drill`을 골랐다.
- 서로 앞으로 들어가는 두 화면 (2026-11-19, 이슈 #446): 다른 번치 프로필 ↔ 그 팔로워·팔로잉 목록(수 → 목록, 행 → 또 다른 프로필), 번치 탭 ↔ 알림 목록, 알림 목록 ↔ 번들 상세는 어느 쪽으로도 push가 있다. 알림 → 멤버·다른 번치 프로필·MY 알림 설정·역할 권한·번들 작성 화면은 한 방향이라 일반 drill이고, 알림 → 추천 후보(번들 만들기 시작)는 번치 탭의 +와 같은 `sheet`다(뒤 화면이 알림 목록, #514). 한 방향 규칙은 반대쪽 push를 뒤로 가는 drill로 보이게 해서, from·to에 같은 두 경로를 넣은 규칙(`historyDrill`)으로 방향을 기록 이동(push는 앞, 뒤로 가기는 뒤)에 맡긴다. 양방향 점수가 같으면 SSGOI가 이동 방향을 쓰는 동작(`@ssgoi/core` 7.4 규칙 해석)에 기댄다. 브라우저·실기기에서는 확인하지 않았다.
- 팔로워·팔로잉 목록 (2026-11-02, 이슈 #192): 번치 홈·다른 번치 프로필 → 팔로워·팔로잉 목록, 목록 → 대기 중인 팔로우 요청도 같은 `drill`이다. 목록 안의 팔로워 ↔ 팔로잉 탭 전환은 화면설계서(`2500:71333` 1번) Dissolve / Ease out / 150ms를 route 전환이 아니라 CSS로 맞췄다. 탭 글자색은 `transition-colors`, 새로 그려지는 패널은 `starting:opacity-0`에서 150ms에 걸쳐 나타나고, 동작 줄이기에서는 끈다. 선택 밑줄은 아래 「메뉴 탭 밑줄 이동」대로 미끄러진다.
- 번치 홈 번들 탭 패널 밀기 (2026-11-22, #505, 사용자 결정): 「완성된 번들」 ↔ 「작성 중인 번들」을 바꾸면 패널이 밑줄과 같은 방향으로 좌우로 밀린다(Instagram 프로필의 그리드 ↔ 릴스 탭, SSGOI showcase Instagram). 오른쪽 탭으로 가면 새 패널은 오른쪽에서 들어오고 나가는 패널은 왼쪽으로 빠진다. 밑줄과 같은 250ms ease-out이다. 탭은 주소가 아니라 화면 안 상태라 SSGOI 7.4.1 페이지 전환으로 할 수 없어 Web Animations로 직접 정의한 예외다(`useTabSlideMotion`). 나가는 패널은 Base UI `Tabs.Panel`이 애니메이션이 끝날 때까지 남겨 두는 패널을 그대로 쓰고, 새 패널을 아래로 밀어내지 않게 겹쳐 둔다(`absolute`). 나가는 패널인지는 `inert`로 판단한다. `data-ending-style`은 다음 프레임에 지워져, 밀리는 도중 반대로 되돌리면 두 패널에 함께 남기 때문이다. 밀리는 동안만 패널 틀에 `overflow: clip`(스크롤 틀이 되지 않아 Tab 초점이 틀을 가로로 밀지 않음)과 나가는 패널 높이의 `min-height`를 걸어, 길게 내린 그리드에서 짧은 목록으로 가도 페이지가 밀리는 도중에 줄지 않게 한다(끝나면 새 패널 높이). 첫 진입·되돌아올 때는 재생하지 않고, 동작 줄이기면 바로 바뀐다. 밀리는 도중 다시 누르면 진행 중인 밀기를 끊고 새 방향으로 처음부터 밀어 패널이 한 번 튈 수 있다(수용). 손가락 스와이프로 탭 넘기기는 하지 않는다. Chromium(390px, 가짜 서버 개발 서버)에서 프레임마다 두 패널의 위치를 재서, 들어오는 패널이 390px → 0, 나가는 패널이 0 → -390px로 약 250ms 동안 감속하며 움직이고 반대 방향도 대칭인 것을 확인했다. iOS WKWebView, 동작 줄이기, VoiceOver 초점은 확인 전이다(나가는 패널은 Base UI가 `inert`로 둬 낭독·초점에서 빠짐, 코드 확인). 화면설계서(`1892:37781` 3번, 내용 75ms 디졸브)와 달라 디자이너에게 공유한다.
- 메뉴 탭 밑줄 이동 (2026-11-02, 사용자 결정): 글자 탭(팔로워·팔로잉)과 아이콘 탭(번치 홈 번들) 모두 선택 밑줄이 사라지고 나타나는 Dissolve 대신, 선택된 탭으로 250ms ease-out에 걸쳐 미끄러진다. 위치 변화가 더 잘 보인다는 판단이다. 처음 200ms로 했지만 탭 폭(약 200px)만큼 움직이는 데 비해 ease-out 앞부분이 빨라(약 100ms에 80% 이동) 250ms로 늘렸다. Base UI `Tabs.Indicator`가 주는 탭 위치·폭 CSS 변수에 `transition`만 걸었다(`MenuTabs.List`). 글자색·아이콘과 팔로워·팔로잉 패널의 페이드는 그대로다(번치 홈 패널은 위 「번치 홈 번들 탭 패널 밀기」). 화면설계서(`1892:37781` 3번 75ms, `2500:71333` 1번 150ms)와 달라 디자이너에게 공유한다. Storybook(Chromium)에서 200ms일 때 밑줄이 프레임마다 감속하며 도착하는 것을 확인했다(글자 탭 0→119px, 아이콘 탭 0→36px). 250ms는 개발 서버에서 직접 보고 확정했다(프레임 측정은 하지 않음).
- 번치 탭 번들 진입 (2026-11-22, 이슈 #514, 사용자 결정): 화면설계서(`1892:37781`)에 번들 영역을 눌렀을 때의 전환 정의가 없다. 완성된 번들 격자(번치 탭·다른 번치 프로필) → 번들 상세는 SSGOI `zoom`(`type: 'static'`)이다. 칸이 상세 화면 전체로 열리고 뒤 번치 화면은 그대로이며, 뒤로 가면 상세 화면 전체가 칸 자리로 접힌다(SSGOI showcase Instagram 「Grid → Post」와 같은 설정). 칸에는 `data-zoom-exit-key`, 상세 틀 안에는 같은 값의 `data-zoom-enter-key`가 있다. 처음에는 피드 사진 탭과 같은 `hero`로 만들었다. 상세가 사진 한 장이 아니라 제목·작성자·여러 사진·댓글이 있는 게시물이라 인스타처럼 화면 전체가 열리는 쪽이 맞고, hero는 착지 자리가 상세 사진 자리와 정확히 같아야 해서 위치·날짜 줄이나 늦은 데이터에 쉽게 어긋나 zoom으로 정했다(사용자가 두 방식을 비교). hero로 되돌리려면 `AppTransitions` 격자 규칙의 `transition`만 `feedBundleHero`로 바꾸면 된다(칸의 hero 키와 아래 hero용 정리는 남겨 둠). 아래는 hero로 다듬을 때 확인한 내용이다. 칸 링크에 `data-hero-enter-key`, 상세 첫 사진에 같은 키의 exit 표식이다(키는 피드·번치 홈이 함께 써서 `shared/lib/navigation/heroKeys.ts`). 상세의 번치 이름 → 번치 탭·다른 번치 프로필은 새 화면으로 들어가는 이동이라 예전처럼 `drill`이다. 그대로 두면 이 zoom 규칙의 돌아가는 방향으로 잡히는데 짝이 없어 전환 없이 바뀌었다. 그래서 이동 직전에 상세 틀의 `data-ssgoi-transition`을 `FEED_PATHS.transitionIds.bundleToBunch`로 바꾸고, 그 id에서 번치 화면으로 가는 drill 규칙을 둔다(SSGOI는 이 속성이 바뀌면 바로 다시 등록한다). 이동이 일어나지 않고 이 화면에 남으면 다음 입력에서 원래 id로 되돌린다. 번치 화면에서 뒤로 가기로 돌아오면 drill 반대 방향이다. SSGOI는 push 때 쓴 규칙을 기록 항목별로 기억해 뒤로 가기에 반대로 재생하는데, 돌아온 상세가 원래 id로 그려지면 기억한 규칙과 맞지 않아 격자 칸에서 zoom이 열렸다. 그래서 떠날 때 기록 항목(`history.state`)에 표시하고, 돌아온 상세는 같은 drill id로 그린 뒤 전환이 끝나면 원래 id로 되돌린다(`features/feed/lib/bunchDrillId.ts`). 다음 뒤로 가기는 다시 격자 칸으로 접히는 zoom이다. Chromium 개발 서버(앱 폭 390px)에서 격자 → 상세 zoom, 번치 이름 → 번치 drill(약 0.3초), 뒤로 가기 drill 반대(약 0.3초), 다시 뒤로 가기 zoom 접힘(약 0.5초)을 프레임으로 확인했다. 실기기와 네이티브 스와이프 뒤로 가기는 확인하지 않았다. 남은 제약: 번치 화면을 받는 동안 상세를 다시 누르면 id가 되돌아가 전환 없이 바뀌고, 캐시가 없어 상세가 받는 중 화면으로 먼저 그려지면 돌아올 때 id가 늦게 바뀌어 zoom이 열릴 수 있다(확인 안 함). 작성 중인 번들 → 번들 작성 화면은 번들 만들기를 이어서 하는 흐름이라 번치 탭 + → 번들 만들기와 같은 `sheet`다. 가짜 서버 개발 서버(Chromium 390px)에서 격자 칸(128x172) ↔ 상세 첫 사진 자리 hero와 작성 화면이 아래(799px)에서 올라오고 내려가는 것을 프레임으로 확인했다. zoom으로 바꾼 뒤 실서버 개발 화면(다른 번치 프로필 격자) 녹화로 칸이 상세 전체로 열리고 돌아갈 때 칸 자리로 접히는 것을 확인했다. 비어 있던 정의라 디자이너에게 공유한다. 처음에는 격자 칸 링크가 넘친 곳을 자르지 않아, SSGOI hero가 칸이 아니라 `object-cover`로 넘친 사진 전체를 날리고 모서리 반경도 읽지 못했다(SSGOI는 스스로 `overflow`를 자르는 요소만 틀·반경으로 봄). 칸 링크에 `overflow: hidden`을 둬 칸 틀(반경 0) → 상세 첫 사진 틀(반경 24px)로 자르며 이어진다. 사진은 링크 안에서 한 번 감싼다. 바로 아래 자식이 사진이면 SSGOI가 사진으로 보고 날아가는 사본을 그 칸 옆에 넣어, 칸(`li`)·링크에 잘려 돌아갈 때 날아가는 모습이 보이지 않았다(사용자 녹화·Playwright 녹화로 확인). 그래서 칸(`li`)은 자르지 않고 사진 자르기는 링크가 맡는다. 또 SSGOI hero(`fade`)는 들어오는 화면을 통째로가 아니라 공유 요소로 가는 길에 있지 않은 요소마다 따로 흐리게 하는데, 투명도는 쌓임 맥락을 만들어 배경 영역 안의 프로필 이미지(`z-index` 10)가 전환 동안 흰 시트 아래로 깔렸다가 끝나면 올라왔다(사용자 제보, 녹화로 확인). 프로필 이미지를 배경 영역 밖 형제로 옮겨 전환 중에도 시트 위에 있다(번치 홈·다른 번치 프로필)(로그인된 개발 화면에서 착지 때 보이는 자리 358x445·top 212와 상세 사진 212·358x448 일치, 반경 0 → 24px 확인). 상세를 받는 동안 칸 데이터로 먼저 그리는 화면은 위치·날짜 두 줄 자리를 잡는다. 칸 데이터에 위치·날짜가 없어 한 줄만 잡으면, 위치가 있는 번들은 다 받은 뒤 사진이 한 줄(27px) 밀려 hero 착지 자리와 어긋났다. 위치·날짜가 없는 번들은 반대로 어긋나(사용자 녹화에서 착지 뒤 사진이 위로 튐), 실제 원인은 번치 탭이 격자 칸을 누를 때 번들 상세만 미리 받고 상세 화면이 함께 쓰는 번치 정보는 받지 않아 늘 미리 그린 화면을 거친 것이었다. 번치 정보도 함께 받아 400ms 안에 다 받은 화면으로 열린다(한때 기다림을 1초로 늘렸지만 누른 뒤 반응이 늦어 되돌림). 그래도 늦으면 미리 그린 화면을 거치므로 격자 응답에 위치·날짜를 넣어 달라고 백엔드에 요청한다. 상세에서 돌아와 격자를 다시 그릴 때 칸 사진이 회색으로 비었다가 나타나 착지 자리가 비어 보였다(녹화에서 약 300ms). 한 번 받은 표지는 다시 그릴 때 페이드 없이 바로 보인다.
- 번들 만들기 진입 (2026-11-06, 이슈 #230, 사용자 결정): 번치 홈 플로팅 「번들 만들기」 → 사진 선택 `/bunch/bundles/new`와 닫기는 SSGOI `sheet` 기본 프리셋이다(SSGOI 데모 YouTube의 Home → Create와 같은 `sheet()`). 모달처럼 아래에서 올라오고 닫으면 내려가며, 시간·곡선은 프리셋 기본(spring)이다. `sheet`는 움직이는 화면만 애니메이션 대상이라 뒤 화면을 같은 전환 영역에서 찾아 다른 전환처럼 `data-page-leaving`·`inert`를 붙인다(`_transitions/pageGuards.ts`의 `guardSheet`). 그래서 상태 바 영역 색이 시트가 다 올라온 뒤가 아니라 전환 시작과 함께 바뀐다. 시트가 움직이는 동안은 화면에 `data-sheet-moving`을 붙여 `AppFrame`의 색 전환을 150ms 대신 300ms ease-in-out으로 늘려, 시트가 위에 닿는 시점에 색이 다 바뀐다(Chromium에서 시트가 47px 남았을 때 흰색 도달, 약 0.31초). 하단 탭 막대는 전환 대상 밖이라 열 때는 이동과 함께 바로 사라진다. 닫을 때는 막대가 내려가는 시트 위로 바로 튀어나와 어색해(2026-11-22, #514, 사용자 제보), 시트가 움직이는 동안(`data-sheet-moving`) 웹 막대를 시트 아래 층(`z-index` 0, 시트는 2)으로 내려 시트가 막대를 덮었다가 내려가며 드러낸다. iOS 시스템 탭 바는 웹 위에 그려져 덮을 수 없어, 다시 보일 때는 탭 바 자리(화면 아래 15%)를 덮던 것이 비켜난 뒤에 표시를 보낸다(`NativeTabBarVisibility`, 최대 1초). 덮는 것으로 보는 요소는 움직이는 화면 sheet(`data-sheet-moving`), 전환 중 나가는 화면(`data-page-leaving`, 상세에서 뒤로 가기 등), 닫히는 중인 바텀시트·대화상자(`data-ending-style`)이고, 그 자리의 20% 넘게 덮으면 기다린다. 처음에는 시트는 완전히 멈출 때까지 기다려 늦게 떴고, 바텀시트·뒤로 가기는 바로 떠서 아직 내려가거나 나가는 화면 위로 탭 바가 튀어나왔다(2026-11-23 사용자 제보). 위치로 판단해 스프링 끝을 기다리지 않는다. 테스트(happy-dom)는 위치를 흉내 내 확인했고 실기기는 확인 전. 로그인된 개발 화면(Chromium 390px)에서 수정 전에는 막대가 첫 프레임부터 시트 위에 있고, 수정 뒤에는 시트가 지나간 자리에서 드러나는 것을 녹화로 확인했다. 실기기는 확인 전. Chromium(앱 폭 430px)에서 열 때 화면 위치가 547→0px로 약 300ms에 대부분 올라오고 약 0.7초에 멈추며, 닫을 때 반대로 내려가는 것을 확인했다. 실기기와 동작 줄이기는 확인하지 않았다. 2026-11-21(#492, 사용자 요청): 시트가 오기 전에 상태 바가 먼저 흰색이 돼 어색해, 올라오는 동안은 뒤 화면 배경 표식을 시트에 잠시 옮겨 상태 바를 번치 색으로 두고, 시트 위에 상태 바 높이의 흰 띠(`box-shadow`)를 붙여 시트가 상태 바를 덮으며 흰색이 되게 했다. 도착 뒤 배경을 흰색으로 바꾸고 띠는 200ms 더 둔다. 닫을 때는 띠가 내려가며 번치 색을 드러낸다. 다음 전환이 이어지면 이전 전환의 띠 걷기 타이머는 취소한다. 상태 바 아이콘은 쉘이 어두운 색으로 고정해(`StatusBar style="dark"`) 흰 띠 위 대비가 유지된다(번치 색 위 대비는 수치 미검증). Chromium(상단 안전 영역 47px 흉내)에서 시트가 움직이는 0.11~0.73초 동안 상태 바 영역이 번치 색을 유지하는 것을 확인했다. 실기기는 확인 전. 2026-11-23(#518): iOS 앱에서는 흰 띠가 전환 영역의 `overflow-hidden`에 잘려 보이지 않았고, 스프링 끝의 느린 감속 때문에 시트가 다 올라와 보인 뒤 1초 넘게 지나서야 상태 바·아래 영역이 흰색이 됐다(사용자 녹화). 띠가 있는 동안(`data-sheet-band`) 전환 영역 자르기를 위아래 안전 영역만큼 넓히고 아래 영역에도 띠를 둬, iOS 전체 화면 모달처럼 시트 윗부분이 상태 바를 덮으며 올라온다. 시트 움직임은 기본 스프링 그대로 두고(400ms 곡선은 빨라 보여 되돌림, 사용자 확인), 시트가 이동 거리의 절반을 지나면 배경 표식을 걷어 상태 바·아래 영역 색이 300ms에 걸쳐 바뀌기 시작하고, 실제 위치가 도착하면(`data-sheet-arrived`) 남은 전환 없이 바로 맞춘다. WebKit(상단 47px 흉내)에서 누른 뒤 약 0.23초에 색이 바뀌기 시작해 약 0.42초에 흰색이 되고, 시트는 약 0.42초에 상태 바 아래 25px까지 올라와 약 0.78초에 멈추는 것을 확인했다.

- 작성 중 카드 모양: 1110판은 왼쪽 대표 사진, 오른쪽 제목, 제목 아래 참여 멤버 프로필 최대 3개 + 「외 N명」이다. 구현 `BundleCard`는 Figma 기준이라 그대로 두고, 디자인과 다른지 확인한다.
- 번치 프로필 이미지(5.1.3): 1110판은 배경 띠 오른쪽에 원형 프로필 이미지를 두고, 아래쪽이 프로필 영역과 겹친다. #300에서 최신 Figma대로 바꿨다. 이미지 로딩 실패 때 기본 이미지로 바꾸는 처리는 아직 없다.
- 배경 띠 색은 분위기(2.2.9) 색을 연하게 칠한다(색은 디자인 기준). 지금의 `characterType`별 색과 같은 값인지 확인한다.
- 접근 불가 번치: 화면설계서 7번은 「Disabled, Interaction 미적용」, 명세 5.2.3은 누르면 안내다. 지금은 명세를 따른다.
- 접근 불가 안내를 바깥 누름으로 닫는 동작(5.2.3)과 디자인 시스템 확인 창(바깥 누름 막음)의 차이.
- 「콕한 장소」 버튼(이전 이름 「가볼 곳」)은 1110판 5.1.4에 들어왔다(깃발 아이콘 + 「콕한 장소」, 상세 동작은 콕 8.1).
- 역할별 권한 표: #175에서 Figma 「역할별 권한보기」(`2500:54066`) 기준으로 위 표를 맞췄다. 서버 권한 규칙은 백엔드와 확인한다.
- 알림 목록은 「알림」 프레임(`1892:36947`, 설정 안내 줄·알림 카드·「모두 읽음」)으로 구현했다(#186). 헤더 알림 아이콘의 안 읽은 점은 GUI 프레임에 없어 「번치 메인 API 연결, 알림 점」 단위에서 정한다.
- 1110판: 알림 목록 입구에 피드 헤더(6.1.2)가 더해졌고, 뒤로가기는 들어온 화면(번치 메인 또는 피드)으로 간다(5.12.1).
- 1110판: 역할별 권한 안내(5.6.2)는 역할 변경 알림(11~13번)으로도 들어오고, 뒤로가기는 들어온 경로(멤버 관리, 알림 목록, 푸시 전 화면, 번치 메인)로 나뉜다. 구현은 아직 이전 기준(멤버 관리로만 돌아감).
- 1110판: 번치 메인의 멤버 수는 「멤버 리스트 화면」으로 간다(5.1.4 상세 5). 멤버 관리(5.6.1)와 다른 화면인지 기획에 확인한다.

### 백엔드

- 접근 불가 번치를 30일 뒤 자동으로 목록에서 빼는 시점과 응답 형태(5.2.3 로직 2).
- 마지막 사용 번치는 서버에 저장한다(`PUT /bunches/{id}/last-used`, #313). 저장 뒤 기본 번치(`members/me`)가 그 번치로 바뀌는지 확인한다.
- 1110판: 번치 응답의 뭉치 유형·단계 대신 분위기와 프로필 사진(없으면 빈 값)을 내려주는지(5.1.3 로직 1).
- 1110판: 같은 번치(현재 번치 명의)는 같은 대상을 첫 신고부터 24시간 동안 최대 2번 신고할 수 있다. 3번째는 접수하지 않고 「이미 신고가 접수되어 검토 중이에요.」(5.10.7). 같은 번치의 다른 멤버 신고도 함께 센다.
- 1122판 5.10.7 로직 2(2026-11-21 변경): 번치·번들·댓글·답글 신고 공통으로 신고만으로는 아무것도 숨기지 않는다. 운영팀이 검토해 위반이면 삭제하고, 운영자가 지운 댓글은 「삭제된 댓글입니다」, 번들은 번들 삭제(6.2.13)와 같게 처리한다. 처리 결과는 신고한 번치에 알리지 않는다.
- 1110판: 이미 다른 멤버가 처리한 팔로우 요청을 누르면 먼저 처리된 결과를 유지하고 「이미 처리된 팔로우 요청이에요」 토스트 후 행을 뺀다(5.11.2). 요청이 취소·삭제됐으면 토스트 없이 뺀다.
- 1110판: 나가거나 내보내진 멤버의 기존 번들 코멘트는 작성자 「작성자」, 내용 「삭제된 코멘트입니다」로 보인다. 같은 계정이 다시 들어오면 참여 멤버·픽·코멘트를 복구하고, 사진함에서 지운 사진은 복구하지 않는다(5.6.5, 5.8.1). 다시 들어오면 일반 멤버다.

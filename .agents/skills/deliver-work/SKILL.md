# 작업 전달

## 목표

이슈·커밋·PR은 각각 skill이 있다. 이 skill은 지금 어느 단계인지 판단하고, 단계를 시작하기 전에 놓치기 쉬운 점검을 하고, 순서와 멈출 지점을 정한다. 각 단계의 규칙은 해당 skill이 정본이며 여기에 복제하지 않는다.

## 현재 상태 점검

원격 ref를 갱신하는 `git fetch` 외에는 읽기만 하는 명령으로 확인한다. 인증을 대신 시도하지 않는다. 작업 브랜치의 기준은 `develop`이다(`main`은 릴리스 PR로만 바뀐다. `docs/conventions/git.md`).

1. `git fetch origin`으로 원격 정보를 갱신한다. 하지 않으면 아래 비교가 오래된 정보를 쓴다.
2. `git branch --show-current`, `git status --short --branch`, `git log origin/develop..HEAD --oneline`, `gh auth status`를 본다.
3. 열린 PR이 있는지는 인증이 있을 때 `gh pr view <브랜치> --json state`로 본다. "no pull requests found"면 PR이 없는 것이고, 그 밖의 오류(네트워크 등)는 확인하지 못한 것이다. 인증이 없으면 확인하지 못했다고 쓰고, 열린 PR이 있는지 사용자에게 묻는다.
4. 이미 push된 브랜치인지는 `git status --short --branch`로 본다. 원격 추적 브랜치가 있고 `[ahead N]`이 없으면 push된 것이다.

위에서부터 처음 맞는 행이 시작 단계다. 브랜치 형식은 `docs/conventions/git.md`의 `<이슈번호>-<타입>/<이름>`이다. 이 형식이 아닌 브랜치는 `develop`·`main`이든 임의의 이름이든 모두 작업 브랜치가 아니다.

| 상태                                                              | 시작 단계                                                                                                                         |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| PR이 이미 있음(`state`가 `OPEN`·`MERGED`·`CLOSED`)                | `OPEN`이면 알리고 5 PR 리뷰로 간다. `MERGED`이면 새 이슈부터 시작한다. `CLOSED`(머지 없이 닫힘)이면 사용자에게 어떻게 할지 묻는다 |
| 작업 브랜치가 아니고 이슈가 아직 없음                             | 1 이슈. 커밋 안 된 변경이 있으면 이슈를 만든 뒤 2에서 `git switch`가 변경을 그대로 가져가는지 본다                                |
| 작업 브랜치가 아니고 이슈는 이미 있음(사용자가 번호를 알려 줌)    | 2 브랜치 이동                                                                                                                     |
| 작업 브랜치이고 커밋 안 된 변경이 있음                            | 3 커밋 후 4 PR                                                                                                                    |
| 작업 브랜치이고 변경은 없고 `origin/develop`보다 앞선 커밋이 있음 | 4 PR                                                                                                                              |
| 작업 브랜치이고 변경도 앞선 커밋도 없음                           | 올릴 변경이 없다고 알리고 멈춘다                                                                                                  |

## 단계 전 점검

결과를 사용자에게 먼저 보여 준다. 변경 파일을 이번 작업과 다른 작업으로 나누는 일, lockfile 포함 판단은 `prepare-commit`의 "읽기와 입력 점검"이 정본이다. 여기서는 아래만 더한다.

- 다른 작업의 변경이 섞여 있으면 제외 목록을 따로 보여 주고 어느 커밋에도 넣지 않는다.
- 커밋을 나누려고 파일을 임시로 줄이거나 바꿨다면, 커밋 전에 `git diff --stat`을 계획한 파일 목록과 대조하고 커밋 후에는 `git status --short`와 `git diff`로 잔여 변경이 없는지 확인한다.
- 의존성을 추가한 변경은 선언 파일(`package.json`), lockfile, 그것을 쓰는 코드가 같은 커밋 상태에서 맞는지 본다. 이 저장소는 PnP라 `.yarn/` 변경이 섞이지 않는지도 본다.
- 이미 push된 브랜치이면 amend·rebase 대신 새 커밋으로 추가한다고 알린다.
- 이번 대화나 이슈에서 약속한 산출물(문서, 기록, 후속 이슈)이 빠졌는지 확인하고, 빠진 항목을 보여 준다.
- 마지막 검증과 마지막 리뷰 이후에 바뀐 파일이 있는지 확인하고, 있으면 해당 검증이나 리뷰를 다시 실행해야 한다고 알린다.

## 단계

1. **이슈** — `prepare-issue`. 만들었으면 이슈 번호와 브랜치 이름을 알린다.
2. **브랜치 이동** — `docs/conventions/git.md`의 "작업 시작과 병렬 세션"대로 `git switch <브랜치>`와 `origin/develop` 대비 뒤처짐 확인을 한다. 커밋 안 된 변경은 `git.md`대로 먼저 확인하고, 새 브랜치로 충돌 없이 따라갈 때만 `git switch`로 옮긴다. `git switch`가 막히면 옮기지 않고 알린다. stash나 reset으로 우회하지 않는다. 이슈를 방금 만들었고 커밋 안 된 변경이 없으면 커밋할 것이 아직 없으므로 여기서 멈추고, 작업을 마친 뒤 다시 부르라고 안내한다. 변경이 있으면 멈추지 않고 3으로 간다.
3. **커밋** — `prepare-commit`. 코드 커밋은 그 skill의 리뷰 게이트를 거친다.
4. **PR** — `prepare-pull-request`. 브랜치 전체 리뷰를 거친다.
5. **PR 리뷰** — PR이 올라갔는지 확인하고 `review-pr`로 inline 리뷰를 만든다. 아래 "PR 리뷰 단계"를 따른다.

## PR 리뷰 단계

1. `gh auth status`가 성공하면 `gh pr view <브랜치> --json state,url`로 열린 PR을 찾는다. 찾았으면 3으로 간다.
2. 찾지 못했거나 인증이 없으면 AskUserQuestion으로 "PR을 올리셨나요?"를 묻는다. 선택지는 "올렸어요(주소나 번호를 입력)", "아직이에요", "리뷰는 필요 없어요"다. 주소는 "Other" 입력칸으로 받는다.
3. 주소나 번호를 받으면 `review-pr`을 그 PR로 실행한다. 리뷰 초안과 dry-run까지 진행한다.
4. 게시는 `review-pr`의 승인 규칙을 따른다. 이 질문에서 주소를 입력한 것은 리뷰를 만드는 승인이고 게시 승인은 아니다.
5. "아직이에요"와 "리뷰는 필요 없어요"는 여기서 끝낸다. PR을 올린 뒤 `review-pr`을 직접 부르면 된다고 안내한다.

## 승인과 중단

- 이 skill을 불렀다는 것이 이슈 생성·커밋·push·PR 생성의 승인은 아니다. 각 단계(PR 리뷰 단계 포함)는 해당 skill의 실행 승인 규칙을 그대로 따르고, 한 번의 승인으로 여러 단계를 몰아서 실행하지 않는다.
- 인증이 없으면 현재 단계부터 초안과 명령만 순서대로 준다.
- 막히면(리뷰 `Critical`·`Major`, hook 실패, 머지된 PR) 거기서 멈추고 이유를 보여 준다. 우회하지 않는다.

## 출력

1. 현재 상태와 시작 단계(근거: 브랜치, 변경 수, push·PR 여부와 확인하지 못한 항목).
2. 단계 전 점검 결과(제외 목록, push 여부, 잔여 변경).
3. 해당 단계 skill의 출력.

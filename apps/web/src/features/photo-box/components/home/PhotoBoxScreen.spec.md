# 페이지: 사진함 목록(하단 탭 `/photos`)

## 메타데이터

- Route: `/photos`(`apps/web/src/app/(app)/(main)/photos/page.tsx`)
- Status: 목록·멤버 필터·날짜 미확인 아코디언·빈 상태·번치 없음·로딩·오류 UI 구현됨(fixture와 목 동작, 개발 서버 headless Chrome 375×812 실측. 실기기 전). 선택 모드(#126: 고르기·「⋯」 메뉴·저장·번들 만들기·삭제)도 같은 화면에 구현했고 삭제는 API 연동, 저장은 쉘 연동이다. 사진 올리기 시트·선택 모드 날짜 바꾸기 시트·끌어서 날짜 변경(#127)도 구현했고 날짜 변경은 목 동작이다. 번치 전환과 앨범·카메라 연동은 호출 지점만 있음.
- 디자인 출처: Figma `사진함`(node `1782:30110`)의 `사진함_01~05`, 선택 모드 `사진함_07·08·10~12`, `번치 Empty Space`(`1861:36971`)와 화면 설계서(`1861:30963`). 이슈 #125.
- 기능 spec: `docs/specs/photo-box.md`의 3.1 사진함 탭.

## 목적과 범위

### 포함

- 헤더(번치 대표 이미지·이름·전환 화살표, 「선택」)는 상단에 고정하고, 멤버 필터 칩과 날짜 미확인 아코디언·날짜별 사진 목록은 함께 스크롤한다. 오른쪽 아래 「+」는 고정한다. 하단 탭 막대는 본문 위에 떠 있고(사진이 뒤로 비친다), 목록 끝 여백은 `PageShell`이 막대 + 36px(Figma 사진함_02)로 확보하며 「+」는 막대 위 10px에 둔다.
- 멤버 필터: 「전체」와 멤버(프로필 이미지·닉네임) 칩, 하나만 선택(radio 그룹), 가로 스크롤, 사진이 없는 멤버도 칩을 보인다.
- 사진은 촬영 날짜 섹션으로 나누고 최신 날짜가 위, 섹션 안은 최근 촬영이 앞, 같은 시각이면 업로드 순이다. 한 줄 3장 정사각형, 사이 1px.
- 섹션 날짜: 올해는 「9월 27일 일요일」, 올해가 아니면 요일 없이 「2025년 12월 24일」.
- 「촬영 날짜를 확인할 사진 N장」 아코디언: 기본 접힘, 펼치면 업로드 최신순 3열, 0장이면 숨김. N은 선택한 멤버 기준.
- 빈 상태: 번치에 사진이 없으면 「첫 번째 사진을 공유해 보세요」, 선택한 멤버의 사진이 없으면 「첫 사진을 기다리고 있어요!」.
- 번치 없음: 「참여 중인 번치가 없어요」와 「새 번치 만들기」(`/onboarding/create`)·「초대 링크로 참여하기」(`/onboarding/join`). 헤더·필터·「+」는 없다.
- 로딩(회색 자리표시)·오류(기획 문서의 기본 문구 「일시적인 오류가 발생했어요. 다시 시도해 주세요」와 「다시 시도」), 처리 중이거나 불러오지 못한 사진의 회색 자리표시(Figma에 없는 상태).

- 선택 모드(#126): 「선택」→「취소」, 사진마다 선택 원과 누른 순서 번호(최대 50장, 51번째는 「사진은 한 번에 50장까지 고를 수 있어요.」), 필터 칩에 「전체 (N)」·멤버별 장수(0장이면 숫자 없음, 함께 올린 사진은 올린 멤버 모두에게), 「+」→「⋯」(0장이면 비활성), 하단 탭 막대 숨김.
- 「⋯」 메뉴: 저장·번들 만들기·날짜 바꾸기, 구분선 아래 빨간 삭제. 열면 첫 항목에 포커스, Esc·바깥 누름·항목 선택으로 닫는다.
- 저장: 확인 없이 호출하고 화면 전체 dim 위 점 3개 로딩, 완료하면 선택 모드를 끝내고 「이미지 저장이 완료되었어요.」. 일부 실패는 저장된 사진을 선택에서 빼고 「N장은 저장하지 못했어요. 다시 시도해 주세요.」, 전부 실패는 「일시적인 오류가 발생했어요. 다시 시도해 주세요」(선택 유지).
- 번들 만들기: 1~20장이면 「이 사진들로 번들을 만들까요?」+ 「작성 중인 번들에 담기고, 멤버들과 함께 완성할 수 있어요.」(「아니요」/「예」, 화면 설계서 5번 항목에 정의된 확인 창), 「예」는 `onCreateBundle`(고른 순서)만 부르고, `/photos` 화면(`PhotoBox`)이 이를 받아 화면 전체 로딩(800ms 목 지연) 뒤 샘플 초안 작성 화면 `/bunch/drafts/draft-1`로 `push`한다. 초안 생성 API 연결 전이라 고른 사진은 초안에 반영되지 않는다. 21장 이상이면 「번들에는 사진을 20장까지 담을 수 있어요.」.
- 삭제: 일반 멤버가 다른 멤버 사진을 섞으면 「내가 올린 사진만 삭제할 수 있어요.」, 아니면 「선택한 사진을 삭제할까요?」 확인 창(「삭제하기」/「취소」, 처음 포커스는 「취소」) 뒤 삭제하고 「사진함에서 사진 N장이 삭제되었어요.」(0장이면 토스트 없음). 함께 올린 사진은 내 이름만 빠진다. 지운 뒤에는 눌렀던 메뉴·선택 칸이 사라지므로 확인 창이 닫힌 뒤 초점을 화면 제목 `h1`(「사진함」, `tabIndex={-1}`)으로 옮긴다(`web-interface-guidelines.md`의 「같은 화면에서 항목이 사라지면」).
- 날짜 바꾸기: 일반 멤버가 다른 멤버 사진을 섞으면 「내가 올린 사진만 날짜를 바꿀 수 있어요.」, 아니면 바텀시트(오늘이 속한 달을 아무것도 고르지 않고 열며 고르기 전에는 「저장」 비활성)를 연다. 「저장」은 고른 사진 전부의 날짜를 한 번에 바꾸고(시각 유지, 전부 성공 또는 전부 실패) 선택 모드를 끝내며 「사진 날짜가 변경되었어요.」(되돌리기 없음)를 띄운다. 실패하면 오류 토스트와 함께 시트를 유지한다. 관리자가 다른 멤버 사진이나 함께 올린 사진을 포함하면 저장 전에 확인 창(문구는 원문이 없어 임시, 「바꾸기」/「취소」)을 거치고, 확인 창은 시트 위에 겹쳐 뜨고(포커스는 창 안에 머묾), 취소하거나 Esc를 누르면 확인 창만 닫혀 고른 날짜가 그대로 남는다.
- 쓸어서 고르기(#284): 선택 모드에서 사진 위를 쓸면 시작한 사진부터 손가락이 있는 사진까지가 하나의 범위가 되어(화면 순서, 줄을 넘어가도 이어짐) 한꺼번에 고르거나 푼다. 시작한 사진이 선택 전이면 범위를 모두 고르고, 선택돼 있으면 모두 푼다. 같은 방향으로 가면 범위가 늘고 되돌아오면 줄며, 벗어난 사진은 쓸기 전 상태로 돌아간다. 시작 사진을 지나 반대편으로 가면 그쪽으로 범위가 뒤집힌다. 손가락은 가로로 먼저 8px 움직일 때만 쓸기이고 세로로 먼저 움직이면 스크롤이다(마우스는 방향 무관). 쓸기가 시작되면 화면은 같이 스크롤되지 않는다. 길게 눌러 끌 수 있는 사진을 약 280ms(끌기 시작 300ms보다 20ms 일찍, 두 판정 시계가 어긋나도 겹치지 않게 함) 넘게 누르고 있다가 움직이면 아래 길게 눌러 날짜 변경으로 넘기고, 끌 수 없는 사진은 오래 눌러도 쓸기로 본다.
- 쓸기 중 가장자리 자동 스크롤(#284): 손가락이 목록 보이는 영역의 위·아래 80px 안으로 들어오면 그쪽으로 스크롤하고, 깊이 들어갈수록 빨라져 끝에서 프레임당 12px이다. 손가락이 멈춰 있어도 계속 가며 스크롤로 밀린 사진까지 범위가 이어진다. 손가락을 떼면 멈춘다. 손가락으로 직접 조작하는 동안만 도는 스크롤이라 동작 줄이기 설정으로 끄지 않는다. 최대 장수에 닿으면 안내 토스트를 한 번 띄우고 그 쓸기는 거기서 멈춘다. 번들 만들기·사진 추가 선택 화면도 같은 영역(`PhotoDragSelect`)을 쓴다. 키보드·스크린 리더는 기존 칸별 버튼(Enter·Space)을 쓴다.
- 탭 처리와 첫 터치 씹힘 수정(#284): 브라우저는 클릭을 손가락을 뗀 위치의 요소로 보내, 칸 사이 간격이 1px뿐인 격자에서 경계 근처를 누르다 조금만 미끄러져도 옆 사진이 토글되던 것이 씹힘의 원인이었다(실기기 이벤트 로그로 확인). 거의 움직이지 않고(8px 미만) 뗀 터치·마우스는 클릭이 아니라 처음 닿은 사진을 토글하고, 뒤따르는 클릭은 400ms 동안 막는다. 누른 순간 100ms 안에 목록이 스크롤됐으면(관성 스크롤을 멈추려는 터치) 선택하지 않고 뒤따르는 클릭도 막는다. 길게 눌러 끌 수 있는 사진을 약 280ms 이상 누르고 뗀 탭은 끌기 쪽이 처리하고, 끌기가 시작되지 않은 280~300ms 구간은 뒤따르는 클릭이 토글을 맡는다. 끌기 라이브러리는 끌기가 시작되면 뒤따르는 클릭을 막으므로, 8px 안에서 놓은 끌기는 탭으로 보고 선택·해제한다. 한 장을 눌러도 그 사진 칸만 다시 그려지도록 선택 목록을 사진별로 구독한다.
- 끌어서 날짜 변경(#127): 선택 모드에서만, 권한 있는(내가 올렸거나 관리자) 처리 끝난 사진을 300ms 길게 누르면 끌 수 있다(짧게 누르면 선택·해제, 이동 8px 안에서 유지). 끄는 사진은 한 장이고 선택 여부와 무관하다. 원래 자리는 흐려지고 반투명 복사본이 따라가며 다른 섹션 위에서는 주변 사진이 비켜 자리를 보여 준다(, 기록 016). 놓으면 그 섹션 날짜로 바꾸고(시각 유지라 같은 날짜 안 자리는 촬영 시각 순) 「사진 날짜가 변경되었어요.」 + 「되돌리기」(5초, 원래 날짜로 한 번 더 바꿈)를 띄운다. 원래 섹션이나 섹션 밖에 놓으면 변경 없고, 실패하면 원래 자리로 돌려 오류 토스트를 띄운다. 날짜 미확인 사진은 끌 수 없고 날짜를 고르는 시트가 대체 경로다. 관리자가 다른 멤버 사진이나 함께 올린 사진을 놓으면 날짜 바꾸기와 같은 확인 창을 거친다.
- 사진 올리기: 「+」는 시트(「{번치 이름}에 사진 올리기」, 「앨범에서 선택」·「카메라로 찍기」)를 열고, 사진함이 1,000장이면 시트 대신 「사진함이 가득 찼어요.」 토스트를 띄운다. 방식을 고르면 시트를 닫고 `onUpload('album' | 'camera')`만 부른다.
- 실행 직전(확인 창의 확정 포함) 고른 사진이 목록에서 사라졌으면 실행하지 않고 선택에서 빼며 「선택한 사진 중 N장이 사진함에서 사라져 선택이 해제됐어요.」를 띄운다(선택 모드 유지).

### 범위 외(추후 작업 예정)

- 번치 전환: 번치 이름은 `onBunchClick` 호출 지점만 있고 이 화면 설계서 범위 밖이다.
- 앨범·카메라 연동, 업로드 결과 토스트·「다시 시도」, 카메라 권한 모달은 `usePhotoUpload`가 맡는다(#317): 시트에서 고른 방식으로 쉘의 선택·촬영을 열고, 고른 사진을 한 장씩 가공해 받아 동시에 3장까지 올린다(`POST /bunches/{bunchId}/photos`, 사진 1장당 요청 1건). 대상 번치는 올리기를 시작한 시점의 번치로 고정하고, 끝나면 결과 토스트 하나(「N장의 사진을 사진함에 추가했어요.」·「N장을 추가했어요. M장은 올리지 못했어요.」·「사진을 올리지 못했어요.」)를 띄우며 새로 들어간 사진이 있으면 목록을 다시 받는다. 네트워크 실패와 일시 장애(`PHOTO_007`, BFF가 백엔드에 닿지 못한 `BFF_UPSTREAM_UNAVAILABLE`, 코드 없는 502·504)로 못 올린 사진이 있으면 토스트에 「다시 시도」(5초)를 붙이고, 누르면 같은 묶음 ID로 처음 가공한 파일을 그대로 다시 보낸다. 형식·용량·한도 오류는 다시 시도 대상이 아니고 「올리지 못한 사진」으로만 센다. 하루 한도(`PHOTO_002`)나 한 번에 올릴 수 있는 수(`PHOTO_003`) 오류를 받으면 남은 사진은 읽지도 보내지도 않고 같은 방식으로 센다(다시 시도에서도 같고, 사진함 1,000장 `PHOTO_001`은 같은 사진 합치기가 허용될 수 있어 계속 보낸다). 쉘이 준 이미지는 웹이 보내기 전에 한 번 더 확인해(비어 있거나 JPEG 시작 바이트가 아니거나 4.4MB를 넘으면) 보내지 않고 올리지 못한 사진으로 센다. 올리는 동안 화면에는 표시를 두지 않고 스크린 리더에게만 「사진을 올리는 중이에요.」를 알린다(문구는 기획 원문이 없어 임시). 올리는 중에 다시 올리면 묶음이 겹쳐 동시 요청이 3개를 넘을 수 있는데 막지 않는다(기획 확인 항목). 재시도 결과 토스트는 다시 시도한 사진만 센다(기획 확인 완료). 쉘이 없는 브라우저와 새 bridge 메서드가 없는 이전 쉘에서는 안내 토스트만 띄운다(문구는 기획 원문이 없어 임시). 내가 이미 올린 같은 사진(`ALREADY_UPLOADED`)은 서버가 변경 없이 제외하므로 추가한 사진에도 올리지 못한 사진에도 세지 않고, 추가한 사진도 올리지 못한 사진도 없으면(모두 제외됨) 토스트를 띄우지 않는다.
- 사진 상세(#128)는 보통 모드에서 사진을 누르면 `/photos/[photoId]`로 이동한다(`PhotoCell`이 링크, 처리 중·실패 사진은 이동하지 않음, 화면 spec은 `PhotoDetail.spec.md`). 번들 만들기 확정은 `onCreateBundle`로 넘기고 `PhotoBox`가 초안 작성 화면 이동을 맡는다.
- 확인 항목: 날짜 바꾸기·끌기 확인 창의 문구와 시안(임시 문구 사용 중), 끌기 시각 값(반투명 정도·그림자·자동 스크롤 영역), 섹션 안 순서 저장 여부(Nice to have).
- 이어서 불러오기는 구현했다(#315): 첫 쪽(100장)이 오면 먼저 보이고 나머지는 이어서 받는다. 받는 동안 목록 아래에 회색 자리표시 한 줄(Figma에 없는 상태), 실패하면 표시를 숨기고 오류 토스트(「일시적인 오류가 발생했어요. 다시 시도해 주세요」, 명세 3.1.1의 목록 로딩 실패 문구)를 띄우며, 아래로 다시 스크롤하면 그 쪽부터 다시 받는다(키보드·스크린 리더는 포커스 때만 보이는 「사진 더 불러오기」 버튼). 당겨서 새로고침은 피드·번치 홈과 공통이라 별도 이슈로 둔다. 상세에서 만난 삭제된 사진(404)은 사진 상세가 처리하고, 삭제 요청 중 사라진 사진(`PHOTO_004`)은 #316에서 처리한다.
- iPhone 상태 바·홈 인디케이터(기기 요소. Safe Area는 `AppFrame`이 처리한다)와 하단 탭(`MainTabBar`).

## Route와 접근

- Path·params·search: `/photos`. params는 없다. 임시 `preview` search(`loading`·`error`·`no-bunch`·`empty`)로 상태를 눈으로 확인할 수 있고, route 경계(`lib/preview.ts`의 `parsePreview`)에서 허용 값만 통과시킨다. 알 수 없는 값은 무시하고 운영(`NODE_ENV=production`)에서는 아예 열지 않는다. 제거 조건: 번들 화면 테스트의 샘플 사진(`photoBox.fixture`)이 필요 없어지면 `preview.ts`·`fixtures/`·page의 `searchParams` 읽기를 함께 삭제한다. 사진함 화면·사진 크게 보기·번들 만들기 화면은 이미 사진함 API(개발·시연에서는 가짜 서버)를 쓴다.
- 렌더링: `searchParams`를 읽어 `/photos`가 정적 prerender 대신 요청마다 렌더되는 동적 route다. 정적 정보뿐인 화면이라 비용은 작고, `preview`를 없애면 함께 사라진다.
- 아직 없는 route: 사진 상세 `/photos/[photoId]`는 #128에서 만든다. 그 전에는 직접 URL로 들어가면 not-found이고, 이 화면에서 사진을 눌러도 이동하지 않는다.
- 접근 권한·guard: 아직 없다(로그인 미구현). 번치 멤버만 볼 수 있어야 하며 서버가 판단한다(`docs/specs/photo-box.md`).
- Layout·redirect·navigation: `(app)/(main)` group의 하단 탭 layout 안에서 `PageShell`을 한 번 쓴다. `robots: noindex`.

## 상태와 흐름

- 화면 상태는 `PhotoBoxState`(`loading`·`error`·`no-bunch`·`ready`)다. `usePhotoBox`가 호출 지점이고 내 프로필(기본 번치)·멤버·사진 목록 query를 합쳐 만든다. 날짜를 아는 사진과 모르는 사진은 따로 받아 한 목록으로 합치고, 목록은 마지막 쪽까지 이어서 불러온다(사진함 화면은 `progressive`로 첫 쪽이 오면 먼저 보이고 남은 쪽이 있으면 `data.more`가 `loading`·`error`).
- 멤버 필터는 화면 안 상태다(기본 「전체」). 번치를 전환하면 「전체」로 돌려야 하며, 번치 전환이 생길 때 함께 한다.
- 처리 중(`processing`)·실패(`failed`) 사진과 이미지 로딩 실패(`onError`)는 회색 자리표시이고 접근성 이름은 「처리 중인 사진」·「불러오지 못한 사진」이다.
- 아코디언은 열림 상태를 스스로 갖는다. 열고 닫는 모션은 화면 설계서의 값(340ms, `cubic-bezier(0, 0, 0.35, 1)`)이다. 높이는 `Accordion`이, 좌우 여백·모서리는 이 화면이 같은 값으로 전환하고 `prefers-reduced-motion`에서는 즉시 바뀐다.

- 선택 모드는 화면 안 상태다(`hooks/usePhotoSelectionFlow.ts`). 서버·기기 동작은 `PhotoBoxActions`(`savePhotos`·`deletePhotos`)로 받고, `usePhotoBox`가 준다. 삭제는 mutation 뒤 사진 목록을 다시 불러와 반영하고, 저장은 사진마다 상세 API로 원본 주소를 받아 쉘의 `saveImagesToAlbum`에 넘겨 기기 앨범에 저장하며(`api/albumSave.ts`, 저장 권한이 거부되어 있으면 `SaveResult.blocked`로 알려 「사진 접근 권한이 필요해요」 창을 띄우고 선택을 유지, 앱이 아니면 안내 토스트만), 날짜 변경은 서버 반영 전이라 이 세션의 목록에만 덮어 보인다(새로고침하면 원래 날짜).
- 선택 모드 동안 `HideMainTabBar`를 렌더해 `(main)` layout이 탭 막대를 숨기고 `--main-tab-bar-*` 변수를 0으로 되돌린다. 「⋯」는 막대가 있을 때와 같은 10px 간격(`float-gap`)으로 화면 끝 위에 놓인다(Figma 사진함_07은 간격 0이지만 막대와 같은 간격으로 맞추기로 했다). iOS 쉘에서는 시스템 탭 바를 숨기는 경로가 없어 선택 모드에도 탭 바가 남는다(`docs/specs/photo-box.md` 확인 항목).
- 사진함 토스트는 모두 목록 폭(343px)이고 탭 막대가 보이면 막대 위 16px에 뜬다(`toast()`의 `tab-bar` 앵커, `Toast.spec.md`). 선택 모드를 끝낸 직후의 완료 토스트는 막대가 다시 나타난 뒤 다음 프레임에 위치를 다시 재서 막대 위에 놓인다. 선택 모드 중에는 막대가 숨겨져 기본 위치다.

## 데이터 의존성

- Query와 enabled 조건: 없음(fixture). 연결 시 `photoKeys.list(bunchId, memberFilter)`(infinite)·`photoKeys.undated(...)`·`bunchKeys.members(bunchId)`(`docs/specs/photo-box.md`의 후보).

## UI와 접근성

- Component mapping: 헤더는 `core`의 `Header`+`AccountSwitcher`+`TextButton`, 필터 칩은 `ChipButton`(`solid`·`avatar`, size L), 아코디언은 `Accordion`, 사진 칸은 `PhotoThumbnail`(`onImageError` 추가), 「+」는 `FloatingButton icon="add"`, 번치 없음 버튼은 `Button`.
- Semantic·heading: 화면 제목 `h1`(「사진함」, 화면에는 숨김), 날짜 섹션 제목은 `h2`와 `section`, 아코디언 제목도 `h2`. 사진 목록은 날짜를 이름으로 가진 `ul`이다.
- 멤버 필터: `radiogroup`(「멤버 필터」)과 칩마다 `role="radio"`·`aria-checked`. Tab은 선택된 칩 하나에만 머물고(roving tabindex) 방향키로 이동하면 바로 선택된다(Home·End 지원). `ChipButton`의 `aria-pressed`는 쓰지 않는다.
- 사진: 이미지 `alt`는 호출하는 쪽이 주는 값이다(사진 상세로 가는 이동은 #128).
- 포커스 링: 칩 둘레 링이 가로 스크롤 영역에 잘리지 않도록 스크롤 영역 아래에 4px 여백을 둔다.

- 삭제 확인 창 문구: Figma와 기획 문서에는 기본 문구(Figma는 「선택한 사진 N장을 삭제할까요?」, 장수는 빼기로 해 「선택한 사진을 삭제할까요? / 삭제 이후에는 복구할 수 없어요.」)만 있고, 사진 종류별(관리자가 다른 멤버 사진, 함께 올린 사진, 섞임, 작성 중인 번들에 쓰인 사진) 원문이 없다. `getDeleteKind`로 종류는 나눠 두었고 지금은 모든 종류가 기본 문구를 쓴다.

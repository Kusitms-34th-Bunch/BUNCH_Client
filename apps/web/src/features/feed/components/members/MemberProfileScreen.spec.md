- 소유: `features/feed`. 번치 쪽 주소는 route-local `MemberProfileRoute`가 `BUNCH_HOME_PATHS`로 조합해 넘긴다
- Status: UI 구현됨(fixture). API·실기기 전
- 기능명세: 피드 6.3.3(`docs/specs/feed.md` 구현 단위 8). 기능명세서 1110판(2026-11-10) 대조, 바뀐 동작 없음(오류 토스트 끝 마침표만 뺌)
- 디자인 출처: Figma `번들_참여 멤버 상세` `5367:110380`(섹션 「피드」 `4940:100716`). 전환은 화면설계서 `5367:114452`

## 목적과 범위

### 포함

- 큰 프로필 이미지와 닉네임, 「참여중인 번치」 목록(이미지, 이름, 비공개면 자물쇠, 팔로우 버튼)
- 정렬: 한글 → 영문(대소문자 무시) → 숫자(`lib/memberBunches.ts`)
- 팔로우 버튼: 팔로워·팔로잉 목록(5.11.1)과 같은 모양과 동작이다. 확인 없이 바로 바뀌고 토스트로 알린다. 공개 번치는 「팔로잉」, 비공개 번치는 「요청됨」이 된다
- 현재 번치 자신의 줄에는 버튼이 없다
- 번치 줄을 누르면 그 번치 프로필, 현재 번치면 번치 메인
- 들어오는 곳: 참여 멤버 시트의 멤버(시트가 닫힌 뒤 이동). 나간·탈퇴한 멤버는 누를 수 없다
- 없는 멤버: 헤더와 「삭제되었거나 볼 수 없는 내용이에요」

### 범위 외

- 서버 연동(구현 단위 10): 지금은 `fixtures/memberProfile.fixture.ts`이고 팔로우는 화면에서만 바뀐다. 번치 프로필과 공유하지 않아, 여기서 팔로우해도 번치 프로필에는 반영되지 않고 다시 들어오면 처음 값이다
- 차단 관계인 번치 제외: 서버가 뺀다고 보고 화면에서는 거르지 않는다. 계약은 API 때 확인한다
- 멤버 정보의 로딩·실패 상태: fixture라 없다. API 연결 때 추가한다

## 상태

- 소속 번치 없음: 모든 줄이 「팔로우」이고, 누르면 「번치에 참여하면 할 수 있어요.」 토스트(`useFeedViewer`)
- 지금 번치를 받는 중: 내 번치 줄을 알 수 없어 번치 줄을 누를 수 없고 팔로우 버튼도 숨긴다. 실패하면 줄과 버튼을 보이고, 팔로우를 누르면 오류 토스트
- fixture 한계: 소속 번치가 없거나 실패한 상태에서 목 서버의 내 번치(`1`) 줄을 누르면 다른 번치 fixture에 없어 404다
- 내 정보 조회가 실패한 화면으로 앱에 돌아오면 재조회 동안 줄과 버튼이 잠시 사라져 초점을 잃을 수 있다. 첫 진입이 오프라인이면 안내 없이 줄을 누를 수 없다(코드로 추론, 재현 전). API 연결 때 `useFeedViewer`에서 함께 본다
- 참여 번치가 없으면 「참여중인 번치」 영역을 숨긴다(Figma에 없음)

## 접근성

- 닉네임이 `h1`, 「참여중인 번치」가 `h2`, 번치는 목록(`ul`)
- 번치 줄의 이미지·이름은 번치 프로필로 가는 버튼이고, 비공개 여부는 「, 비공개 번치」로 읽는다
- 팔로우 버튼 이름에 번치 이름과 누른 결과를 붙인다(예: 「야간러너스 팔로잉, 누르면 팔로우 취소」)

## Styling과 의존성

- 이미지 90(`ProfileImage` `L`), 이미지와 닉네임 사이 14, 위 10. 번치 영역 위 30·좌우 16, 제목과 목록 사이 10, 줄 사이 8
- 닉네임 `body-1-semi-bold` `text-primary`, 영역 제목 `body-4-semi-bold` `text-quaternary`
- 줄은 `FollowListItem`, 버튼은 `Button` `sm`(`primary`·`secondarySubtle`)
- 전환은 `bunchDrill`이다. 화면설계서의 Slide In 200ms 대신 다른 화면과 같은 프리셋을 쓴다

## 확인할 항목

- 비공개 번치 소속이 승인 전 번치에도 보인다. API 연결 전에 기획 결정이 필요하다(`docs/specs/feed.md` 확인 항목)
- 화면설계서의 전환(Ease In 200ms)과 `bunchDrill`의 차이는 디자이너 확인이 필요하다

## API 연동 때 확인할 조건

- 현재 번치 입력: 요청자가 그 번치 소속인지 서버가 검증한다. 번치가 없는 요청의 기준도 정한다
- 차단: 양방향으로 응답에서 뺀다. 번치가 모두 빠지거나 멤버 본인과 차단 관계일 때와, 차단 관계에서 주소로 직접 들어올 때의 화면을 정한다
- 비공개 번치: 응답 필드를 이름·이미지·공개 범위·팔로우 상태로 제한한다
- 팔로우: 결과 상태(`following`·`requested`)는 서버가 정한다. 차단 관계, 소속이 아닌 번치 명의, 자기 번치 팔로우를 거절한다
- memberId: 없음·탈퇴·권한 없음의 응답을 구분할 수 없게 통일한다. 나간·탈퇴 멤버의 ID를 응답에 싣지 않는다
- 캐시: query key에 memberId와 현재 번치를 함께 넣고, 번치를 알기 전에는 요청하지 않는다. 경로의 memberId는 `encodeURIComponent`로 넘긴다

## 검증

- 단위 테스트: 닉네임, 정렬, 자물쇠 글자, 현재 번치 줄, 번치 이동, 팔로우 상태 4가지, 소속 번치 없음, 지금 번치 받는 중, 내 정보 조회 실패, 없는 멤버
- 개발 서버(Chrome, 폭 430) 측정: 이미지 90, 닉네임 위치·글자(16/600), 영역 제목(13/600, #969AA0), 번치 줄 56·사이 8로 Figma 값과 같음. 참여 멤버 시트에서 멤버를 눌러 시트가 닫힌 뒤 이동하는 것과 나간 멤버에 링크가 없는 것을 확인함

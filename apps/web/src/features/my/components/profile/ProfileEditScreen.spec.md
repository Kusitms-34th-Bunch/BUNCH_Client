## 목적과 범위

### 포함

- 지금 값을 채운 닉네임(필수)·프로필 사진·출생연도·성별(Figma 개인 프로필 편집 `6745:46068`, #345). 추가 개인정보 수집·이용에 동의하지 않았으면 출생연도·성별은 비활성이고 값이 비어 있으며 입력란 안내는 「약관 동의 후 입력할 수 있어요.」다. 동의했으면 저장된 값을 채워 고칠 수 있다(기능명세서 7.2.6). 입력 칸과 검증 규칙은 가입 프로필과 같은 `src/shared/components/profile/ProfileFields`(`demographicsDisabled`)·`useProfileFields`를 쓴다. 동의 상태는 서버 API가 없어 이 기기에만 저장하는 임시 값(`useDemographicsConsent`)이고 `ProfileEditRoute`가 `demographicsConsent`로 넘긴다.
- 프로필 사진: 가입과 같은 `ProfilePhotoField`(선택지 → 원형 조정 → 미리보기, `shared/components/profile/ProfilePhotoField.spec.md`). 사진이 지금 값과 달라지면(기본 이미지로 되돌리기 포함) 변경으로 본다.
- 바뀐 값이 있는데 뒤로 가면 「저장하지 않고 나갈까요?」 / 「변경한 내용이 반영되지 않아요.」 / 나가기·취소 확인 창(기능명세서 7.2.1 상세 7). 「취소」는 창만 닫고 입력을 둔다. 바뀐 값이 없으면 바로 나간다.
- 내 정보(`GET /members/me`)는 `ProfileEditRoute`가 `useMyProfile`로 받아 지금 값으로 채운다. 받을 때까지 `PageLoading`을 보이고, 받지 못하면 MY로 돌아가고, 오류 토스트는 이동을 기다렸다가 도착한 MY에서 보인다(`toastAfterNavigation`, 기능명세서 7.2.1 예외). 들어올 때마다 다시 불러온다.
- 닉네임 중복 확인(`GET /members/nickname-availability`, `shared/api/nickname.ts`): 입력을 멈추고 0.5초 뒤 확인하고, 지금 내 닉네임과 같은 값(앞뒤 공백 제외)은 확인하지 않는다(7.2.5 로직 1). 이미 쓰는 닉네임이면 오류 문구와 수정하기 비활성, 확인 실패면 오류 토스트와 비활성이다.
- 「프로필 수정하기」: 바뀐 값이 있고 모두 유효할 때만 활성. 누르면 MY로 돌아가고 토스트 「프로필을 수정했어요.」를 띄운다. 누른 뒤에는 다시 누를 수 없다.

### 범위 외

- 프로필 수정·이미지 업로드 API와 저장 실패 처리(운영 서버 미배포). 지금은 저장 없이 이동과 토스트만 한다. 연결할 때 저장 실패면 수정하기를 다시 누를 수 있게 되돌리고, 저장 직전 닉네임 중복은 입력란 Error로 알린다.

## Route와 접근

- Path·params·search: `/my/profile`, 없음.
- 접근 권한·guard: `(app)` 그룹 기준을 따른다. 추가한 guard는 없다.
- Layout·redirect·navigation: `(main)` 밖이라 하단 탭이 없다. page가 전환 경계(`data-ssgoi-transition="/my/profile"`)를 두고 MY와 slide로 오간다. 뒤로 가기와 저장 뒤 이동 모두 `useBackOr(MY_PATHS.home)`(MY에서 들어왔으면 그 기록으로 돌아가고, 기록이 없으면 MY로 바꿈). 저장 뒤 `replace`를 쓰면 MY 기록이 두 번 쌓여 뒤로 가기가 한 번 헛돈다. 기록 유무만 보므로 MY 밖에서 들어오면 직전 페이지로 돌아간다(지금 입구는 MY 프로필 행뿐).

## 상태와 흐름

- 초기 진입: 닉네임을 지금 값으로 채우고 수정하기는 비활성.
- 변경 판단: 닉네임은 앞뒤 공백을 지우고 NFC로 맞춘 값, 사진은 바뀐 여부로 비교한다. 원래 값으로 되돌리면 다시 비활성.
- Disabled·invalid: 닉네임 규칙 위반(허용 문자, 1~12자)이면 비활성. 오류 문구는 가입과 같다.
- Success·완료 후 이동: MY로 이동하고 토스트.

## 데이터 의존성

- Query·mutation: 없음. 화면은 `profile`(`nickname`, `imageSrc?`, `birthYear?`, `gender?`)을 prop으로 받는다.
- API 계약 확인 항목: `MemberResponse`의 `gender`는 `FEMALE`·`MALE`이고 화면은 `female`·`male`을 쓴다. 연결할 때 변환한다.

## 확인할 항목

- 헤더와 사진 사이 (제안): Figma 49를 가장 가까운 토큰 `s18`(48)로 맞췄다.
- 화면 전환 (결정): 화면 설계서에 정의가 없어, 번치 프로필 편집과 같은 미는 slide(Ease out, 300ms)를 양방향으로 쓴다(2026-11-05 사용자 결정, `AppTransitions`의 `menuSubSlide`).
- 나가기 확인 창 모양 (제안): Figma 노드가 없어 번들 사진 추가 화면과 같은 `ConfirmDialog`를 썼다.
- 나가기 확인 범위 (기획 확인): 헤더 「뒤로 가기」에서만 뜬다. 브라우저·스와이프·하드웨어 뒤로 가기는 확인 없이 나간다. 명세 7.2.1 상세 7의 「뒤로가기」가 어디까지인지 확인한다.
- 앱 안 뒤로 가기 (실기기 확인 필요): `useBackOr`는 `history.length > 1`로 기록을 판단한다. 쉘이 딥링크로 이 화면을 바로 열 때 WebView 기록이 남아 있으면 저장·뒤로 가기가 MY가 아닌 곳으로 갈 수 있다.
- 명세 개정 대조 (2026-11-13): 이전 판(1110)은 출생연도·성별을 빼 두었지만 개정판 7.2.6이 다시 넣었다. 동의하지 않은 사람은 비활성으로 보이게 한다(Figma `6745:46068`).
- 붙여넣기 처리 (반영, #324): 1110판 7.2.5 예외대로 특수문자·이모지·줄바꿈이 섞인 글을 붙여넣으면 허용하지 않는 문자만 빼고 넣는다(`pasteIntoNickname`). 입력 칸이 공용 `ProfileFields`라 가입 화면에도 같이 적용된다(`login-signup.md`도 같은 규칙). 허용 문자만 있는 붙여넣기는 브라우저 기본 동작이다.
- 붙여넣기 한계 (알려진 차이, #324): 허용하지 않는 문자가 섞인 글을 붙여넣을 때는 `preventDefault` 뒤 상태로 넣어, 그 붙여넣기가 브라우저 실행 취소 기록에 남지 않을 수 있다. 허용 문자가 하나도 남지 않으면 아무 일도 일어나지 않고 안내도 없다(안내 문구는 기획 확인 필요). 일부 Android 키보드가 붙여넣기 이벤트 없이 입력으로 넣는 경우는 기존 오류 문구 경로를 탄다. 실기기 확인 전이다.
- 기준값 고정 (알려진 차이, #324): `ProfileEditRoute`는 이 화면이 열린 시점의 프로필을 기준으로 고정한다. 받아 둔 값이 오래됐으면(다른 기기에서 닉네임을 바꾼 경우 등) 폼과 「내 닉네임이면 확인 생략」 기준이 그 값으로 남을 수 있다. 저장할 때 서버가 닉네임을 다시 확인하므로 영향은 작다.
- 비로그인 접근: `(app)` 그룹에는 페이지 guard가 없어 지금은 누구나 열린다. 내 정보 API 연결(#324)에서도 401 처리와 로그인 이동은 따로 추가하지 않았다.

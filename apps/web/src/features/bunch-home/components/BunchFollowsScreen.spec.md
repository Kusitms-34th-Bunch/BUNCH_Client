# 페이지: 팔로워·팔로잉 목록과 팔로우 요청

## 메타데이터

- Route: `/bunch/follows`(내 번치), `/bunch/follows/requests`(내 번치의 대기 중인 요청), `/bunches/[bunchId]/follows`(다른 번치). `?tab=following`이면 팔로잉 탭으로 연다.
- Status: 두 탭 목록, 목록에서 팔로우·언팔로우, 요청 승인·거절 구현. 데이터와 처리 결과는 fixture·메모리 저장소다. 이슈 #192.
- 디자인 출처: 화면설계서 `2500:71333`(1~~3-1번, 목록)·`2500:72664`(1~~5번, 요청), Figma `2500:73493`(팔로워 탭과 요청 줄)·`2500:73508`(요청 목록).
- 기능 spec: 기능명세서 5.11, `docs/specs/bunch-home.md`.

## 목적과 범위

### 포함

- 번치 홈과 다른 번치 프로필의 「팔로워」·「팔로잉」 수를 누르면 누른 쪽 탭으로 열린다(1번). 탭 이름 오른쪽에 수.
- 행: 번치 이미지·이름·비공개 자물쇠, 오른쪽에 내 번치의 팔로우 상태 버튼(팔로우·팔로잉·요청됨).
- 버튼을 누르면 확인 없이 바로 팔로우(비공개는 요청)·언팔로우하고, 행은 그대로 둔 채 버튼만 바꾸며 토스트로 알린다(3·3-1번).
- 내 번치에 대기 중인 요청이 있으면 팔로워 탭 맨 위에 「팔로우 요청 N」 줄. 누르면 요청 목록(`2500:72664` 1번).
- 요청 목록: 「대기 중인 요청 N개」, 행마다 「N일 전」과 승인·거절. 확인 없이 바로 처리해 목록에서 빼고 토스트(2~4번).
- 승인한 번치는 팔로워 맨 위에 더하고 팔로워 수 +1, 거절한 번치는 팔로워에 없다. 요청이 0개면 요청 줄을 숨긴다(5번).
- 팔로우 승인 전의 비공개 다른 번치는 수치만 보이고 목록은 열 수 없다(기능명세 5.10). 프로필의 수는 링크가 아니고, 주소로 직접 들어오면 목록 대신 「비공개 번치예요 / 목록을 보려면 이 번치를 팔로우하세요.」를 보인다.
- 목록에서 팔로우·언팔로우한 결과는 번치 홈의 팔로잉 수와 다른 번치 프로필의 버튼·팔로워 수에도 반영한다.

### 범위 외(후속)

- 서버 처리, 실패, 연타 방지, 목록 페이지 나누기: 팔로우 API 연결 때.
- 비공개 번치 목록 잠금의 서버 쪽 처리: 지금은 화면에서만 가린다. API를 연결하면 잠금일 때 목록 요청을 보내지 않고(query `enabled: false`), 서버도 승인 전 요청을 거절해야 명단이 네트워크로 나가지 않는다.
- 행을 눌러 그 번치 프로필로 가기: 화면설계서에 정의가 없고 지금은 프로필 fixture가 두 번치뿐이라 두지 않았다.
- 비공개 → 공개로 바꿀 때 대기 요청을 모두 승인하는 처리(프로필 편집 안내 문구만 있음).

## 흐름과 결정

- 팔로우 상태는 다른 번치 프로필과 같은 메모리 저장소(`useBunchFollow`)를 쓴다. 상대 번치 id만 구분하므로 내 번치를 바꿔도 같은 상태로 보인다(API 연결 때 반영).
- 「요청됨」을 누르면 화면설계서에 정의가 없어 「팔로잉」처럼 바로 요청을 취소하고 토스트로 알린다(확인할 항목).
- 프로필에서는 「팔로잉」에 확인 시트가 뜨지만 목록은 화면설계서(3-1번)대로 바로 취소한다.
- 승인·거절한 행의 버튼이 사라지므로 초점은 「대기 중인 요청 N개」 줄로 옮긴다(차단 목록과 같은 방식).
- 탭 전환은 글자색·패널을 Dissolve / Ease out / 150ms로 CSS로 맞췄고, 선택 밑줄은 250ms ease-out으로 미끄러진다(사용자 결정, `docs/architecture/motion.md`). 화면 이동은 `drill`.
- 첫 hydration에는 저장된 지금 번치를 몰라 목록을 그리지 않는다(다른 번치 목록이 잠깐 보이지 않게).

## UI와 접근성

- Component mapping: `MenuTabs`(팔로워·팔로잉 탭, 수 포함), `NudgeBanner`(「팔로우 요청 N」, Figma `Label`), `FollowListItem`(행, 요청 행은 `meta`), `Button` `sm`(팔로우는 `primary`, 팔로잉·요청됨·거절은 `secondarySubtle`), `toast`.
- 버튼 이름에 번치 이름을 붙인다(예: 「서핑크루 팔로우 요청 승인」). 「팔로잉」·「요청됨」은 상태 이름이라 누르면 바로 취소된다는 동작을 덧붙인다(「산책클럽 팔로잉, 누르면 팔로우 취소」). 자물쇠의 숨은 글자는 「비공개 번치」.
- 결과는 토스트로 알린다. 토스트 영역은 sonner의 `aria-live="polite"` 영역이다(디자인 시스템 `Toast.test.tsx`). 승인·거절은 줄어든 개수를 그린 뒤 그 줄로 초점을 옮긴다.
- 보이는 제목이 없어 sr-only `h1`(「{번치} 팔로워·팔로잉」, 「팔로우 요청」).
- 「대기 중인 요청 N개」는 Figma `Label`(화살표 없음)과 같은 모양의 글자 줄이고 누를 수 없다.

## 확인할 항목

- 「요청됨」을 눌렀을 때의 동작(바로 취소로 둠, 프로필처럼 확인 시트일 수도 있음).
- 「팔로우 요청 3」·「대기 중인 요청 3개」의 숫자는 Figma에서 굵지만 `NudgeBanner`는 글자 하나만 받아 같은 굵기다.
- 빈 목록 문구(「아직 팔로워가 없어요.」 등)는 Figma에 없어 임시로 넣었다.
- 프로필 이미지 자리 (임시): fixture가 번치 타입별 기본 이미지를 돌려가며 쓴다. 실제 팔로우 API가 붙으면 각 번치의 `characterType`과 이미지를 응답으로 받는다.
- 참여 번치가 없는 사용자가 주소로 직접 들어오면 빈 화면이다(지금 번치 저장소가 hydration 대기와 번치 없음을 구분하지 못함). 입구가 없어 직접 입력·새로고침에서만 생긴다.
- 「팔로우 요청 N」은 디자인 시스템 `NudgeBanner`라 버튼으로 읽히지만 화면을 이동한다.
- 수와 목록이 어긋나는 경우: 목록에서 팔로우하면 내 번치 팔로잉 수는 늘지만 팔로잉 목록에 그 번치 행이 생기지 않고, 다른 번치를 팔로우하면 그 번치 팔로워 수만 늘고 내 번치 행은 생기지 않는다. 요청 승인만 수와 행이 함께 바뀐다. API 연결 때 서버 목록으로 맞춘다.

# 페이지: 팔로워·팔로잉 목록과 팔로우 요청

## 메타데이터

- Route: `/bunch/follows`(내 번치), `/bunch/follows/requests`(내 번치의 대기 중인 요청), `/bunches/[bunchId]/follows`(다른 번치). `?tab=following`이면 팔로잉 탭으로 연다.
- Status: 두 탭 목록, 목록에서 팔로우·언팔로우, 요청 승인·거절 구현. 목록·요청·처리 모두 서버(가짜 서버 포함)다. 이슈 #192(화면), #347(서버 연결).
- 디자인 출처: 화면설계서 `2500:71333`(1~~3-1번, 목록)·`2500:72664`(1~~5번, 요청), Figma `2500:73493`(팔로워 탭과 요청 줄)·`2500:73508`(요청 목록).
- 기능 spec: 기능명세서 5.11(1110판, 2026-11-10 기준), `docs/specs/bunch-home.md`.

## 목적과 범위

### 포함

- 번치 홈과 다른 번치 프로필의 「팔로워」·「팔로잉」 수를 누르면 누른 쪽 탭으로 열린다(1번). 탭 이름 오른쪽에 수.
- 행: 번치 이미지·이름·비공개 자물쇠, 오른쪽에 내 번치(명의, `members/me` 기본 번치)의 팔로우 상태 버튼(팔로우·팔로잉·요청됨). 명의 번치 자신의 행과 번치가 없는 회원에게는 버튼이 없다.
- 버튼을 누르면 확인 없이 바로 팔로우(비공개는 요청)·언팔로우한다. 서버 처리가 끝나면 버튼을 서버 상태로 바꾸고 토스트로 알린다(3·3-1번). 처리 중인 버튼은 흐리게 두고 다시 눌러도 보내지 않는다. 실패하면 버튼을 그대로 두고 공통 실패 토스트.
- 내 번치에 대기 중인 요청이 있으면 팔로워 탭 맨 위에 「팔로우 요청 N」 줄. 누르면 요청 목록(`2500:72664` 1번).
- 요청 목록: 「대기 중인 요청 N개」, 행마다 「N일 전」(요청 시각 기준)과 승인·거절. 확인 없이 바로 처리하고, 서버 처리가 끝나면 목록에서 빼고 토스트(2~4번).
- 승인·거절 뒤 팔로워 목록·수와 요청 목록을 서버에서 다시 받는다. 요청이 0개면 요청 줄을 숨긴다(5번).
- 다른 멤버가 먼저 처리한 요청(`applied: false`, `APPROVED`·`REJECTED`)은 먼저 처리된 결과를 유지하고 「이미 처리된 팔로우 요청이에요.」 토스트 후 행을 뺀다. 요청한 번치가 취소·삭제한 요청(`UNAVAILABLE`)은 토스트 없이 행을 뺀다(1110판 5.11.2).
- 팔로우 승인 전의 비공개 다른 번치는 수치만 보이고 목록은 열 수 없다(기능명세 5.10). 서버 `canViewRelations`가 false면 프로필의 수는 링크가 아니고, 주소로 직접 들어오면 목록을 요청하지 않고 「비공개 번치예요 / 목록을 보려면 이 번치를 팔로우하세요.」를 보인다.
- 목록에서 팔로우·언팔로우하면 모든 팔로워·팔로잉 목록, 그 번치의 프로필, 내 번치 홈을 다시 받는다(프로필에서 팔로우해도 목록을 다시 받음).

### 범위 외(후속)

- 목록 더 불러오기: 지금은 첫 쪽 50개만 받는다.
- 행을 눌러 그 번치 프로필로 가기: 화면설계서에 정의가 없어 두지 않았다.
- 비공개 → 공개로 바꿀 때 대기 요청을 모두 승인하는 처리(프로필 편집 안내 문구만 있음).

## 흐름과 결정

- 목록 query key에 명의 번치를 둔다(행의 팔로우 상태가 명의마다 다름, `bunchHomeKeys.followList`). 팔로우·취소와 요청 결정은 `bunchHomeKeys.follows()` 전체를 무효화한다.
- 내 번치 목록의 이름·수는 번치 홈 응답(`GET /bunches/{id}/home`), 다른 번치 목록은 그 번치의 홈(EXTERNAL) 응답을 쓴다.
- 「요청됨」을 누르면 화면설계서에 정의가 없어 「팔로잉」처럼 바로 요청을 취소하고 토스트로 알린다(확인할 항목).
- 프로필에서는 「팔로잉」에 확인 시트가 뜨지만 목록은 화면설계서(3-1번)대로 바로 취소한다.
- 승인·거절한 행의 버튼이 사라지므로 서버 처리가 끝나 줄어든 개수가 그려진 뒤 초점을 「대기 중인 요청 N개」 줄로 옮긴다(차단 목록과 같은 방식). 그 사이 초점을 다른 곳으로 옮겼으면 가져오지 않는다. 처리 중 버튼은 `aria-disabled`.
- 탭 전환은 글자색·패널을 Dissolve / Ease out / 150ms로 CSS로 맞췄고, 선택 밑줄은 250ms ease-out으로 미끄러진다(사용자 결정, `docs/architecture/motion.md`). 화면 이동은 `drill`.
- 처음 받는 동안은 로딩 표시와 숨은 「목록을 불러오는 중이에요」, 탭 목록을 받는 중에도 같은 문구. 탭 목록이 실패하면 탭 안에 「목록을 불러오지 못했어요. 다시 시도해 주세요.」와 다시 시도. 번치 홈·내 정보를 처음부터 못 받으면 다시 시도 화면.
- 번치가 없는 회원이 목록·요청 주소로 들어오면 번치 탭(번치 없음 안내)으로 보낸다. 다른 번치 목록 주소가 내 번치면 지금 번치는 `/bunch/follows`(탭 유지), 다른 소속 번치는 그 프로필(전환 뒤 번치 탭)로 보낸다.
- 서버가 본 명의(home `currentBunchId`)가 캐시의 기본 번치와 다르면 내 정보를 다시 받고, 그동안 모든 팔로우 버튼을 막는다(행 상태는 서버 명의, 요청은 캐시 명의라 엉뚱한 번치 명의로 나가지 않게). 다시 받아도 어긋나면 계속 막힌다(실서버 확인 뒤 다시 시도 화면 검토).

## UI와 접근성

- Component mapping: `MenuTabs`(팔로워·팔로잉 탭, 수 포함), `NudgeBanner`(「팔로우 요청 N」, Figma `Label`), `FollowListItem`(행, 요청 행은 `meta`), `Button` `sm`(팔로우는 `primary`, 팔로잉·요청됨·거절은 `secondarySubtle`), `toast`.
- 버튼 이름에 번치 이름을 붙인다(예: 「서핑크루 팔로우 요청 승인」). 「팔로잉」·「요청됨」은 상태 이름이라 누르면 바로 취소된다는 동작을 덧붙인다(「산책클럽 팔로잉, 누르면 팔로우 취소」). 자물쇠의 숨은 글자는 「비공개 번치」.
- 결과는 토스트로 알린다. 토스트 영역은 sonner의 `aria-live="polite"` 영역이다(디자인 시스템 `Toast.test.tsx`). 승인·거절은 줄어든 개수를 그린 뒤 그 줄로 초점을 옮긴다.
- 보이는 제목이 없어 sr-only `h1`(「{번치} 팔로워·팔로잉」, 「팔로우 요청」).
- 「대기 중인 요청 N개」는 Figma `Label`(화살표 없음)과 같은 모양의 글자 줄이고 누를 수 없다.

## 확인할 항목

- 「요청됨」을 눌렀을 때의 동작(바로 취소로 둠, 프로필처럼 확인 시트일 수도 있음).
- 「팔로우 요청 3」·「대기 중인 요청 3개」의 숫자는 Figma에서 굵지만 `NudgeBanner`는 글자 하나만 받아 같은 굵기다.
- 빈 목록 문구(「아직 팔로워가 없어요.」 등)는 Figma에 없어 임시로 넣었다.
- 프로필 이미지: 응답에 이미지가 없으면 번치 성격(`characterType`)별 기본 이미지.
- 「팔로우 요청 N」은 디자인 시스템 `NudgeBanner`라 버튼으로 읽히지만 화면을 이동한다.
- 서버의 행 `followState`·home 명의가 `members/me` 기본 번치인지, 요청 결정 `applied`·`state` 의미(가짜 서버는 위 해석대로 둠)를 실서버로 확인한다.
